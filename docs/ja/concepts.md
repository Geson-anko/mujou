# 🧠 Mujou の仕組み

このページでは、mujou の考え方を説明する。扱うのは次の 5 つである。

- **ノード**: 計算の単位
- **Port と Channel**: ノード同士をつなぐ口と接続
- **ネットワーク**: ノードの組み合わせ方
- **グローバル時間**: すべてのノードが従う時間の流れ
- **状態**: 走っているネットワークから取り出し、後で戻せるもの

コードの書き方は[ユーザーガイド](user-guide/index.md)にある。

```mermaid
flowchart TB
    H["ホスト（ネットワークを動かす Python のコード）"]
    subgraph N["ネットワーク"]
        direction LR
        A["ノード A"] <-->|Channel| B["ノード B"] <-->|Channel| C["ノード C"]
    end
    T["実行のタイマー"]
    H -->|"mujou.run(net) が返す Run で、入力を書き、出力を読み、状態を取る"| N
    T -.->|"時刻と dt"| N
```

## ノード

ノードは計算の単位である。ノードは `mujou.Node` を継承したクラスとして書く。

ノードの内側では、普通の PyTorch のコードを同期的に実行する。ノードの内側に閉じていれば、誤差逆伝播法（BP）も使える。

ノードの間はすべて非同期である。mujou はノードごとのスレッドで `on_update(dt)` を繰り返し呼び、ノードはほかのノードを待たない。ノードは `on_update` のたびに次のことをする。

1. 隣のノードが送った最新の値を読む
2. 自分の状態を更新する
3. 結果を送る

ループは mujou が回すので、ノードは自分の `while` ループを持たない。mujou は、実行の開始時や終了時などにも、ノードが override できる hook を呼ぶ。その順は API リファレンスの [`Node`](api/node.md) にある。

エポックも、学習と推論の切り替えも、メッセージを受け取るたびに呼ばれる hook も無い。

1 つのノードにどれだけの計算を入れるかは、ノードのクラスで決まる。1 つの層でも、複数の層でも、モデル全体でもよい。ノードの境界が非同期の境界になる。複数の層を同期的に計算したいなら、それらを 1 つのノードのクラスにまとめる。複数の層を BP で一緒に学習させたいときも同じである。

!!! info "ノードが守る 3 つの規則"

    - **計算グラフをつなげない**: ノードをまたいで計算グラフをつなげない。送った値は送るときに計算グラフから切り離されるので、勾配はノードの間を通らない
    - **Port だけでやり取りする**: ほかのノードやホストとは、自分の Port だけでやり取りする
    - **時間は読むだけ**: 時間を動かすのはホストだけである

どれかのノードが例外を投げると、実行全体が止まる。例外を投げたノードだけを止めて、ほかのノードを動かし続けることはない（[例外と終了](user-guide/errors.md)）。

既定の更新手法は [PC-ALM](https://pub.sakana.ai/pc-alm/)（Augmented Lagrangian Predictive Coding。実装予定）で、各ノードは局所的な更新だけで学ぶ。更新手法は mujou に組み込まれていない。ノードは、上の 3 つを守る限りどの手法でも使える。

## Port と Channel

**Port** は、ノードが持つ接続口である。**Channel** は、2 つの Port をつなぐ 1 本の接続で、`connect` で作る。

Channel は向きごとに 1 つずつ値の置き場所を持ち、各置き場所に書くのはその向きの送り手だけである。

Port は、送る値と受け取る値の型を shape と dtype で宣言する。2 つの Port は、互いの送る型が相手の受け取る型と一致するときだけつながる。`connect` を呼ぶと、mujou がこれを検査する。dtype は変換しない。

読み書きは次のように動く。

- **待たない**: 読む側は、そのときの最新の値を受け取る。新しい値が来るまで待つことはない
- **溜まらない**: 誰も読まないうちに上書きされる値もあれば、同じ値を何度も読むこともある。どちらも正常な動作である
- **初期値**: 送り手がまだ書いていなければ、送り手の Port の初期値を読む（既定はゼロ）。送り手が書いたかどうかは `has_received()` でわかる
- **コピー**: 値はどれも `torch.Tensor` のコピーで、計算グラフから切り離されている。受け取ったテンソルを書き換えても、ほかのノードには影響しない
- **時刻付き**: 値には送った時刻が付く。新しい値かどうかを知るには、値を時刻と一緒に読み（`recv_with_time()`）、前回読んだ値の時刻と比べる。時刻が進んでいれば新しい値である

Port は複数の相手につなげることもできる。そのときは Channel ごとに 1 つずつ値を受け取り、それらをどう束ねるか（足す、平均する、など）はノードが決める。

どこにもつながっていない Port も残せる。つながっていない Port は、ネットワークの入力と出力になる。

- ホストは、つながっていない入力の Port に入力を書く。書いた値は、ホストが次に書くまでその Port に残る
- ホストは、値を送るどの Port からも、送られた最新の値を読める。つながっていない出力の Port だけでなく、ノード同士をつなぐ Port も読める

## ネットワーク

ネットワークは、ノードの組み合わせ方を宣言する。`mujou.Network` を継承したクラスとして書く。PyTorch の `nn.Module` に子のモジュールを持たせるのと同じ書き方で、次の 3 段階で組む。

1. ノードや別のネットワークを属性として持つ
2. それらの Port を `connect` でつなぐ
3. 外からつなぎたい Port を、ネットワーク自身の属性として公開する

Port を公開したネットワークは、ノードと同じようにほかのノードやネットワークとつなげる。

ネットワークは、組み立てるときにだけ使う。ネットワークは hook を持たず、自身では何も実行しない。中のノードは、実行中もそれぞれ独立に動く。ネットワークで囲んでも、中のノードは同期しない。

`mujou.run(net)` は、構造と型を検査して凍結し、走らせる。その後は接続を足せない。

各ノードには、パスという名前が付く。パスは、ルートからの属性名を `.` でつないだもので、`"body.l1"` のようになる。状態はこのパスを使う。

!!! warning "名前と接続を変えると状態を戻せない"

    属性の名前や接続を変えると、変える前に取った状態は復元できなくなる。

## グローバル時間

mujou は、学習するネットワークを、時間とともに連続的に変わる系として扱う。`dt` は、そのノードの前回の更新からの経過時間（秒）である。

ノードは状態を `dt` に比例して更新する。状態 $x$ が $\frac{dx}{dt} = f(x)$ に従うなら、1 回の更新は次のようになる（陽的 Euler 法）。

```python
x = x + dt * f(x)
```

ノードごとに更新の速さは違い、負荷によっても揺らぐ。更新量を反復 1 回あたりで決めると、速く回るノードほど状態が大きく変わってしまう。`dt` に比例させれば、どのノードも同じ時間の流れの上で同じダイナミクスに従う。負荷が高くなっても、`dt` が伸びるだけである。

!!! warning "`dt` を打ち切らない"

    `dt` に上限を設けて打ち切ってはならない。打ち切ると、実際に経った時間が失われる。`dt` が大きくて更新が不安定になるなら、1 回の `on_update` の中で刻みを分割する。

ノードは周期を持つ（既定は 0.01 秒）。1 回ごとの更新の間隔は揺らぐが、平均すると周期ごとに 1 回更新する。遅れたときの `dt` は周期より長い。`dt` は実際に経った時間なので、周期を決めても `dt` に比例して更新する。

実行ごとにタイマーが 1 つあり、その実行のすべてのノードとホストがそれを使う。既定では、プロセスに 1 つのグローバルタイマーを使う。ホストは時間を実時間より速くも遅くも進められる。ノードは時間を読むだけである。

!!! tip "ホストは `mujou.time.sleep` で待つ"

    ホストがその時間で待つとき（たとえば入力を 2 秒見せるとき）は、`mujou.time.sleep` を使う。標準の `time.sleep` は実時間で待つので使わない。

走っているネットワークの状態を取るとき、mujou は実行を一時停止し、そのタイマーを止める。止まっていた時間は、再開後のどの `dt` にも入らない。ノードから見ると、一時停止は無かったのと同じである。

一時停止は、同じタイマーを使うすべての実行の時間を止める。ほかの実行と時間を止め合わないようにするには、その実行に専用のタイマーを持たせる（[時間の制御](user-guide/time.md)）。

一時停止は、状態の取得と観測のためのものである。一時停止を学習の手順の一部にしてはならない。

## 状態

走っているネットワークの状態は、実行を終了させずに取れる。後でその状態から走らせ直せる。状態は 1 つの木で、次のものを持つ。

- ノードのパスごとの、各ノードの状態（重み、活動などのテンソル）
- 値の置き場所ごとの、最新の値とその時刻
- 各ノードの最後の更新の時刻と、タイマーの時刻

置き場所の値も状態に入るのは、ネットワークがノードとその間を流れる値を合わせたものだからである。置き場所の値が初期値に戻ると、隣のノードはそれまでにたどり着いた平衡から外れてしまう。

ノードは、`nn.Module` と同じように自分の状態を自分で集める。属性に代入したテンソルと `nn.Module` は、自動で状態に入る。

状態を取る間は、前の節で述べた一時停止が起きる。各ノードは `on_update` の途中では止まらず、1 回の更新を終えてから次の更新を始めるまでの間で止まる。そのため、木の中の値はすべて同じ時点のものになる。

| 状態を取るとき       | 得られるもの                                                        |
| -------------------- | ------------------------------------------------------------------- |
| ネットワークの実行中 | その時点の状態                                                      |
| 正常に終了した後     | `on_stop` の後に、ノードが残した値                                  |
| 例外で終了した後     | 取れない。`NetworkError` になる。残したい状態は、実行中に取っておく |

正常に終了した後の木が持つタイマーの時刻は、`shutdown()` が終了を求めた時刻と、ノードが最後に更新か送信をした時刻の、遅いほうである。この木から復元した実行は、終了した後に経った時間を数えない。

!!! warning "`on_stop` で状態を変えない"

    正常に終了した後の木は `on_stop` の後に取るので、`on_stop` で状態を変えると、その変更が木に入る。たとえば `on_stop` で `self.w = None` とすると、木から `w` が消える。`on_stop` では状態を変えず、I/O などの資源だけを解放する。

復元するには、木を `mujou.run(net, state=tree)` に渡す。ネットワークは、木を取った時刻から、同じノードの状態と置き場所の値で続きを走る。走らせるネットワークは、木を取ったネットワークと同じノードのパスと接続を持たなければならない。

木をファイルに保存する方法（`torch.save`、`pickle` など）は利用者が決める。手順は[状態の保存と復元](user-guide/state.md)にある。
