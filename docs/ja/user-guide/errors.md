# 🚨 例外と終了

このページでは、ノードの hook が例外を投げたときに何が起き、ホストがどこでそれを受け取るかを書く。あわせて、終了を待つときと状態を取るときのタイムアウトを書く。

## 1 つのノードの例外で全体が止まる

どのノードのどの hook（`on_update` に限らず、`on_start`・`on_pause`・`state_dict` なども）が例外を投げても、その実行の全ノードが止まる。流れは次のとおりである。

1. mujou が例外を捕まえ、ノードのパスと hook の名前、traceback を、logger `"mujou"` に ERROR で出す
2. 各ノードは、実行中の hook を終えて止まり、ほかのノードを待たずに自分の `on_exception()` を呼ぶ。例外を投げていないノードも呼ばれる
3. 全ノードの `on_exception()` が終わったら、全ノードの `on_stop()` を呼ぶ。例外を投げたノードも呼ばれる
4. ホストに `NetworkError` を送出する。`__cause__` は最初の例外である。ほぼ同時に複数のノードが例外を投げたときは、2 つ目以降の例外はログに出るだけである

!!! note "全体を止める理由"

    例外を投げたノードだけを止めて、ほかのノードを動かし続けることはしない。止まったノードの古い値を隣のノードが読み続け、気づかれないまま平衡から外れるからである。

## ホストが受け取る場所

| 例外が起きたとき          | `NetworkError` を送出するもの                                                                                                                                           |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 起動中（`on_start` など） | `mujou.run` そのもの。終了の処理（`on_exception`・`on_stop`）を済ませてから送出する                                                                                     |
| 起動の後                  | その後にホストが呼ぶ `write`・`read`・`subscribe`（とそのイテレータ）・`wait_for`・`state_dict`・`shutdown`・`join`、または `ManualRun`（`mujou.testing.run`）の `step` |

起動の後の例外は、ホストが次に `Run` のメソッドを呼ぶまで届かない。

!!! warning "sleep ではなく run.join で待つ"

    ホストが何も呼ばずに待つと、例外に気づかない。実行が止まるのを待つときは、`mujou.time.sleep` ではなく `run.join(timeout)` で待つ。

```python
--8<-- "examples/errors.py"
```

`NetworkError` は `RuntimeError` の派生である。原因の型で分けるときは、`error.__cause__` を調べる。

### with 文の中で起きたとき

with 文は、抜けるときに `run.shutdown()` を呼ぶ。

- with の本体が例外なく終わったとき: ノードの例外は、`shutdown()` が送出する `NetworkError` として、with 文の終わりで届く
- with の本体も例外を投げたとき: 本体の例外がそのまま伝わり、`NetworkError` は捨てられる。ノードの例外はログ（下の「ログ」の節）で確かめる

## on_exception と on_stop

| hook             | 呼ばれるとき                                         | 書くこと                                             |
| ---------------- | ---------------------------------------------------- | ---------------------------------------------------- |
| `on_exception()` | 例外による終了のときだけ。全ノードで、`on_stop` の前 | アクチュエータの安全停止など、異常な終了に固有の処理 |
| `on_stop()`      | 終了のたびに 1 回。正常な終了でも例外による終了でも  | I/O などの資源の解放。状態は変えない                 |

- `on_exception` は引数を取らない。ノードは、どのノードのどの例外で止まったかを知ることができない。原因に応じた対処はホストが `__cause__` を見て行う
- 自分の hook の中の例外に対処したいだけなら、その hook の中で `try`/`except` する。捕まえた例外は全体を止めない
- `on_exception` と `on_stop` が例外を投げても、ログに出るだけで、終了の処理は続く

## ログ

ノードの例外は、traceback 付きで logger `"mujou"` に ERROR のレベルで出る。ログの設定をしていないプログラムでは、Python の既定の振る舞いで標準エラー出力に出る。

出し先を変えるには、Python の `logging` で設定する。上のサンプル（`examples/errors.py`）は、次の行でログを標準出力に出している。

```python
--8<-- "examples/errors.py:logging"
```

## 例外の後の状態

例外で終了した実行の状態は保存されない。`run.state_dict()` も `NetworkError` を送出する。状態を残したいときは、実行中に定期的に取る（[状態の保存と復元](state.md)）。

走らせ直すときは、ノードも含めて新しいインスタンスを作る。1 つのネットワークは 1 回しか走らせられない。

## タイムアウト

`shutdown`・`join`・`subscribe`・`wait_for` は、引数 `timeout` に実時間の秒を取る。既定は `math.inf`（いつまでも待つ）である。

| 呼び出し                                 | 時間切れのとき                                                                                                                                                                               |
| ---------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `run.shutdown(timeout)`                  | `TimeoutError`。終了の要求は取り消されず、ノードはもう更新しない。終了の処理は裏で続く。`join` で待つ                                                                                        |
| `run.join(timeout)`                      | `TimeoutError`。何も変わらず、実行は走り続ける                                                                                                                                               |
| `run.subscribe(port, timeout)`           | イテレータが `TimeoutError` を送出する。時間切れの後に始まる回か、時間切れを越えて待つことになる回で送出する。時間はループの本体を含む反復全体で数える。イテレータは終わり、実行は走り続ける |
| `run.wait_for(port, condition, timeout)` | `TimeoutError`。実行は走り続ける                                                                                                                                                             |

実行中の `run.state_dict(timeout)` は、全ノードが止まるのを最長 `timeout` 秒（実時間、既定は 30 秒）待つ。この `timeout` は有限の正の数でなければならない。終了した実行では待つものが無いので、`timeout` は検査するだけである。

時間内に止まらないノードがあると、`run.state_dict()` は `PauseTimeoutError`（`TimeoutError` の派生）を送出する。メッセージには止まらなかったノードの名前が入る。状態は取れず、止まっていたノードも再開して、実行は走り続ける。

!!! note "長い更新は停止を遅らせる"

    `state_dict` の時間切れは、1 回の `on_update` が長いノード（重い BP など）で起きやすい。ノードは実行中の `on_update` を最後まで終えてから止まるからである。

`timeout` に負の数か NaN を渡すと `ValueError` になる。`state_dict` では 0 と `math.inf` も `ValueError` になる。

## インタプリタの終了

実行が走っている間にインタプリタが終了すると、mujou は実行を止め、全ノードの `on_stop` が終わるまで待つ。

!!! tip "実行は自分で終了させる"

    それでも、実行は `shutdown()` か with 文で自分で終了させる。
