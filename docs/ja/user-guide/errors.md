# 🚨 例外と終了

ノードの hook が例外を投げたときに何が起き、ホストがそれをどこで受け取るかを説明する。終了を待つときと状態を取得するときのタイムアウトも扱う。

## 1 つのノードの例外で全体が止まる

どのノードのどの hook（`on_update` に限らず、`on_start`・`on_pause`・`state_dict` なども）が例外を投げても、その実行の全ノードが止まる。流れは次のとおり。

1. mujou が例外を捕まえ、ノードのパス・hook の名前・traceback を logger `"mujou"` に ERROR で出す
2. 各ノードは実行中の hook を終えて止まり、ほかのノードを待たずに自分の `on_exception()` を呼ぶ。例外を投げていないノードでも呼ばれる
3. 全ノードの `on_exception()` が終わったら、全ノードの `on_stop()` を呼ぶ。例外を投げたノードでも呼ばれる
4. ホストに `NetworkError` を送出する。`__cause__` は最初の例外。複数のノードがほぼ同時に例外を投げたときは、2 つ目以降の例外はログに出るだけ

!!! note "全体を止める理由"

    例外を投げたノードだけを止め、ほかのノードを動かし続けることはしない。そうすると止まったノードの古い値を隣のノードが読み続け、気づかないうちに平衡から外れてしまう。

## ホストが受け取る場所

| 例外が起きたとき          | `NetworkError` を送出するもの                                                                                                                                           |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 起動中（`on_start` など） | `mujou.run`。終了処理（`on_exception`・`on_stop`）を済ませてから送出する                                                                                                |
| 起動の後                  | その後にホストが呼ぶ `write`・`read`・`subscribe`（とそのイテレータ）・`wait_for`・`state_dict`・`shutdown`・`join`、または `ManualRun`（`mujou.testing.run`）の `step` |

起動後の例外は、ホストが次に `Run` のメソッドを呼ぶまで届かない。

!!! warning "sleep ではなく run.join で待つ"

    ホストが何も呼ばずに待つと例外に気づかない。実行の停止を待つときは `run.timer.sleep` ではなく `run.join(timeout)` で待つ。


`NetworkError` は `RuntimeError` の派生。原因の型で処理を分けるときは `error.__cause__` を調べる。

### with 文の中で起きたとき

with 文は抜けるときに `run.shutdown()` を呼ぶ。

- with の本体が例外なく終わったとき: ノードの例外は `shutdown()` が送出する `NetworkError` として、with 文の終わりで届く
- with の本体も例外を投げたとき: 本体の例外がそのまま伝わり、`NetworkError` は捨てられる。ノードの例外はログ（下の「ログ」の節）で確認する

## on_exception と on_stop

| hook             | 呼ばれるとき                                      | 書くこと                                           |
| ---------------- | ------------------------------------------------- | -------------------------------------------------- |
| `on_exception()` | 例外による終了時だけ。全ノードで `on_stop` の前   | アクチュエータの安全停止など、異常終了に固有の処理 |
| `on_stop()`      | 終了のたびに 1 回。正常終了でも例外による終了でも | I/O などの資源の解放。状態は変えない               |

- `on_exception` は引数を取らないので、ノードはどのノードのどの例外で止まったかを知ることができない。原因に応じた対処はホストが `__cause__` を見て行う
- 自分の hook の中の例外に対処したいだけなら、その hook の中で `try`/`except` する。捕まえた例外は全体を止めない
- `on_exception` と `on_stop` が例外を投げてもログに出るだけで、終了処理は続く
- 実行の時刻は終了の時点で止まるので、`on_exception` と `on_stop` の中では `self.timer` で経過時間を測れない。ロボットを 1 秒かけて減速させるような処理は、実時間で測る

## ログ

ノードの例外は traceback 付きで logger `"mujou"` に ERROR レベルで出る。ログを設定していないプログラムでは、Python の既定の振る舞いにより標準エラー出力に出る。

出力先は Python の `logging` で変更できる。上のサンプル（`examples/errors.py`）は次の行でログを標準出力に出している。

## 例外の後の状態

例外で終了した実行の状態は保存されず、`run.state_dict()` も `NetworkError` を送出する。状態を残したいときは実行中に定期的に取得する（[状態の保存と復元](state.md)）。

1 つのネットワークは 1 回しか走らせられないので、再実行するときはノードも含めて新しいインスタンスを作る。

## タイムアウト

`shutdown`・`join`・`subscribe`・`wait_for` は引数 `timeout` に実時間の秒数を取る。既定は `math.inf`（無期限に待つ）。

| 呼び出し                                 | 時間切れのとき                                                                                                                                                                       |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `run.shutdown(timeout)`                  | `TimeoutError`。終了の要求は取り消されず、ノードはもう更新しない。終了処理は裏で続くので `join` で待つ                                                                               |
| `run.join(timeout)`                      | `TimeoutError`。何も変わらず、実行は走り続ける                                                                                                                                       |
| `run.subscribe(port, timeout)`           | 時間切れの後に始まる回か、時間切れを越えて待つことになる回で、イテレータが `TimeoutError` を送出する。時間はループの本体を含む反復全体で数える。イテレータは終わり、実行は走り続ける |
| `run.wait_for(port, condition, timeout)` | `TimeoutError`。実行は走り続ける                                                                                                                                                     |

実行中の `run.state_dict(timeout)` は、全ノードが止まるのを最長 `timeout` 秒（実時間、既定は 30 秒）待つ。この `timeout` は有限の正の数でなければならない。終了した実行では待つものが無いので、`timeout` は値の検査にだけ使う。

時間内に止まらないノードがあると、`run.state_dict()` は `TimeoutError` を送出し、メッセージには止まらなかったノードの名前が入る。状態は取得できず、止まっていたノードも再開して実行は走り続ける。

!!! note "長い更新は停止を遅らせる"

    ノードは実行中の `on_update` を最後まで終えてから止まるので、1 回の `on_update` が長いノード（重い BP など）では `state_dict` の時間切れが起きやすい。

`timeout` に負の数か NaN を渡すと `ValueError` になる。`state_dict` では 0 と `math.inf` も `ValueError` になる。

## インタプリタの終了

実行中にインタプリタが終了すると、mujou は実行を止めて全ノードの `on_stop` が終わるまで待つ。

!!! tip "実行は自分で終了させる"

    それでも実行は `shutdown()` か with 文で自分で終了させる。
