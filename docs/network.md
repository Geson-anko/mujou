# ネットワーク

ノードをどう組み合わせ、ノード間をどう双方向に接続するかを定める。メッセージの型とスロットは [メッセージ](messages.md) を参照。

## 構成要素

| 構成要素     | 役割                                                                                 |
| ------------ | ------------------------------------------------------------------------------------ |
| ノード     | 非同期処理の単位。ネットワークの末端の要素で、Port を宣言する                        |
| ネットワーク | ノードや別のネットワークを子として持ち、内側の Port を外向きに公開する             |
| Port         | ノードやネットワークの接続口。送るメッセージの型と受け取るメッセージの型の組を持つ |
| Channel      | 2 つの Port の間の接続 1 本。向きごとのスロット 2 本と、その両端からなる             |

ノードとネットワークは共通の基底を持つ（Composite）。どちらも Port を持ち、同じ書き方で接続できる。共通の基底が持つのは、Port を持つことと接続できることだけである。

ノードは実行時に存在する分散処理の最小単位で、ライフサイクル hook を持つ（[ノード](nodes.md#ライフサイクル-hook)）。ネットワークは構築時だけの構造で、hook を持たない。ネットワークに `on_update` を持たせると、ネットワークの単位で同期的に回すという意味が紛れ込むからである。

## define-and-run

ネットワークの構造は define-and-run で記述する。PyTorch の実行方式は define-by-run だが、mujou はこれと異なる。利用者は、PyTorch の `nn.Module` のように組み合わせて宣言的に書ける API でネットワークを記述し、最終的にスキーマオブジェクトを作る。各スロットのメッセージの型・shape・初期値は、このスキーマオブジェクトの構築時に確定し、以後は変えない。

この API は `nn.Module` にたとえているだけで、`nn.Module` に相当する単位がノードになるわけではない。

`nn.Module` と同じく、ノードやネットワークのインスタンスは定義と実行の両方を担う。構築すると、各 Port は実際のスロットに結び付けられ、同じノードのインスタンスが実行時に hook を呼ばれる。凍結したスキーマから実行時のオブジェクトを別に作り直すことはしない。

## Port

Port は向きを持たない。送るメッセージの型（send）と受け取るメッセージの型（recv）の組だけを持ち、2 つの Port は型が互いに逆向きのとき、つまり片方の send がもう片方の recv と一致するときだけ接続できる。一致を確かめる対象は、メッセージの型と各値の `TensorSpec`（shape と dtype）である。一致しなければ、`connect` を呼んだ時点でエラーになる。

Port は send と recv の一方だけを持ってもよい。send だけの Port と recv だけの Port は、メッセージの型と `TensorSpec` が一致すれば接続でき、その Channel のスロットは 1 本になる。入力を送るだけのノードや観測するだけのノードは、こうして使わない向きのスロットとメッセージを持たずに済む。

Port は未接続のまま残ってもよい。未接続の Port も、スキーマで宣言した型の値を持つスロットを持つ。ノードが未接続の Port から受け取ると、相手 1 つの Port は初期値を返し、複数の相手を取る Port は空の対応表を返す。

上流と下流、上と下の区別は、フレームワークでは決めない。PC-ALM の層の間の結合も、softmax のような層内の横方向の結合も、同じ仕組みで表す。こうして、PC-ALM 固有の上下という区別を基盤に持ち込まない。

Port は、つながる相手が 1 つか複数かを持つ。相手 1 つの Port に 2 本目の Channel を接続すると、`connect` を呼んだ時点でエラーになる。

### PrevPort と NextPort

Port の宣言には 3 種類がある。

| 宣言       | 役割                                | 相手の数の既定 |
| ---------- | ----------------------------------- | -------------- |
| `PrevPort` | 前側の Port。`a.connect(b)` の b 側 | 1 つ           |
| `NextPort` | 次側の Port。`a.connect(b)` の a 側 | 複数           |
| `Port`     | 前側でも次側でもない Port           | 1 つ           |

分岐は次側で起きることが多いので、`NextPort` は既定で複数の相手を取る。どの宣言でも、相手の数は明示して上書きできる。たとえば合流を受けるノードは、`PrevPort` を複数と宣言する。

相手の数は宣言の時点で決まるので、受け取るときの戻り値の型（メッセージそのものか、相手ごとの対応表か）が静的に決まる。

ノードとネットワークが直接の属性として持てる `PrevPort` と `NextPort` は、それぞれ 1 つまでである。前側や次側が無いノード（入力だけを流すノードなど）は、その宣言を持たない。

## 接続

接続には 2 つの書き方がある。どちらも Channel を 1 本作り、その両端を 2 つの Port に同時に登録する。そのため、B を A に接続した時点で、A にも B からの逆向きの経路が登録される。ネットワークは define-and-run なので、実行中に経路が増えたり減ったりすることはない。

1 つ目は Port 同士をつなぐ書き方で、`a.next.connect(b.prev)` のように書く。

2 つ目はノード同士（またはネットワーク同士）をつなぐ書き方で、`a.connect(b)` のように書く。`a.connect(b)` は、a の `NextPort` と b の `PrevPort` をつなぐ。同じ種類の層を並べるときは、型だけではどの Port 同士をつなぐか決められないので、この宣言で決める。

前側・次側は `a.connect(b)` という省略形と相手の数の既定のための宣言であり、Port 自体は向きを持たない。そのため `a.connect(b)` と `b.connect(a)` は別の接続になる。`PrevPort`・`NextPort` 以外の Port をつなぐときは、Port 同士の書き方で明示する。

```python
class Hidden(Node):
    def __init__(self, n_in: int, n_out: int) -> None:
        # 前へ W^T ε を送り、前から h を受け取る（相手 1 つ）
        self.prev = PrevPort(send=TensorSpec((B, n_in)), recv=TensorSpec((B, n_in)))
        # 次へ h を送り、次から W^T ε を受け取る（相手は複数）
        self.next = NextPort(send=TensorSpec((B, n_out)), recv=TensorSpec((B, n_out)))

l1, l2 = Hidden(784, 256), Hidden(256, 256)
ch = l1.connect(l2)              # l1.next <-> l2.prev
# l1.next.connect(l2.prev) と同じ
```

Channel のスロット 2 本は、それぞれ書く側の端が所有する。各スロットの書き手は 1 つという原則は、分岐や合流があってもそのまま保たれる。

## 入れ子

ネットワークは、ノードや別のネットワークを子として持てる。ネットワークは内側の Port を自分の属性として持つことで外向きに公開し、外から見るとノードと同じように接続できる。内側の `PrevPort`・`NextPort` を自分の属性にすれば、それがネットワークの前側・次側になる。

```python
class Stack(Network):
    def __init__(self) -> None:
        self.l1 = Hidden(784, 256)
        self.l2 = Hidden(256, 256)
        self.l1.connect(self.l2)
        self.prev = self.l1.prev         # 外向きに公開（前側）
        self.next = self.l2.next         # 外向きに公開（次側）

stack, head = Stack(), Head()
stack.connect(head)                      # stack.next（= l2.next） <-> head.prev
stack.build()                            # ルートで構築する
```

入れ子は構築時の構造にとどまる。ネットワークの中のノードは、実行時もそれぞれ独立に非同期で動き、ネットワークの境界は非同期の境界を変えない。複数の層を 1 つの非同期処理の単位にしたいときは、スタックの大きさのノードとして書く（[ノード](nodes.md#ノードの大きさ)）。複数のノードを同じワーカーで決まった順に回すのは実行の配置の話で、ネットワークの構造とは別に扱う（[ノード](nodes.md#非同期の境界と実行の配置)）。

## ネットワークの入力と出力

> 状態: 実装済み（2026-10-16）。名前と振る舞いは[実装](#実装)のとおり。形は暫定で、使ってみて問題が見つかれば見直す。

ネットワークの入力と出力は、未接続のまま外に出ている Port である。外からの入出力には 2 つの方法があり、両方を使える。どちらの方法でも、書く値と読む値は `torch.Tensor` である（[メッセージ](messages.md#値の型)）。

1. ホスト（ネットワークを動かす Python のコード）が、ネットワークの公開インターフェイスで Port を読み書きする
2. 入出力を普通のノードとして書き、ネットワークの中に置く。カメラやセンサのドライバのように、自分の周期で動いて外界と値をやり取りしたい入出力に向く。スケジューラの上で動くので、決定的なテストにも載せやすい

### 実行はバックグラウンドで行う

`run()` はネットワークをバックグラウンドで動かし始め、全ノードの起動（`on_start` と、復元するときの `load_state_dict`）が終わってグローバルタイマーが動き出したところで戻る。ノードの `on_update` は待たない。ホストのスレッドはノードの実行に使われず、以後ホストは公開インターフェイスだけでネットワークとやり取りする。

起動が終わるまで待つのは、起動中にノードが投げた例外を `run()` 自身が送出できるようにするためである。

公開インターフェイスは、`build()` を呼んだネットワーク（ルート）のインスタンスが持つ。インスタンスが定義と実行を兼ねるという方針（[define-and-run](#define-and-run)）に合わせるためである。子のネットワークやノードからは呼べない。

| 操作                     | 呼べるとき         | 内容                                                                     |
| ------------------------ | ------------------ | ------------------------------------------------------------------------ |
| `build()`                | 最初に 1 回        | 構造と型を確定し、Port をスロットに結び付ける                            |
| `write(...)`             | `build()` の後     | 未接続の Port に書く。`run()` の前に書けば、そのスロットの初期値になる  |
| `load_state_dict(state)` | `run()` の前       | 状態の木から復元する（[実行モデル](execution-model.md#停止と状態の取得復元)） |
| `run()`                  | `build()` の後に 1 回 | バックグラウンドで実行を始め、全ノードの起動が終わったら戻る             |
| `read(port)`             | `build()` の後     | Port に送られた最新の値と時刻の組を返す                                  |
| `subscribe(port)`        | `run()` の後       | 新しい値が書かれるたびに最新の値と時刻を返すイテレータ                   |
| `state_dict()`           | 実行中             | 時刻のそろった状態の木のコピーを返す                                     |
| `shutdown()`             | `run()` の後       | 終了を要求し、終了するまで待つ                                           |
| `join()`                 | `run()` の後       | 終了するまで待つ                                                         |

```python
net = Classifier()                 # body.prev と head.teacher を未接続のまま公開
net.build()
net.write({net.prev: x0, net.teacher: y0})       # run の前に初期値を書く
net.run()                                        # バックグラウンドで開始し、起動が終わったら戻る

for x, y in dataset:
    net.write({net.prev: x, net.teacher: y})     # 複数の Port に同時に書く
    mujou.time.sleep(0.1)                        # グローバル時間で提示時間だけ待つ
    pred, t = net.read(net.head.next)            # 最新値と時刻の組
    h1, t1 = net.read(net.body.l1.next)          # 中間層を観測する

for y, t in net.subscribe(net.head.next):        # 新しい値が来るたびに最新値を受け取る
    actuator.send(y)

net.shutdown()
```

### 入力はグローバル時間上の信号

スロットは最新値だけを持つので、ホストが書いた値は、次に書くまでそのまま保たれる。そのため入力は、値の列ではなく、グローバル時間上で階段状に変わる信号 $x(t)$ として与えられる。

データセットを流すときは、1 つのサンプルをグローバル時間でどれだけ保つか（提示時間）を、ユーザーが決める。推論が平衡に近づくには、活動の時定数程度の時間がかかるからである。ホストはグローバル時間で待つ（`mujou.time.sleep`、[実行モデル](execution-model.md#グローバルタイマー)）。実時間で待つと、時間のスケール・停止・テスト用の仮想時計と噛み合わない。速く回したいときは、グローバルタイマーを加速する。

### 書き込み

ホストが書けるのは未接続の Port だけである。接続済みの Port には書けない。各スロットの書き手は 1 つという原則を保つためである。ホストは、外から書けるスロットの唯一の書き手になる。複数のホストのスレッドから `write` を呼んでもよく、その場合はホストの側で 1 回ずつ順に処理する。

`run()` の前に書いた値は、そのスロットの初期値になる。最初の入力を書いてから `run()` すれば、ノードがゼロの入力で動き出すことはない。状態の木から復元する場合は、`load_state_dict()` の後に書いた値が優先される（前に書いた値は木の値で置き換わる）。`load_state_dict()` の後、`run()` の前に書いた値には、木の時刻 $T$ が付く。復元した系は時刻 $T$ から始まるので、そのときのプロセスの時刻を付けると、スロットの時刻が復元した時間軸から外れるからである。

1 回の `write` で複数の Port に書いた値は、どのノードから見ても一斉に切り替わる。どの瞬間に見ても、新しい入力と古い教師信号が混ざることはない。ただし、ノードが 2 つの Port を順に読む間に、次の `write` が終わることはある。書いた値にはすべて同じ時刻が付くので、時刻を比べれば同じ `write` の値かどうかを判別できる。1 つの Port に書くのは、要素が 1 つの場合として同じ仕組みで扱う。

この切り替えは、書き手も読み手も待たずに行う。暫定的な方式として、外から書けるスロットとネットワークに次の仕組みを持たせる。

1. ネットワークは、外からの書き込みの版番号 $V$ を atomic な整数として 1 つ持つ
2. 外から書けるスロットは、現在の値と、版番号の付いた次の値の組を持つ
3. `write` は、書く各スロットに、版番号 $V+1$ を付けた次の値を置く（それまでの次の値は現在の値に繰り上げる）。全部置いてから $V$ を 1 つ進める
4. 読み手は、次の値の版番号が $V$ 以下なら次の値を、そうでなければ現在の値を読む

$V$ を進める 1 回の atomic な操作で、すべてのスロットが同時に切り替わる。接続済みの Port のスロットはノードが書くので、この仕組みを持たない。読み手のコストは、外から書けるスロットを読むときに atomic な読み出しが 1 回増えることだけである。

全ノードを止めてから書く方式も考えたが、書くたびに一番遅いノードの `on_update` が終わるのを待つことになり、サンプルごとに払うには重いので採らなかった。

### 読み出し

ホストはどの Port からでも、そのノードが送った値を時刻と組で読める。未接続の Port から読めばネットワークの出力になり、接続済みの Port から読めば中間層の観測になる。外からの読み出しは読み手が 1 つ増えるだけなので、ノードの動作には影響しない。

読み出しには 2 つの方法がある。

| 方法                       | 返すもの                                                                       | 向いている用途                                 |
| -------------------------- | ------------------------------------------------------------------------------ | ---------------------------------------------- |
| `read(port)`               | その時点の最新値と時刻                                                         | 消費者が自分の周期で最新値を読む（制御ループなど） |
| `subscribe(port)`          | 新しい値が書かれるたびに、その時点の最新値と時刻を返すイテレータ                 | 出力が更新されるたびに処理したい                 |

どちらも、外の消費者がどれだけ遅くてもノードを待たせない。`subscribe` で待つのは消費者だけで、書き手は通知するだけで待たない。消費者が遅いと途中の値は飛ばされ、最新値だけが返る。ネットワークが正常に終了すると、`subscribe` のイテレータは終わる。

次の方法は持たない。

| 持たない方法                     | 理由                                                                                   |
| -------------------------------- | -------------------------------------------------------------------------------------- |
| 書き込みごとのコールバック       | ノードのスレッドで利用者のコードが走り、消費者の遅さがそのまま書き手に伝わる         |
| すべての値の記録                 | ログには欲しいが、最初は要らない。future work とする（あふれたら古い値を捨て、書き手を待たせない形にする） |
| mujou の外のプロセスへの転送     | 複数マシンでの実行を想定していない。ROS や ZeroMQ などへの橋渡しは、ホストのスレッドか出力のノードでユーザーが書く |

### 入力と出力の対応

出力は、入力が変わってから平衡に近づくまでの時間だけ遅れて追従する。`write` の直後に `read` すると、前の入力に対する出力が返る。入力と出力を対応させたいときは、提示時間の終わりに読む。連続時間系なので、ある区間の終わりの出力を、その区間の入力に対する応答とみなす。

サンプルの ID をネットワークに流して対応させることはしない。ID を運ぶ仕組みを、すべてのノードに背負わせることになるからである。

## 分岐と合流

分岐と合流は、どちらも Port に Channel が複数つながった状態として表す。

```text
         ┌─ Channel ─ B.prev
A.next ──┼─ Channel ─ C.prev
         └─ Channel ─ D.prev
```

この形は `a.connect(b)`、`a.connect(c)`、`a.connect(d)` と 3 回接続して作る。`A.next` は `NextPort` なので、既定で複数の相手を取れる。

### 送る側

複数の相手を持つ Port では、全員に同じメッセージを送る操作と、相手を指定して送る操作の両方を使える。全員に送ると、送った値はコアのバッファへ 1 回だけコピーされ、各 Channel のスロットにはそのバッファへの参照が書かれる。バッファは不変で参照カウントで管理するので、相手が何個でもそれ以上のコピーは起きない。

相手を指定して送る操作は、相手ごとに中身が違うメッセージのためにある。たとえば PC-ALM で B の前側に A1 と A2 が合流しているとき、B は相手ごとに異なる重みを使って、A1 には $W_1^\top \varepsilon$、A2 には $W_2^\top \varepsilon$ を送る。

### 受け取る側

相手 1 つの Port は、受け取ったメッセージをそのまま返す。複数の相手を持つ Port は、相手ごとのメッセージの対応表を返す。

対応表のキーは、接続のときに返る接続ごとのハンドル（Channel の端）である。同じノードと 2 本つないだ場合でも、ハンドルで区別できる。対応表の並びは接続した順に固定し、実行の再現性を保つ。

### 集約は更新手法の責任

複数の相手から受け取ったメッセージをどう束ねるかは、受け取るノードの更新手法が決める。たとえば PC-ALM なら $\sum_k W_k^\top \varepsilon_k$ のように足し合わせる。足し合わせなどの集約をフレームワークに組み込まないのは、更新手法を差し替えられるようにするためである（[更新手法](update-rules.md)）。

## 実装

> 状態: 実装済み（2026-10-16）。

利用者が使う名前は `mujou` のトップレベルにある: `Node`、`Network`、`Port`、`PrevPort`、`NextPort`、`Channel`、`TensorSpec`、`DictSpec`、`NetworkError`、`PauseTimeoutError`、`run`。グローバル時間は `mujou.time`（`time` / `time_ns` / `sleep` / `get_time_scale` / `set_time_scale`）。

### 構築と実行

- `Network.build()` が構造を検査して凍結し、全 Port をスロットに結び付ける。以後 `connect` は `RuntimeError`
- `mujou.run(network, *, capture_state_on_exception=False, pause_timeout=10.0)` は、未構築なら `build()` してから `network.run(...)` を呼び、同じ `network` を返す。`Network.run()` も同じ引数を取る。2 回目の `run` は `RuntimeError`
- 送る spec を持つ Port は、外向きのスロット 1 本と、Channel ごとのスロットを持つ。未接続で相手 1 つの、受ける spec を持つ Port は、ホストが書くスロットを 1 本持つ。ホストが書くスロットは、ネットワークに 1 つの版番号 $V$ を共有する（版番号は同じネットワークの中でしか一斉に切り替えないので、1 つにする）
- スロットの名前は、所有ノードのパスと Port の属性名から作る: 外向きは `"body.l1.next/out"`、Channel は `"body.l1.next/ch0"`（番号は書く側の Port で接続した順）、ホストが書くスロットは `"body.l1.prev/in"`（公開した名前 `body.prev` ではなく、所有ノードのパスで付ける）。状態の木の `"slots"` のキーになる

### Port の読み書き

- `recv()` は相手 1 つなら値、複数なら `{Channel: 値}`（接続順）を返す。`recv_with_time()` は値と書かれた時刻（ns）の組を返す。どちらも毎回コアのバッファからノードのデバイスの新しい Tensor へコピーするので、受け取った Tensor をその場で書き換えても、スロットにもほかの読み手にも影響しない。`requires_grad` は False
- 相手 1 つの Port は、相手（未接続ならホスト）がまだ書いていなければ初期値（ゼロ）を返す。相手を複数取る未接続の Port は `{}` を返す
- `send(msg)` は全員に送り、外向きのスロットも更新する。`send_to(channel, msg)` はその Channel のスロットだけを更新し、外向きのスロットは変えない。そのため `send_to` だけを使う Port をホストが `read` すると、初期値（復元したなら木の値）が返る
- 送るときは値を `detach()` し、GPU の値は自分のストリームでホストへコピーしてから、コアがプールのバッファへコピーする。送った後に値を書き換えても、読み手には見えない
- `recv` / `send` / `send_to` を呼べるのは、Port を所有するノードのスレッドだけである。ほかのスレッド（ホストやほかのノード）から呼ぶと `RuntimeError` になる。スロットの書き手を 1 つに保ち、ノードが読めるのを自分の Port のスロットに限るため（局所性）である。受け取った値を所有ノードのデバイスとストリームに載せるためでもある。判定は OS のスレッド ID（`threading.get_ident()`）で行い、ホストが終了を見たとき（`shutdown`・`join` などや、次の `run`）にノードはスレッドを忘れる。`state_dict()` は制御スレッドで呼ばれるので、その中では `recv` できない（スロットは木に別に入る）
- 新しい値が書かれるまで待つ機能は Port に持たせない。ノードが隣のノードを待つことになるからである。待つのはホストの `subscribe` だけである

### ホストの入出力

| メソッド                         | 振る舞い                                                                                                     |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `write({port: value, ...})`      | 木の中の、未接続で相手 1 つの、受ける spec を持つ Port だけに書ける。ほかは `ValueError`。shape の違いは `ValueError`、型と dtype の違いは `TypeError` |
| `read(port)`                     | 送る spec を持つ Port の外向きのスロットの値と、時刻（秒、`time_ns / 1e9`）を返す。値は CPU 上の新しい Tensor。最初に送られるまではゼロ（復元したなら木の値） |
| `subscribe(port)`                | `run` の後だけ。呼んだ後に書かれた値を返すイテレータ。待つ間に書かれた値は飛ばし、最新値だけを返す。正常に終了すると終わる |
| `state_dict()`                   | 実行中だけ呼べる。`run` の前と正常な終了の後は `RuntimeError`                                               |
| `load_state_dict(state)`         | `run` の前だけ。スロットはその場で戻し、ノードの状態・最後の更新の時刻・タイマーは `run` で戻す         |
| `exception_state_dict()`         | 例外のときに取得した木。取得していなければ `None`                                                           |
| `shutdown()` / `join()`          | 終了を要求して待つ／終了を待つ。`shutdown` は `run` の前と終了の後は何もしない（`build` の前は `RuntimeError`） |

- 例外で終了した後は、`write`・`read`・`subscribe`（とそのイテレータ）・`state_dict`・`shutdown`・`join` が `NetworkError` を送出する。`__cause__` は最初にノードが投げた例外である
- `run()` の起動中も、ほかのホストのスレッドの `write` は待たずにノードへ届く（`on_start` がホストの書き込みを待ってもよい）。ただし `load_state_dict` で復元したネットワークでは、`write` が木の時刻で書くか起動後の時刻で書くかを決めるために、起動が終わるまで待つ
- これらはホストのためのメソッドで、ノードの hook の中（ノードのスレッド、`state_dict()` を呼んでいる制御スレッド）から呼ぶと `RuntimeError` になる。ノードは自分の Port だけでやり取りする（局所性）。待つメソッドでは、待ち合いでデッドロックする代わりでもある。ほかのネットワークのメソッドも hook からは呼べない。ネットワークの間の橋渡しは、ホストのスレッドで書くか、外界とやり取りする I/O のノードとして書く
- 走っているネットワークは、ホストが参照を手放しても止まらない。フレームワークは、ホストが終了を見るまで（`shutdown`・`join` など、または次の `run`）参照を持ち、遅くともインタプリタの終了時に終了させて `on_stop` を待つ。終了させるのは non-daemon のスレッドを join するより前なので（`threading._register_atexit`）、`subscribe` を回すスレッドが残っていても、ネットワークの終了とともにイテレータが終わり、プロセスは終われる。それでも、使い終わったら `shutdown()` を呼ぶ
