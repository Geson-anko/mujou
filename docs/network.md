# ネットワーク

ブロックをどう組み合わせ、ブロック間をどう双方向に接続するかを定める。メッセージの型とスロットは [メッセージ](messages.md) を参照。

## 構成要素

| 構成要素     | 役割                                                                                 |
| ------------ | ------------------------------------------------------------------------------------ |
| ブロック     | 非同期処理の単位。ネットワークの末端の要素で、Port を宣言する                        |
| ネットワーク | ブロックや別のネットワークを子として持ち、内側の Port を外向きに公開する             |
| Port         | ブロックやネットワークの接続口。送るメッセージの型と受け取るメッセージの型の組を持つ |
| Channel      | 2 つの Port の間の接続 1 本。向きごとのスロット 2 本と、その両端からなる             |

ブロックとネットワークは共通の基底を持つ（Composite）。どちらも Port を持ち、同じ書き方で接続できる。共通の基底が持つのは、Port を持つことと接続できることだけである。

ブロックは実行時に存在する分散処理の最小単位で、ライフサイクル hook を持つ（[ブロック](blocks.md#ライフサイクル-hook)）。ネットワークは構築時だけの構造で、hook を持たない。ネットワークに `on_update` を持たせると、ネットワークの単位で同期的に回すという意味が紛れ込むからである。

## define-and-run

ネットワークの構造は define-and-run で記述する。PyTorch の実行方式は define-by-run だが、mujou はこれと異なる。利用者は、PyTorch の `nn.Module` のように組み合わせて宣言的に書ける API でネットワークを記述し、最終的にスキーマオブジェクトを作る。各スロットのメッセージの型・shape・初期値は、このスキーマオブジェクトの構築時に確定し、以後は変えない。

この API は `nn.Module` にたとえているだけで、`nn.Module` に相当する単位がブロックになるわけではない。

`nn.Module` と同じく、ブロックやネットワークのインスタンスは定義と実行の両方を担う。構築すると、各 Port は実際のスロットに結び付けられ、同じブロックのインスタンスが実行時に hook を呼ばれる。凍結したスキーマから実行時のオブジェクトを別に作り直すことはしない。

## Port

Port は向きを持たない。送るメッセージの型（send）と受け取るメッセージの型（recv）の組だけを持ち、2 つの Port は型が互いに逆向きのとき、つまり片方の send がもう片方の recv と一致するときだけ接続できる。一致を確かめる対象は、メッセージの型と各 Tensor の shape の両方である。一致しなければ、`connect` を呼んだ時点でエラーになる。

Port は send と recv の一方だけを持ってもよい。send だけの Port と recv だけの Port は、型と shape が一致すれば接続でき、その Channel のスロットは 1 本になる。入力を送るだけのブロックや観測するだけのブロックは、こうして使わない向きのスロットとメッセージを持たずに済む。

Port は未接続のまま残ってもよい。未接続の Port も、スキーマで宣言した型の値を持つスロットを持つ。ブロックが未接続の Port から受け取ると、相手 1 つの Port は初期値を返し、複数の相手を取る Port は空の対応表を返す。

上流と下流、上と下の区別は、フレームワークでは決めない。PC-ALM の層の間の結合も、softmax のような層内の横方向の結合も、同じ仕組みで表す。こうして、PC-ALM 固有の上下という区別を基盤に持ち込まない。

Port は、つながる相手が 1 つか複数かを持つ。相手 1 つの Port に 2 本目の Channel を接続すると、ネットワークの構築時にエラーになる。

### PrevPort と NextPort

Port の宣言には 3 種類がある。

| 宣言       | 役割                                | 相手の数の既定 |
| ---------- | ----------------------------------- | -------------- |
| `PrevPort` | 前側の Port。`a.connect(b)` の b 側 | 1 つ           |
| `NextPort` | 次側の Port。`a.connect(b)` の a 側 | 複数           |
| `Port`     | 前側でも次側でもない Port           | 1 つ           |

分岐は次側で起きることが多いので、`NextPort` は既定で複数の相手を取る。どの宣言でも、相手の数は明示して上書きできる。たとえば合流を受けるブロックは、`PrevPort` を複数と宣言する。

相手の数は宣言の時点で決まるので、受け取るときの戻り値の型（メッセージそのものか、相手ごとの対応表か）が静的に決まる。

ブロックとネットワークが直接の属性として持てる `PrevPort` と `NextPort` は、それぞれ 1 つまでである。前側や次側が無いブロック（入力だけを流すブロックなど）は、その宣言を持たない。

## 接続

接続には 2 つの書き方がある。どちらも Channel を 1 本作り、その両端を 2 つの Port に同時に登録する。そのため、B を A に接続した時点で、A にも B からの逆向きの経路が登録される。ネットワークは define-and-run なので、実行中に経路が増えたり減ったりすることはない。

1 つ目は Port 同士をつなぐ書き方で、`a.next.connect(b.prev)` のように書く。

2 つ目はブロック同士（またはネットワーク同士）をつなぐ書き方で、`a.connect(b)` のように書く。`a.connect(b)` は、a の `NextPort` と b の `PrevPort` をつなぐ。同じ種類の層を並べるときは、型だけではどの Port 同士をつなぐか決められないので、この宣言で決める。

前側・次側は `a.connect(b)` という省略形と相手の数の既定のための宣言であり、Port 自体は向きを持たない。そのため `a.connect(b)` と `b.connect(a)` は別の接続になる。`PrevPort`・`NextPort` 以外の Port をつなぐときは、Port 同士の書き方で明示する。

以下はイメージである。API の具体的な形は未決定で、名前や書き方はこのとおりになるとは限らない。

```python
class Hidden(Block):
    def __init__(self, n_in: int, n_out: int) -> None:
        # 前へ W^T ε を送り、前から h を受け取る（相手 1 つ）
        self.prev = PrevPort(send=TensorSpec((B, n_in)), recv=TensorSpec((B, n_in)))
        # 次へ h を送り、次から W^T ε を受け取る（相手は複数）
        self.next = NextPort(send=TensorSpec((B, n_out)), recv=TensorSpec((B, n_out)))

l1, l2 = Hidden(784, 256), Hidden(256, 256)
ch = l1.connect(l2)              # l1.next <-> l2.prev
# l1.next.connect(l2.prev) と同じ
```

Channel のスロット 2 本は、それぞれ書く側の端が所有する。各スロットの書き手は 1 つという原則は、分岐や合流があってもそのまま保たれる。

## 入れ子

ネットワークは、ブロックや別のネットワークを子として持てる。ネットワークは内側の Port を自分の属性として持つことで外向きに公開し、外から見るとブロックと同じように接続できる。内側の `PrevPort`・`NextPort` を自分の属性にすれば、それがネットワークの前側・次側になる。

```python
class Stack(Network):
    def __init__(self) -> None:
        self.l1 = Hidden(784, 256)
        self.l2 = Hidden(256, 256)
        self.l1.connect(self.l2)
        self.prev = self.l1.prev         # 外向きに公開（前側）
        self.next = self.l2.next         # 外向きに公開（次側）

stack, head = Stack(), Head()
stack.connect(head)                      # stack.next（= l2.next） <-> head.prev
stack.build()                            # ルートで構築する
```

入れ子は構築時の構造にとどまる。ネットワークの中のブロックは、実行時もそれぞれ独立に非同期で動き、ネットワークの境界は非同期の境界を変えない。複数の層を 1 つの非同期処理の単位にしたいときは、スタックの大きさのブロックとして書く（[ブロック](blocks.md#ブロックの大きさ)）。複数のブロックを同じワーカーで決まった順に回すのは実行の配置の話で、ネットワークの構造とは別に扱う（[ブロック](blocks.md#非同期の境界と実行の配置)）。

## ネットワークの入力と出力

> 状態: この節の実行と外からの読み書きの形は暫定である（2026-10-14）。実装で問題が見つかれば見直す。

ネットワークの入力と出力は、未接続のまま外に出ている Port である。外からの入出力には 2 つの方法があり、両方を使える。

1. ホスト（ネットワークを動かす Python のコード）が、ネットワークの公開インターフェイスで Port を読み書きする
2. 入出力を普通のブロックとして書き、ネットワークの中に置く。カメラやセンサのドライバのように、自分の周期で動いて外界と値をやり取りしたい入出力に向く。スケジューラの上で動くので、決定的なテストにも載せやすい

### 実行はバックグラウンドで行う

`run()` はネットワークをバックグラウンドで動かし始め、すぐに戻る。ホストのスレッドはブロックの実行に使われず、以後ホストは公開インターフェイスだけでネットワークとやり取りする。

公開インターフェイスは、`build()` を呼んだネットワーク（ルート）のインスタンスが持つ。インスタンスが定義と実行を兼ねるという方針（[define-and-run](#define-and-run)）に合わせるためである。子のネットワークやブロックからは呼べない。

| 操作                     | 呼べるとき         | 内容                                                                     |
| ------------------------ | ------------------ | ------------------------------------------------------------------------ |
| `build()`                | 最初に 1 回        | 構造と型を確定し、Port をスロットに結び付ける                            |
| `write(...)`             | `build()` の後     | 未接続の Port に書く。`run()` の前に書けば、そのスロットの初期値になる  |
| `load_state_dict(state)` | `run()` の前       | 状態の木から復元する（[実行モデル](execution-model.md#停止と状態の取得復元)） |
| `run()`                  | `build()` の後に 1 回 | バックグラウンドで実行を始め、すぐに戻る                                 |
| `read(port)`             | `build()` の後     | Port に送られた最新の値と時刻の組を返す                                  |
| `subscribe(port)`        | `build()` の後     | 新しい値が書かれるたびに最新の値と時刻を返すイテレータ                   |
| `state_dict()`           | いつでも           | 時刻のそろった状態の木のコピーを返す                                     |
| `shutdown()`             | `run()` の後       | 終了を要求し、終了するまで待つ                                           |
| `join()`                 | `run()` の後       | 終了するまで待つ                                                         |

以下はイメージである。名前や書き方はこのとおりになるとは限らない。

```python
net = Classifier()                 # body.prev と head.teacher を未接続のまま公開
net.build()
net.write({net.prev: x0, net.teacher: y0})       # run の前に初期値を書く
net.run()                                        # バックグラウンドで開始し、すぐ戻る

for x, y in dataset:
    net.write({net.prev: x, net.teacher: y})     # 複数の Port に同時に書く
    mujou.time.sleep(0.1)                        # グローバル時間で提示時間だけ待つ
    pred, t = net.read(net.head.next)            # 最新値と時刻の組
    h1, t1 = net.read(net.body.l1.next)          # 中間層を観測する

for y, t in net.subscribe(net.head.next):        # 新しい値が来るたびに最新値を受け取る
    actuator.send(y)

net.shutdown()
```

### 入力はグローバル時間上の信号

スロットは最新値だけを持つので、ホストが書いた値は、次に書くまでそのまま保たれる。そのため入力は、値の列ではなく、グローバル時間上で階段状に変わる信号 $x(t)$ として与えられる。

データセットを流すときは、1 つのサンプルをグローバル時間でどれだけ保つか（提示時間）を、ユーザーが決める。推論が平衡に近づくには、活動の時定数程度の時間がかかるからである。ホストはグローバル時間で待つ（`mujou.time.sleep`、[実行モデル](execution-model.md#グローバルタイマー)）。実時間で待つと、時間のスケール・停止・テスト用の仮想時計と噛み合わない。速く回したいときは、グローバルタイマーを加速する。

### 書き込み

ホストが書けるのは未接続の Port だけである。接続済みの Port には書けない。各スロットの書き手は 1 つという原則を保つためである。ホストは、外から書けるスロットの唯一の書き手になる。複数のホストのスレッドから `write` を呼んでもよく、その場合はホストの側で 1 回ずつ順に処理する。

`run()` の前に書いた値は、そのスロットの初期値になる。最初の入力を書いてから `run()` すれば、ブロックがゼロの入力で動き出すことはない。状態の木から復元する場合は、`load_state_dict()` の後に書いた値が優先される。

1 回の `write` で複数の Port に書いた値は、どのブロックから見ても一斉に切り替わる。新しい入力と古い教師信号の組を読むブロックが、一瞬も存在しない。書いた値にはすべて同じ時刻が付く。1 つの Port に書くのは、要素が 1 つの場合として同じ仕組みで扱う。

この切り替えは、書き手も読み手も待たずに行う。暫定的な方式として、外から書けるスロットとネットワークに次の仕組みを持たせる。

1. ネットワークは、外からの書き込みの版番号 $V$ を atomic な整数として 1 つ持つ
2. 外から書けるスロットは、現在の値と、版番号の付いた次の値の組を持つ
3. `write` は、書く各スロットに、版番号 $V+1$ を付けた次の値を置く（それまでの次の値は現在の値に繰り上げる）。全部置いてから $V$ を 1 つ進める
4. 読み手は、次の値の版番号が $V$ 以下なら次の値を、そうでなければ現在の値を読む

$V$ を進める 1 回の atomic な操作で、すべてのスロットが同時に切り替わる。接続済みの Port のスロットはブロックが書くので、この仕組みを持たない。読み手のコストは、外から書けるスロットを読むときに atomic な読み出しが 1 回増えることだけである。

全ブロックを止めてから書く方式も考えたが、書くたびに一番遅いブロックの `on_update` が終わるのを待つことになり、サンプルごとに払うには重いので採らなかった。

### 読み出し

ホストはどの Port からでも、そのブロックが送った値を時刻と組で読める。未接続の Port から読めばネットワークの出力になり、接続済みの Port から読めば中間層の観測になる。外からの読み出しは読み手が 1 つ増えるだけなので、ブロックの動作には影響しない。

読み出しには 2 つの方法がある。

| 方法                       | 返すもの                                                                       | 向いている用途                                 |
| -------------------------- | ------------------------------------------------------------------------------ | ---------------------------------------------- |
| `read(port)`               | その時点の最新値と時刻                                                         | 消費者が自分の周期で最新値を読む（制御ループなど） |
| `subscribe(port)`          | 新しい値が書かれるたびに、その時点の最新値と時刻を返すイテレータ                 | 出力が更新されるたびに処理したい                 |

どちらも、外の消費者がどれだけ遅くてもブロックを待たせない。`subscribe` で待つのは消費者だけで、書き手は通知するだけで待たない。消費者が遅いと途中の値は飛ばされ、最新値だけが返る。ネットワークが正常に終了すると、`subscribe` のイテレータは終わる。

次の方法は持たない。

| 持たない方法                     | 理由                                                                                   |
| -------------------------------- | -------------------------------------------------------------------------------------- |
| 書き込みごとのコールバック       | ブロックのスレッドで利用者のコードが走り、消費者の遅さがそのまま書き手に伝わる         |
| すべての値の記録                 | ログには欲しいが、最初は要らない。future work とする（あふれたら古い値を捨て、書き手を待たせない形にする） |
| mujou の外のプロセスへの転送     | 複数マシンでの実行を想定していない。ROS や ZeroMQ などへの橋渡しは、ホストのスレッドか出力のブロックでユーザーが書く |

### 入力と出力の対応

出力は、入力が変わってから平衡に近づくまでの時間だけ遅れて追従する。`write` の直後に `read` すると、前の入力に対する出力が返る。入力と出力を対応させたいときは、提示時間の終わりに読む。連続時間系なので、ある区間の終わりの出力を、その区間の入力に対する応答とみなす。

サンプルの ID をネットワークに流して対応させることはしない。ID を運ぶ仕組みを、すべてのブロックに背負わせることになるからである。

## 分岐と合流

分岐と合流は、どちらも Port に Channel が複数つながった状態として表す。

```text
         ┌─ Channel ─ B.prev
A.next ──┼─ Channel ─ C.prev
         └─ Channel ─ D.prev
```

この形は `a.connect(b)`、`a.connect(c)`、`a.connect(d)` と 3 回接続して作る。`A.next` は `NextPort` なので、既定で複数の相手を取れる。

### 送る側

複数の相手を持つ Port では、全員に同じメッセージを送る操作と、相手を指定して送る操作の両方を使える。全員に送ると、各 Channel のスロットに同じ Tensor への参照が書かれる。Tensor は不変で参照カウントで管理するので、相手が何個でもコピーは起きない。

相手を指定して送る操作は、相手ごとに中身が違うメッセージのためにある。たとえば PC-ALM で B の前側に A1 と A2 が合流しているとき、B は相手ごとに異なる重みを使って、A1 には $W_1^\top \varepsilon$、A2 には $W_2^\top \varepsilon$ を送る。

### 受け取る側

相手 1 つの Port は、受け取ったメッセージをそのまま返す。複数の相手を持つ Port は、相手ごとのメッセージの対応表を返す。

対応表のキーは、接続のときに返る接続ごとのハンドル（Channel の端）である。同じブロックと 2 本つないだ場合でも、ハンドルで区別できる。対応表の並びは接続した順に固定し、実行の再現性を保つ。

### 集約は更新手法の責任

複数の相手から受け取ったメッセージをどう束ねるかは、受け取るブロックの更新手法が決める。たとえば PC-ALM なら $\sum_k W_k^\top \varepsilon_k$ のように足し合わせる。足し合わせなどの集約をフレームワークに組み込まないのは、更新手法を差し替えられるようにするためである（[更新手法](update-rules.md)）。

## 未決定事項

API の具体的な形（クラス名・メソッド名、shape の決め方など）は未決定である。実行と外からの読み書きの形は暫定である（[ネットワークの入力と出力](#ネットワークの入力と出力)）。相手を指定して送る Port（相手ごとに中身が違う）を外から読んだときに何を返すかも未決定である（[未決定事項](open-decisions.md#ネットワークスキーマの-api)）。
