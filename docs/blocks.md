# ブロック

## 定義

ブロックは mujou の計算の基本単位であり、基盤となる抽象である。ブロックの内側は同期的に計算し、ブロック同士は非同期にやり取りする。非同期・分散の境界は、常にブロックの境界と一致する。

局所性・非同期性の不変条件は、**ブロックの間に課す**。ブロックの内側の計算方法（ニューロンの合成、行列演算、BP など）は、ブロックごとに自由に選べる。

## ブロックの大きさ

ブロックの大きさは、どのブロックのクラスを書くか、使うかで決まる。設定を変えるだけでブロックを分割したり統合したりはしない。対象とするのは次の 3 つのレベルである。

| レベル     | 内容                                                                   |
| ---------- | ---------------------------------------------------------------------- |
| ニューロン | 1 ニューロンを 1 ブロックにする。最小のブロック。future work           |
| レイヤー   | 1 レイヤーを 1 ブロックにする。既定                                    |
| スタック   | 複数のレイヤーを 1 ブロックにする。モデル全体を 1 ブロックにしてもよい |

既定をレイヤーにしたのは、わかりやすさのためである。

### ニューロンが最小である理由

既定の更新手法 PC-ALM の更新式（活動・双対変数・重み）は、ニューロン自身の値と、シナプスでつながった相手の値だけで計算できる。そのため、ニューロン 1 個を 1 ブロックにまで分割できる。

ニューロン単位のブロックによる分散処理は future work とする。必要になったら、`nn.Linear` に当たるレイヤーのブロックとは別のクラスとして書く。

### 設定で分割しない理由

ブロックを自動で分割するには、ブロックの内側の計算と、重みを誰が持つかを、フレームワークが知っていなければならない。これは、ブロックの内側を自由にするという方針と合わない。

全結合のレイヤーは、重みの行が出力のニューロンごとに独立しているので、ニューロンごとに分けやすい。畳み込みは、1 つのカーネルを出力のすべての位置で共有するので、そうはいかない。出力の位置ごとにブロックに分けると、各ブロックがカーネルのコピーを持ち、非同期に動くうちにコピー同士がずれる（[ブロック間の契約](#ブロック間の契約) の weight transport と同じ問題）。カーネルを別のブロックに持たせると、重みの持ち主がニューロンでなくなり、値のやり取りも増える。

### 非同期の境界と実行の配置

「ブロックの大きさ」と「どう実行するか」は分けて考える。

| 軸             | 意味                                                                   | 決め方                       |
| -------------- | ---------------------------------------------------------------------- | ---------------------------- |
| 非同期の境界   | どこで最新値の読み書きになり、一貫したスナップショットを失うか         | ブロックのクラスで決まる     |
| 実行の配置     | どのブロックをどのワーカーで、どの順に回すか                           | 実行時に選ぶ（[ネイティブコア](native-core.md#mn-スケジューリング)） |

複数のブロックを 1 本のワーカーで決まった順に、同じ $\Delta t$ で回せば、まとめて 1 つのブロックのように動く。どのブロックも状態とライフサイクル hook からなるので、フレームワークはブロックの内側を知らなくてもこれができる。テストで全ブロックを固定の $\Delta t$ で同期的に回すのも、この配置の一例である（[実行モデル](execution-model.md#テスト)）。配置を利用者が指定する API は未決定である。

### 粒度を選べるようにする理由

どの粒度が最適かは、ハードウェアと用途（ロボティクス、ニューロモーフィックなど）によって変わる。ブロックを基盤にすれば、ニューロン単位の細かい非同期も、BP のような同期的な手法も、同じ枠組みで扱える。

## ライフサイクル hook

ブロックは、実行時に存在する分散処理の最小単位である。ネットワークは構築時だけの構造であり、実行時の単位にはならない（[ネットワーク](network.md#構成要素)）。

ブロックは、フレームワークが呼ぶ hook を override して書く。ループはフレームワークが持ち、ブロックの作者は 1 ステップ分の処理だけを書く。こうするのは、次の 3 つのためである。

- M:N スケジューリング: `on_update` の 1 回が協調スケジューリングの区切りになる。作者が自分でループを書くと、そのブロックはワーカープールに載せられない
- 決定的なテスト: 仮想時計で固定の $\Delta t$ のまま全ブロックを決まった順に回すには、ループをフレームワークが持っている必要がある
- 言語の境界: Rust のネイティブなブロックは同じ hook を trait として実装し、Python のブロックは専用スレッドから同じ hook を呼ばれる

| hook                     | 呼ばれるとき                                       | 役割                                                         |
| ------------------------ | -------------------------------------------------- | ------------------------------------------------------------ |
| `on_start()`             | 実行開始時に 1 回。ブロックを実行するスレッドの上で | 状態の確保・初期化                                           |
| `on_update(dt)`          | 自分の周期で繰り返し                               | 隣の最新値を読み、$\Delta t$ ぶん更新し、書き込む。他を待たない |
| `on_pause()`             | 停止の要求を受けて、ループの区切りで止まったとき   | I/O の一時停止など                                           |
| `on_resume()`            | 停止から再開し、次の `on_update` の前              | I/O の再開、停止中に溜まった外界の値の破棄など               |
| `on_stop()`              | 実行終了時に 1 回。例外による終了でも呼ぶ          | I/O などの資源の解放                                         |
| `state_dict()`           | 状態の保存時。全ブロックが止まっている間           | 保存すべき状態を pickle できるオブジェクトの木として返す     |
| `load_state_dict(state)` | 状態の復元時。`on_start` の後、最初の `on_update` の前 | `state_dict()` が返した木から状態を戻す                      |

`on_pause` と `on_resume` は引数を取らない。停止している間、グローバル時間は進まないので、グローバル時間で測ると停止と再開は同じ時刻に起きる（[停止と状態の保存・復元](execution-model.md#停止と状態の保存復元)）。必要ならその時刻はグローバルタイマーから読める。停止していた実時間の長さはダイナミクスの外の量なので、それが必要な I/O のブロックは自分で測る。

どの hook が例外を投げても、システム全体を終了する（[実行モデル](execution-model.md#例外による終了)）。

`state_dict()` が返す木は、pickle できれば中身を問わない。mujou の Tensor のほか、NumPy の配列や PyTorch のテンソル、optimizer の状態を含めてよい。ファイルへの書き出しはフレームワークが行い、ブロックはファイルのパスを扱わない。

次の hook は持たない。

| 持たない hook                          | 理由                                                                               |
| -------------------------------------- | ---------------------------------------------------------------------------------- |
| エポックの開始・終了、学習・推論モード | 継続学習の原則（エポックを前提にしない、モードを分けない）に反する                 |
| メッセージの受信ごとに呼ぶ hook        | 受信ごとに呼ぶには受信を溜める必要があり、実質的に queue に戻る。最新値の読み書きと衝突する |
| 固定刻みの更新                         | 本番の $\Delta t$ は可変。固定刻みはテストで仮想時計の側から作る                   |

以下はイメージである。名前や書き方はこのとおりになるとは限らない。

```python

    def __init__(self, n_in: int, n_out: int) -> None:

        self.prev = PrevPort(send=TensorSpec((B, n_in)), recv=TensorSpec((B, n_in)))
        self.next = NextPort(send=TensorSpec((B, n_out)), recv=TensorSpec((B, n_out)))

    def on_update(self, dt: float) -> None:
        x = self.prev.recv()      # 前から受け取った最新値
        fbs = self.next.recv()    # 次の相手ごとの最新値
        ...                       # dt に比例した更新

    def state_dict(self) -> object:
```

ブロックのインスタンスは、定義と実行の両方を担う。`__init__` で Port を宣言したインスタンスが、そのまま実行時に hook を呼ばれる。ネットワークを構築すると、Port は実際のスロットに結び付けられる。

更新手法を差し替えられるという要件（[更新手法](update-rules.md)）は、基盤が特定の学習則を知らないことを指す。PC-ALM のレイヤーは、`Block` を継承したクラスとして提供すれば足りる。

## BP の取り込み

ブロックの内側は同期的なので、BP のような forward/backward も、そのブロックの中に閉じていれば許容する。外から見れば、値をやり取りする 1 つのブロックに過ぎない。

ただし、ブロックをまたいで計算グラフをつなげてはならない。ブロックをまたぐ `.backward()` は禁止である。ブロック内で autograd を使う書き方は skill `locality-and-async` を参照。

## ブロック間の契約

ブロック間でやり取りする値は、結合ごとの値の束として定義する。こうしておけば、ブロックの大きさを変えてもブロック間の契約は変わらない。

ブロックをまたぐ結合の重みは、**後シナプス側のブロックが所有する**。前シナプス側へは $W[k,j]\,\varepsilon_k$ を結合ごとの値として送る。両端で重みのコピーを持つと、非同期に実行するうちにコピー同士がずれる（weight transport の問題）。

層内で横方向に結合する演算（softmax、LayerNorm など）も、ニューロン単位で表せるようにする。同じ層のニューロン同士の結合を横方向の値のやり取りとして扱い、ブロック間と同じ不変条件を適用する。

## 設計目標から外すもの

GPU 計算での最適性は設計目標にしない。ニューロン単位に分割すると行列積が値のやり取りの集まりに分解されるので、GPU では非効率になる。しかし、それを理由に設計を制限しない。

## テストで確かめること

ブロックの分け方とスケジュールを変えても、同じ不動点に収束することを確かめる。ニューロン単位のブロックを実装したら、PC-ALM のレイヤーブロックをニューロンブロックの合成として組んでも、まとめて行列演算で組んでも、同じ結果になることも確かめる。
