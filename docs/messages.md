# メッセージ

ブロック間でやり取りするメッセージの型と、それを運ぶスロットの仕様を定める。実行モデル全体は [実行モデル](execution-model.md) を参照。

## 双方向通信の構成

ブロック間の双方向通信は、向きごとに 1 本ずつ、計 2 本の片方向スロットで構成する。この 2 本の組を Channel と呼ぶ（[ネットワーク](network.md)）。各スロットの書き手は、そのスロットを所有するブロック 1 つだけである。1 つのスロットを複数のブロックが読んでもよい。

既定の PC-ALM では、層 $i$ のブロックが上向きのスロットに $h_i$ を書き、層 $i+1$ のブロックが下向きのスロットに $W_{i+1}^\top \varepsilon_{i+1}$ を書く。それぞれのスロットは、書く側のブロックが所有する。

## Tensor

Tensor は mujou のコアが独自に持つ値の型である。

dtype は f32 だけをサポートする。データは CPU 上に、連続した row-major の配置で置く。バッチを使う場合は、バッチ次元も shape の一部として扱う。フレームワークはバッチ次元を特別扱いしない。

Tensor は不変であり、一度作った Tensor の中身は変更できない。この性質により、複数の読み手が同じ Tensor を同時に読んでも、書き手との間でデータ競合が起きない。

Tensor の役割は、データの入れ物と、外部ライブラリとの変換である。Tensor から参照できるのは shape と dtype で、NumPy・PyTorch とは相互に変換できる（変換時にコピーする）。Tensor は演算を持たない。演算はブロックの内側で、既存のライブラリを使って行う。

## メッセージの型

メッセージの型は次の 3 種類である。

| 型               | 意味                                             |
| ---------------- | ------------------------------------------------ |
| `Tensor`         | Tensor 1 つ。常に値がある                        |
| `Tensor \| None` | Tensor 1 つ。値が無いことがある                  |
| `TypedDict`      | キー名と値の型を明示した辞書。入れ子は許さない   |

`TypedDict` を定義するときは、キー名と値の型を明示する。値の型は `Tensor` か `Tensor | None` のどちらかである。たとえば教師信号のように、ステップによって無いことがある値は `Tensor | None` で宣言する。

```python
class Feedback(TypedDict):
    error: Tensor
    target: Tensor | None
```

値が `None` になれるのは、`| None` を付けて宣言したものだけである。

## スキーマと初期値

スロットのスキーマは、メッセージの型と各 Tensor の shape からなる。スキーマはネットワークを構築するときに確定し、以後は変えない（[ネットワーク](network.md#define-and-run)）。書き込みはスキーマに照らして検証する。shape が固定されているので、メッセージ用のメモリは構築時に確保できる。

スロットは常に、宣言どおりの型の値を持つ。そのため、スキーマを作るときに初期値を与える。既定の初期値は、`Tensor` ならゼロ、`Tensor | None` なら `None` である。書き手は `| None` と宣言した値にだけ `None` を書ける。

## グローバル時刻の付与

スロットは、書き込みのたびに、書いた時点のグローバル時刻を自動で添える。時刻は秒（f64）とナノ秒（u64）の両方で持つ。読み手はメッセージと時刻を組で受け取り、値がどれだけ古いかを判断できる。

## メモリ管理: バッファプール

実行中にメッセージ用のメモリをヒープへ毎回確保し、使い終わったら解放する処理は避けたい。そこで、スロットはバッファのプールを持ち、バッファを再利用する。

書き手は、プールから空いているバッファを取り出して新しいメッセージを書き、書き終えたらスロットの参照を差し替える。読み手が見ているバッファに書き手が書き込むことはないので、書き込み先が競合しない。

N 個の読み手は、最新のバッファを読み取り専用で共有する。そのため、読み手の数に比例したバッファは要らない。バッファは参照カウントで管理し、どの読み手からも参照されなくなるとプールへ戻って再利用される。読み手が Tensor を長く持ち続けても、そのバッファがプールへ戻るのが遅れるだけで、寿命の制約は設けない。

プールに空きが無いときは、書き手はバッファを追加で確保し、読み手を待たない。各ブロックは連続時間上で動くものの、周期は近いと見込まれる。そのため定常状態では、ヒープへの確保と解放を起こさずに再利用が回る。

メモリの使用量は増えるが、安全性と速度を優先し、これ以外の方式（seqlock で 1 つのバッファを上書きし、読み手がコピーする方式など）は持たない。プールの初期サイズや縮小の方針は、実装時に決める。
