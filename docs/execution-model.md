# 実行モデル

ブロック（[ブロック](blocks.md)）を非同期に動かす方法を定める。

## 要点

1. ブロック間の通信に queue・pipe を使わない。lock 付きの **共有スロット** への値の読み書きだけで通信する
2. 各ブロックは、自分の周期で独自にループする
3. システム全体を、**グローバルタイマー** の上の連続時間系として定義する
4. 各ブロックの更新則は微分方程式として扱い、グローバルタイマーで測った経過時間 $\Delta t$ で離散化する

## 共有スロット

### 方式

- ブロック同士のやり取りは「値の読み取りと書き込み」だけで行う。排他制御は lock だけにし、メッセージングのためにブロック同士が同期することはない
- 共有する値を **スロット** と呼ぶ。各スロットの書き手は、そのスロットを所有するブロック 1 つだけである
- 書き込みは、新しい値への参照の差し替え（またはコピー）で行う。読み手が書きかけの値を見ないようにするためである
- 書き込みには、書いた時点のグローバル時刻を添えることを検討する。読み手が値の古さを判断できるようにするためである

### 読み手から見た性質

次の振る舞いは **正常な動作** として扱う。

- 読み手は常に最新値だけを見る
- 書かれた値が一度も読まれずに上書きされることがある
- 同じ値が何度も読まれることがある
- 複数の隣接スロットをまとめて読んでも、全体として一貫したスナップショットにはならない。各値が個別に一貫していればよい

### queue を使わない理由

queue で値を溜めると、送り手と受け手の速度差でバックログが生じ、実質的にブロック同士の歩調が結合してしまう。最新値の読み書きだけにすれば、各ブロックは互いを待たずに動ける。

## ブロックのループ

各ブロックは次の 1 ステップを自分の周期で繰り返す。

1. 隣接ブロックのスロットから、そのとき読める最新値を読む
2. 前回の更新からの経過時間 $\Delta t$ ぶん、自分の状態を更新する
3. 結果を自分のスロットに書き込む

ブロックは他のブロックを待たない。

## 連続時間の定式化

### グローバルな時間で定義する理由

各ブロックの計算は離散時間のステップで行うが、ステップの間隔はブロックごとに異なり、揺らぐ。そのため「1 ステップ分の更新」の意味がブロックごとに変わってしまう。ダイナミクスをステップ数ではなくグローバルな時間 $t$ に対する微分方程式として定義すれば、周期が違っても同じダイナミクスを近似できる。

### 離散化

各ブロックは、前回の更新からグローバルタイマーで測った経過時間 $\Delta t$ を使って微分方程式を離散化する。陽的 Euler 法なら次のようになる。

$$x \leftarrow x + \Delta t \cdot f(x)$$

- 更新量は経過時間 $\Delta t$ に比例させる。ステップ数で更新量を決めない
- $\Delta t$ が大きすぎると陽的 Euler 法は不安定になる。$\Delta t$ を上限で打ち切るか、内部で刻みを分割する
- 負荷が高いときは各ブロックの $\Delta t$ が伸びるだけで、連続時間の定式化がそれを吸収する

既定の更新手法 PC-ALM の連続時間形は [更新手法](update-rules.md#pc-alm-の連続時間形) を参照。

## グローバルタイマー

- **シングルトンにする。** システム全体で時間は 1 つだけである
- pamiq-core の `TimeController` を参考に実装する（<https://github.com/MLShukai/pamiq-core/blob/main/src/pamiq_core/time.py>）。次の機能を持つ
  - 時間のスケール（加速・減速）
  - 一時停止・再開
  - スレッドセーフ
  - 状態の保存・復元
- コア（Rust）側に置き、GIL なしでブロックから参照できるようにする（[ネイティブコア](native-core.md)）

## テスト

- テストでは、別のタイマーを外から渡すのではなく、シングルトンのグローバルタイマーの時刻の源を **手動で進める仮想時計** に切り替える。固定スケジュールで決定的に動かす
- 全ブロックを固定の $\Delta t$ で同期的に回すと、元の離散アルゴリズムに一致すること。これをテストのオラクルにする
