# 実行モデル

ブロック（[ブロック](blocks.md)）を非同期に動かす方法を定める。

## 要点

1. ブロック間の通信に queue・pipe を使わない。lock 付きの共有スロットへの値の読み書きだけで通信する
2. 各ブロックは、自分の周期で独自にループする
3. システム全体を、グローバルタイマーの上の連続時間系として定義する
4. 各ブロックの更新則は微分方程式として扱い、グローバルタイマーで測った経過時間 $\Delta t$ で離散化する

## 共有スロット

### 方式

ブロック同士は、値を読み取ることと書き込むことだけでやり取りする。排他制御は lock だけで行い、メッセージングのためにブロック同士が同期することはない。

共有する値を **スロット** と呼ぶ。各スロットに書き込むのは、そのスロットを所有するブロック 1 つだけである。書き込みは新しい値への参照の差し替え（またはコピー）で行い、読み手が書きかけの値を見ないようにする。

スロットは、書き込みのたびに、書いた時点のグローバル時刻を自動で添える。時刻があれば、読み手は値がどれだけ古いかを判断できる。メッセージの型とスロットの詳細は [メッセージ](messages.md) にある。

### 読み手から見た性質

読み手は常に最新値だけを見る。そのため、書かれた値が一度も読まれずに上書きされることも、同じ値が何度も読まれることもある。複数の隣接スロットをまとめて読んでも、全体として一貫したスナップショットにはならない。各値が個別に一貫していればよい。これらはすべて正常な動作として扱う。

### queue を使わない理由

queue に値を溜めると、送り手と受け手の速度差でバックログが生じる。その結果、実質的にブロック同士の歩調が結合してしまう。最新値の読み書きだけにすれば、各ブロックは互いを待たずに動ける。

## ブロックのループ

各ブロックは次の 1 ステップを自分の周期で繰り返し、その間に他のブロックを待つことはない。

1. 隣接ブロックのスロットから、そのとき読める最新値を読む
2. 前回の更新からの経過時間 $\Delta t$ ぶん、自分の状態を更新する
3. 結果を自分のスロットに書き込む

この 1 ステップが、ブロックの `on_update(dt)` である。ループ自体はフレームワークが持ち、ブロックの作者は 1 ステップ分だけを書く（[ブロック](blocks.md#ライフサイクル-hook)）。

## 連続時間の定式化

### グローバルな時間で定義する理由

各ブロックの計算は離散時間のステップで行う。しかしステップの間隔はブロックごとに異なり、しかも揺らぐ。そのため「1 ステップ分の更新」の意味がブロックごとに変わってしまう。ダイナミクスをステップ数ではなくグローバルな時間 $t$ に対する微分方程式として定義すれば、周期が違っても同じダイナミクスを近似できる。

### 離散化

各ブロックは、前回の更新からグローバルタイマーで測った経過時間 $\Delta t$ を使って微分方程式を離散化する。陽的 Euler 法なら次のようになる。

$$x \leftarrow x + \Delta t \cdot f(x)$$

更新量は、ステップ数ではなく経過時間 $\Delta t$ に比例させる。負荷が高いときは各ブロックの $\Delta t$ が伸びるだけで、その影響は連続時間の定式化が吸収する。ただし $\Delta t$ が大きすぎると陽的 Euler 法は不安定になるので、$\Delta t$ を上限で打ち切るか、内部で刻みを分割する。

既定の更新手法 PC-ALM の連続時間形は [PC-ALM の連続時間系](pc-alm-continuous-time.md) を参照。

## グローバルタイマー

グローバルタイマーはシングルトンにする。システム全体で時間は 1 つだけである。時刻は秒（f64）とナノ秒（u64）の両方で持つ。

実装は pamiq-core の `TimeController`（<https://github.com/MLShukai/pamiq-core/blob/main/src/pamiq_core/time.py>）を参考にする。時間のスケール（加速・減速）、一時停止・再開、スレッドセーフ、状態の取得・復元の機能を持たせる。

タイマーはコア（Rust）側に置き、ブロックが GIL なしで参照できるようにする（[ネイティブコア](native-core.md)）。

ホストが入力の提示時間などを待つために、グローバル時間で待つ関数（`mujou.time.sleep(dt)` など、名前は暫定）を用意する。時間のスケール・停止・仮想時計に従って待つ。実時間の `time.sleep` で待つと、これらと噛み合わない（[ネットワーク](network.md#入力はグローバル時間上の信号)）。

## 停止と状態の取得・復元

実行中のシステムを止めて、状態を取得・復元できるようにする。停止の流れは pamiq-core の `ThreadController`（<https://github.com/MLShukai/pamiq-core/blob/main/src/pamiq_core/thread/thread_control.py>）を参考にする。

### 停止

1. 制御側（ホスト）が停止要求のフラグを立て、続けてすぐにグローバルタイマーを時刻 $T$ で凍結する。ブロックが止まるのを待ってから凍結するのではない
2. 各ブロックは、実行中の `on_update` を最後まで終え、次のループの区切りでフラグを見て止まり、`on_pause()` を呼ばれる。`on_update` の途中では止めない
3. スケジューラが、全ブロックが区切りで止まったことを確かめる。ワーカープールのブロックは、ワーカーが実行を割り当てなくなった時点で止まる。専用スレッドのブロックは、区切りでフラグを見て止まる
4. 全ブロックが止まっている間、制御側は全ブロックの状態とスロットを lock なしで読める

pamiq-core は全スレッドが止まってからタイマーを止めるが、mujou では先にタイマーを凍結する。全ブロックが止まるのを待ってから凍結すると、早く止まったブロックの最後の更新から凍結までの待ち時間が、再開後の最初の $\Delta t$ に混ざるからである。フラグを凍結より先に立てるので、凍結の後に始まる `on_update` は無い。

凍結した後は、全ブロックの最後の更新の時刻も、全スロットの値の時刻も $T$ 以下になる。通常の実行中にスロットを読んでも一貫したスナップショットにはならないが、停止中に読めば、連続時間系の時刻 $T$ の状態として一貫する。

### 再開

制御側がグローバルタイマーを再開し、続けてすぐに停止要求のフラグを下ろす。各ブロックは `on_resume()` を呼ばれてから、次の `on_update` に進む。タイマーを先に再開するので、再開後の最初の $\Delta t$ は 0 にならない。停止と再開のどちらでも、$\Delta t$ に混ざるのは制御側の 2 つの操作の間隔だけである。

### 状態の取得

ホストがビルドしたネットワークの状態を求めると、フレームワークは次の順に処理する。

1. [停止](#停止)する
2. 全ブロックの `state_dict()` を呼び、スロットなどと合わせて 1 つの木にまとめ、そのコピーを作る
3. [再開](#再開)する
4. コピーした木をホストに返す

すでに停止しているときに求められた場合は、再開せずに停止したままにする。

フレームワークの役割は、時刻のそろった状態の木を返すところまでである。木を pickle するか、どこにどう書き出すかは、ユーザーが決める。そのため、木の中身はすべて pickle できるようにしておく。

以下はイメージである。名前や書き方はこのとおりになるとは限らない。

```python
state = net.state_dict()         # 停止 → コピー → 再開 → 木を返す
with open("state.pkl", "wb") as f:
    pickle.dump(state, f)        # 保存の方法はユーザーが決める
```

### 状態の木の中身

| 対象                                                   | 持ち主         | 木への入れ方                     |
| ------------------------------------------------------ | -------------- | -------------------------------- |
| ブロックの内部状態（重み、活動、双対変数など）         | ブロック       | ブロックの `state_dict()` が返す |
| 全スロットの最新値と書き込み時刻                       | フレームワーク | 自動                             |
| 各ブロックの最後の更新の時刻（次の $\Delta t$ の起点） | スケジューラ   | 自動                             |
| グローバルタイマー（時刻、スケールなど）               | フレームワーク | 自動                             |

システムの状態は、ブロックの状態とスロットの中身を合わせたものである。スロットを初期値に戻して再開すると、隣のブロックが再開直後に初期値を読み、平衡から外れる。そのためスロットも木に入れる。ホストが外から書き込む入力のスロットも含む。バッファプールは含めない。

各ブロックの状態は、ネットワークの木の中の属性のパス（`body.l1` など）で識別する。

### コピーを取る理由

ブロックの `state_dict()` は、PyTorch のテンソルのように、ブロックが更新し続ける値への参照を返すことがある。参照のままホストに返すと、再開した後のブロックの更新で、ホストの手元の木が書き換わってしまう。そこでフレームワークは、停止している間に木のコピーを作ってから再開する。mujou の Tensor は不変なので、コピーせずに共有できる。

### 復元

ホストが `run()` の前に状態の木を渡し（`load_state_dict`）、フレームワークがそこから状態を戻す。ネットワークを構築し、各ブロックの `on_start()` を呼んだ後、最初の `on_update` の前に `load_state_dict()` で各ブロックの状態を戻す。スロットの値、各ブロックの最後の更新の時刻、グローバルタイマーも戻し、木を取得した時刻 $T$ から実行を始める。

### 停止のタイムアウト

`on_update` の 1 回が長いブロック（重い BP のスタックなど）があると、停止が遅れる。停止にはタイムアウトを設け、時間内に止まらなかったら状態の取得を中止し、止まらなかったブロックをログに出す。

## 終了と例外

### 終了

1. 制御側が終了要求のフラグを立てる
2. 各ブロックは、実行中の hook を最後まで終え、次のループの区切りで止まる
3. 全ブロックの `on_stop()` を呼ぶ。ある `on_stop()` が例外を投げても、ログに出して残りのブロックの `on_stop()` を呼び続ける
4. 専用スレッドを join し、ワーカープールを止める

停止中に終了を求められた場合も、同じ流れで終了する。

### 例外による終了

ブロックのどの hook（`on_update` に限らず `on_start`・`on_pause`・`state_dict` なども）が例外を投げても、システム全体を終了する。流れは pamiq-core（スレッドが例外を投げると例外のフラグを立て、制御スレッドがそれを見つけて全体を終了する）を参考にする。

1. ブロックを実行しているワーカーまたは専用スレッドが例外を捕まえ、ブロックの属性のパスとトレースバックをログに出し、例外を記録する。そのブロックの hook はそれ以後 `on_stop()` しか呼ばない
2. 同じ場所で、ただちに終了要求のフラグを立てる。ループはフレームワークが持っていて、各ブロックはループの区切りごとにフラグを見るので、pamiq-core の制御スレッドのようにポーリングしなくてよい
3. 全ブロックがループの区切りで止まるのを待つ
4. 例外のときに状態を取得する設定になっていれば、状態の木を取得する（[例外のときの状態の取得](#例外のときの状態の取得)）
5. 全ブロックの `on_stop()` を呼び、専用スレッドを join し、ワーカープールを止める（[終了](#終了)と同じ）。例外を投げたブロックの `on_stop()` も呼び、I/O などの資源を解放する
6. ホストに最初に記録した例外を伝える（[ホストへの伝え方](#ホストへの伝え方)）。ほぼ同時に複数のブロックが例外を投げた場合、2 つ目以降はログに出すだけにする

Rust のネイティブなブロックの panic も、例外と同じように扱う。

### ホストへの伝え方

> 状態: 暫定（2026-10-14）。

`run()` はバックグラウンドで実行してすぐに戻るので（[ネットワーク](network.md#実行はバックグラウンドで行う)）、例外を返せる待ち中の呼び出しが無い。そこで、例外で終了した後のホストの操作で伝える。

- `write`・`read`・`state_dict` などの公開インターフェイスを呼ぶと、ネットワークが例外で終了したことを表す例外を送出する。最初に記録した例外を `__cause__` につなぐ
- `subscribe` のイテレータも同じ例外を送出する。ホストが購読のループで待っていても気づける
- `shutdown()` と `join()` も、例外で終了していれば同じ例外を送出する
- 例外のときに取得した状態の木は、例外で終了した後も受け取れる

### 例外のときの状態の取得

例外で終了するときに、状態の木を取得するかどうかは設定で選べる。既定では取得しない。原因を調べたり、途中から実行し直したりするためである。木の中身は[状態の木の中身](#状態の木の中身)と同じで、フレームワークはファイルには書き出さない。

- 例外のときは、終了要求のフラグを立てた直後にグローバルタイマーを凍結する。こうすると、停止のときと同じく、時刻のそろった状態の木になる
- 例外を投げたブロックの `state_dict()` も呼ぶ。そのブロックの状態は更新の途中かもしれないので、木に、どのブロックが例外を投げたかと例外の内容を記録しておく
- 取得中にどれかのブロックの `state_dict()` が例外を投げたら、そのブロックの状態だけを欠かして続け、ログに出す。取得のために終了が止まることはない
- 取得した木はネットワークに残る。ホストは、送出された例外を捕まえた後、ネットワークからその木を受け取り、保存するかどうかを自分で決める

例外を投げたブロックだけを止めて、ほかのブロックを動かし続けることはしない。止まったブロックのスロットには最後に書いた値が残り、隣のブロックはその古い値を読み続けて、気づかれないまま平衡から外れていくからである。ブロックの再起動や、例外を投げた 1 ステップを飛ばして続けることもしない。

### グローバルなバリアとの関係

停止はシステム全体のバリアだが、不変の原則「グローバルなバリアを持ち込まない」の例外として認める。停止している間はグローバル時間が進まないので、系のダイナミクスから見れば停止は存在しないのと同じだからである。終了も、系のダイナミクスをそこで打ち切るだけなので、同じく例外として扱う。

ただし停止を使ってよいのは、状態の取得・復元や観測などの制御のための操作だけである。全ブロックを定期的に止めて重みを平均するなど、停止を学習アルゴリズムの一部に使ってはならない。

## テスト

テストでは、別のタイマーを外から渡すことはしない。代わりに、シングルトンのグローバルタイマーの時刻の源を、手動で進める仮想時計に切り替える。これで固定スケジュールのもと決定的に動かせる。

全ブロックを固定の $\Delta t$ で同期的に回すと、元の離散アルゴリズムに一致するはずである。これをテストのオラクルにする。
