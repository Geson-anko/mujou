# ネイティブコア

## コアの役割

mujou のコアには 2 つの責務がある。1 つは、各ブロックを非同期・分散的に回すことである。もう 1 つは、非同期・分散的に学習するためのフレームワーク自体を提供することである。ブロック同士が非同期に値を交換し、推論と学習を同時に進める仕組みそのものが、フレームワークの本体になる。

ブロックの内側は自由にし、ブロックの間のやり取りには不変条件を課す、という分担にしている。mujou 固有の価値はブロックの内側の計算ではなく、ブロック同士を非同期につなぎ、その上で学習させる部分にある。

### ブロックを非同期・分散的に回す

この責務の中身は、ブロック間で値をやり取りするプロトコルと、その実行フレームである。設計と実装は次の順に優先する。

1. プロトコル: 何を、どの形式で、いつ読み書きするか
2. 実行フレーム: スケジューラ・通信・状態の所有

ブロック内部の実装（PyTorch による PC-ALM ブロックや BP ブロックなど）は、プロトコルの上に載る差し替え可能な部品として扱う。ブロックの内側では PyTorch などの既存ライブラリを使ってよく、テンソル演算や autograd（ブロック内 BP を含む）をそれらに任せられる。

### 非同期・分散的に学習するためのフレームワーク

mujou は、ブロックを回す基盤だけでなく、その上で非同期・分散的に学習するためのフレームワークも、コアの責務として提供する。学習フレームワークとして提供するのは PC-ALM である。

PC-ALM をコアで提供しても、ブロック・スロット・スケジューラは特定の学習則を前提にしない。更新手法を差し替えられるという要件（[更新手法](update-rules.md)）はそのまま保ち、PC-ALM 固有の状態や値は PC-ALM の更新手法の側に閉じ込める。局所性・非同期性の不変条件も、実行の基盤と同じように守る。

## 実装言語

コアは Rust で実装し、Python はインターフェースにする。Python からは PyO3 + maturin で呼ぶ想定で、コアの処理中は GIL を解放する。Rust を選んだのは、並行処理の安全性をコンパイラが保証し、PyO3 で Python から使えるからである。

## M:N スケジューリング

M 個のブロックを N 本のワーカースレッド（目安は CPU コア数）に載せる。各ブロックは次のどちらかの実行クラスを持つ。

| 実行クラス   | 実行のされ方                         | 向いているブロック                                           |
| ------------ | ------------------------------------ | ------------------------------------------------------------ |
| タスク       | 共有ワーカープールで協調的に実行する | ネイティブのニューロンブロックなど、小さく大量の軽いブロック |
| 専用スレッド | 自分の OS スレッドを持つ             | Python/PyTorch のブロック、ブロック内 BP、I/O、重いスタック  |

Python のコードを動かすブロックは GIL を要する場合があるので、タスクのプールには載せない。

### M:N にした理由

asyncio や Redis が 1 スレッドで大量のタスクを捌けるのは、タスクの多くが I/O 待ちだからである。mujou のブロックは CPU を使い続けるので、1 スレッドでは 1 コアしか使えない。かといってブロックごとに OS スレッドを立てると、スレッド数の上限とコンテキストスイッチのコストに縛られる。M:N なら、大量の小さなブロックと、重いブロックや GIL が要るブロックを、同じ仕組みで扱える。

### ブロックの形

ブロックは「状態 + step 関数」である。ブロックは他のブロックを待たないので（[実行モデル](execution-model.md)）、async/await のコルーチンにする必要はない。スロットを読み、$\Delta t$ ぶん更新し、書き込むという 1 ステップが、協調スケジューリングの区切りになる。ブロックに目標周期を持たせる場合、スケジューラは期限の早い順に実行する。

### スロットの実装

スロットの読み書きでワーカーを止めないようにする。atomic なポインタ差し替え（`arc-swap` など）や seqlock を使い、OS の mutex で長く待たせない。

複数マシンにまたがって動かす場合に備えて、スロットは抽象として定義する。そうすれば、スロットの実装を KV ストア（Redis など）に差し替えられる。

## メッセージの値の型

値の型はコアが独自に持ち、特定のテンソルライブラリには依存しない。フレームワークの基礎を自分たちで制御するためである。PyTorch を使うブロックは、ブロックの境界でコアの値の型と相互に変換する。

PyTorch テンソルとの直接連携（DLPack など）や、変換を省く最適化は future work とする。値の型の具体形（dtype、shape、メモリ配置など）は未決定である（[未決定事項](open-decisions.md)）。
