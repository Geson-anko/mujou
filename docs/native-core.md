# ネイティブコア

## コアの役割

mujou のコアは、**ブロック間で値をやり取りするプロトコルと、その実行フレーム** である。ブロック同士が非同期に値を交換し、推論と学習を同時に進める仕組みそのものがフレームワークの本体になる。

ブロックの内側は自由、ブロックの間は不変条件付きのやり取り、という分担にしている。mujou 固有の価値はブロックの内側の計算ではなく、ブロック同士を非同期につなぐ部分にある。そのため、設計と実装は次の順に優先する。

1. プロトコル: 何を、どの形式で、いつ読み書きするか
2. 実行フレーム: スケジューラ・通信・状態の所有

ブロック内部の実装（PyTorch による PC-ALM ブロックや BP ブロックなど）は、プロトコルの上に載る差し替え可能な部品として扱う。ブロックの内側では PyTorch などの既存ライブラリを使ってよく、テンソル演算や autograd（ブロック内 BP を含む）を任せられる。

## 実装言語

- **コアは Rust で実装する。Python はインターフェースである**
- Python からは PyO3 + maturin で呼ぶ想定。コアの処理中は GIL を解放する
- Rust を選んだ理由: 並行処理の安全性をコンパイラが保証し、PyO3 で Python から使えるため

## M:N スケジューリング

M 個のブロックを N 本のワーカースレッド（目安は CPU コア数）に載せる。各ブロックは **実行クラス** を持つ。

| 実行クラス   | 実行のされ方                         | 向いているブロック                                           |
| ------------ | ------------------------------------ | ------------------------------------------------------------ |
| タスク       | 共有ワーカープールで協調的に実行する | ネイティブのニューロンブロックなど、小さく大量の軽いブロック |
| 専用スレッド | 自分の OS スレッドを持つ             | Python/PyTorch のブロック、ブロック内 BP、I/O、重いスタック  |

Python のコードを動かすブロックは GIL を要する場合があるので、タスクのプールには載せない。

### M:N にした理由

- asyncio や Redis が 1 スレッドで大量のタスクを捌けるのは、タスクの多くが I/O 待ちだからである。mujou のブロックは CPU を使い続けるので、1 スレッドでは 1 コアしか使えない
- 一方、ブロックごとに OS スレッドを立てると、スレッド数の上限とコンテキストスイッチのコストに縛られる
- M:N なら、大量の小さなブロックと、重い・GIL が要るブロックを同じ仕組みで扱える

### ブロックの形

- ブロックは **「状態 + step 関数」** である。ブロックは他のブロックを待たないので（[実行モデル](execution-model.md)）、async/await のコルーチンにする必要はない
- 1 ステップ（スロットを読む → $\Delta t$ ぶん更新 → 書き込む）が協調スケジューリングの区切りになる
- ブロックに目標周期を持たせる場合、スケジューラは期限順に実行する

### スロットの実装

- スロットの読み書きはワーカーを止めない形にする。atomic なポインタ差し替え（`arc-swap` など）や seqlock を使い、OS の mutex で長く待たない
- 複数マシンにまたがるレベルでは、スロットの実装を KV ストア（Redis など）に差し替えられるよう、スロットを抽象として定義する

## メッセージの値の型

- **値の型はコアが独自に持つ。** 特定のテンソルライブラリには依存しない。フレームワークの基礎を自分で制御するためである
- PyTorch を使うブロックは、ブロックの境界でコアの値の型と相互に変換する
- **PyTorch テンソルとの直接連携（DLPack など）や、変換を省く最適化は future work** とする
- 値の型の具体形（dtype、shape、メモリ配置など）は未決定（[未決定事項](open-decisions.md)）
