2026-10-14 決定（ユーザーの指示）。詳細は `docs/execution-model.md` の終了と例外の節。

- **どの hook の例外でも全体を終了する。** `on_update` に限らない。Rust ネイティブブロックの panic も同じ扱い
- **流れ:** ブロックを動かしているワーカー／専用スレッドが例外を捕まえ、属性パスとトレースバックをログに出して記録 → その場で終了要求のフラグを立てる → 全ブロックがループの区切りで止まる → 全ブロックの `on_stop()`（例外を投げたブロックも含む。`on_stop` の例外はログに出して続行）→ ホストが待つ実行の呼び出しから最初の例外を送出（2 つ目以降はログのみ）
- **例外のときの状態の取得は任意（設定、既定は取得しない）。** 取得する場合は、終了フラグの直後にタイマーを凍結し、全ブロックが区切りで止まってから `on_stop` の前に、停止時と同じ中身の木（`state_dict()` + スロット + 最後の更新時刻 + タイマー）を作ってランタイムに残す。ホストは例外を捕まえた後にランタイムから木を受け取り、保存するかを自分で決める（フレームワークはファイルを書かない）。例外を投げたブロックの `state_dict()` も呼び、どのブロックが例外を投げたかと例外の内容を木に記録する（そのブロックの状態は更新途中かもしれない）。取得中の `state_dict()` の例外は、そのブロックを欠かしてログに出し、取得と終了を続ける（2026-10-14、ユーザーの指示）
- **pamiq-core との違い:** pamiq は制御スレッドが tick ごとに例外フラグをポーリングする。mujou はループをフレームワークが持つので、例外を捕まえた場所で直接終了フラグを立てる

**Why:** 例外を投げたブロックだけを止めると、そのスロットに最後の値が残り、隣のブロックが古い値を読み続けて、気づかれないまま平衡から外れていく。fail fast にする。

**How to apply:** スケジューラ・ランタイムを実装するとき、ブロック単位の再起動やステップのスキップのような回復処理を足さない。pamiq は終了時に必ず保存するが、mujou ではフレームワークが保存しない。正常に終了する前に状態が欲しければ、ホストが取得してから終了する。
