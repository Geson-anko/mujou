2026-10-19、`on_thread_start` を廃止するときに「サブクラスが定義していたら TypeError で案内する」と提案したところ、ユーザーが「まだ pypi 等に正式に公開してないので、単に消して良い」と指示した。同日、続けて「破壊的変更で互換のために実装した機能があれば、複雑さを減少させるためにすべて廃止して」と指示され、既存の互換の仕組みを洗い出して消した（ブランチ refactor/2026-10-19/drop-compat-shims）。このときの方針は「PyPI への正式公開までは互換を残さない。公開後は方針を確かめ直す」だった。

0.1.0 を PyPI に公開した後の 2026-11-16、ユーザーは方針を「0.x の間は互換を残さない」に改めることを承認した。

**Why:** `CHANGELOG.md` の冒頭で、1.0.0 までは minor の版で API を壊すことがあると利用者に伝えている。API はまだ固まっていないので、互換のための検査や移行の案内はコードと複雑さを増やすだけになる。利用者には CHANGELOG で変更を伝えれば足りる。

**How to apply:** 0.x の間は、API を消すとき・名前を変えるときに、古い名前を受け付けるコード・移行を案内する例外・deprecation の警告を足さない。docs・specs・テストからも古い名前を消すだけにする。その代わり、利用者に見える変更として `CHANGELOG.md` の `## [Unreleased]` の Removed（消したもの）か Changed（名前や振る舞いを変えたもの）に書き、何に置き換えればよいかを添える。破壊的変更は minor の版（0.x.0）で出し、パッチ（0.x.y）には混ぜない（[[project-release-strategy]]）。1.0 以降の方針は改めて決める。
