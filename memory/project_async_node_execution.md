2026-10-11 決定。ノード（[[project-compute-granularity]]）を非同期に動かす方法について。詳細は `specs/execution-model.md`。

- **ノード間の通信に queue・pipe を使わない。** やり取りは「値の読み取りと書き込み」だけで、排他制御は lock だけにする。メッセージングのためにノード同士が同期することはない
- **各ノードは独自に活動する。** 自分の周期でループし、そのときに読める隣のノードの最新値で自分の状態を更新し、結果を書き込む
- **1 つの実行は、その実行のタイマーの上の連続時間系として定義する。** ステップの間隔はノードごとに異なり揺らぐので、ダイナミクスはステップ数ではなく時間 $t$ に対して定義する。時間軸は実行ごとに 1 本（[[project-timer-per-run]]）
- **更新則は微分方程式として扱い直す。** 各ノードは、前回の更新からその実行のタイマーで測った経過時間 $\Delta t$ で離散化する（例: 陽的 Euler で $x \leftarrow x + \Delta t \cdot f(x)$）
- **タイマーは pamiq-core の `TimeController` を参考にした**（<https://github.com/MLShukai/pamiq-core/blob/main/src/pamiq_core/time.py>）。時間のスケール、一時停止・再開、スレッドセーフ

**Why:** queue でメッセージを溜めると、送り手と受け手の速度差でバックログが生じ、実質的にノード同士の歩調が結合する。最新値の読み書きだけにすれば、各ノードは互いを待たずに動ける。ノードごとに周期が違うと「1 ステップ分の更新」の意味がノードごとに変わるので、時間に対する微分方程式として定義すれば、周期が違っても同じダイナミクスを近似できる。

**How to apply:**

- 共有する値は「スロット」として扱う。各スロットの書き手は 1 つだけ。書き込みは新しい値への参照の差し替えで行い、読み手が書きかけの値を見ないようにする
- 読み手は常に最新値だけを見る。書かれた値が一度も読まれずに上書きされることも、同じ値が何度も読まれることもある。これを正常な動作として扱う
- 複数のスロットをまとめて読んでも、全体として一貫したスナップショットにはならない。各値が個別に一貫していればよい
- 書き込みには、その実行の時計の時刻をスロットが自動で添える（[[project-message-types]]）
- 更新量は経過時間 $\Delta t$ に比例させる。ステップ数で更新量を決めない
- テストは `mujou.testing.run` の `VirtualTimer` と `ManualRun.step(dt, *nodes)` で、固定スケジュールで決定的に動かす。全ノードを固定の $\Delta t$ で同期的に回すと、元の離散アルゴリズムに一致することをオラクルにする（[[project-testing-api]]）
- 既定の PC-ALM の連続時間形は skill `pc-alm` 7 節
