2026-10-14 決定。詳細は `docs/execution-model.md` の停止と状態の取得・復元の節。停止の流れは pamiq-core の `ThreadController` を参考にする（`StateStore` のようにフレームワークがファイルへ書く方式は採らない）。

- **停止:** 停止要求フラグを立て、続けてすぐにグローバルタイマーを時刻 T で凍結する → 各ノードは実行中の `on_update` を終え、ループの区切りで止まって `on_pause()` → スケジューラが全ノードの停止を確認 → 制御側が全状態を lock なしで読む
- **pamiq-core と順序が逆。** pamiq は全スレッド停止後にタイマーを止めるが、mujou では先に凍結する。待ってから凍結すると、早く止まったノードの待ち時間が再開後の Δt に混ざる。凍結後は全ノードの最後の更新時刻と全スロットの時刻が T 以下になり、時刻 T の一貫したスナップショットになる
- **再開:** タイマーを再開し、続けてすぐにフラグを下ろす（最初の Δt が 0 にならない）。各ノードは `on_resume()` の後に `on_update` へ進む
- **状態の取得:** ホストがビルドしたネットワークの状態を求めると、停止 → 全ノードの `state_dict()` とスロットなどを 1 つの木にまとめてコピー → 再開 → 木をホストに返す。すでに停止中なら再開しない
- **保存はユーザーが行う（2026-10-14、ユーザーの指摘で改訂）。** フレームワークは時刻のそろった木を返すところまで。pickle するか、どこに書くかはユーザーが決める。木の中身はすべて pickle 可能にする
- **コピーする理由:** `state_dict()` が PyTorch のテンソルのように更新し続ける値への参照を返すと、再開後にホストの手元の木が書き換わる。停止中にコピーしてから再開する。スロットの値は `torch.Tensor` にコピーして木に入れる
- **木の中身:** ノードの `state_dict()`、全スロットの最新値と時刻（ホストの入力スロットも）、各ノードの最後の更新時刻、グローバルタイマー。ノードはネットワーク木の属性パス（`body.l1`）で識別。バッファプールは含めない
- **スロットも木に入れる理由:** 系の状態はノード状態 + スロットの中身。スロットを初期値に戻すと再開直後に平衡から外れる
- **復元:** ホストが木を渡す。構築 → `on_start()` → `load_state_dict()` → スロット・最後の更新時刻・タイマーを戻し、時刻 T から開始
- **タイムアウト:** 停止が時間内に終わらなければ状態の取得を中止し、止まらなかったノードをログに出す

**Why（バリアの例外）:** 停止はシステム全体のバリアだが、停止中はグローバル時間が進まないので、系のダイナミクスからは存在しないのと同じ。ユーザーが提案し、2026-10-14 に例外として認めた。

**How to apply:** 停止を使ってよいのは状態の取得・復元や観測などの制御のための操作だけ。フレームワークにファイルへの保存処理を持たせない。定期的に止めて重みを平均するなど、停止を学習アルゴリズムの一部に使う実装は不変条件違反として扱う。タイムアウトの既定値・スロットの識別名・取得と復元の API は未決定（[[project-open-decisions]]）。
