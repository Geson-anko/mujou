ノードは `Node(*, period=0.01, ...)` の `period`（その実行のタイマーの秒、読み取り専用 `Node.period`）で `on_update` の周期を持つ。このシグネチャは推奨案で、ユーザーの確認待ち（`specs/open-decisions.md`）。`period=0.0` はできるかぎり速く（Δt > 0 になりしだい）回す。既定を 0.01 にし、周期を持たないノードは `0.0` を明示したときだけにした（ユーザーの決定:「周期を持たないノードを想定しない」。周期を持たないノードは CPU のコアを使い切り、ほかのノードの dt を乱すため）。負か NaN は `Node.__init__` で断る（K5）。詳細は `specs/nodes.md` の「実行の周期」。

- 待つのはランタイム（Rust の `lifecycle.rs` と `sched.rs`）。目標の時刻（最初は最初の Δt の起点 + period、その後は前回の目標 + period）まで Timer の上で待つ。スケール・仮想時計に従い、停止・終了の要求ですぐ起きる。周期は秒のまま native に渡し、bindings が ns に丸める（1 ns 未満は 1 ns）
- 数え方（2026-10-17、ユーザーの決定）: 次の目標は前回の目標 + P。P 以上遅れたときだけ、その更新の時刻 + P に数え直す。まとめて回らない。pamiq-core の `SleepIntervalAdjustor`（起きた時刻から数え直す）からの意図した変更で、理由は macOS で起床が遅れ、周期 10 ms が約 80 Hz になった実測
- 復元では目標が木に入らないので、目標は「保存した最後の更新 + P」に置き直される。止めずに続けた場合と次の更新の時刻が変わりうる。推奨案で、ユーザーの確認待ち（代案は次の目標を木に入れる。`specs/open-decisions.md`）
- Δt は実際の経過時間。コアは `max_dt` を持たないので、`on_update` は長い Δt でも安定でなければならない（打ち切るかはノードの選択。`mujou.pc` は打ち切る）
- 手動モード（`ManualRun.step`）は周期を無視する（ユーザーの決定）

**Why:** hook の中からの `sleep` を禁じたので、周期はフレームワークが持つ必要がある。待ちをランタイムに置けば、停止・終了の要求とスケール・仮想時計にそのまま従う。

**How to apply:** 周期の振る舞いを変えるとき、`specs/nodes.md` の「実行の周期」と `crates/mujou-core/tests/runtime/period.rs` を合わせる。
