2026-10-11 決定。

- **コアは Rust で実装する。Python はインターフェース。** Python からは PyO3 + maturin で呼ぶ想定。コアの処理中は GIL を解放する
- **実行モデルは M:N スケジューリング。** M 個のブロックを N 本のワーカースレッド（目安はコア数）に載せる。ブロックは実行クラスを持つ
  - **タスク**: 共有ワーカープールで協調的に実行する軽いブロック（ネイティブのニューロンブロックなど、小さく大量のもの）
  - **専用スレッド**: 自分の OS スレッドを持つブロック（Python/PyTorch のブロック、ブロック内 BP、I/O、重いスタック）。Python のコードを動かすブロックは GIL を要するので、タスクのプールに載せない
- **ブロックは「状態 + step 関数」。** ブロックは他のブロックを待たない（[[project-async-block-execution]]）ので、async/await のコルーチンにする必要はない。1 ステップ（スロットを読む → $\Delta t$ ぶん更新 → 書き込む）が協調スケジューリングの区切りになる
- **スロットの読み書きはワーカーを止めない形にする。** atomic なポインタ差し替え（`arc-swap` など）とバッファプールを使い、OS の mutex で長く待たない（seqlock + copy は 2026-10-13 に不採用、[[project-message-types]]）
- **メッセージの値の型はコアが独自に持つ。** PyTorch のテンソルを直接扱えると便利だが、コア・基礎は独自の型で作る。**PyTorch テンソルとの連携（DLPack など）は future work**
- **グローバルタイマー（シングルトン）もコア側に置く。** GIL なしでブロックから参照できるようにする

**Why:** asyncio や Redis が 1 スレッドで大量のタスクを捌けるのは、タスクの多くが I/O 待ちだから。mujou のブロックは CPU を使い続けるので、1 スレッドでは 1 コアしか使えない。一方、ブロックごとに OS スレッドを立てると、スレッド数の上限とコンテキストスイッチのコストに縛られる。M:N なら大量の小さなブロックと、重い・GIL が要るブロックを同じ仕組みで扱える。Rust は並行処理の安全性をコンパイラが保証し、PyO3 で Python から使える。コアの型を外部ライブラリに依存させないことで、フレームワークの基礎を自分で制御できる。

**How to apply:**

- 負荷が高いときは各ブロックの $\Delta t$ が伸びるだけで、連続時間の定式化がそれを吸収する。$\Delta t$ の上限は別に持つ
- ブロックに目標周期を持たせる場合、スケジューラは期限順に実行する
- 複数マシンにまたがる実行は、現状は想定しない（2026-10-13 決定）
- PyTorch を使うブロックは、ブロックの境界でコアの値の型と変換する。変換を省く最適化は future work
- ツールチェーン（maturin のビルドバックエンド、Rust の lint・テスト、CI、`just` レシピ）はまだ整えていない。最初の実装タスクで整える
