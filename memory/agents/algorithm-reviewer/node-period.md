# node-period（ノードの実行周期 `period`）の監査

対象: worktree `.claude/worktrees/node-period`、ブランチ `feature/2026-10-17/node-period`、`git diff 3583478..HEAD`（`2cca89f`〜`8f82ae2` の 4 commit）。基準は skill `locality-and-async`、`specs/execution-model.md`、`specs/nodes.md`、判断ログ `memory/agents/plan-implementer/node-period.md`。

## verdict

**approve**（確信度: 高）。must-fix は無い。

`node_loop` の変更は、待つ条件を `now_ns <= last_ns` から `now_ns < last_ns + min_dt_ns` へ一般化しただけである。周期なしは `min_dt_ns = 1` で従来と同じ式になる。待つ処理は従来の Δt = 0 の待ちと同じ `wait_until_ns_or` を使い、起きた後は必ず `boundary` を通り直す。そのため、停止・復元まわりの既存の論証（word → time → word で時刻 ≤ T）はそのまま成り立つ。停止・再開・復元の起点も、時間が凍結されることと `last_ns` を持ち越すことから正しく決まる。この 2 点は、実際に動かして確かめた（下の「検証結果」）。

直した方がよいのは次の 2 点。

- 監査を依頼された「停止・再開・復元のときの周期の起点」を守る回帰テストが無い（should-fix 1）
- 周期を入れたことで Δt ≥ P が利用者の選ぶ量になった。それなのに、陽的離散化の安定性の責任がどこにあるかを文書に書いていない（should-fix 2）

観点ごとの結論:

- **グローバルなバリアにならないか**: ならない。待ちはノードごとの `next_ns = last_ns + P` を目標にした `Timer::wait_until_ns_or` で、他ノードの状態を条件に含まない。待っている間に保持する lock は無い（`wait_timeout` がタイマーの lock を手放し、`hooks[i]` も取っていない）。タイマーの condvar は全ノードで共有している。そのため `advance`・スケール変更・停止で全員が起きるが、起きた後は各自の目標を見直すだけで、誰も誰かを待たない。実測でも、P = 1 ms〜100 ms のノードの隣で、周期なしのノードが約 90 万回/秒で回り続けた
- **Δt が実経過時間で、連続時間の定式化と整合するか**: 整合する。Δt は従来どおり `boundary` で読んだ時刻の ns 差で、連続する更新の Δt を足すと `t_K - t_0` になる。周期を変えても、同じ時間区間を隙間も重なりも無く Euler で積分することになる。違うのは刻みの粗さと、入力を読む頻度（隣の値のサンプル & ホールド）だけで、P → 0 で同じ ODE に近づく。仮想時計で Δt = P が ns まで一致し、遅れたときは Δt = 実経過（1.5 P、2.5 P）になることをテストが確かめている
- **停止中の時刻 ≤ T**: 保たれる。周期の待ちから起きる理由は、目標に達したか、制御語が変わったかのどちらかで、どちらの場合も `continue` で `boundary` に戻る。更新に使う `now_ns` は常に `boundary` の word → time → word の手順で読んだ値で、待ちが返した時刻は使わない
- **停止・再開の起点**: 正しい。停止中はタイマーが凍結されるので、`next_ns` に向けて時刻は進まない。再開後は `last_ns` を持ち越したまま残りの時間だけ待ち、まとめて回ることもない。実測では、P = 0.3 s で、更新の 0.1 s 後にホストが 0.5 s 停止した。再開から次の更新までは 0.205 s で、Δt = 0.305 s（≈ P + 起床の遅れ）、その後は静かだった。`state_dict()` による停止（ランタイムの capture）の後も同じだった
- **復元の起点**: 正しい。`last_update_ns` と `timer_state` は session が必ず組で渡すので、次の更新は「保存した最後の更新 + P」に来る。実測では、仮想時計で last = 15 ms、T = 20 ms、P = 10 ms の木を、時刻を 999 ms に動かしたタイマーへ復元した。24 ms では更新せず、25 ms で Δt = 0.01 の更新が 1 回だけ来た
- **最初の更新を開始から P 後にした判断**: 妥当。周期なしでも最初の更新は開始から Δt > 0 の後なので、同じ規則（`last_ns` = 開始時刻、`last_ns + min_dt` まで待つ）の自然な延長になっている。開始直後に呼ぶと Δt = 0 の `on_update` になり、「Δt ぶん進める」という hook の意味と合わない。副作用として、同じ P のノードは開始時の位相がそろい、同じ時刻に起きてタイマーの lock を取り合う。正しさには影響しない
- **遅れを取り戻さない判断**: 妥当で、連続時間形とも整合する。遅れた 1 回の更新が Δt = 実経過で区間全体を積分するので、時間は失われない。取り戻すために続けて回すと、Δt ≈ 0 の更新が古い入力で連続するだけになる。注意点として、Δt が P より大きくなるのは、まさに陽的離散化が不安定になりやすい場面である（should-fix 2）
- **手動モードが同じループの特殊なスケジュールのままか**: そのまま。分岐は `min_dt_ns` を 1 に差し替える 1 行だけで、ループ・区切り・Δt の計算は共通である。手動モードは「どのノードをいつ回すか」を外から与えるスケジュールなので、周期（自由実行の自己スケジュール）を無視するのは一貫している
- **学習則の焼き付け**: 無い。`period_ns` / `min_dt_ns` は時間の量だけを扱い、`NodeHooks` の契約も変えていない。`Node.period` は `device` と同じ並びの、更新手法に依らない属性である

## should-fix

1. **停止・再開と復元のときの周期の起点を確かめる回帰テストが無い**（確信度: 高）
    - `mod period` は、待ち・遅れ・手動・停止の起床・実時計・スケールを確かめている。しかし「capture の後も `last_ns` を持ち越し、残りの時間だけ待つ」ことと、「復元した `last_update_ns` から P を数える」ことを確かめるテストが無い。今の実装は正しい（実測で確認済み）。それでも、たとえば `pause_node` や `on_resume` の後に `last_ns` を読み直す・開始時刻で上書きするような変更が入ると、周期の位相がずれるか、再開直後に余分な更新が走る。その回帰は今のテストでは捕まらない
    - 仮想時計で決定的に書ける。案:
        - capture: P/2 進める → `capture` → P/2 − 1 進めて静か → 1 進めて Δt == P が 1 回だけ
        - 復元: `RuntimeConfig { last_update_ns: Some(vec![T - P/2]), timer_state: Some(T) }` で開始 → P/2 − 1 進めて静か → 1 進めて Δt == P
    - 仮想時計では、停止中に時間が進まないことは自明に成り立つ。そのため、実時計の停止（ホストの `pause` を挟んでも Δt が P + 小さな遅れに収まる）を 1 本足すかどうかは任意でよい

2. **Δt ≥ P（遅れればもっと大きい）になったのに、安定性の責任を文書に書いていない**（確信度: 中）
    - skill `locality-and-async` は「Δt が大きすぎると陽的な離散化は不安定になる。上限で打ち切るか、内部で刻みを分割する」と定める。`max_dt` を入れないのは指示どおりで、未決定事項にも記録してある。ただ、周期を入れたことで、大きな Δt は事故ではなく利用者が選ぶ量になった。今の `specs/nodes.md#実行の周期` は「`max_dt` は今は持たない」としか書いていない
    - 足す内容の案（1〜2 文）: 「`on_update` は Δt ≥ `period` でも安定でなければならない（例: $\Delta t/\tau$ が上限を超えるならノードの内側で刻みを分割する）。Δt を打ち切ると経過時間が失われ、連続時間の定式化からずれる」。後で `max_dt` を入れるとき、打ち切りか分割かを選ぶ材料にもなる

## nit

1. **停止で周期の数え方が変わらないことを仕様に 1 行書く**（確信度: 中）。`specs/nodes.md#実行の周期` の箇条書きには「停止と終了の要求で、すぐに起きる」とある。しかし起きた後のことは書いていない。依頼の観点そのものなので、明文化しておくとよい。案: 「停止中はタイマーが止まるので、停止していた時間は周期に数えない。再開後は残りの時間だけ待ち、まとめて回ることはない」。また `Node` の docstring は起点を「the start of the last update (or since the start of the run)」とだけ書き、復元の場合（保存した最後の更新）が抜けている

2. **起床の遅れが短い周期で大きい（macOS 実測）**（確信度: 中）。周期だけのノードを 1 秒回したとき、更新が目標から遅れた量の中央値は、P = 1 ms で約 250 µs、10 ms で約 2.5 ms、100 ms で約 1.8 ms だった。周期なしの隣接ノードがあっても無くても同程度だったので、lock の競合ではなく OS のタイマーの粒度・まとめ起こし（coalescing）によると見られる。Δt は実経過なのでダイナミクスは正しい。ただし P = 10 ms では実際の更新頻度が 1/P より約 20% 低い。docstring の「the least time between two updates」は正確だが、`specs/nodes.md` にも「周期は間隔の下限で、実際の頻度は起床の遅れのぶん下がる」と 1 行あるとよい。未決定の `offset` を検討するときの材料として 1 つ挙げておく。目標を「前回の目標 + P」に取り、P 以上遅れたときだけ起点を数え直す方式にすると、まとめて回ることなく平均の頻度を 1/P に保てる。実時間の定数も要らない。採るかどうかはユーザーの判断（pamiq-core 優先の指示があるため）

3. **周期の違う 2 ノードの独立性を確かめるテスト**（確信度: 低）。仮想時計で P と 3P の 2 ノードを回し、P 進めたら前者だけが更新することを確かめる。既存の非同期テストで全体の独立性は担保されている。それでも、周期の設定がノードごとに効いていること（`period_ns` の添字の取り違えなど）を直接押さえられる

4. **`Node(period=True)` が 1 秒として通る**（確信度: 高、影響は小）。`bool` は `int` の派生なので、`math.isfinite(True) and True > 0` を通る。session の `_is_int` が `bool` を除いているのと揃えるなら、ここでも弾く

## 照合メモ

- 連続時間形（skill `pc-alm` 7.1、`specs/execution-model.md`）: $x(t_k) = x(t_{k-1}) + (t_k - t_{k-1})\, f(x(t_{k-1}), \text{入力}(t_k))$。$t_k$ は `boundary` で読んだ時刻、$\Delta t_k = t_k - t_{k-1}$。$\sum_k \Delta t_k = t_K - t_0$ は周期によらないので、周期の選び方は刻み幅とサンプリング頻度だけを変え、近似する ODE は変えない
- 周期なしの式との一致: 旧 `now <= last`（待つ）⇔ 新 `now < last + 1`（ns の整数なので同値）。手動モードは常に `min_dt = 1` で、旧の振る舞いと同じ
- pamiq-core との対応: `SleepIntervalAdjustor` は `reset` を待ち明けの時刻で行い、`step` の後に `reset + interval` まで眠る。mujou の `last_ns` は待ち明け後に `boundary` で読む時刻で、`on_update` の前にある。したがって計算時間は周期に含まれ、遅れたら起点を数え直す。対応は判断ログの表どおり
- 停止の論証: 周期の待ちが返した後は `continue` → `boundary`。待ちの中の `interrupted` は atomic の `word` だけを読み、`set_command` は word を store してから `interrupt_waiters`（タイマーの lock を取って notify_all）を呼ぶ。そのため取りこぼしは無い
