# 実行モデル・mujou.Node（execution-model / torch / nodes）理解度テスト

## 対象

- ファイル: `docs/execution-model.md`、`docs/torch.md`、`docs/nodes.md`
- 範囲: グローバルタイマーの停止の保持とスイッチ、停止・再開・取得・復元・例外の実装、複数のネットワーク、Δt に混ざるもの、`mujou.Node` のスレッドの設定と CUDA の同期の順序、フレームワーク用の hook
- 読者と用途: mujou の開発者と、ノードを書く利用者。3 文書だけを読んで、停止中の時刻が T 以下でそろう理由、Δt に何が混ざり何が混ざらないか、複数のネットワークでの時間の意味、CUDA のノードでいつ何が同期されるかを正しく説明できる

## 事実確認（R1 執筆時）

- 取得: `capture` がフラグ（Pause）を立て、同じ lock の下ですぐ `freeze.hold(Capture)`。再開は `resume_after_pause` で保持を解いてからフラグを Run に戻す（`crates/mujou-core/src/runtime.rs`）
- ノードの区切りは制御語 → 時刻 → 制御語の順に読み、制御語が変わっていたら時刻を捨てる。使う時刻は凍結前に読んだもので T 以下
- Δt = 0 のノードは `wait_until_ns_or` で時刻の前進か制御語の変化を待つ（別ネットワークの停止中はこれで待つ。`on_pause` は呼ばれない）
- 保持（`PauseHold`）は数え、スイッチ（`pause`/`resume`）は 1 本。`resume` は保持を解かない（`time.rs`）
- 保持の理由は Startup / Capture / Failure。Failure は `capture_on_failure` のときだけ。`mark_finished` で全部解く
- 復元時に別のランタイムが live なら `InvalidArgument` → Python で `ValueError`、`_session.run` が `_runtime=None` に戻すので再実行できる
- `PyNode::start`: `_on_thread_start` → `on_start` →（復元なら）`load_state_dict`。`update`: `on_update` → `_after_update`
- `_capture_state` のエラーは hook 名 `state_dict` で報告（`crates/mujou-python/src/runtime.rs` の `attribute`）
- `_session.run` は起動前に呼んだスレッドの現在のストリームを同期。`_tree` はコピー後に制御スレッドの現在のストリームを同期。`_load_state_dict` は deepcopy 後にホストのスレッドの現在のストリームを同期

## 評価用問題

### Q1 状態の取得で、制御側は「停止要求のフラグを立てる」と「グローバルタイマーを凍結する」をどの順で、どのタイミングで行うか。全ノードが止まるのを待ってから凍結しないのはなぜか。

- 要点: フラグを先に立て、続けてすぐ（ノードが止まるのを待たずに）凍結する
- 要点: 待ってから凍結すると、早く止まったノードの最後の更新から凍結までの待ち時間が、再開後の最初の Δt に混ざるから

### Q2 停止中に、全ノードの最後の更新の時刻と全スロットの値の時刻が、凍結した時刻 T 以下でそろうのはなぜか。

- 要点: 凍結の前に読んだ時刻は T より前で、凍結の後はタイマーが T のまま進まない
- （R1 で要点から外した: 「フラグを凍結より先に立てるので T より後に始まる `on_update` は無い」は Q1 の論点で、T 以下になる理由には凍結だけで足りる）

### Q3 状態の取得のために停止し、再開した。再開後の各ノードの最初の Δt に混ざるものと混ざらないものを答えよ。

- 要点: 停止していた時間は混ざらない
- 要点: 混ざるのは、制御側の 2 つの操作（タイマーの再開とフラグを下ろす）の間隔と、再開から `on_resume` を終えて次の `on_update` に進むまでの時間（スレッドが起きる遅れを含む）
- （R1 で要点から外した: 「最初の Δt は 0 にならない」は問いが尋ねていない）

### Q4 同じプロセスでネットワーク A と B が走っている。ホストが A の `state_dict()` を呼んでいる間、B のノードはどうなるか。`on_pause` は呼ばれるか。

- 要点: グローバルタイマーはプロセスに 1 つなので、B の時刻も止まる
- 要点: B のノードは `on_pause` を呼ばれず、Δt = 0 のまま（更新せずに）待つ
- （R1 で要点から外した: 「系のダイナミクスから見れば停止は存在しない」は問いが尋ねていない）

### Q5 A が状態を取得している最中に、テストのコードが `mujou._core.timer.resume()` を呼んだ。グローバル時刻は進み始めるか。理由も答えよ。

- 要点: 進まない
- 要点: `resume()` はスイッチを切るだけで、ランタイムが取った保持は解かない。時刻は保持が 1 つも無く、スイッチも切れているときだけ進む

### Q6 ネットワーク B が走っている間に、保存した状態の木を `load_state_dict` したネットワーク A を `run()` した。どうなるか。A を動かすにはどうすればよいか。

- 要点: `ValueError` になり、何も起動しない
- 要点: B を終了させてから A の `run()` をし直せばよい
- （R1 で要点から外した: 理由は問いが尋ねていない）

### Q7 状態の木から復元して `run()` するとき、次をどの順で行うか: タイマーの再開、タイマーの時刻を戻す、各ノードの `on_start`、各ノードの `load_state_dict`、タイマーの凍結。走っているタイマーに時刻を戻さないのはなぜか。

- 要点: 凍結 → 時刻（と各ノードの最後の更新の時刻）を戻す → `on_start` → `load_state_dict` → 再開（`_on_thread_start` を含めても可）
- 要点: 走っているタイマーに戻すと、戻してから最初の `on_update` までの準備の時間が最初の Δt に混ざるから

### Q8 CUDA を使う `mujou.Node` のノードの状態を取得するとき、`state_dict()` はどのスレッドで呼ばれるか。その前後で何がどの順で同期されるか。

- 要点: ノードのスレッドではなく制御スレッドで、`_capture_state()` を通して呼ばれる
- 要点: 自分のストリームの下で、まず自分のストリームを同期（どの hook が積んだ仕事も終わる）→ `state_dict()`（コピーは自分のストリームに積まれる）→ もう一度自分のストリームを同期

### Q9 フレームワークは、制御スレッドで状態の木をコピーした後、ノードを再開する前に何を同期するか。それをしないと何が起きうるか。

- 要点: 制御スレッドの現在のストリームを、ノードが使うデバイスごとに同期する（デバイス全体ではない）
- 要点: しないと、再開したノードがその場で更新した重みが、木のコピーに混ざりうる

### Q10 CUDA のノードの `on_update` で積んだカーネルが device-side assert を起こした。`NetworkError` のメッセージに出る hook の名前は何か。原因はどこを調べるか。

- 要点: `_after_update`
- 要点: 原因は `on_update` で積んだ仕事（非同期のエラーが `_after_update` の同期で表に出る）

### Q11 `mujou.Node` のサブクラスで `on_start` を override し、`super().on_start()` を呼ばなかった。勾配の記録の停止と、CUDA のストリームの設定は行われるか。理由も答えよ。

- 要点: 行われる
- 要点: それらは `on_start` ではなく、フレームワーク用の hook `_on_thread_start()` で、`on_start` の前に同じスレッドで行われるから

### Q12 ホストがメインスレッドとは別のスレッド X で CUDA の Tensor を確保し、ノードに持たせた。メインスレッドで `run()` する前に何をすべきか。理由も答えよ。

- 要点: スレッド X で、X の現在のストリームを同期してから `run()` する
- 要点: `run()` が同期するのは、`run()` を呼んだスレッドの現在のストリーム（ノードが使うデバイスごと）だけだから

## 保留問題

### H1 `capture_state_on_exception=True` で走るネットワーク A のノードが例外を投げた。同じプロセスで走るネットワーク B の時刻はどうなるか。いつまでそうなるか。

- 要点: B の時刻も止まる（A が例外を記録してフラグを立てた直後にタイマーの停止を保持する）。B のノードは `on_pause` を呼ばれず Δt = 0 のまま待つ
- 要点: A の終了処理が完了したとき（例外による終了の最後に保持を解く）まで

### H2 ホストが `mujou.time.sleep(1.0)` で待っている途中で、ネットワークの状態の取得が実時間 0.3 秒かかった（スケール 1）。`sleep` が戻るのは呼んでから実時間でおよそ何秒後か。理由も。

- 要点: 約 1.3 秒後
- 要点: `sleep` はグローバル時間で待ち、停止中はグローバル時刻が進まないので、止まっていた実時間だけ延びる

### H3 CUDA のノードを復元するとき、ノードの `load_state_dict` に渡る状態のコピーはどのスレッドで作られ、ノードが使う前に何が同期されるか。

- 要点: `Network.load_state_dict` を呼んだホストのスレッドで作られる（`copy.deepcopy`）
- 要点: ホストのスレッドの現在のストリームを、ノードが使うデバイスごとに同期する（`run()` も起動前に呼んだスレッドの現在のストリームを同期する）
