# docs/en/topics/simulation.md 理解度テスト

## 対象

- ファイル: `docs/en/topics/simulation.md`（サンプルは `examples/simulation.py` を snippet で取り込む）
- 読者と用途: PyTorch に慣れた Python 開発者が、実時間の `mujou.run`（デプロイ用）と仮想時間の `mujou.run_manually` / `ManualRun`（シミュレーション用）を使い分け、`ManualRun` でシミュレーションを正しく・決定的に回す。

## 評価用問題

### Q1 カメラから 30 Hz で画像を受け取り、ロボットのモーターを制御するネットワークを動かす。`mujou.run` と `mujou.run_manually` のどちらを使うか。理由も。

- 要点: `mujou.run`
- 要点: 実世界の入力は実時間で届き、ネットワークがそれに追いつく必要がある（`run_manually` の時間は `step` でしか進まず実時間に従わない）

### Q2 シミュレーションのループで、入力がステップごとに変わる。`run.write` はいつ呼ぶか。ステップ中に別のスレッドから書くと何が困るか。

- 要点: ステップの間（次のステップの前）に、ステップを回すスレッドで書く
- 要点: ステップ中の write は、そのステップで読むノードと次のステップで読むノードに分かれ、結果が決定的でなくなる

### Q3 値が出力方向にだけ流れる chain `u → a → b` がある。`run.step(h, net.a, net.b)` と `run.step(h, net.b, net.a)` のうち、`run.step(h)` と同じ結果になるのはどちらか。理由も。

- 要点: `run.step(h, net.b, net.a)`（出力側から逆順）
- 要点: `step(h)` では b はステップ開始時の a を読む。b を先に更新すれば b も古い a を読むので一致する。a, b の順だと b はこのステップで送られた新しい a を読む

### Q4 2 つのノード a と b が互いに値を送り合う（a ↔ b）。`run.step(h)` と同じ結果になるように、ノードを渡す順を選べるか。

- 要点: 一般には選べない（どの順も一致しない）。R2 で文書を「in general」に補正したのに合わせて要点も直した
- 要点: 値が逆向きにも流れるため（pc.Chain も同じ）

### Q5 `period=0.01` のノードを `run_manually` で走らせ、`run.step(0.001)` を 10 回呼ぶ。ノードは何回更新され、各更新の `dt` はいくつか。

- 要点: 10 回（period は無視される）
- 要点: 各 dt は 0.001

### Q6 時刻 0 に始めた `ManualRun` で、`run.step(h, net.a)` を 3 回呼び、その後 `run.step(h)` を 1 回呼ぶ。最後のステップで `net.b` が見る `dt` はいくつか。

- 要点: 4h
- 要点: dt は自分の最後の更新からの時間で、最初の更新は実行の開始からの時間。b は前の 3 ステップで更新されていないので、その時間が足される

### Q7 ステップを回しているスレッドで、ステップの間に `run.wait_for(net.next, cond)` をタイムアウトなしで呼んだ。何が起きるか。代わりに、出力はどの呼び出しで読むべきか。

- 要点: 返らない（永遠に待つ）。step を呼ぶまで何も送られず時間も進まないため
- 要点: ステップの間に `run.read`（/ `run.read_with_time`）で読む

### Q8 更新則を「`step` の境界では全ノードの更新が終わっている」ことを前提に作ってよいか。理由も。

- 要点: よくない
- 要点: `mujou.run` にはその瞬間がなく、各ノードが自分の時刻にばらばらの dt で更新する。step でしか動かないネットワークはデプロイ時に失敗する

### Q9 CPU で多くのノードを並列ステップで回すと遅い。ホストは何を、いつ設定するか。

- 要点: `torch.set_num_threads(1)` など torch のスレッド数を少なくする（各ワーカーが torch のスレッドを使い、コアを取り合うため）
- 要点: ホストが実行の前に 1 回設定する（ノードの中ではない）

## 保留問題

### H1 2 つの `ManualRun` を同じ時間軸で動かし、片方の `step` で両方の時間を進めたい。どうするか。

- 要点: 同じ `VirtualTimer` を両方の `run_manually(..., timer=)` に渡す
- 要点: 片方の step がもう片方の時間も進める

### H2 同じシミュレーションを `workers=1` と `workers=8` で走らせた。結果は違うか。

- 要点: 同じ（bit 単位で一致）。ワーカー数やどのスレッドがどのノードを走らせるかに依らない

### H3 2 つのノードが `on_update` でモジュールレベルのリストに追記する。`run.step(h)` を繰り返したとき、リストの中身の順は毎回同じか。どうすべきか。

- 要点: 同じとは限らない（並列に更新されるので追記の順が変わる）
- 要点: ノードどうしで Python のオブジェクトを共有しない

### R2 の改稿で反映する事実（レビューから、オーケストレーター経由）

1. 逆順の逐次が `step(dt)` と一致する条件: メッセージの流れが一方向（DAG）なら、出力側から入力側への順（トポロジカル順の逆）で一致する。chain はその特別な場合。「no order gives it」は「in general, no order gives it」にする（値が変わらない間は一致しうる）
2. 手動の実行では、ノードが自分につないだポートに送った値を同じ hook の中で recv しても、ステップ前の値が返る（逐次の `step(dt, *nodes)` でも同じ）。書くなら 1 行
3. 逐次の `step(dt, *nodes)` ではノードごとに送信が公開されるので、ステップ中のホストは前のノードの値を見うる。「ステップ中はステップ前の値」はノードなしの `step(dt)` に限る（Calls of the host の表と Q2 周辺）
4. pc.Chain の credit が `step(h)` で遅れる件は、ユーザーの判断待ちなので書かない
