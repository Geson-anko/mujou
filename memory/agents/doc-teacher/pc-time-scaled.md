# docs/en/topics/pc.md「One stream as a batch of consecutive samples」理解度テスト

## 対象
- ファイル: docs/en/topics/pc.md の節 "## One stream as a batch of consecutive samples"（"## Pitfalls" の手前まで）だけ。ja の同期はループ後にオーケストレーターが別に頼む
- 読者と用途: mujou の pc で実験する研究者が、長い 1 本のストリームを連続した c サンプルずつのバッチで速く流すとき、`pc.optim.TimeScaled` を正しく設定し（scale、時定数の単位、見せる時間、包むノード）、1 サンプルずつの実行とのずれ（RMSProp/AdamW の歩みが最大で約 sqrt(c) 倍、行ごとの r/lam が c 個前から続く、大きな c での不安定）を予想して確かめる

## 事実確認（R1、実物）
- `src/mujou/pc/optim.py` `TimeScaled(optimizer, *, scale)`: 束縛は内側の `step_(grads, elapsed * scale)` を呼ぶだけ。状態は内側のまま。scale は有限で > 0
- 時定数を c で割ったのと同じ（elapsed/tau の形で読むものすべて、丸めを除く）。weight_decay は無次元でそのまま、減衰の時定数 tau/w は c で割られる
- r・lam の緩和と learn_interval は倍にしない（Layer の時間は run のまま）
- 例: AdamW(tau=0.032/1e-3=32 s, tau_m=0.3, tau_v=32), scale=8、各バッチ 32 ms。1 バッチの学習率 = 0.032*8/32 = 8e-3 = 8 サンプル分の 1e-3。tau_m・tau_v は 32 ms ごとの betas (0.9, 0.999)（「Choosing the optimizer」と同じ換算）
- RMSProp/AdamW: 平均勾配のノイズ分散が 1/c → 歩みは c 歩より大きく、ノイズ支配で最大約 sqrt(c) 倍。歩みは 1/tau に比例するので tau を最大 sqrt(c) 倍にすれば打ち消せる（導出による目安。未測定と明記）
- SGD は 1 次の近似で c 歩と同じ
- pc.Chain は 1 つの optimizer をすべてのノードに渡す（「Choosing the optimizer」）ので、Chain なら optimizer= を 1 回包めばよい

## 評価用問題
### Q1 1 サンプルが 10 ms ごとに届くストリームを、連続した 16 サンプルずつのバッチで流す。各バッチを何秒見せ、`TimeScaled` の `scale` をいくつにするか。
- 要点:
  - 各バッチは 10 ms（ストリームの 1 サンプル分）見せる
  - `scale=16`

### Q2 同僚が Q1 の設定で各バッチを 160 ms 見せ、さらに `scale=16` で包んだ。これで正しいか。正しくなければ何が起き、どう直すか。
- 要点:
  - 正しくない。時間を 2 回倍にしている
  - 重みが 16 倍（c 倍）速く学びすぎる
  - 見せる時間を 10 ms（1 サンプル分）にする（scale はそのまま）

### Q3 1 サンプルずつの実行で使っていた `pc.optim.AdamW(tau=..., tau_m=..., tau_v=..., weight_decay=...)` の値がある。`TimeScaled` で包むとき、これらの値を自分で c で割るべきか。`weight_decay` はどうするか。
- 要点:
  - 割らない。時定数はストリームの秒（1 サンプルずつの実行と同じ値）で書き、`TimeScaled` が c で割る
  - `weight_decay` は無次元なのでそのまま（減衰は tau とともに速くなる）

### Q4 `pc.Chain` を使わず、3 つの `pc.Layer` と 1 つの `pc.Output` を手で作った。どのノードの optimizer を `TimeScaled` で包むか。`scale` はノードごとに変えてよいか。
- 要点:
  - 学習するすべてのノード: 3 つの `pc.Layer` と `pc.Output` の 4 つ
  - すべて同じ `scale=c`。変えてはいけない

### Q5 `TimeScaled` を使うとき、`pc.TimeConstants`（r と lam の時定数）と `learn_interval` もストリームの秒に書き直す、または c で割る必要があるか。
- 要点:
  - 必要ない。どちらも run の秒のまま（同じ見せる時間で 1 サンプルずつ流す実行と同じ値）。「ストリームの秒」と答えたら、「実行のタイマーの秒」と同一視していても誤り（ストリームの秒は run の秒の c 倍）
  - `TimeScaled` は重みの時間だけを倍にする

### Q6 `pc.optim.AdamW` で c = 16 にした。勾配のノイズが支配的なとき、1 バッチの歩みは 1 サンプルずつの 16 歩と比べてどうなると予想されるか。その理由と、歩みが大きすぎたときの対処も答えよ。
- 要点:
  - 16 歩の合計より大きく、最大で約 sqrt(16) = 4 倍
  - 理由: v が平均の勾配のもので、ノイズの分散が c 分の 1
  - 対処: tau を伸ばす。倍率はノイズの割合で 1 から約 4（sqrt(c)）の間。良い値は未測定（「4 倍で打ち消せる」と断定したら要点の誤り）
  - （R1 で改訂。メインの差し戻し: 平均の勾配が支配的なら歩みは c 歩とほぼ同じで、tau を伸ばすと遅く学ぶだけ）

### Q7 `reset` を False にして c = 8 で流す。あるバッチの 3 行目のサンプルの r と lam は、ストリームのどのサンプルから続いているか。
- 要点:
  - 8 個前（c 個前）のサンプル、つまり前のバッチの 3 行目から続く
  - 直前（1 個前）のサンプルからではない

## 保留問題
### H1 節の例（`AdamW(tau=0.032 / 1e-3, ...)`, `scale=8`、各バッチ 32 ms）で、`tau=0.032 / 1e-3` はストリームの 1 サンプルあたりの学習率いくつを表すか。1 バッチの学習で実際に使われる学習率はいくつか。
- 要点:
  - ストリームの 1 サンプル（32 ms の 1 歩）あたり 1e-3
  - 1 バッチでは 8 サンプル分の 8e-3（elapsed 0.032 s × 8 / tau 32 s）

### H2 もっと速く流そうと c を 8 から 64 に上げる。どんな危険があり、どう確かめるか。
- 要点:
  - 1 歩が c 倍長い 1 回の Euler 歩になるので、1 サンプルずつのストリームに遅れる、または学びすぎて不安定になりうる
  - 1 サンプルずつの実行と比べて確かめる

### H3 `pc.optim.SGD` を `TimeScaled` で包んだ場合、1 バッチの歩みは 1 サンプルずつの c 歩と比べてどうなるか。
- 要点:
  - 1 次の近似で c 歩と同じ（RMSProp/AdamW のような sqrt(c) 倍までの増加はない）
