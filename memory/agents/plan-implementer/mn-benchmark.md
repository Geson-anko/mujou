- Apple M4 Pro、14 コア（性能コア 10 + 効率コア 4）、SMT なし（`hw.physicalcpu` = `hw.logicalcpu` = 14）、メモリ 48 GB、macOS 26.5.2
- Python 3.14.8 の free-threaded（3.14t、uv）と GIL あり（Homebrew の 3.14）、torch 2.14.1、`torch.set_num_threads(1)`
- 拡張は `uv sync` のリリースビルド。各設定は 0.5 s 温めてから 2 s 測る（`switch` は 3 回の中央値）
- 負荷（`on_update` 1 回、単独のスレッドで）: `light`（Python で Δt をリストに足すだけ、hook の経路込みで約 0.6 µs）、`addmm`（384×384 の `addmm_`、約 65 µs）、`tanh`（32768 要素の `tanh`、約 78 µs）

## timekeeper の起こしすぎ（mixed）

周期 0.01 s のノード 64 個に周期 0 のノードを 2 個混ぜた。同じタイマーで周期 1 s の専用スレッドのノードとホストの `mujou.time.sleep` も待つ。表の更新/s と達成率は周期 0.01 s のノードの値、「周期 0」は周期 0 の 2 ノード（と 1 s のノード）の更新/s の合計。free-threaded。

| ワーカー | 周期 0 | 版 | `interrupt_waiters`/s | タイマーの起床/s | スイッチ/s | 周期 0 の更新/s | 0.01 s の達成率 | Δt p99 ms |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 4 | 0 個 | 修正前 | 0 | 113 | 3,420 | - | 95% | 14.7 |
| 4 | 2 個 | 修正前 | 179,890 | 218,927 | 396,052 | 181,976 | 95% | 10.1 |
| 4 | 2 個 | 修正後 | 0 | 116 | 68,808 | 1,460,474 | 97% | 10.0 |
| 14 | 0 個 | 修正前 | 1 | 115 | 7,052 | - | 95% | 14.7 |
| 14 | 2 個 | 修正前 | 208,986 | 233,263 | 429,711 | 210,256 | 96% | 10.0 |
| 14 | 2 個 | 修正後 | 0 | 117 | 68,711 | 1,405,803 | 97% | 11.1 |

GIL あり（修正後）: 2 個の場合の `interrupt_waiters` は 0 回/s、周期 0 の更新は 71〜72 万回/s。

- 修正前は、周期 0 のノードが更新を終えて戻るたびに、新しい期限（今 + 1 ns）が timekeeper の期限より早いので `interrupt_waiters` を呼んでいた。周期 0 の更新 1 回につき 1 回で、同じタイマーの全 waiter（ほかの実行の timekeeper、専用スレッド、ホストの `sleep`）が起きる
- 修正後は 0 回。スイッチは約 1/6 に、周期 0 のノードの更新頻度は 7〜8 倍になった。周期 0.01 s のノードの達成率と Δt は変わらない
- ほかのシナリオ（scale・workers）の修正前後の差は、ばらつきの範囲だった（周期のそろったノードでは、もともと `interrupt_waiters` がほぼ呼ばれない）

### 直し方（`crates/mujou-core/src/runtime/pool.rs`）

- `place` は timekeeper を起こさず、起こす必要があるか（ライフサイクルの仕事を積んだ、または timekeeper の期限より早い更新を積んだ）を返す
- ノードを戻したワーカー（`run_work`・`take`）は、その戻り値を使わない。すぐ自分でキューを見るので、期限が来ていれば自分で取る
- ワーカーが仕事を待つ前に、先頭の期限（まだ来ていない）が timekeeper の期限より早いと見たら、そこで timekeeper を起こす。これが無いと、ワーカーが戻した「今 + 1 ns」や次の周期の期限を timekeeper が知らず、timekeeper の期限まで更新が遅れる（仮想時計では止まる）
- 制御の側の `wake_pool` は全ノードを評価し直した後に 1 度だけ、`wake_node` は 1 ノードぶんで 1 度だけ起こす。以前は積むたびに起こしていた（M 回）
- 決定的なテスト `period::a_target_a_worker_puts_back_before_the_timekeepers_is_kept` を足した（ワーカーを 2 本以上にして、1 本が更新している間にもう 1 本が遠い期限で timekeeper になる。戻したノードの次の期限が来たら更新されること）。3 番目の規則を外すと 3 回とも落ちることを確かめた。待ちは `thread::sleep(QUIET)` で起こりやすくしているだけで、結果は眠る長さに依らない
- 計画に挙げた「置いた期限が今の時刻以下なら割り込まない」は採らなかった。周期 0 のノードの期限は「今 + 1 ns」で、更新を始めた時刻より後になるので効かない。また制御の側から置いた場合は、ほかに誰もキューを見ないので割り込みが要る

- 軽い負荷（約 0.6 µs）の周期 0 では、lock がはっきり律速。ワーカーを 7 本以上にすると合計が約 33〜39 万回/s に頭打ちし、1 本（約 80 万回/s）より遅い
- 数十 µs の負荷では待つ取得は数 % で、更新 1 回（lock を 2 回取る）の待ちは、ワーカーがコア数（14）以下なら更新の 3% 以下、28 本で約 15%
- 待った 1 回あたりの待ちが数十 µs と長いのは、lock の持ち主が lock を持ったまま OS に止められた場合や、起きたスレッドが走り出すまでの遅れを含むため（macOS）。ワーカーの数がコア数を超えると急に増える
- 今は直さない（計画の「想定リスク」のとおり）。小さなネイティブのノードを載せるときに、ワーカーごとのキューと work stealing を検討する

## 既定のワーカー数の判断

- free-threaded: 既定（min(M, `available_parallelism`) = 14）が `tanh` で最速。変えない
- 物理コア数にすべきか: この機械は SMT が無いので、論理コアと物理コアの差を測れない。free-threaded で論理コア数を超えると（28 本）遅くなり、論理コア数までは伸びるので、上限としての論理コア数は妥当。SMT のある x86 で測るまでは今のままにする
- 物理コア数を使う場合の方法と費用（変更はしていない）
  - `num_cpus::get_physical()`: コアに初めて依存 crate を足す（小さく、依存は `libc` だけ）。ただし CPU affinity と cgroup の割り当てを見ないので、`available_parallelism()` との min を取る必要がある
  - 依存を足さずに OS ごとに読む: Linux は `/sys/devices/system/cpu/cpu*/topology/core_cpus_list`（または `/proc/cpuinfo` の `core id`）、macOS は `sysctl hw.physicalcpu`、Windows は `GetLogicalProcessorInformationEx`。コードが 3 通りに増える
- GIL あり: 既定の 14 本は最速の 7〜8 本の約半分の速さ（`tanh`）。`addmm` でも 14 本は 8 本より 12% 遅い。既定をビルドで分けるか（例: GIL ありでは論理コア数の半分）はユーザーに確認する。計画では「両方のビルドで同じ」と決めていたので、変更はしていない

## 計画からの逸脱

1. 負荷に `tanh` を足した。計画の `addmm_`（n=32）は約 4 µs と軽すぎ、384×384 にしても Apple silicon では行列演算器の共有で 2 本を超えて伸びないので、コア数で伸びる負荷が別に要った
2. M は 8・64・256・1024 まで（4096 は既定に入れていない。`--nodes` で足せる）
3. 自発と非自発のスイッチの内訳は取れなかった（macOS の制約、上記）
4. timekeeper の直し方は計画の 2 案と違う（上記「直し方」）
5. CUDA の切り替えの費用は測っていない（この機械に CUDA が無い）

## 別タスクの提案

- 仕事を取ったワーカーが次のワーカーを起こす（`run_work` の `notify_one`）ので、周期のあるノードでは更新 1 回につき約 1 回のスイッチが起きる。ワーカーを減らすとスイッチが大きく減ることから、空いたワーカーの起こし方（例: 期限が来ている仕事があるときだけ起こす）を詰めれば減らせる見込み。正しさに関わる部分なので、PR 3 では触れていない

### native の周期の `Option` を消した（#75 で後回しにした分）
- bindings の `Runtime.start(periods=)` は `list[float] | None`、コアの `RuntimeConfig::period_ns` は `Option<Vec<u64>>`。ノードごとの `None`（「周期なし」）は無くし、0.0 秒は bindings の `period_to_ns` が 1 ns に丸める（振る舞いは今と同じ）
- 外側の `Option` は残した。省いたときに全ノードが 1 ns になる既定で、`dedicated`・`workers`・`last_update_ns` と同じ形。Python は常に渡すので、使うのは Rust のテストの `RuntimeConfig::default()` だけ
- Rust のテスト: `with_period(None, false)` は `with_period(1, false)` にし、テスト名を `with_a_period_of_1_ns_any_time_passing_is_enough` に変えた。周期の数の検査のテストは `[vec![0], vec![1, 1]]`

### GIL ありの既定のワーカー数を変えた（推奨案 1）
- 判定は bindings の `Runtime.start` で、`workers` が無いときに `sys._is_gil_enabled()` を呼ぶ。真なら `max(1, available_parallelism / 2)` をコアに渡し、偽ならコアの既定（`available_parallelism`）。コアの `min(プールのノード数)` はそのまま効く
- bindings で見る理由: free-threaded のビルドでも、実行時に GIL が有効になることがある（`PYTHON_GIL=1`、free-threaded に対応しない拡張の import）。コンパイル時の `Py_GIL_DISABLED` では判定できない。コアは Python を知らない
- テスト `TestWorkers.test_the_default_number_of_workers_all_take_updates`: 更新のたびに 5 ms 眠るノードを CPU 数 + 2 個、実時間で 0.5 s 回し、更新を走らせたスレッドの数が既定のワーカー数（`os.process_cpu_count()` から求め、GIL ありなら半分）と等しいこと。両方のビルドで 5 回ずつ通した。GIL ありのビルドで `tests/mujou` と `tests/test_examples.py` が通る（560 passed）
- 推奨案 2（物理コア数にしない）は記録だけ（`specs/native-core.md#ベンチマーク`、`memory/project_mn_scheduler.md` の Q2）
