## 原因の主張の検証

- 再現プログラム `abarepro` を自分の scratchpad にコピーし、debug ビルドで 50 万回 × 読み手 8 本を 3 回走らせた。`a` が `b` の値を返した回数は 5 / 0 / 2 だった。3 回のうち 2 回で再現した（メモには「3 回中 3 回」とある）。使っているのは safe Rust と `ArcSwap::from_pointee` / `load_full` / `store` だけで、型も 1 種類しかない。したがって mujou 側の誤用（型を取り違えた使い方や unsafe）は原因ではない
- 修正前の `slot.rs`（edaf433）も、`ArcSwap::new` / `from_pointee` / `load` / `load_full` / `store` を普通に呼んでいるだけで、unsafe は `Buffer::bytes` の slice 化しかない
- arc-swap 1.9.2 のソースと照らした結果。`HybridProtection::attempt`（`src/strategy/hybrid.rs`）は「ptr を読む → `new_fast(ptr)` → 読み直す → 違えば `debt.pay(ptr)`、失敗したら『誰かが払った』とみなして `Self::new(ptr, None)` で所有する」という流れになっている。一方 `Debt::pay_all`（`src/debt/mod.rs`）は、全スレッドの fast slot と helping slot を対象に、外したポインタの**値**だけで CAS して払う。storage は区別しない（helping の `help` は `storage_addr` を見るが、fast slot の支払いは見ない）。このため「A から P を読む → A の書き手が P を外して解放 → B の新しい値が同じアドレス P に置かれる → R が P の debt を置く → B の書き手が P を外して R の debt を払う → R は読み直して不一致を見て、支払い済みなので P（B の値）を返す」という筋書きが成り立つ。`Debt::pay` のコメントにある前提（同じポインタなら同じオブジェクト・同じ型）が、別の storage でアドレスが再利用されると破れる
- fallback の経路についての主張（「別の型の値を `Message` として drop しうる」）は、B の書き手の inc と R の `T::dec` で数は釣り合う。ただし、その間に B 側の参照が全部落ちると、R の dec が最後の参照になり、`drop_slow` が別の型として走る。主張は条件付きで正しい（確信度: 中）
- Web 検索でも、upstream にこの不具合の報告は見つからなかった（メモの「未報告」と一致）

## 修正の正しさの検証

- 臨界区間: `Slot::load` は guard の一時値の中で `Arc::clone` するだけ。`publish` は `mem::replace` の文末で guard が落ち、`notify_all` と `drop(old)` は lock の外にある。`InputGroup::write` は `Arc::new(Message)` を lock の外で作り、lock の下で行うのは `resolve` と `Arc::clone` と `replace` だけ。`drop(old)` は lock の外（`write_lock` の内側だが、これは以前と同じ）
- `wait_newer` の通知: 待ち手は `fetch_add` → lock → 確認 → `wait_timeout`（lock を手放す）の順に動く。書き手が lock を取るのが待ち手の確認より後なら、mutex の happens-before によって、書き手の `load(Relaxed)` は待ち手の +1 より古い値を読めない。前なら、待ち手が新しい値を見る。取りこぼしはない。`last` は呼び出し側が `Arc` を持っているので、`ptr_eq` で ABA は起きない
- 版番号による一斉切り替え: `InputSlot::load` は pair の lock を持ったまま版を読む。読み手が古い pair を見たなら、その lock は書き手が S の pair を置き換えるより前に取られている。だから版の load は書き手の `version.store` より happens-before になり、V+1 は見えない。「1 つでも新しい値が見えたら、その後に読む他のスロットも新しい」という性質は、以前（Acquire/Release だけ）より強い形で成り立つ
- ロックの順序: `write` / `InputSlot::restore` は `write_lock` → `pair`。`load` は `pair` だけ。`Slot` は `value` だけで、他の lock と入れ子にならない。プールの lock は drop の中で取るが、スロットの lock の外である。Python の bindings は lock の下で Python を呼ばないので、GIL ありのビルドでも循環はない。デッドロックの経路は見当たらない
