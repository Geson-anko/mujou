# コーディング・リファクタリング規約

CLAUDE.md の開発原則を補完し、判断基準と具体例を示す。テスト方針は skill `testing-strategy` が正典。

## 数式との対応

- 学習則のコードは skill `pc-alm` の記号に揃える（`a`, `r`, `lam`, `eps`, `e_out` など）。docstring か直前のコメントに対応する式を書く
- 1 つの式を 1 つの関数またはまとまった数行に対応させる。複数の式を 1 行に畳んで速くする最適化は、効果を測ってから行い、そのときも式との対応をコメントで残す
- 誤差の向き（$r_i = h_i - \sigma(a_i)$、$e_L = y - \hat y$）を変数名や docstring で明示する

## テンソル

- 公開関数の docstring にテンソル引数・戻り値の shape を書く（例: `h: (batch, n_in)`）
- バッチ次元は先頭に置く
- 状態の in-place 更新は所有者だけが行う（skill `locality-and-async` の不変条件 4）

## カプセル化

- クラスの内部実装と `__init__` で設定する属性は原則 `_` prefix
- 外部から参照する必要がある属性のみ public にする
- 「テストから参照したい」は public 化の理由にならない。公開 API 経由でテストする

## private モジュール規約

`src/mujou/` 配下のモジュールはテストの有無で `_` prefix を決める。

- テストを書かない（真に private な実装）→ ファイル名に `_` prefix を付ける
- テストを書く → `_` prefix を付けない
- 便宜的な再 export と互換ファサードは作らない。`__init__.py` が公開する名前は意図して選ぶ

## 型

- pyright strict を通す。`Any` と `# type: ignore` は理由をコメントで添えたときだけ使う（blanket な ignore は pre-commit が弾く）
- 型エイリアスは `type X = ...` 構文を使う
- 変換・検証付きの生成は `@classmethod` ファクトリに置く

## エラーハンドリング

- 検証は境界（ユーザー入力・外部ストリーム・設定）でだけ行う。内部で起こり得ない状態の防御コードは書かない
- shape 不一致など利用者の誤りは、何が期待され何が来たかを含むメッセージで早く失敗させる
- NaN / Inf の扱いは学習則ごとに方針を決めて docstring に書く。黙って握りつぶさない

## リファクタリング技法

### 適用する

- 不要なネストの平坦化（early return / guard clause）
- 1 箇所でしか使わない関数・クラスの解消
- 意図が読めない命名（`data`, `tmp`, `helper`）の改善
- wrapper / pass-through メソッドの除去
- 重複の抽出（3 度現れたら、が目安）

### 適用しない

- 仮想的な将来要件のための抽象化（「いずれ GPU 分散するかもしれないから」など）
- 「綺麗に見える」だけの分割
- 公開 IF を変えるリファクタ（別タスクで合意してから）
- 数式との対応が読めなくなる「賢い」書き換え
