# ソロ開発サイクル（ロール切替・逐次）

サブエージェントを起動せず、**自分自身**が 5 つのロールを順に演じて 1 タスクを仕上げる手順。
[agent-team-startup](../agent-team-startup/SKILL.md) と工程の骨格は同じで、委譲コスト
（文脈の再構築・報告の往復）を払わない代わりに、レビューの独立性を自分で担保する。

## 使い分け

| 状況                                                   | 使うもの                     |
| ------------------------------------------------------ | ---------------------------- |
| ユーザーが「エージェントチームで」「並列で」と明示した | `agent-team-startup`         |
| 上の明示がない（規模不問）                             | **この skill**               |
| 数回の tool 呼び出しで終わる trivial な修正            | どちらも使わない（直に直す） |

## 原則

- **委譲しない。** Agent tool を使わない。調査・実装・レビューをすべて自分で行う
    （唯一の例外は「自己レビュー」節の末尾）
- **段階を飛ばさない。** 順序は固定。省略してよいのは「段階の省略基準」に該当する場合だけ
- **ロールを混ぜない。** その段階の担当範囲外のファイルは触らない。別段階に属する気付きは
    記録ファイルに書き留め、その段階が来てから手を付ける
- **切り替わりを宣言する。** 「段階 3（機能実装）に入る」と 1 行述べてから着手する。
    ユーザーが今どこにいるかを追えるようにするため

## 5 段階

### 1. 計画

要件を仕様に変換する。解釈の違いで成果物が変わる点だけをユーザーに確認する（軽微な選択は
自分で決めて 1 行理由を添える。[CLAUDE.md](../../../CLAUDE.md) 開発原則 1）。

- 決めること: 公開インターフェース（シグネチャレベル）／実装ステップ／テスト観点／リスク
- 触らない: `src/` `tests/`。この段階ではコードを書かない

### 2. テスト実装

仕様を実行可能なテストに翻訳する。テストは実装より**先に書く**。

- 触ってよい: `tests/` のみ
- 方針は [testing-strategy](../testing-strategy/SKILL.md) が正典（数値的オラクル優先、seed 固定、
    内部関数のモック禁止、`class TestXxx` 集約）
- 実装を先に書きたくなっても書かない。実装前にテストが通ってしまうなら、仕様をテストに写しきれていない

### 3. 機能実装

段階 2 のテストを green にする。

- 触ってよい: `src/`（テストが実装の都合で誤っていた場合のみ `tests/` も。理由を記録する）
- テストを通すために期待値を緩めない。緩めるなら仕様の再解釈なので段階 1 に戻る
- 計画外の判断は記録ファイルに理由付きで残す

### 4. リファクタリング

**ここが自己レビューの段階**でもある。まず読み直し、次に整理する。

- 公開インターフェースとテストの green を保ったまま、内部を簡素化する
    （技法は [refactor-conventions](../refactor-conventions/SKILL.md)）
- レビュー観点は下の「自己レビュー」に従う
- ここで見つけた仕様レベルの欠陥は段階 3 に戻して直す。整形でごまかさない

### 5. ドキュメント

変更で古くなった記述を現状コードに合わせる。

- 対象: docstring／README／`CLAUDE.md`／`memory/`／関連 skill／ユーザー向けの `docs/`
- 公開 API を変えたら、`docs/en/api/*.md` の `:::`（足した名前・消した名前）と、その API を説明する `docs/en/` と `docs/ja/` のページを直す。最後に `just docs-build` を通す
- 変更していない箇所の「ついで改善」はしない（[CLAUDE.md](../../../CLAUDE.md) 開発原則 3）

## 段階ゲート

前段のゲートを通してから次に進む。

| 段階               | 完了条件                                                                                                      |
| ------------------ | ------------------------------------------------------------------------------------------------------------- |
| 1 計画             | 公開 IF がシグネチャレベルで書けている／テスト観点が列挙済み／確認事項が解消済み                              |
| 2 テスト実装       | 新規テストだけを実行（`uv run pytest <path>`）し、**期待どおりに失敗する**ことを確認（red） |
| 3 機能実装         | `just run` が green                                                  |
| 4 リファクタリング | 公開 IF 不変・green 維持・diff の全行が要求からトレース可能                                                   |
| 5 ドキュメント     | docstring / README / memory / docs/ が現状コードと整合。最後にもう一度 3 のコマンド                           |

反復中は `just test-fast` や対象を絞った `uv run pytest <path>` でよいが、各ゲートの判定には
`just run`（slow テストを含む）を使う。学習則・局所性・非同期性に触れる変更では、段階 1 で
skill [pc-alm](../pc-alm/SKILL.md) / [locality-and-async](../locality-and-async/SKILL.md) を読み、
段階 4 の自己レビューでその不変条件と突き合わせる。

## 自己レビュー

チーム版の `code-reviewer` は独立 context だが、ソロでは実装した本人が読み直すため
見落としが増えやすい。記憶に頼らず、diff や計画などの外部の根拠と突き合わせて確認する。

1. `git diff main...HEAD` を通しで読む。**記憶ではなく diff を根拠にする**
2. 段階 1 の計画と突き合わせ、要求からトレースできない行を洗い出す
3. 観点チェックリストで見る: 仕様準拠／境界値・エラーパス／カプセル化（`_` prefix）／
    テストが公開インターフェースを見ているか／無関係な変更の混入／更新式の符号・係数と
    ノード間の局所性（skill `pc-alm` / `locality-and-async`）
4. 実装中に「後で直す」と思った箇所を記録ファイルから回収し、対応または却下理由を書く

設計上の裁定に迷い、自分の判断に自信が持てない場合に限り、`code-reviewer` への単発委譲を
検討してよい（ユーザーが委譲を禁じている場合を除く）。実装のやり直しは委譲しない。

## 段階の省略基準

- **段階 2 を省略可**: 振る舞いが変わらない純リファクタ、ドキュメントのみの変更。
    既存テストの green が仕様の担保になる
- **段階 4 の整理・段階 5 を省略可**: それぞれ整理の余地・同期対象が無い場合。ただし黙って
    飛ばさず「読み直したが整理点なし」「ドキュメントへの影響なし」と 1 行述べる
- **段階 1・3、および段階 4 の自己レビューは省略しない**

## 記録

`memory/agents/<セッションのエージェント名>/<task-slug>.md`（既定は `orchestrator/`）に
**1 ファイルで**残し、段階ごとに追記する。ロールごとにファイルを分けない（単一 context なので
引き継ぎ用の分割が不要）。書く内容は計画・計画外の判断とその理由・自己レビューの指摘と対応・
却下した案。
