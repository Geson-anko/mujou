# teacher-student による文書改善

`doc-teacher` が文書を書き、理解度テストを作る。`doc-student`（haiku）がテストを解く。全問正解するまで `doc-teacher` が文書を直す。低性能モデルが誤解なく読める文書は、人にとっても短く明確になる。

このループはメインエージェント（あなた）が回す。あなたは問題文と解答を 2 つの agent の間で受け渡し、採点が妥当かを確かめる。文書を自分で直さない。

## 役割

| 誰               | 何をする                                           | 見てよいもの                         |
| ---------------- | -------------------------------------------------- | ------------------------------------ |
| メイン（あなた） | 対象の確定・受け渡し・採点の点検・終了判断・commit | すべて                               |
| `doc-teacher`    | 執筆・出題・採点・改稿                             | すべて                               |
| `doc-student`    | 対象文書だけを読んで解答する                       | 対象文書と、プロンプト内の問題文だけ |

模範解答は `doc-teacher` のノート（`memory/agents/doc-teacher/<task-slug>.md`）にだけ置く。`doc-student` へのプロンプトに模範解答やノートのパスを書かない。

## 手順

### 1. 準備

1. `main` から作業ブランチを切る（種別は `docs`）
2. 次の 3 つを決める。決まらなければユーザーに聞く
    - 対象ファイル（複数可）
    - 読者と用途（誰が、読んで何をするか）
    - `<task-slug>`（ノートのファイル名）
3. 対象が複数あるときは、ファイルごとに別の `doc-teacher` を立てる。対象ファイルが重ならなければ並列に進めてよい

### 2. 執筆と出題（R1 の準備）

`doc-teacher` を起動する。後で続きを頼むため、`name` を付ける（例: `doc-teacher-<task-slug>`）。

```text
Agent(subagent_type="doc-teacher", name="doc-teacher-<task-slug>", run_in_background=false,
      prompt="対象: <パス>。読者と用途: <1〜2 文>。ノート: memory/agents/doc-teacher/<task-slug>.md。
              1 回目の起動として、執筆と出題をして報告して。")
```

報告の「生徒に渡す問題文」を受け取る。

### 3. 解答

`doc-student` を**毎回新しく**起動する。前のラウンドの生徒を再利用しない（前の問題と文書を覚えているため、測定にならない）。

```text
Agent(subagent_type="doc-student", run_in_background=false,
      prompt="次のファイルだけを読んで、問題に答えて。<対象のパス>\n\n<生徒に渡す問題文をそのまま>")
```

### 4. 採点と改稿

同じ `doc-teacher` に SendMessage で解答を渡す。SendMessage は deferred tool なので、未ロードなら先に `ToolSearch("select:SendMessage")` を呼ぶ。

```text
SendMessage(to="doc-teacher-<task-slug>",
            message="R<n> の生徒の解答です。採点・原因分類・改稿をして報告して。\n\n<生徒の解答をそのまま>")
```

報告を受けたら、次の 2 点を自分で確かめる。

- **採点が甘くないか。** 生徒の解答とノートの要点を突き合わせる。要点の欠けを正解にしていたら差し戻す
- **テスト対策をしていないか。** `git diff` で改稿を読む。問題文の言い回しの持ち込みや、特定の 1 問を正解させるためだけの注記があれば差し戻す

### 5. 繰り返し

| 状況                      | 次にすること                                       |
| ------------------------- | -------------------------------------------------- |
| 不正解がある、R5 未満     | 手順 3 に戻る（生徒は新しく起動する）              |
| 全問正解                  | 手順 6 に進む                                      |
| R5 を終えても不正解が残る | ループを止め、残った問題と原因をユーザーに報告する |

同じ問題が 3 ラウンド続けて不正解なら、R5 を待たずにユーザーに報告してよい。問題そのものか、文書の目的の見直しが要る可能性が高い。

### 6. 汎化確認

改稿に使っていない保留問題で、過学習していないかを確かめる。

1. `doc-teacher` に「保留問題を生徒に渡す問題文として出して」と頼む
2. 新しい `doc-student` に解かせ、その解答を `doc-teacher` に採点させる
3. 全問正解なら手順 7 に進む
4. 不正解があれば、その保留問題を評価用に移し、手順 4 に戻る。汎化確認は 1 回だけ行う（2 回目の保留問題は作らない）

### 7. 仕上げ

1. 対象文書の最終 diff を読み、事実の誤りと不要な肥大化がないかを確かめる
2. `just run` を通す（docstring を変えたときに特に必要）
3. 対象文書とノートを commit する。1 文書 1 commit
4. ユーザーに報告する: 対象、ラウンド数、最終の正解数、行数の変化、主な改稿、`doc-teacher` が挙げた対象外の問題

## 注意

- 生徒が一般知識で正解できる問題は、文書の良し悪しを測れない。そういう問題を見つけたら、`doc-teacher` に「問題不良」として差し替えさせる
- 「全問正解」はゴールであって目的ではない。正解数のために文書が長くなったなら失敗。行数の変化を報告に必ず入れる
- 解答は確率的にぶれる。1 ラウンドだけ現れた「誤読」に合わせて文書を変えるかどうかは、`doc-teacher` の判断に任せる
