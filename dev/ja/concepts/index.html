    🧠 Mujou の仕組み¶

    PyTorch の nn.Module とテンソルを使ったことがある前提。手を動かすなら ネットワークを走らせる から。

    全体像¶

    flowchart TB
    H["ホスト（ネットワークを動かす Python のコード）"]
    subgraph N["ネットワーク"]
        direction LR
        A["ノード A"] <-->|Channel| B["ノード B"] <-->|Channel| C["ノード C"]
    end
    T["実行のタイマー"]
    H -->|"mujou.run(net) が返す Run で、入力を書き、出力を読み、状態を取得する"| N
    T -.->|"時刻と dt"| N
    部品 ひとことで 行き先
    ノード 1 回分の更新を on_update(dt) に書くクラス。繰り返し呼ぶのは mujou ノード
    Port と Channel ノードの接続口と、2 つの口をつなぐ線。値は溜まらず、最新の値だけが残る Port と Channel
    ネットワーク ノードを組み立てる入れ物。中のノードはパスで指す ネットワークとパス
    実行 mujou.run が全ノードをバックグラウンドで走らせ、Run を返す。ホストは Run だけでネットワークとやり取りする ネットワークを走らせる
    時間 ノードは前回の更新から経った時間 dt に比例して状態を進める 時間
    状態 run.state_dict() で実行を終えずに取得し、新しいインスタンスに state= で渡すと続きから走る 保存と再開
    シミュレーション mujou.run_manually は仮想時間を step で進め、結果は毎回同じになる シミュレーション
    学習 更新則はノードの中に書き、どの則で学ぶかはノードが決める 学習

    PyTorch との対応¶

    PyTorch mujou
    モデルの forward を自分のループで呼ぶ ノードの on_update(dt) を mujou が呼ぶ。ループは書かない
    forward の引数と戻り値 Port の recv() と send()
    親のモジュールの属性に子を代入する Network の属性にノードを代入する
    model.train() と model.eval() 無い。推論と学習を同時に行う
    loss.backward() がモデル全体に届く 勾配はノードの中だけ。ノードの間はメッセージ
    model.state_dict() ノードごとの state_dict() と、実行全体の run.state_dict()

    ノード¶

    stateDiagram-v2
    [*] --> on_start
    on_start --> load_state_dict : 状態から再開するとき
    on_start --> on_update : 新しく始めるとき
    load_state_dict --> on_update
    on_update --> on_update : 平均 period ごと
    on_update --> on_pause : run.state_dict()
    on_pause --> on_resume : 状態を複製した後
    on_resume --> on_update
    on_update --> on_stop : 正常な終了
    on_update --> on_exception : どれかのノードの hook が例外
    on_exception --> on_stop
    on_stop --> [*]

    override では最初に super() を呼ぶ

    __init__ でも hook でも、最初に super().__init__(...) や super().on_update(dt) を呼ぶ（Node）。

    ノードの内側 ノードの間
    実行 同期。ふつうの PyTorch のコード 非同期。互いを待たない
    やり取り 変数と計算グラフ Port のメッセージ（計算グラフから切り離したコピー）
    勾配 通常の PyTorch と同じく記録する 届かない

    ノードに入れる計算の量（1 つの層でも、複数の層やモデル全体でもよい）は設定ではなくノードのクラスで決まり、BP で一緒に学ばせたい層は 1 つのクラスにまとめる。

    flowchart LR
    subgraph N1["ノード 1（BP で一緒に学ぶ 2 層。内側は同期）"]
        direction LR
        L1["Linear"] --> R["ReLU"] --> L2["Linear"]
    end
    subgraph N2["ノード 2"]
        L3["Linear"]
    end
    N1 -. "メッセージ（非同期）" .-> N2
    ノードにループを書かないのはなぜ？

    mujou は多くのノードを少ないワーカースレッドで回す。ノードが 1 回分の更新だけを書けば、いつどのスレッドで呼ぶかを mujou が決められる。状態を取得するために全ノードを止めることも、テストで 1 回ずつ進めることも、この形ならできる。

    Port と Channel¶

    sequenceDiagram
    participant A as ノード A（送る）
    participant C as Channel
    participant B as ノード B（読む）
    B->>C: recv()
    C-->>B: 初期値（既定はゼロ、時刻は None）
    A->>C: send(1)
    A->>C: send(2)
    B->>C: recv()
    C-->>B: 2（1 は読まれずに上書きされた）
    B->>C: recv()
    C-->>B: 2（同じ値をもう一度）
    A->>C: send(3)
    キューにしないのはなぜ？

    キューに溜めると、送る側と読む側の速さの差で値が増え続け、遅い側に歩調がそろってしまう。最新の値だけを読み書きすれば、各ノードは互いを待たずに自分の速さで動ける。

    読む側は待たない。相手がまだ送っていなければ初期値を返し、時刻は None になる（Port.recv・Port.recv_with_time）。

    メッセージの型は Port の spec で決まり、送った値は計算グラフから切り離したコピーとして届く。

    受け取る相手が 1 つなら Port（送るだけなら相手はいくつでもよい）、同じ役割の複数の相手から受け取って束ねるなら MultiPort（使い分けは Port の種類）。

    ネットワークとパス¶

    Network は、ノードを属性に代入して Port を connect でつなぐ入れ物。自分では何も実行しない。子の Port を自身の属性（慣例で prev・next）に代入して公開すれば、ノードと同じように外からつなげる（コードは ネットワーク）。

    flowchart TB
    subgraph net["mujou.run(Classifier())"]
        R["Classifier（ルート）"] -->|body| B["Stack"]
        R -->|head| H["Head<br/>パス head"]
        B -->|l1| L1["Hidden<br/>パス body.l1"]
        B -->|l2| L2["Hidden<br/>パス body.l2"]
    end
    subgraph one["mujou.run(Head())"]
        N["Head（ルートのノード）<br/>パス #quot;#quot;"]
    end

    パスは状態の木のキーになる（属性名を変えたときは 再開するときの注意）。

    複数のネットワークを 1 つの実行に並べるには Group を使う（Group）。

    時間¶

    時間軸は実行ごとに 1 本のタイマーで、全ノードとホストがこれを使う（時間）。

    更新の間隔はノードごとに違い揺らぐため、on_update は呼ばれた回数ではなく渡された dt に比例して状態を進める（書き方は dt に比例して更新する）。

    学習¶

    mujou はノード・Port・スケジューラに更新則を組み込まない。

    更新則 勾配を取る範囲 読むページ
    ノードの中の BP 1 つのノードの中。ふつうの loss.backward() ノードの中で学習する
    PC-ALM（mujou.pc） 各ノードの中。隣とはメッセージでやり取り PC-ALM で学習する
    自作の則 ノードが決める 更新則

    ノードが守る規則¶

    規則 守らないと 代わりに
    time.sleep でブロックしない ほかのノードの dt が伸びる 一定間隔なら period。待つしかないなら dedicated_thread=True。ホストが待つなら run.timer.sleep
    ノードは 1 回だけ走る RuntimeError もう一度走らせるなら新しいインスタンスを作る（mujou.run）
    走っている間はホストからノードの属性を読まない ノードの更新と競合する Port は run.read、状態は run.state_dict() で読む。属性は実行が終わった後なら読める
    on_start では状態に依存する値を送らない 復元する前の状態を送ってしまう 最初の on_update で送る（load_state_dict は on_start の後。ノード の図）
    on_stop で状態を変えない 正常に終了した後に取得する状態が変わる on_stop では I/O などの資源だけを解放する
    実行中に変わる素の値とテンソルの入れ物は登録する 復元すると初めからになる カウンタ・最後に見た時刻・テンソルのリストや dict は register_state
    計算グラフは 1 回の更新の中に閉じる グラフが伸び続ける 次の更新へ持ち越す値は detach し、パラメータは torch.no_grad() の中で更新する（下のコード）
    on_exception・on_stop では self.timer で時間を測らない 実行の終了で時刻が止まり、時間が経たない 実時間で測る（Node.timer）
    時間を動かせるのはホストだけ、ノードは Port だけで話す RuntimeError 時間の操作はホストの run.timer で。ノードは Run のメソッドも mujou.run も呼ばず、自分の Port で話す 
    self.last_y = self.model(x).detach()  # 次の更新へ持ち越す値はグラフから切り離す
with torch.no_grad():  # パラメータの更新は記録しない
    for p in self.model.parameters():
        p -= lr * p.grad
