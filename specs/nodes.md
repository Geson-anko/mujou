# ノード

## 定義

ノードは mujou の計算の基本単位であり、基盤となる抽象である。ノードの内側は同期的に計算し、ノード同士は非同期にやり取りする。非同期・分散の境界は常にノードの境界と一致する。

ノードは実行の単位であり、分散処理でいう「マシン 1 台」ではない。1 台のマシンの上で多数のノードが動く（[ネイティブコア](native-core.md#mn-スケジューリング)）。

局所性・非同期性の不変条件は**ノードの間に課す**。ノードの内側の計算方法（ニューロンの合成、行列演算、BP など）は、ノードごとに自由に選べる。

## ノードの大きさ

ノードの大きさは、どのノードのクラスを書くか・使うかで決まる。設定を変えるだけでノードを分割したり統合したりはしない。

| レベル | 内容 |
| --- | --- |
| ニューロン | 1 ニューロンを 1 ノードにする。最小のノード。future work |
| レイヤー | 1 レイヤーを 1 ノードにする。既定 |
| スタック | 複数のレイヤーを 1 ノードにする。モデル全体を 1 ノードにしてもよい |

既定をレイヤーにしたのは、わかりやすさのため。

### ニューロンが最小である理由

既定の更新手法 PC-ALM の更新式（活動・双対変数・重み）は、ニューロン自身の値と、シナプスでつながった相手の値だけで計算できる。そのため、ニューロン 1 個を 1 ノードにまで分割できる。ニューロン単位のノードは、必要になったら `nn.Linear` に当たるレイヤーのノードとは別のクラスとして書く。

### 設定で分割しない理由

ノードを自動で分割するには、ノードの内側の計算と、重みを誰が持つかを、フレームワークが知っていなければならない。これはノードの内側を自由にする方針と合わない。

全結合のレイヤーは、重みの行が出力のニューロンごとに独立しているので分けやすい。畳み込みは 1 つのカーネルを出力のすべての位置で共有するので、そうはいかない。位置ごとにノードに分けると各ノードがカーネルのコピーを持ち、非同期に動くうちにコピー同士がずれる（[ノード間の契約](#ノード間の契約) の weight transport と同じ問題）。

### 非同期の境界と実行の配置

| 軸 | 意味 | 決め方 |
| --- | --- | --- |
| 非同期の境界 | どこで最新値の読み書きになり、一貫したスナップショットを失うか | ノードのクラスで決まる |
| 実行の配置 | どのノードをどのワーカーで、どの順に回すか | 実行時に選ぶ |

複数のノードを 1 本のワーカーで決まった順に、同じ $\Delta t$ で回せば、まとめて 1 つのノードのように動く。テストで全ノードを固定の $\Delta t$ で同期的に回すのも、この配置の一例（[実行モデル](execution-model.md#テスト)）。

利用者が選べる配置は 2 つある。

- 実行ごとのワーカー数（`mujou.run(..., workers=None)`）。既定は、プロセスが使える CPU の数（GIL が有効なときはその半分、少なくとも 1）を、ワーカーに載るノードの数で頭打ちにした値（[ネイティブコア](native-core.md#ワーカー数の既定)）
- ノードごとの実行クラス（`Node(dedicated_thread=False)`）。既定はワーカーに載り、`dedicated_thread=True` のノードだけが自分の OS スレッドで動く。hook がブロッキングするノードはその間ワーカーを占有してほかのノードの $\Delta t$ を伸ばすので、専用スレッドにする

複数のノードを決まった順に同じワーカーで回す指定は未決定（[未決定事項](open-decisions.md)）。

### 粒度を選べるようにする理由

どの粒度が最適かは、ハードウェアと用途（ロボティクス、ニューロモーフィックなど）によって変わる。ノードを基盤にすれば、ニューロン単位の細かい非同期も、BP のような同期的な手法も、同じ枠組みで扱える。

## ライフサイクル hook

ノードは実行時に存在する分散処理の最小単位で、ネットワークは組み立てだけの構造である（[ネットワーク](network.md#構成要素)）。

ノードはフレームワークが呼ぶ hook を override して書く。ループはフレームワークが持ち、作者は 1 ステップ分の処理だけを書く。理由は 3 つ。

- M:N スケジューリング: `on_update` の 1 回が協調スケジューリングの区切りになる。作者が自分でループを書くと、そのノードはワーカーに載せられない
- 決定的なテスト: 仮想時計で固定の $\Delta t$ のまま全ノードを決まった順に回すには、ループをフレームワークが持っている必要がある
- 言語の境界: ランタイムは同じ hook を trait（`NodeHooks`）として呼ぶ

| hook | 呼ばれるとき | 役割 |
| --- | --- | --- |
| `on_start()` | 実行の開始に 1 回 | I/O を開く。状態に依存する出力をしない |
| `load_state_dict(state)` | 復元するときだけ。`on_start` の後、最初の `on_update` の前 | 状態を戻す |
| `on_update(dt)` | 自分の周期で繰り返し（[実行の周期](#実行の周期)） | 隣の最新値を読み、$\Delta t$ ぶん更新し、書く。他を待たない |
| `on_pause()` | 状態の取得のための停止の要求で、更新の区切りで止まったとき。タイマーの `pause` では呼ばない | I/O の一時停止など |
| `on_resume()` | 停止から再開し、次の `on_update` の前 | I/O の再開、停止中に溜まった外界の値の破棄など |
| `on_exception()` | どれかのノードの例外で終わるとき、全ノードに 1 回。`on_stop` の前 | アクチュエータの安全停止など、異常終了に固有の処理 |
| `on_stop()` | 実行の終わりに 1 回。例外による終了でも呼ぶ | 資源の解放。状態を変えない |
| `state_dict()` | 状態を取るとき。全ノードが止まっている間か、正常に終わった後 | 状態を返す |

呼ぶ順は `on_start` →（復元するなら）`load_state_dict` → `on_update` の繰り返し（間に `on_pause` → `on_resume`）→（例外で終わるなら `on_exception`）→ `on_stop`。

- `on_start` の後に `load_state_dict` を呼ぶ。`on_start` で状態を作るノードが、復元した値を黙って上書きしないためである。代わりに `on_start` では状態に依存する出力（送信、アクチュエータへの指令）をしない。状態は `__init__` で作る書き方を勧める（PyTorch と同じ）
- `on_stop` は `state_dict()` が返す状態を変えない。正常に終わった後の木を、終了を求めた時点の状態に保つため（[状態の取得](execution-model.md#状態の取得)）
- `state_dict` の中では、そのノードの Port は送受信を断る（K12）。状態を取るための停止を、ほかのノードからもホストからも見えなくするため
- `on_exception` は、`on_stop` だけでは正常終了と異常終了を区別できず、ロボットのアクチュエータを安全な姿勢で止めるといった処理を書けないので持つ。自分の hook の例外に対処したいだけなら、その hook の中で `try`/`except` する
- `on_exception` は引数を取らない。例外オブジェクトを渡すと、ノードがほかのノードの例外の型で分岐できてしまい、局所性から外れる。例外はトレースバックを通してフレームのローカル変数を参照しており、多数のスレッドに渡すと解放されにくい。原因はログとホストに残るので、原因に応じた対処はホストが行う
- `on_pause` と `on_resume` は引数を取らない。停止の間その実行のタイマーは進まないので、その時間で測ると停止と再開は同じ時刻に起きる。停止していた実時間はダイナミクスの外の量なので、要る I/O のノードが自分で測る

次の hook は持たない。

| 持たない hook | 理由 |
| --- | --- |
| エポックの開始・終了、学習・推論モード | 継続学習の原則に反する |
| メッセージの受信ごとに呼ぶ hook | 受信を溜める必要があり、実質的に queue に戻る |
| 固定刻みの更新 | 本番の $\Delta t$ は可変。固定刻みはテストで仮想時計の側から作る |

### super の慣習

サブクラスは `__init__` の最初で `super().__init__(...)` を呼ぶ（必須。呼ばないと run の段 1 で K2）。override した hook の最初で `super()` の同じ hook を呼ぶのは慣習で、基底の hook は何もしないので呼ばなくても壊れない。docs、examples、docstring の例は常に呼ぶ形で書く。

`super().__init__()` の前の代入は、普通の代入として通る（`Component` は `__setattr__` を持たない）。呼ばなかったことは、`Node.__init__` が置く設定の属性が `__dict__` に無いことで段 1 に分かる。

## Driver

ランタイムは、ノード 1 つにつき 1 つの `Driver`（`driver.py`）のメソッド（`start` / `restore` / `update` / `pause` / `resume` / `exception` / `stop` / `capture`）を、hook 1 回につき 1 回だけ呼ぶ。Driver はどのメソッドでも同じ順で動く。

1. CUDA のノードなら、ノードの device と stream をこのスレッドの現在のものにする。自分の device 以外の CUDA device にある値を読むノード（CPU のノードを含む）は、その device ごとの副 stream もこのスレッドの現在のものにする（[CUDA](#cuda)）
2. ノード専用の `contextvars.Context` に入る
3. hook を呼ぶ。hook はノードの属性から呼ぶたびに引くので、いつインスタンス属性に差し替えても次の呼び出しから反映される
4. `on_update` と `load_state_dict` の後は、ノードの stream に積んだ仕事を待つ

この仕事は hook の外にあるので、どの hook を override しても、`super()` を呼ばなくても飛ばない。CPU のノードでは CUDA に触れない（CUDA を初期化しない）。

- `capture` は、ノードの `state_dict()` の戻り値のテンソルを detach してから `copy.deepcopy` する。状態はデータで、計算グラフを持ち越さない。複製はノードの stream の上で行い、前後で stream を待つ（どの hook が積んだ仕事も、複製の前に終わる）。正常に終わった後はホストのスレッドで走るので、`torch.cuda.stream` で呼んだスレッドの device と stream を戻す
- `capture` の間、Driver の `wires` は空になる。Port の lookup が失敗するので、`state_dict` の中の送受信は K12 で断られる
- 「いま hook を走らせている Driver」は、bindings の thread-local（`_native.current()`）が持つ。Rust が Python を呼ぶ直前に付け、戻ったら外す。Python からの入口は `current.py` の `running()` 1 つで、Port、`Node.timer`、ホスト専用の操作の検査（K12、K16）は、どれもこれを通してこの 1 つの事実を見る

ノードのクラスは純 Python で、Rust の基底クラスを継承しない。利用者の MRO と `help(Node)` には private な hook が出てこない。

## 時計

ノードは hook の中で `self.timer` を読む。返すのは、いま hook を走らせている Driver の時計（その実行の `ReadOnlyTimer`）で、1 つの実行の全ノードは同じ時計を持つ。hook の外で読むか、別のノードの `timer` を読むと K12。

- `ReadOnlyTimer` は読むだけの見方（`now()` と `time_scale()`）で、制御するメソッドを持たない。タイマーを動かすのはホストだけ（`run.timer`）
- hook の中から `Timer.sleep`・`pause`・`resume`・`set_time_scale`・`VirtualTimer.advance`、`mujou.run`、`Run` のホスト向けのメソッドを呼ぶと `RuntimeError`（K16）。ノードが時間を止めるかスケールを変えると、同じ実行のほかのノードの $\Delta t$ が変わり、Port を通らない通信路になる。ノードがタイマーで待つと、停止はタイマーを先に凍結するので状態の取得が終わらない
- 時計はその実行の終わりで止まる（[実行モデル](execution-model.md#runclock)）。終わった後の `on_exception` と `on_stop` では経過時間を測れないので、減速のような処理は実時間で測る

## 実行の周期

`on_update` をどの間隔で呼ぶかは、ノードの `period`（その実行のタイマーの秒、既定 0.01）で決める。

| `period` | 振る舞い |
| --- | --- |
| `0.0` | できるかぎり速く回す。ただし $\Delta t > 0$ になるまで（時刻が進むまで）は待つ |
| 正の数 $P$ | 更新ごとに目標の時刻を決め、タイマーの時刻がそこに達するまで待ってから呼ぶ。`on_update` の時間と起床の遅れの和が $P$ に収まる間は、平均で $P$ に 1 回更新する |

負か NaN は `Node.__init__` で断る（K5）。既定を 0.01 にし、周期を持たないノードは `period=0.0` を明示したときだけにした。周期を持たないノードは CPU のコアを使い切り、ほかのノードの計算時間を奪ってその $\Delta t$ を乱す。

目標の時刻は次のように決める。

1. 最初の目標は、最初の $\Delta t$ の起点（実行の開始の時刻、復元したなら保存した最後の更新の時刻）から $P$ 後。状態の木は目標を持たないので、復元すると目標の位相は最後の更新から数え直しになる
2. 更新したら、次の目標を「前回の目標 + $P$」にする。起きるのが少し遅れても次の目標は動かない
3. 更新したときに次の目標にすでに達していたら（$P$ 以上遅れたら）、次の目標をその更新の時刻 + $P$ に数え直す。遅れを取り戻すために続けて回すことはしない

待つのはランタイムで、ノードが hook の中で `sleep` して周期を作ることはしない。

- その実行のタイマーの時刻で測るので、時間のスケールと仮想時計に従う
- 停止と終了の要求ですぐに起きる。停止の間はタイマーが止まるので、停止の時間は周期に数えない
- 手動モード（`ManualRun.step`）は周期を使わない。$\Delta t > 0$ なら更新する

$\Delta t$ は周期ではなく、前回の更新からの実際の経過時間である。遅れれば $P$ より長く、遅れた次の更新では短い（常に $\Delta t > 0$）。コアは $\Delta t$ の上限を持たない。打ち切ると経過時間が失われ、連続時間の定式化からずれるからである。そのため `on_update` は長い $\Delta t$ でも安定でなければならない。ノードの内側で刻みを分割すると自分の状態の陽的 Euler は安定になるが、隣のノードとの陽的な結合（読んだメッセージを $\Delta t$ の間固定する）は安定にならない。それが不安定になるノードは、失う時間と引き換えに自分で $\Delta t$ を打ち切ってよい（`mujou.pc` のノードは `max_dt` で打ち切る。[mujou.pc](pc.md#dt-の打ち切り)）。

### pamiq-core との違い

pamiq-core の `SleepIntervalAdjustor` は、step の後に「前回の待ちが明けた時刻 + interval」まで眠り、起きた時刻から次を数える。計算時間が周期に含まれる点と、遅れを取り戻さない点は同じにした。次の 3 点は変えた。

- 次の目標を、起きた時刻ではなく前回の目標から数える。起きた時刻から数えると起床の遅れが周期ごとに積み重なる（macOS の実測で、周期 10 ms のノードが約 80 Hz でしか回らなかった）
- 最初の更新は開始から $P$ 後に行う。開始の時刻では $\Delta t = 0$ で、呼ぶ意味が無い
- 待ち時間から引く定数の `offset` は持たない。計算時間と起床の遅れは、前回の目標から数えることで補われる

## 状態

状態の規則の正本は `Node` の docstring。ここには理由を書く。

状態に入るのは、テンソルの属性（`nn.Parameter` を含む）、`mujou.Stateful` の属性（`nn.Module`、`pc.LearnClock`、束縛した optimizer など。クラスそのものは除く）、`register_state` した名前、そして乱数生成器の状態である。どれも取得と復元のときに `__dict__` から決め、最後に代入した値で決まる。

- `mujou.Stateful` は `state_dict` と `load_state_dict` を抽象メソッドに持つ ABC。継承で名目上の型にし、メソッドの名前で判定するダックタイピングはしない（2026-10-23、ユーザーの決定）。メソッドを書き忘れたクラスは作った時点で `TypeError` になる。継承できない他のライブラリの型は `Stateful.register(cls)` で登録し、mujou は `nn.Module` を登録する
- `state_dict` と `load_state_dict` を持つだけで `Stateful` でないオブジェクトは、状態に入らない（黙って落ちる）。検出するには名前を見るダックタイピングに戻るので、ガードは置かない

- `nn.Module` と同じ線引き（テンソルと部品は状態、Python の属性は設定）にした。設定（コンストラクタの引数から作る時定数など）は状態に入れない。設定まで状態にすると、引数を変えて作り直したネットワークに古い木を戻したとき新しい値が黙って上書きされ、状態から外す仕組みが要り、I/O のハンドルやロガーで取得が壊れる
- 実行中に変わる普通の値（カウンタ、最後に見た時刻）は `register_state` で加える。まだ代入していない名前は K30（綴りの誤りは、`__dict__` から決める以上黙って漏れる）。値は `torch.load(weights_only=True)` で読める型にする
- 乱数生成器の状態は、既定の `state_dict` が `"generator"` のキーで必ず含める。`generator` は property なので利用者の属性と衝突しない
- 既定の `load_state_dict` は strict で、キーの集合が一致することを求める（K22）。テンソルは shape を照合して `copy_` し、`Stateful` は `load_state_dict` を呼び、`register_state` した値は `copy.deepcopy` を代入する。オブジェクトは差し替えないので、`on_start` で取った参照は復元後の値を指し、勾配を記録する leaf は leaf のまま。全部を検査してからコピーする原子性は持たない。失敗すれば `NetworkError` で実行が終わるので「何も変わらない」ことに意味が無い
- 2 つのノードが同じテンソル、同じ `Stateful`、module の同じ Parameter・buffer を状態に持つことは、段 1 で断る（K24）。2 つのノードから in place で書かれると、free-threaded ではデータ競合になり、黙って誤った結果になる。見つけるのは同じオブジェクトだけで、view による部分的な共有はサポートしない
- 状態を自分で選ぶノードは、`state_dict` と `load_state_dict` の両方を override する。`super().state_dict()` の戻り値を拡張し、`super().load_state_dict` には自分で足したキーを除いて渡す
- 状態は `__init__` で作り、`add_`・`addmm_` などでその場で更新する。ステップごとに大きなテンソルを確保すると、多数のスレッドで動かしたときにメモリの確保が律速になる（[性能の基準値](research/benchmarks.md#ノードの内側のライブラリ)）
- `requires_grad` と `.grad` は状態に入らない（`nn.Module.state_dict` と同じ）。数歩分の勾配を溜めてから更新するノードや optimizer を持つノードは、`state_dict` を override して足す

ノードのインスタンスは定義と実行の両方を担う。`__init__` で Port を宣言したインスタンスが、そのまま実行時に hook を呼ばれる。1 つのインスタンスは 1 回だけ走る（K14）。終わった後は、ノードの属性（学習した module など）を読んでよい。

## スレッド

ノードは既定でワーカーに載り、hook ごとに別のワーカーで走りうる。1 つのノードの hook は重ならず、前の hook の書き込みは次の hook から見える。

- hook の間で保たれるのは、ノードごとの `contextvars.Context`（空で作り、ホストの文脈を引き継がない）と、Driver が設定する CUDA の device と stream だけ。`threading.local`・`threading.current_thread()`・`threading.get_ident()` は hook ごとに変わりうる
- hook の中で変えたほかのスレッドごとの設定（勾配の記録、`torch.autocast` など）は、hook を抜ける前に戻す（`with` に閉じる）。戻さないと、同じワーカーで次に走るほかのノードに漏れる。設定の種類は無数にあり、フレームワークが網羅的に戻すことはしない
- スレッドごとの設定に頼るノードは `dedicated_thread=True` にして、自分のスレッドで呼ばれる `on_start` で設定する

## 勾配

フレームワークは勾配の記録を切り替えない。hook は通常の PyTorch と同じく勾配を記録し、ノードの内側の BP をそのまま書ける。パラメータの更新は `torch.no_grad()` の中で行う。勾配の要らない更新手法（PC-ALM など）は、自分の hook の中で `torch.no_grad()` を使う。

- ノードをまたぐグラフは作れない。Port は detach したコピーを送り、受け手のテンソルは `requires_grad=False` で届く。局所性のために既定で勾配を切る必要が無く、切ると BP を書く利用者に mujou 固有の書き方を強いる
- パラメータから計算した値を属性に持って次の更新で使うと、グラフが更新ごとに伸びる。detach するか `no_grad` の下で計算する
- `torch.inference_mode()` は使わない。その中で作ったテンソルは backward に使えないので、スロットから来た入力を使うノード内の BP が壊れる
- `src/mujou/` の中でノード内の autograd を書くときは `# mujou: local-autograd` を付ける（skill `locality-and-async`）。利用者のノード（examples、docs）は目印を付けない

## CUDA

ノードのデバイスは CPU と CUDA だけ（K4）。MPS など、ほかのアクセラレータはサポートしない。PyTorch の MPS は 2 スレッドから同時に使うとプロセスが落ち、複数のスレッドが並行してノードを計算する実行モデルと合わない。ほかのアクセラレータは確かめる環境が無く、stream の意味と性能も確かめられない。

CUDA のノードが自分の device の上で送ったテンソルは、スロットの中でもその device に置いたままにし、読み手は device の上でコピーして受け取る（2026-10-24。[メッセージ](messages.md#コアの中の値)）。ホストとの間を通るのは、CPU のノードとの境界と、ホストの読み書きだけになる。GPU のノード同士が正しさと実行順序の面で互いに影響しないよう、次を守る。

1. ノードごとに自分の CUDA stream を持つ（Driver が作る）。既定の stream を共有すると、送るときの同期がほかのノードの仕事まで待つ
2. 同期は自分の stream に対してだけ行う。`torch.cuda.synchronize()` は使わない
3. プロセス全体に効く設定を、ノードの中で変えない（[プロセス全体に効くもの](#プロセス全体に効くもの)）

GPU の演算器・帯域・メモリの取り合いは、CPU のコアの取り合いと同じく各ノードの $\Delta t$ の伸びとして連続時間の定式化が吸収する。

| いつ | どのスレッドで | 何を待つか | 待たないと |
| --- | --- | --- | --- |
| `send` / `send_to` の中（device に置く値を `clone` した後） | ノードの hook を走らせるスレッド | 自分の stream に積んだ仕事 | 読み手が、device の上でまだ出来上がっていない値をコピーする |
| 各 `on_update` の後 | 同上 | 同上 | CPU が GPU を追い越し、$\Delta t$ と実際に計算した時間がずれる。メッセージの正しさには要らなくなったが、この理由で残す |
| `load_state_dict` の後 | 同上 | 同上 | 起動が戻った後にホストが木を手放すと、まだ読んでいる記憶域がほかの確保に回る |
| `capture` の前後 | 制御スレッド（終わった後はホストのスレッド） | 同上 | 複製が、ほかの hook の仕事が終わる前の値か、再開後に更新した値を写す |
| 起動の前（段 2 の終わり） | `mujou.run` を呼んだスレッド | そのスレッドの、ノードが使う各 device の現在の stream | ノードが、`__init__` で確保したテンソルを確保が終わる前に使う |

- 自分の device 以外の CUDA device にある値を読むノードには、Driver がその device ごとに副 stream を作り、hook のたびに current にする（`Wiring.read_devices` が、読むスロットの書き手の device から決める）。ATen は device の間のコピーを、呼んだスレッドの元の device の current stream に積む。副 stream が無いと、ワーカーで直前に走った別のノードの stream に積まれ、ノード同士が同じ stream で絡む。`torch.cuda.set_stream` は current device をその stream の device に変えるので、自分の stream を最後に設定する。副 stream のコピーは待たない。CUDA の読み手なら ATen が自分の stream に event で繋ぎ、CPU の読み手なら `.to("cpu")` が同期のコピーだからである
- 待つときは stream 全体を `synchronize` せず、stream に event を記録してその event だけを待つ。PyTorch は `torch.cuda.Stream()` を device ごとのプール（32 本）から割り当てるので、32 を超える CUDA のノードは stream を共有する。event なら、記録より後にほかのノードが積んだ仕事を待たない
- `"cuda"` のように添字の無いデバイスは、構築したときのホストの現在のデバイスに決める
- CUDA のテンソルやモジュールは `on_start` 以降で作るよう docs で勧める。`__init__` で作っても起動の前の同期で正しく動くが、キャッシュアロケータはメモリを確保した時点の現在の stream に結び付けるので、ノードがテンソルを捨てたとき、ノードの stream の計算が終わる前にホストの確保へ回りうる
- 乱数生成器はノードの device の上に作る。生成器の状態は device の種類ごとの形式なので、CUDA のノードの状態を CPU のノードに戻すことはサポートしない（同じ形に作り直すことが S5 の前提）
- CPU と CUDA の境界（CPU のノードとの送受信、ホストの読み書き）と状態の取得の転送に、pinned memory は使っていない。使うかどうかは未決定（[未決定事項](open-decisions.md)）

## プロセス全体に効くもの

次の設定と状態はプロセス全体で共有されるので、ノードの中で変えない。要るならホスト（またはテスト）が実行の前に 1 回だけ設定する。

- `torch.manual_seed` と既定の乱数生成器。ノードの中では `self.generator` を使い、`TensorSpec.rand` にも `generator=` を渡す
- `torch.set_num_threads`、`torch.use_deterministic_algorithms`、`torch.backends.*` のフラグ
- `torch.cuda.synchronize()`、`torch.cuda.empty_cache()` など device 全体に効く操作

CPU で計算する torch の演算は、呼び出したスレッドごとに内部でスレッドを立てる。mujou は内部のスレッド数を設定しない。目安は `torch.set_num_threads(n)` の `n` について「(ワーカー数 + 専用スレッドのノード数) × n ≤ 物理コア数」で、小さな行列のノードが多いときは `n = 1` でよい。

## BP の取り込み

ノードの内側は同期的なので、BP のような forward/backward も、そのノードの中に閉じていれば許容する。外から見れば値をやり取りする 1 つのノードに過ぎない。ノードをまたいで計算グラフをつなげてはならない。

## ノード間の契約

ノード間でやり取りする値は、結合ごとの値の束として定義する。こうしておけば、ノードの大きさを変えてもノード間の契約は変わらない。

ノードをまたぐ結合の重みは**後シナプス側のノードが所有する**。前シナプス側へは $W[k,j]\,\varepsilon_k$ を結合ごとの値として送る。両端で重みのコピーを持つと、非同期に実行するうちにコピー同士がずれる（weight transport の問題）。

層内で横方向に結合する演算（softmax、LayerNorm など）も、同じ層のニューロン同士の結合を横方向の値のやり取りとして扱い、ノード間と同じ不変条件を適用する。

## 設計目標から外すもの

GPU 計算での最適性は、ノードの分け方を決める理由にしない。ニューロン単位に分割すると行列積が値のやり取りの集まりに分解されるので GPU では非効率になるが、それを理由に設計を制限しない。

## テストで確かめること

ノードの分け方とスケジュールを変えても、同じ不動点に収束することを確かめる（`tests/mujou/pc/test_layer.py`）。ニューロン単位のノードを実装したら、レイヤーノードをニューロンノードの合成として組んでも、まとめて行列演算で組んでも、同じ結果になることも確かめる。
