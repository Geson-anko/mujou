# ノード

## 定義

ノードは mujou の計算の基本単位であり、基盤となる抽象である。ノードの内側は同期的に計算し、ノード同士は非同期にやり取りする。非同期・分散の境界は、常にノードの境界と一致する。

mujou のノードは実行の単位であり、分散処理でいう「マシン 1 台」ではない。1 台のマシンの上で多数のノードが動く（[ネイティブコア](native-core.md#mn-スケジューリング)）。

局所性・非同期性の不変条件は、**ノードの間に課す**。ノードの内側の計算方法（ニューロンの合成、行列演算、BP など）は、ノードごとに自由に選べる。

## ノードの大きさ

ノードの大きさは、どのノードのクラスを書くか、使うかで決まる。設定を変えるだけでノードを分割したり統合したりはしない。対象とするのは次の 3 つのレベルである。

| レベル     | 内容                                                                   |
| ---------- | ---------------------------------------------------------------------- |
| ニューロン | 1 ニューロンを 1 ノードにする。最小のノード。future work           |
| レイヤー   | 1 レイヤーを 1 ノードにする。既定                                    |
| スタック   | 複数のレイヤーを 1 ノードにする。モデル全体を 1 ノードにしてもよい |

既定をレイヤーにしたのは、わかりやすさのためである。

### ニューロンが最小である理由

既定の更新手法 PC-ALM の更新式（活動・双対変数・重み）は、ニューロン自身の値と、シナプスでつながった相手の値だけで計算できる。そのため、ニューロン 1 個を 1 ノードにまで分割できる。

ニューロン単位のノードによる分散処理は future work とする。必要になったら、`nn.Linear` に当たるレイヤーのノードとは別のクラスとして書く。

### 設定で分割しない理由

ノードを自動で分割するには、ノードの内側の計算と、重みを誰が持つかを、フレームワークが知っていなければならない。これは、ノードの内側を自由にするという方針と合わない。

全結合のレイヤーは、重みの行が出力のニューロンごとに独立しているので、ニューロンごとに分けやすい。畳み込みは、1 つのカーネルを出力のすべての位置で共有するので、そうはいかない。出力の位置ごとにノードに分けると、各ノードがカーネルのコピーを持ち、非同期に動くうちにコピー同士がずれる（[ノード間の契約](#ノード間の契約) の weight transport と同じ問題）。カーネルを別のノードに持たせると、重みの持ち主がニューロンでなくなり、値のやり取りも増える。

### 非同期の境界と実行の配置

「ノードの大きさ」と「どう実行するか」は分けて考える。

| 軸             | 意味                                                                   | 決め方                       |
| -------------- | ---------------------------------------------------------------------- | ---------------------------- |
| 非同期の境界   | どこで最新値の読み書きになり、一貫したスナップショットを失うか         | ノードのクラスで決まる     |
| 実行の配置     | どのノードをどのワーカーで、どの順に回すか                           | 実行時に選ぶ（[ネイティブコア](native-core.md#mn-スケジューリング)） |

複数のノードを 1 本のワーカーで決まった順に、同じ $\Delta t$ で回せば、まとめて 1 つのノードのように動く。どのノードも状態とライフサイクル hook からなるので、フレームワークはノードの内側を知らなくてもこれができる。テストで全ノードを固定の $\Delta t$ で同期的に回すのも、この配置の一例である（[実行モデル](execution-model.md#テスト)）。配置を利用者が指定する API は未決定である。

### 粒度を選べるようにする理由

どの粒度が最適かは、ハードウェアと用途（ロボティクス、ニューロモーフィックなど）によって変わる。ノードを基盤にすれば、ニューロン単位の細かい非同期も、BP のような同期的な手法も、同じ枠組みで扱える。

## ライフサイクル hook

ノードは、実行時に存在する分散処理の最小単位である。ネットワークは構築時だけの構造であり、実行時の単位にはならない（[ネットワーク](network.md#構成要素)）。

ノードは、フレームワークが呼ぶ hook を override して書く。ループはフレームワークが持ち、ノードの作者は 1 ステップ分の処理だけを書く。こうするのは、次の 3 つのためである。

- M:N スケジューリング: `on_update` の 1 回が協調スケジューリングの区切りになる。作者が自分でループを書くと、そのノードはワーカープールに載せられない
- 決定的なテスト: 仮想時計で固定の $\Delta t$ のまま全ノードを決まった順に回すには、ループをフレームワークが持っている必要がある
- 言語の境界: Rust のネイティブなノードは同じ hook を trait として実装し、Python のノードは専用スレッドから同じ hook を呼ばれる

| hook                     | 呼ばれるとき                                       | 役割                                                         |
| ------------------------ | -------------------------------------------------- | ------------------------------------------------------------ |
| `on_thread_start()`      | 実行開始時に 1 回。フレームワークのスレッドの設定の後、`on_start` の直前に同じスレッドで | ノード自身のスレッドごとの設定。`super()` を呼ぶ必要はない |
| `on_start()`             | 実行開始時に 1 回。ノードを実行するスレッドの上で | 状態の確保・初期化                                           |
| `on_update(dt)`          | 自分の周期で繰り返し                               | 隣の最新値を読み、$\Delta t$ ぶん更新し、書き込む。他を待たない |
| `on_pause()`             | 停止の要求を受けて、ループの区切りで止まったとき   | I/O の一時停止など                                           |
| `on_resume()`            | 停止から再開し、次の `on_update` の前              | I/O の再開、停止中に溜まった外界の値の破棄など               |
| `on_exception()`         | どれかのノードの例外で終了するとき、全ノードに 1 回。`on_stop` の前 | アクチュエータの安全停止など、異常終了に固有の I/O の処理 |
| `on_stop()`              | 実行終了時に 1 回。例外による終了でも呼ぶ          | I/O などの資源の解放。`state_dict()` が返す状態は変えない     |
| `state_dict()`           | 状態の取得時。全ノードが止まっている間、または正常に終了した後。ノードのスレッドではなく制御スレッド（終了した後はホストのスレッド）で呼ぶので、Port は使えない | 状態を pickle できるオブジェクトの木として返す。`mujou.Node` の既定は自動で集めた状態（[状態の自動収集](#状態の自動収集)） |
| `load_state_dict(state)` | 状態の復元時。`on_start` の後、最初の `on_update` の前 | `state_dict()` が返した木から状態を戻す。`mujou.Node` の既定はその場でコピーする |

表の hook のほかに、フレームワークが自分のために使う内部の hook がある。`_on_thread_start()`（`on_thread_start` の直前に同じスレッドで）、`_after_update()`（各 `on_update` の直後に同じスレッドで）、`_restore_state(state)`（状態の復元で `load_state_dict(state)` の代わりに呼び、既定は `load_state_dict(state)` を呼ぶ）、`_capture_state()`（状態の取得で `state_dict()` の代わりに呼び、既定は `state_dict()` を返す）である。`mujou.Node` はこれらでスレッドの設定と CUDA の同期を行う（[PyTorch の利用](torch.md#実行スレッドの設定)）。利用者は override しない。公開の hook とは別なので、どの公開の hook を override しても、`super()` を呼ばなくても、設定と同期は漏れない。`_restore_state` の中の例外は `load_state_dict` と出る。CUDA の非同期のエラー（`on_update` のカーネルの device-side assert など）は `_after_update` の同期で表に出る。そのため、`NetworkError` のメッセージには `_after_update` と出るが、原因は `on_update` で積んだ仕事にある。`_capture_state` の中の例外は `state_dict` と出る。

`on_pause` と `on_resume` は引数を取らない。停止している間、グローバル時間は進まないので、グローバル時間で測ると停止と再開は同じ時刻に起きる（[停止と状態の取得・復元](execution-model.md#停止と状態の取得復元)）。必要ならその時刻はグローバルタイマーから読める。停止していた実時間の長さはダイナミクスの外の量なので、それが必要な I/O のノードは自分で測る。

どの hook が例外を投げても、システム全体を終了する（[実行モデル](execution-model.md#例外による終了)）。そのとき、例外を投げていないノードも含めて全ノードの `on_exception()` を呼ぶ。`on_stop()` だけでは通常の終了と異常な終了を区別できず、ロボットのアクチュエータを安全な姿勢で止めるといった処理を書けないからである。自分の hook の例外に対処したいだけなら、その hook の中で `try`/`except` すればよい。

`on_exception` は引数を取らない。例外オブジェクトを渡すと、ノードがほかのノードの例外の型で分岐できてしまい、局所性の原則から外れる。Rust のノードの panic には型の付いた例外オブジェクトが無く、Python と同じシグネチャにできない。例外はトレースバックを通してフレームのローカル変数を参照しており、多数のスレッドに渡すとそれらが解放されにくくなる。原因はログとホストに残るので（[実行モデル](execution-model.md#例外による終了)）、原因に応じた対処はホストが行う。

`on_stop` では、`state_dict()` が返す状態を変えない。正常に終了した後に取得する状態の木を、終了を要求した時点のものに保つためである（[状態の取得](execution-model.md#状態の取得)）。資源を解放するときも、状態として返すテンソルを手放したり 0 にしたりしない。

`state_dict()` が返す木は、pickle できれば中身を問わない。`torch.Tensor` や optimizer の状態を含めてよい。ノードが更新し続ける値への参照を返してもよい。フレームワークは停止している間に木のコピーを取ってから再開する。木をどう保存するかはユーザーが決め、フレームワークもノードもファイルを扱わない。

次の hook は持たない。

| 持たない hook                          | 理由                                                                               |
| -------------------------------------- | ---------------------------------------------------------------------------------- |
| エポックの開始・終了、学習・推論モード | 継続学習の原則（エポックを前提にしない、モードを分けない）に反する                 |
| メッセージの受信ごとに呼ぶ hook        | 受信ごとに呼ぶには受信を溜める必要があり、実質的に queue に戻る。最新値の読み書きと衝突する |
| 固定刻みの更新                         | 本番の $\Delta t$ は可変。固定刻みはテストで仮想時計の側から作る                   |

以下はイメージである。名前や書き方はこのとおりになるとは限らない。

```python
class Linear(Node):
    def __init__(self, n_in: int, n_out: int) -> None:
        # 構築時: Port を宣言するだけ
        self.prev = PrevPort(send=TensorSpec((B, n_in)), recv=TensorSpec((B, n_in)))
        self.next = NextPort(send=TensorSpec((B, n_out)), recv=TensorSpec((B, n_out)))

    def on_start(self) -> None:
        self._w = ...             # Tensor を代入すると、状態として自動で集まる
        self._h = ...

    def on_update(self, dt: float) -> None:
        x = self.prev.recv()      # 前から受け取った最新値
        fbs = self.next.recv()    # 次の相手ごとの最新値
        ...                       # dt に比例した更新
        self.next.send(h)
        self.prev.send(wt_eps)

    # state_dict / load_state_dict は既定のままで {"_w": ..., "_h": ...} を保存・復元する
```

### 状態の自動収集

`mujou.Node` は、`nn.Module` と同じく `__setattr__` をフックして状態を集める。名前の `_` の有無にかかわらず、`torch.Tensor`（`nn.Parameter` を含む）か `nn.Module` を代入した属性を、代入した順に登録する。

| 操作 | 登録 |
| --- | --- |
| Tensor か nn.Module を代入 | 登録する。登録済みの名前なら順序はそのまま |
| ほかの値（`None` を含む）で上書き | 外す |
| `del` | 外す |

Port・数値・Tensor のリストや dict は集めない。property も集めない（setter が別の名前の属性に Tensor を置けば、そちらが集まる）。

状態にする Tensor は `on_start` までに確保し、その後はその場で更新するのが基本である。後で初めて代入したものも復元できるが、その場の更新ではなく新しいテンソルになる。`on_stop` で GPU メモリを返すつもりで `self._w = None` とすると、そのキーは終了後の `state_dict()` から消える（`on_stop` は `state_dict()` が返すものを変えない、という規約に反する）。

既定の `state_dict()` は、属性名をキーにした dict を返す。値は、Tensor なら `detach()` したもの（記憶域は共有し、コピーはフレームワークが取る）、nn.Module ならその `state_dict()` である。`requires_grad` は木に入れない（`nn.Module.state_dict` と同じ）。`detach` するので、ノード内 BP のグラフにつながったテンソルでも pickle できる。

既定の `load_state_dict(state)` は、登録した Tensor へ `torch.no_grad()` の下で `copy_` し、nn.Module には `load_state_dict`（strict）を呼ぶ。どちらもその場で書き換え、オブジェクトを差し替えない。そのため `on_start` で取った参照は復元後の値を指し、`requires_grad` の leaf は leaf のまま勾配を記録し続ける。`copy_` なので dtype とデバイスは合わせられる。木にあって登録に無い Tensor（`on_start` の後で初めて代入したもの）は、木の値のコピーを新しい属性として置く（登録される）。

| 不一致 | 例外 |
| --- | --- |
| `state` や nn.Module の状態が mapping でない、登録した Tensor の値が Tensor でない | `TypeError` |
| 登録した名前が木に無い、登録に無いキーの値が Tensor でない、Tensor の shape の違い、要素が記憶域を共有する Tensor（`expand` など） | `ValueError` |
| nn.Module の状態のキーや shape がモジュールの `state_dict()` と違う | `RuntimeError`（strict な `nn.Module.load_state_dict` と同じ型） |

どれもコピーの前に確かめるので、例外のときは何も書き換えない。

自分で状態を選ぶノードは、`state_dict` と `load_state_dict` を override する。`super()` を呼んで既定の木に足してもよい（乱数生成器の状態など）。

ノードのインスタンスは、定義と実行の両方を担う。`__init__` で Port を宣言したインスタンスが、そのまま実行時に hook を呼ばれる。ネットワークを構築すると、Port は実際のスロットに結び付けられる。

更新手法を差し替えられるという要件（[更新手法](update-rules.md)）は、基盤が特定の学習則を知らないことを指す。PC-ALM のレイヤーは、`mujou.Node` を継承したクラスとして `mujou.pc` で提供すれば足りる（[更新手法](update-rules.md#実装と公開元)）。

## BP の取り込み

ノードの内側は同期的なので、BP のような forward/backward も、そのノードの中に閉じていれば許容する。外から見れば、値をやり取りする 1 つのノードに過ぎない。

ただし、ノードをまたいで計算グラフをつなげてはならない。ノードをまたぐ `.backward()` は禁止である。ノード内で autograd を使う書き方は skill `locality-and-async` を参照。

## ノード間の契約

ノード間でやり取りする値は、結合ごとの値の束として定義する。こうしておけば、ノードの大きさを変えてもノード間の契約は変わらない。

ノードをまたぐ結合の重みは、**後シナプス側のノードが所有する**。前シナプス側へは $W[k,j]\,\varepsilon_k$ を結合ごとの値として送る。両端で重みのコピーを持つと、非同期に実行するうちにコピー同士がずれる（weight transport の問題）。

層内で横方向に結合する演算（softmax、LayerNorm など）も、ニューロン単位で表せるようにする。同じ層のニューロン同士の結合を横方向の値のやり取りとして扱い、ノード間と同じ不変条件を適用する。

## 設計目標から外すもの

GPU 計算での最適性は、ノードの分け方を決める理由にしない。ニューロン単位に分割すると行列積が値のやり取りの集まりに分解されるので、GPU では非効率になる。しかし、それを理由に設計を制限しない。

mujou のコアとメッセージは GPU をサポートしない。ノードの内側で GPU を使うのはノードの自由で、その場合はノードの境界でホストとの間をコピーする（[PyTorch の利用](torch.md#gpu-の扱い)）。

## テストで確かめること

ノードの分け方とスケジュールを変えても、同じ不動点に収束することを確かめる。ニューロン単位のノードを実装したら、PC-ALM のレイヤーノードをニューロンノードの合成として組んでも、まとめて行列演算で組んでも、同じ結果になることも確かめる。
