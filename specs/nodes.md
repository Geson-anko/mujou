# ノード

## 定義

ノードは mujou の計算の基本単位であり、基盤となる抽象である。ノードの内側は同期的に計算し、ノード同士は非同期にやり取りする。非同期・分散の境界は、常にノードの境界と一致する。

mujou のノードは実行の単位であり、分散処理でいう「マシン 1 台」ではない。1 台のマシンの上で多数のノードが動く（[ネイティブコア](native-core.md#mn-スケジューリング)）。

局所性・非同期性の不変条件は、**ノードの間に課す**。ノードの内側の計算方法（ニューロンの合成、行列演算、BP など）は、ノードごとに自由に選べる。

## ノードの大きさ

ノードの大きさは、どのノードのクラスを書くか、使うかで決まる。設定を変えるだけでノードを分割したり統合したりはしない。対象とするのは次の 3 つのレベルである。

| レベル     | 内容                                                                   |
| ---------- | ---------------------------------------------------------------------- |
| ニューロン | 1 ニューロンを 1 ノードにする。最小のノード。future work           |
| レイヤー   | 1 レイヤーを 1 ノードにする。既定                                    |
| スタック   | 複数のレイヤーを 1 ノードにする。モデル全体を 1 ノードにしてもよい |

既定をレイヤーにしたのは、わかりやすさのためである。

### ニューロンが最小である理由

既定の更新手法 PC-ALM の更新式（活動・双対変数・重み）は、ニューロン自身の値と、シナプスでつながった相手の値だけで計算できる。そのため、ニューロン 1 個を 1 ノードにまで分割できる。

ニューロン単位のノードによる分散処理は future work とする。必要になったら、`nn.Linear` に当たるレイヤーのノードとは別のクラスとして書く。

### 設定で分割しない理由

ノードを自動で分割するには、ノードの内側の計算と、重みを誰が持つかを、フレームワークが知っていなければならない。これは、ノードの内側を自由にするという方針と合わない。

全結合のレイヤーは、重みの行が出力のニューロンごとに独立しているので、ニューロンごとに分けやすい。畳み込みは、1 つのカーネルを出力のすべての位置で共有するので、そうはいかない。出力の位置ごとにノードに分けると、各ノードがカーネルのコピーを持ち、非同期に動くうちにコピー同士がずれる（[ノード間の契約](#ノード間の契約) の weight transport と同じ問題）。カーネルを別のノードに持たせると、重みの持ち主がニューロンでなくなり、値のやり取りも増える。

### 非同期の境界と実行の配置

「ノードの大きさ」と「どう実行するか」は分けて考える。

| 軸             | 意味                                                                   | 決め方                       |
| -------------- | ---------------------------------------------------------------------- | ---------------------------- |
| 非同期の境界   | どこで最新値の読み書きになり、一貫したスナップショットを失うか         | ノードのクラスで決まる     |
| 実行の配置     | どのノードをどのワーカーで、どの順に回すか                           | 実行時に選ぶ（[ネイティブコア](native-core.md#mn-スケジューリング)） |

複数のノードを 1 本のワーカーで決まった順に、同じ $\Delta t$ で回せば、まとめて 1 つのノードのように動く。どのノードも状態とライフサイクル hook からなるので、フレームワークはノードの内側を知らなくてもこれができる。テストで全ノードを固定の $\Delta t$ で同期的に回すのも、この配置の一例である（[実行モデル](execution-model.md#テスト)）。

利用者が選べる配置は 2 つある。実行ごとのワーカー数は `mujou.run(..., workers=None)` で選び、既定は `min(ワーカーに載るノード数, 論理 CPU 数)`、実行時に GIL が有効なとき（`sys._is_gil_enabled()`）は `min(ワーカーに載るノード数, max(1, 論理 CPU 数 // 2))`（2026-10-19、[ベンチマーク](native-core.md#ベンチマーク)）。ノードは `Node(dedicated_thread=False)` が既定でワーカーに載り、`dedicated_thread=True` のノードだけが自分の OS スレッドで動く。どのワーカーがどのノードを回すかは期限の順に決まり、ノードはワーカーの間を移る。hook がブロッキングするノードはその間ワーカーを占有してほかのノードの $\Delta t$ を伸ばすので、`dedicated_thread=True` にする。`dedicated_thread` は `period` と同じ予約名で、読み取り専用の property `Node.dedicated_thread`（`bool`）で読む。複数のノードを決まった順に同じワーカーで回す指定は未決定（[未決定事項](open-decisions.md#実行の配置)）。

### 粒度を選べるようにする理由

どの粒度が最適かは、ハードウェアと用途（ロボティクス、ニューロモーフィックなど）によって変わる。ノードを基盤にすれば、ニューロン単位の細かい非同期も、BP のような同期的な手法も、同じ枠組みで扱える。

## ライフサイクル hook

ノードは、実行時に存在する分散処理の最小単位である。ネットワークは構築時だけの構造であり、実行時の単位にはならない（[ネットワーク](network.md#構成要素)）。

ノードは、フレームワークが呼ぶ hook を override して書く。ループはフレームワークが持ち、ノードの作者は 1 ステップ分の処理だけを書く。こうするのは、次の 3 つのためである。

- M:N スケジューリング: `on_update` の 1 回が協調スケジューリングの区切りになる。作者が自分でループを書くと、そのノードはワーカープールに載せられない
- 決定的なテスト: 仮想時計で固定の $\Delta t$ のまま全ノードを決まった順に回すには、ループをフレームワークが持っている必要がある
- 言語の境界: Rust のネイティブなノードは同じ hook を trait として実装し、Python のノードはワーカーか専用スレッドから同じ hook を呼ばれる

| hook                     | 呼ばれるとき                                       | 役割                                                         |
| ------------------------ | -------------------------------------------------- | ------------------------------------------------------------ |
| `on_start()`             | 実行開始時に 1 回。ノードの hook を走らせるスレッドの上で | 状態の確保・初期化                                           |
| `on_update(dt)`          | 自分の周期で繰り返し（[実行の周期](#実行の周期)）  | 隣の最新値を読み、$\Delta t$ ぶん更新し、書き込む。他を待たない |
| `on_pause()`             | 停止の要求を受けて、ループの区切りで止まったとき   | I/O の一時停止など                                           |
| `on_resume()`            | 停止から再開し、次の `on_update` の前              | I/O の再開、停止中に溜まった外界の値の破棄など               |
| `on_exception()`         | どれかのノードの例外で終了するとき、全ノードに 1 回。`on_stop` の前 | アクチュエータの安全停止など、異常終了に固有の I/O の処理 |
| `on_stop()`              | 実行終了時に 1 回。例外による終了でも呼ぶ          | I/O などの資源の解放。`state_dict()` が返す状態は変えない     |
| `state_dict()`           | 状態の取得時。全ノードが止まっている間、または正常に終了した後。ノードの hook を走らせるスレッドではなく制御スレッド（終了した後はホストのスレッド）で呼ぶので、Port は使えない | 状態を pickle できるオブジェクトの木として返す。`mujou.Node` の既定は自動で集めた状態（[状態の自動収集](#状態の自動収集)） |
| `load_state_dict(state)` | 状態の復元時。`on_start` の後、最初の `on_update` の前 | `state_dict()` が返した木から状態を戻す。`mujou.Node` の既定はその場でコピーする |

表の hook のほかに、フレームワークが自分のために使う内部の hook がある。`_on_enter()`（スレッドがそのノードに切り替わるたび、次の hook の直前に同じスレッドで）、`_before_hook()`（`state_dict` 以外の公開の hook の直前に毎回、`_on_enter()` の後に）、`_after_update()`（各 `on_update` の直後に同じスレッドで）、`_restore_state(state)`（状態の復元で `load_state_dict(state)` の代わりに呼び、既定は `load_state_dict(state)` を呼ぶ）、`_capture_state()`（状態の取得で `state_dict()` の代わりに呼び、既定は `state_dict()` を返す）である。`mujou.Node` はこれらでスレッドごとの設定と CUDA の同期を行う（[PyTorch の利用](torch.md#切り替えごとの設定)）。利用者は override しない。公開の hook とは別なので、どの公開の hook を override しても、`super()` を呼ばなくても、設定と同期は漏れない。内部の hook の中の例外は、それが属する公開の hook の名前で出る。`_on_enter` と `_before_hook` は次に呼ぶはずだった公開の hook、`_after_update` は `on_update`、`_restore_state` は `load_state_dict`、`_capture_state` は `state_dict` と出る。CUDA の非同期のエラー（`on_update` のカーネルの device-side assert など）は `_after_update` の同期で表に出るが、原因は `on_update` で積んだ仕事にあるので、`on_update` と出るのが正しい。

サブクラスは、継承の慣習どおり `__init__` の最初で `super().__init__()` を、override した hook の最初で `super()` の同じ hook を呼ぶ。ドキュメント・サンプル・docstring の例は常にそう書く（2026-10-17、ユーザーの決定）。呼ばなくても動くように、`mujou.Node` は `__init__` で設定する値の既定をクラスに置く。

フレームワークは起動の hook（`on_start`・`load_state_dict` と、その前に呼ぶ内部の `_on_enter`・`_before_hook`）を呼んだ後、残りの hook（`on_update`・`on_pause`・`on_resume`・`on_exception`・`on_stop` と内部の `_on_enter`・`_before_hook`・`_after_update`・`_capture_state`）の関数を 1 回だけ探して持っておく。起動の hook の中でインスタンス属性に差し替えれば反映されるが、起動の後に差し替えても反映されない。`state_dict` だけは既定の `_capture_state` が取得のたびに探すので、後で差し替えても反映される。

ノードは、自分の実行のタイマーの読み取り側を、属性 `timer` として持つ（`mujou.time.ReadOnlyTimer`。時刻は `self.timer.now()` で `Timestamp` として読み、スケールは `get_time_scale()` で読む）。元のタイマーは `mujou.run(..., timer=...)` に渡したもので、省略すればグローバルタイマーである。`on_update(dt)` の $\Delta t$ もこのタイマーで測る。`ReadOnlyTimer` は pamiq-core の `ReadOnlyController` と同じ作りで、元のタイマーの読み取りのメソッドだけを属性として写し、タイマーそのものは持たない。そのため、ノードはそこからスケールを変えたり時計を進めたり、タイマーで待ったりできない。タイマーを動かすのはホストだけで、hook の中から `Timer.sleep`・`set_time_scale`・`pause`・`resume`・`VirtualTimer.advance`・`mujou.time.sleep`・`mujou.time.set_time_scale`・`mujou.time.pause`・`mujou.time.resume` を呼ぶと `RuntimeError` になる（[グローバルタイマーの実装](execution-model.md#実装)）。hook の中から `mujou.run`・`mujou.testing.run` や、`Run` のホスト向けのメソッド（`write`・`read`・`state_dict`・`shutdown`・`join`・`step` など）を呼んでも `RuntimeError` になる。ノードは自分の Port だけでやり取りする。

`timer` は、実行がノードを起動するとき（`on_start` を含む）から読める。ホストが正常な終了を見たとき（`shutdown`・`join` などが戻ったとき）に、状態の時刻（終了を要求した時刻）で止まった `ReadOnlyTimer` に一度だけ差し替わり、以後はそれを返す。正常に終了した後にホストが取る `state_dict` の中でも同じものを読む。差し替える前にノードが取っておいた `ReadOnlyTimer` は、元のタイマーを読み続ける。実行の前と起動が断られた後に読むと `RuntimeError` になる。例外で終了したときも、ホストが終了を見た後（起動中の例外なら `mujou.run` が、実行中の例外なら `write`・`state_dict`・`shutdown` などが例外を送出した後）に読むと `RuntimeError` になる。例外が起きてからホストが終了を見るまでの間は読める。`timer` は予約された名前なので、ノードの属性に同じ名前を使わない。

`on_pause` と `on_resume` は引数を取らない。停止している間、その実行のタイマーは進まないので、その時間で測ると停止と再開は同じ時刻に起きる（[停止と状態の取得・復元](execution-model.md#停止と状態の取得復元)）。必要ならその時刻は、その実行のタイマー（`self.timer`）から読める。停止していた実時間の長さはダイナミクスの外の量なので、それが必要な I/O のノードは自分で測る。

どの hook が例外を投げても、システム全体を終了する（[実行モデル](execution-model.md#例外による終了)）。そのとき、例外を投げていないノードも含めて全ノードの `on_exception()` を呼ぶ。`on_stop()` だけでは通常の終了と異常な終了を区別できず、ロボットのアクチュエータを安全な姿勢で止めるといった処理を書けないからである。自分の hook の例外に対処したいだけなら、その hook の中で `try`/`except` すればよい。

`on_exception` は引数を取らない。例外オブジェクトを渡すと、ノードがほかのノードの例外の型で分岐できてしまい、局所性の原則から外れる。Rust のノードの panic には型の付いた例外オブジェクトが無く、Python と同じシグネチャにできない。例外はトレースバックを通してフレームのローカル変数を参照しており、多数のスレッドに渡すとそれらが解放されにくくなる。原因はログとホストに残るので（[実行モデル](execution-model.md#例外による終了)）、原因に応じた対処はホストが行う。

`on_stop` では、`state_dict()` が返す状態を変えない。正常に終了した後に取得する状態の木を、終了を要求した時点のものに保つためである（[状態の取得](execution-model.md#状態の取得)）。資源を解放するときも、状態として返すテンソルを手放したり 0 にしたりしない。

`state_dict()` が返す木は、pickle できれば中身を問わない。`torch.Tensor` や optimizer の状態を含めてよい。ノードが更新し続ける値への参照を返してもよい。フレームワークは停止している間に木のコピーを取ってから再開する。木をどう保存するかはユーザーが決め、フレームワークもノードもファイルを扱わない。

次の hook は持たない。

| 持たない hook                          | 理由                                                                               |
| -------------------------------------- | ---------------------------------------------------------------------------------- |
| エポックの開始・終了、学習・推論モード | 継続学習の原則（エポックを前提にしない、モードを分けない）に反する                 |
| メッセージの受信ごとに呼ぶ hook        | 受信ごとに呼ぶには受信を溜める必要があり、実質的に queue に戻る。最新値の読み書きと衝突する |
| 固定刻みの更新                         | 本番の $\Delta t$ は可変。固定刻みはテストで仮想時計の側から作る                   |

以下はイメージである。名前や書き方はこのとおりになるとは限らない。

```python
class Linear(Node):
    def __init__(self, n_in: int, n_out: int) -> None:
        super().__init__()
        # 構築時: Port を宣言するだけ
        self.prev = PrevPort(send=TensorSpec((B, n_in)), recv=TensorSpec((B, n_in)))
        self.next = NextPort(send=TensorSpec((B, n_out)), recv=TensorSpec((B, n_out)))

    def on_start(self) -> None:
        super().on_start()
        self._w = ...             # Tensor を代入すると、状態として自動で集まる
        self._h = ...

    def on_update(self, dt: float) -> None:
        super().on_update(dt)
        x = self.prev.recv()      # 前から受け取った最新値
        fbs = self.next.recv()    # 次の相手ごとの最新値
        ...                       # dt に比例した更新
        self.next.send(h)
        self.prev.send(wt_eps)

    # state_dict / load_state_dict は既定のままで {"_w": ..., "_h": ...} を保存・復元する
```

### 実行の周期

`on_update` をどの間隔で呼ぶかは、ノードの `period`（`Node.__init__(*, device="cpu", seed=None, period=0.01)`、読み取り専用の `Node.period`（`float`））で決める。単位はその実行のタイマーの秒である。

| `period` | 振る舞い |
| --- | --- |
| `0.0` | できるかぎり速く回す。`on_update` が戻るとすぐ次を呼ぶ。ただし $\Delta t > 0$ になるまで（時刻が進むまで）は待つ |
| 正の有限の数 $P$（既定は 0.01） | 更新ごとに目標の時刻を決め、タイマーの時刻がそこに達するまで待ってから呼ぶ。`on_update` の時間と起床の遅れの和が $P$ に収まる間は、平均で $P$ に 1 回更新する |

負・無限大・NaN は `ValueError`、`bool` は `TypeError` にする。上限は無く、ns にすると `u64::MAX`（約 584 年）を超える周期もエラーにならない。そのときは ns への変換が `u64::MAX` に飽和し、目標の時刻が上限に張り付くので、実質的に更新されない。`super().__init__()` を呼ばないノードの周期は既定の 0.01 になる。

既定を 0.01 秒にし、周期を持たないノードは `period=0.0` を明示したときだけにした（2026-10-17、ユーザーの決定）。周期を持たないノードは CPU のコアを 1 つ使い切り、ほかのノードの計算時間を奪ってその $\Delta t$ を乱す。周期を持たないノードを想定の既定にせず、必要なノードだけが明示して選ぶ。以前の既定は `None`（できるかぎり速く）だった。

`period` は `device`・`generator`・`dedicated_thread`・`timer` と同じ予約名で、サブクラスがクラス属性などで置き換えると、実行の開始で `TypeError` にする。クラス属性で既定の周期を置く書き方は認めない（2026-10-17、ユーザーの決定）。周期の指定は `__init__` の引数だけにして、検証を 1 か所に保つ。

目標の時刻は次のように決める。

1. 最初の目標は、実行の開始から $P$ 後である。復元したときは、状態を取った時点の最後の更新から $P$ 後になる。状態の木は目標を持たないので、復元すると目標の位相は最後の更新から数え直しになる。少し遅れて更新した後に状態を取ったノードは、止めずに続けた場合より次の更新が最大で $P$ 近く遅れることがある（$\Delta t$ は実際の経過時間のまま）。状態を取ってそのまま続けるとき（停止して再開するとき）は目標を保つ
2. 更新したら、次の目標を「前回の目標 + $P$」にする。起きるのが少し遅れても、次の目標は動かない
3. ただし、更新したときに次の目標（前回の目標 + $P$）にすでに達していたら（$P$ 以上遅れたら）、次の目標をその更新の時刻 + $P$ に数え直す。遅れを取り戻すために続けて回すことはしない

待ちは次のように振る舞う。周期で待つのはランタイム（専用スレッドのループか、ワーカーの timekeeper）であり、ノードが hook の中で `sleep` して周期を作ることはしない。

- その実行のタイマーの時刻で測るので、時間のスケールと仮想時計に従う。仮想時計なら、前回の更新から合計で目標まで進めたときにだけ更新する（1 回の `advance` で進める必要はない）
- 停止（状態の取得）と終了の要求で、すぐに起きる。停止している間はタイマーが止まるので、停止の時間は周期に数えない。再開した後は目標までの残りだけ待ち、まとめて回ることはない
- `on_update` にかかった時間も、起床の遅れも、周期の中に数える
- 手動モード（`mujou.testing.run` と `ManualRun.step`。テストで決まった順に 1 ステップずつ回す）では周期を使わない。$\Delta t > 0$ なら更新する

$\Delta t$ は周期ではなく、前回の更新からの実際の経過時間である。おおむね $P$ だが、遅れれば $P$ より長く、遅れた次の更新では $P$ より短い。遅れが $P$ に近いほど次の $\Delta t$ は 0 に近づく（常に $\Delta t > 0$）。$\Delta t$ の上限（`max_dt`）は今は持たない（[未決定事項](open-decisions.md#時定数)）。そのため、`on_update` は `period` より長い $\Delta t$ でも安定でなければならない。陽的な離散化で $\Delta t/\tau$ が大きすぎるなら、ノードの内側で刻みを分割する。$\Delta t$ を打ち切ると経過時間が失われ、連続時間の定式化からずれる。

#### pamiq-core との違い

pamiq-core の `SleepIntervalAdjustor`（`interaction/interval_adjustors.py`）を参照した。pamiq-core は step の後に「前回の待ちが明けた時刻 + interval」まで眠り、起きた時刻から次を数える。step の計算時間が周期に含まれる点と、遅れを取り戻さない点は同じにした。次の 3 点は変えた。

- 次の目標を、起きた時刻ではなく前回の目標から数える（2026-10-17、ユーザーの決定）。起きた時刻から数えると、起床の遅れが周期ごとに積み重なる。macOS の実測では、周期 10 ms のノードが約 80 Hz でしか回らなかった（遅れの中央値は約 2.5 ms）。前回の目標から数えれば、遅れは次の待ちで吸収され、`on_update` の時間と起床の遅れの和が $P$ に収まる間は、平均の頻度が $1/P$ に保たれる。$P$ 以上遅れたときだけ数え直すので、まとめて回ることはない
- 最初の更新は、開始から $P$ 後に行う。pamiq-core の `FixedIntervalInteraction` は開始直後に最初の step を回す。mujou の `on_update(dt)` は $\Delta t$ ぶん進める処理なので、開始時刻では $\Delta t = 0$ になり、呼ぶ意味が無い
- pamiq-core の `offset`（利用者が与える定数で、待ち時間から引いてオーバーヘッドを補う）は持たない。計算時間と起床の遅れは、目標を前回の目標から数えることで補われる

### 状態の自動収集

`mujou.Node` は、`nn.Module` と同じく `__setattr__` をフックして状態を集める。名前の `_` の有無にかかわらず、`torch.Tensor`（`nn.Parameter` を含む）か `nn.Module` を代入した属性を、代入した順に登録する。

| 操作 | 登録 |
| --- | --- |
| Tensor か nn.Module を代入 | 登録する。登録済みの名前なら順序はそのまま |
| ほかの値（`None` を含む）で上書き | 外す |
| `del` | 外す |

Port・数値・Tensor のリストや dict は集めない。property も集めない（setter が別の名前の属性に Tensor を置けば、そちらが集まる）。

状態にする Tensor は `on_start` までに確保し、その後はその場で更新するのが基本である。後で初めて代入したものも復元できるが、その場の更新ではなく新しいテンソルになる。`on_stop` で GPU メモリを返すつもりで `self._w = None` とすると、そのキーは終了後の `state_dict()` から消える（`on_stop` は `state_dict()` が返すものを変えない、という規約に反する）。

既定の `state_dict()` は、属性名をキーにした dict を返す。値は、Tensor なら `detach()` したもの（記憶域は共有し、コピーはフレームワークが取る）、nn.Module ならその `state_dict()` である。`requires_grad` は木に入れない（`nn.Module.state_dict` と同じ）。`detach` するので、ノード内 BP のグラフにつながったテンソルでも pickle できる。

既定の `load_state_dict(state)` は、登録した Tensor へ `torch.no_grad()` の下で `copy_` し、nn.Module には `load_state_dict`（strict）を呼ぶ。どちらもその場で書き換え、オブジェクトを差し替えない。そのため `on_start` で取った参照は復元後の値を指し、`requires_grad` の leaf は leaf のまま勾配を記録し続ける。`copy_` なので dtype とデバイスは合わせられる。木にあって登録に無い Tensor（`on_start` の後で初めて代入したもの）は、木の値のコピーを新しい属性として置く（登録される）。

| 不一致 | 例外 |
| --- | --- |
| `state` や nn.Module の状態が mapping でない、登録した Tensor の値が Tensor でない | `TypeError` |
| 登録した名前が木に無い、登録に無いキーの値が Tensor でない、Tensor の shape の違い、要素が記憶域を共有する Tensor（`expand` など） | `ValueError` |
| nn.Module の状態のキーや shape がモジュールの `state_dict()` と違う | `RuntimeError`（strict な `nn.Module.load_state_dict` と同じ型） |

どれもコピーの前に確かめるので、例外のときは何も書き換えない。

自分で状態を選ぶノードは、`state_dict` と `load_state_dict` を override する。`super()` を呼んで既定の木に足してもよい（乱数生成器の状態など）。

ノードのインスタンスは、定義と実行の両方を担う。`__init__` で Port を宣言したインスタンスが、そのまま実行時に hook を呼ばれる。`mujou.run` でネットワークを走らせると、Port はその実行のスロットに結び付けられる。

更新手法を差し替えられるという要件（[更新手法](update-rules.md)）は、基盤が特定の学習則を知らないことを指す。PC-ALM のレイヤーは、`mujou.Node` を継承したクラスとして `mujou.pc` で提供すれば足りる（[更新手法](update-rules.md#実装と公開元)）。

## BP の取り込み

ノードの内側は同期的なので、BP のような forward/backward も、そのノードの中に閉じていれば許容する。外から見れば、値をやり取りする 1 つのノードに過ぎない。

ただし、ノードをまたいで計算グラフをつなげてはならない。ノードをまたぐ `.backward()` は禁止である。ノード内で autograd を使う書き方は skill `locality-and-async` を参照。

## ノード間の契約

ノード間でやり取りする値は、結合ごとの値の束として定義する。こうしておけば、ノードの大きさを変えてもノード間の契約は変わらない。

ノードをまたぐ結合の重みは、**後シナプス側のノードが所有する**。前シナプス側へは $W[k,j]\,\varepsilon_k$ を結合ごとの値として送る。両端で重みのコピーを持つと、非同期に実行するうちにコピー同士がずれる（weight transport の問題）。

層内で横方向に結合する演算（softmax、LayerNorm など）も、ニューロン単位で表せるようにする。同じ層のニューロン同士の結合を横方向の値のやり取りとして扱い、ノード間と同じ不変条件を適用する。

## 設計目標から外すもの

GPU 計算での最適性は、ノードの分け方を決める理由にしない。ニューロン単位に分割すると行列積が値のやり取りの集まりに分解されるので、GPU では非効率になる。しかし、それを理由に設計を制限しない。

mujou のコアとメッセージは GPU をサポートしない。ノードの内側で GPU を使うのはノードの自由で、その場合はノードの境界でホストとの間をコピーする（[PyTorch の利用](torch.md#gpu-の扱い)）。

## テストで確かめること

ノードの分け方とスケジュールを変えても、同じ不動点に収束することを確かめる。ニューロン単位のノードを実装したら、PC-ALM のレイヤーノードをニューロンノードの合成として組んでも、まとめて行列演算で組んでも、同じ結果になることも確かめる。
