# 性能の基準値

作り直しの各ステップが性能を落としていないかを、ここに記録した値と比べて確かめる。値は作り直しの前のコード（commit `1f1a465`）で測った。比べるときは、同じマシンで、ほかの負荷が無いときに測り直した値と比べる。

## 測った環境

- CPU: AMD Ryzen 9 7950X（16 コア 32 スレッド）、メモリ 61 GB、Linux 6.8
- Python 3.14.8（free-threaded）、torch 2.14.1+cu130
- GPU: なし。GIL ありのビルドの値も、まだ無い（環境を作ってから測る）

## 何をどの比較に使うか

| 値 | 測り方 | 比べるステップ |
|---|---|---|
| `Port.send` / `recv` の 1 回の時間 | `uv run python benchmarks/ports.py` | ステップ 5（R9: 悪化が 5% 未満） |
| M:N スケジューラの更新回数 / 秒と Δt の p99 | `uv run python benchmarks/mn_scheduler.py` | ステップ 3（R11: 専用スレッドの fast path） |
| MNIST の 1 epoch | `uv run python examples/mnist/main.py --epochs 1`（`--time-scale 1` と `2`） | ステップ 6（R12: 悪化が 5% 未満） |
| 密な y（回帰）の PC の鎖の 1 ステップの時間と更新回数 / 秒 | `uv run python benchmarks/pc_dense.py` | ステップ 6（R12: 記録だけ） |
| 状態の取得（capture）の時間 | `uv run python benchmarks/capture.py [--device cuda]` | ステップ 9（R10: 素の dict の木と GPU のノード） |

## MNIST の 1 epoch

`examples/mnist/main.py --epochs 1`（784-256-256-10、B = 64、S = 32、tau.h = 4 ms、4 workers）。実データ（`~/.cache/mujou/mnist`）で測った。

time scale 1 では、ホストが各バッチを S × period = 32 ms（実時間）見せるので、学習の時間は 938 バッチ × 32 ms ≒ 30 s でほぼ決まる。計算が遅くなったことは、epoch の時間より先に、ノードの更新回数と dt の分布に出る。time scale 2 では最初の層（784 入力）が周期に追いつかなくなり始めるので、計算の悪化が epoch の時間と l1 の更新回数に出る。

| time scale | 学習の時間（PC-ALM） | 1 バッチ | prequential | test | l1 / l2 / out の更新回数 | l1 の dt（50/90/99%、周期） | BP の学習の時間 |
|---|---|---|---|---|---|---|---|
| 1 | 30.4 s | 32.42 ms | 92.32% | 96.50% | 35,316 / 35,317 / 35,449 | 1 / 1.25 / 1.25 | 0.8 s |
| 2 | 15.3 s | 16.32 ms | 92.34% | 96.49% | 30,567 / 35,353 / 35,634 | 1.25 / 1.25 / 2 | 0.8 s |

| 64 | pool w=16 | 0.63M〜0.89M | 1.05M〜1.22M | 0.11〜0.16 | 0.08〜0.11 |
| 256 | pool | 0.54M | 0.71M | 0.55 | 0.42 |
| 1024 | pool | 0.48M〜0.49M | 0.62M | 2.30〜2.37 | 1.81 |

- プールが速くなったのは、ノードを戻したワーカーがほかのワーカーを起こさなくなったため。前は戻すたびに `notify_one` で 1 本を起こしていたが、戻したワーカーは自分ですぐキューを見るので、起きたワーカーは空のキューを見て眠り直すだけだった。今は、仕事を取った後に残りがあるときだけ起こす（`sched.rs` の `run_work`、`Shared::schedule`）。最初の版の測定では、プールの M=8 が前より 15〜20% 遅かった（1.10M〜1.18M）。前の bindings は hook の戻り値を `Python::attach` の外で落としていて、pyo3 がその参照の解放をプロセス全体の参照の pool（mutex 1 つ）に回していた。この偶然の直列化が、無駄な起こし合いを和らげていた。
- period 0.01 は、すべての構成で 1/period の 100% を保つ（前と同じ）。addmm と tanh も、おおむね上の表（基準値）と同じかそれ以上の値になる。tanh の M=64 のプールだけは、交互に 3 回ずつ測って 3〜5% 低い（既定のワーカー数で 216k〜222k から 208k〜212k、w=16 で 233k〜244k から 225k〜227k）。上の基準値の表（202k と 224k）の範囲には収まり、p99 は同じか良い。M=256 では差が無い。
- `switch` の 1 ノードは 0.732 から 0.301 µs/update、2 ノードの交互は 1.511 から 1.180 µs/update になった。
- ノードが 1 つのレーン（専用スレッドと、ノードが 1 つのプール）は、コマンドが変わるまで制御の lock を取らずに更新する。前の専用スレッドも lock を取らなかったが、全ノードの `last_update_ns` を 1 つの配列に並べていて、専用スレッドどうしが同じキャッシュラインに書いていた。ノードごとのレコードにまとめてそれが無くなったことが、専用スレッドが速くなった主な理由とみている（確かめてはいない）。
- GIL を有効にした実行（3.14t に `PYTHON_GIL=1`。既定のワーカー数は半分の 16）でプールを交互に 2 回ずつ測ると、light の M=8 は 0.21M から 0.23M、M=64 と tanh は前と同じ範囲（light M=64 で 0.13M〜0.16M、tanh M=64 で 79k〜89k。どちらの版も同じ幅で揺れる）。

## ステップ 6 の前（carry のある実装。R12 の密な y の基準値）

`benchmarks/pc_dense.py` を、carry を廃止する前の作業ツリー（ステップ 5 の後）で測った。B = 64 の `Input` → 784-256 tanh の `Layer` → 256-256 tanh の `Layer` → `Output` の鎖に、1 つのサンプルを書いて学習させる。y は 2 通り。

- ラベル: `(B,)` の int64 で、MNIST と同じ形。出力は 10 次元、損失は `pc.cross_entropy`

manual は `mujou.testing.run` の 1 ステップ（4 ノードを 1 回ずつ、1 スレッドで更新する）の時間で、2000 ステップを 5 回測った中央値と最小値。free は、全ノードの period を 0 にして 4 ワーカーで 3 秒走らせたときの、ノードごとの更新回数 / 秒（5 回の中央値）。
