# 性能の基準値

作り直しの各ステップが性能を落としていないかを、ここに記録した値と比べて確かめる。値は作り直しの前のコード（commit `1f1a465`）で測った。比べるときは、同じマシンで、ほかの負荷が無いときに測り直した値と比べる。

## 測った環境

- CPU: AMD Ryzen 9 7950X（16 コア 32 スレッド）、メモリ 61 GB、Linux 6.8
- Python 3.14.8（free-threaded）、torch 2.14.1+cu130
- GPU: 2026-10-21 までは無し。GPU の値（R10・R12・R13、CUDA のメッセージを device に置いた後）は、同じマシンに NVIDIA GeForce RTX 4090（24 GB、`cuda:0`）と RTX 4060（8 GB、`cuda:1`）を付けて測った。計測は `cuda:0`（CUDA のメッセージの測定は `cuda:1` も）

## 何をどの比較に使うか

| 値 | 測り方 | 比べるステップ |
|---|---|---|
| `Port.send` / `recv` の 1 回の時間 | `uv run python benchmarks/ports.py` | ステップ 5（R9: 悪化が 5% 未満） |
| M:N スケジューラの更新回数 / 秒と Δt の p99 | `uv run python benchmarks/mn_scheduler.py` | ステップ 3（R11: 専用スレッドの fast path） |
| MNIST の 1 epoch | `uv run python examples/mnist/main.py --epochs 1`（`--time-scale 1` と `2`） | ステップ 6（R12: 悪化が 5% 未満） |
| 密な y（回帰）の PC の鎖の 1 ステップの時間と更新回数 / 秒 | `uv run python benchmarks/pc_dense.py` | ステップ 6（R12: 記録だけ） |
| 状態の取得（capture）の時間 | `uv run python benchmarks/capture.py [--device cuda]` | ステップ 9（R10: 素の dict の木と GPU のノード） |

## MNIST の 1 epoch

`examples/mnist/main.py --epochs 1`（784-256-256-10、B = 64、S = 32、tau.h = 4 ms、4 workers）。実データ（`~/.cache/mujou/mnist`）で測った。

time scale 1 では、ホストが各バッチを S × period = 32 ms（実時間）見せるので、学習の時間は 938 バッチ × 32 ms ≒ 30 s でほぼ決まる。計算が遅くなったことは、epoch の時間より先に、ノードの更新回数と dt の分布に出る。time scale 2 では最初の層（784 入力）が周期に追いつかなくなり始めるので、計算の悪化が epoch の時間と l1 の更新回数に出る。

| time scale | 学習の時間（PC-ALM） | 1 バッチ | prequential | test | l1 / l2 / out の更新回数 | l1 の dt（50/90/99%、周期） | BP の学習の時間 |
|---|---|---|---|---|---|---|---|
| 1 | 30.4 s | 32.42 ms | 92.32% | 96.50% | 35,316 / 35,317 / 35,449 | 1 / 1.25 / 1.25 | 0.8 s |
| 2 | 15.3 s | 16.32 ms | 92.34% | 96.49% | 30,567 / 35,353 / 35,634 | 1.25 / 1.25 / 2 | 0.8 s |

CUDA の送受信（scratch のスクリプト。manual run で書き手と読み手を交互に 3000 回 step し、後半 2500 回の中央値。読み手の recv の時間は、GPU の読み手なら自分の stream の同期まで含む）。前は、同じビルドで `Wire` が `to_core` に device を渡さない（ホストのメモリを経由する、変更前の経路）ように差し替えたもの。`cuda:1`（RTX 4060）は専用。`cuda:0`（RTX 4090）は測定中、ほかのプロセスが 65〜69% 使っていたので、小さいメッセージの値は 140 µs 前後の同期の待ちに埋もれた。各 2 回の範囲。

- 同じ GPU のノードの間は、100 万要素で send + recv が 2.9 ms から 0.06 ms になった。小さいメッセージは同期の遅延が支配的で、差は小さい
- CPU の読み手には、D2H が send から recv へ移る。100 万要素では合計が 1.7 ms から 1.4 ms に減るが、小さいメッセージでは合計が約 17 µs 増える（書き手の stream の待ちと、読み手の D2H の同期の 2 回になる）。2026-10-25 に、CUDA のノードが読まないポートは device に置かない（send でホストへ移す）ようにして解消した。同じスクリプトで `cuda:1 → CPU` を前（`device=None`）と後で交互に 2 回ずつ測ると、send 18.8〜19.0 / 18.3〜19.2 µs、recv 4.4〜4.7 / 3.3〜4.5 µs（64 要素）、send 1561〜1564 / 1562〜1563 µs、recv 87 / 87〜91 µs（100 万要素）で、差は測定の揺れの中。`cuda:1 → cuda:1` は 100 万要素で send 30〜31 µs、recv 31〜32 µs のまま
- P2P の無い 2 枚（4090 と 4060。`torch.cuda.can_device_access_peer` が False）の間の recv は、ドライバがホストを中継するので変わらない。send の D2H は無くなる
- ホストを経由しないことは、`tests/mujou/test_port.py` の `test_a_message_between_cuda_nodes_skips_host_memory` が `torch.profiler` の Memcpy の端点で確かめる

## M:N スケジューラの比較

ワーカープールに載せる設計と既定のワーカー数を決めたときの測定。`benchmarks/mn_scheduler.py` を Apple M4 Pro（14 コア = 性能コア 10 + 効率コア 4、SMT なし、macOS 26.5、torch 2.14.1）で回した。ノードの負荷は `on_update` 1 回あたり、軽い Python のカウンタ（約 0.6 µs）、`addmm_`（384×384、約 65 µs）、`tanh`（32768 要素、約 78 µs）の 3 通り。torch の内部スレッドは 1 本。

| 項目 | 専用スレッド（1:1） | ワーカー（N = 14） |
| --- | --- | --- |
| スレッド数（M = 1024） | 1027 | 17 |
| 周期 0.01 s の達成率の最小（`tanh`、M = 256 / 1024、3.14t） | 43% / 0% | 97% / 86% |
| $\Delta t$ の最大（`tanh`、周期 0.01 s、M = 1024、3.14t） | 81 s | 0.10 s |
| 周期 0.01 s の達成率の中央値（軽い負荷、M = 1024、GIL あり） | 1% | 81% |

- M が論理コア数以下なら、両者の更新頻度は同程度。M が大きいと、専用スレッドではノードの間の不公平が大きく、届かないノードが出る。ワーカーは期限の早い順に回すので、全ノードの頻度がそろう
- コンテキストスイッチの数は、ワーカーにしても桁では減らない。周期のあるノードでは更新ごとにワーカーが眠って起きるため。減るのは、ワーカーの数を減らしたとき（軽い負荷・M = 256・周期 0.01 s で、14 本なら約 1.6 万回/s、1 本なら約 100 回/s）
- 制御の lock は、軽い負荷の周期 0 では律速になる。ワーカーを 7 本以上にすると全体で約 36 万回/s に頭打ちし、ワーカー 1 本（約 80 万回/s）より遅い。`tanh` の負荷では待つ取得は 4〜6% で、約 78 µs の更新に対してワーカーがコア数以下なら 3% 以下、コア数の 2 倍で約 15% になる。小さなネイティブのノードを載せるときに、ワーカーごとのキューと work stealing を検討する
- timekeeper の起こしすぎを直す前は、周期 0.01 s のノード 64 個に周期 0 のノード 2 個を混ぜると、タイマーの waiter の起こしが毎秒 18〜21 万回、スイッチが毎秒 40〜43 万回だった。直した後は起こしが 0 回、スイッチが毎秒約 7 万回、周期 0 のノードの更新頻度が 7〜8 倍
- 既定のワーカー数: free-threaded では、`tanh` の更新頻度がワーカー 14 本（= 論理コア数）で最大（7 本の約 1.45 倍、28 本より約 8% 速い）。GIL ありでは 7〜8 本で最大になり、10 本以上で約半分に落ちる（GIL の取り合い）。`addmm_` は Apple silicon の行列演算器をコアのクラスタで共有するため、2 本を超えるとほとんど伸びない。この機械は SMT が無く、論理コア数と物理コア数の差は測れていない

## ノードの内側のライブラリ

ノードの内側で使うライブラリを選ぶため、PC-ALM の隠れ層 1 つ分の `on_update` を多数のスレッドから同時に呼ぶ速さを測った。

- 1 ステップ: 隣の値 2 つをコピーして読む → 連続時間形を陽的 Euler で 1 回進める → 自分の値 2 つをコピーして書く。バッチ 1、f32、重みは n × n。各スレッドが自分専用のノードを 1 つ持ち、スロットのコストは含まない
- 環境: Python 3.14t（GIL 無効）、torch 2.14.1、jax 0.11.2。AMD Ryzen 9 7950X（16 コア 32 スレッド）、RTX 4090。各条件 3 回の中央値

全スレッドの合計で 1 秒あたりに進んだステップ数（torch は状態をその場で更新する版）:

| 条件 | torch | jax（`jit`） |
| --- | --- | --- |
| CPU、n=32、16 スレッド | 329k | 52k |
| CPU、n=256、16 スレッド | 322k | 47k |
| CPU、n=1024、1 スレッド | 5.6k | 3.0k |
| CPU、n=1024、16 スレッド | 36.9k | 1.8k |
| GPU、n=1024、8 スレッド（ノードごとの stream） | 44.1k | 8.4k |
| GPU、n=4096、1 スレッド | 6.1k | 1.4k |

- JAX は、XLA の設定（非同期ディスパッチ・内部スレッド数）を変えても、合計が 4〜8 スレッドで頭打ちになった。スレッド数が論理コア数に達すると 1 ステップ 10 ms まで落ちた。GPU でも stream を分けられないので、スレッド数にかかわらず合計が一定だった。このため JAX は採らない
- torch は、状態をその場で更新するかどうかで大きく変わった。新しいテンソルを確保する書き方では、CPU、n=1024、16 スレッドの合計が 1.1k に落ちた（その場で更新すると 36.9k）
- GPU でノードごとに stream を分けると、既定の stream を共有するより約 2 倍速かった（n=1024、8 スレッド）
- torch でも、スレッド数を論理コア数（32）まで増やすと、16 スレッドのときより遅くなった
- CUDA のノードの待ちで、stream 全体の `synchronize` の代わりに event を記録してその event を待つと、1 回の同期が約 1 µs 長くなる。RTX 4090 で、64・256 ノードを 16 ワーカーで走らせた更新の速さは、測定の揺れの中で変わらなかった
