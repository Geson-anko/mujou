# 性能の基準値

作り直しの各ステップが性能を落としていないかを、ここに記録した値と比べて確かめる。値は作り直しの前のコード（commit `1f1a465`）で測った。比べるときは、同じマシンで、ほかの負荷が無いときに測り直した値と比べる。

## 測った環境

- CPU: AMD Ryzen 9 7950X（16 コア 32 スレッド）、メモリ 61 GB、Linux 6.8
- Python 3.14.8（free-threaded）、torch 2.14.1+cu130
- GPU: なし。GIL ありのビルドの値も、まだ無い（環境を作ってから測る）

## 何をどの比較に使うか

| 値 | 測り方 | 比べるステップ |
|---|---|---|
| `Port.send` / `recv` の 1 回の時間 | `uv run python benchmarks/ports.py` | ステップ 5（R9: 悪化が 5% 未満） |
| M:N スケジューラの更新回数 / 秒と Δt の p99 | `uv run python benchmarks/mn_scheduler.py` | ステップ 3（R11: 専用スレッドの fast path） |
| MNIST の 1 epoch | `uv run python examples/mnist/main.py --epochs 1`（`--time-scale 1` と `2`） | ステップ 6（R12: 悪化が 5% 未満） |
| 状態の取得（capture）の時間 | `uv run python benchmarks/capture.py [--device cuda]` | ステップ 9（R10: 素の dict の木と GPU のノード） |

## MNIST の 1 epoch

`examples/mnist/main.py --epochs 1`（784-256-256-10、B = 64、S = 32、tau.h = 4 ms、4 workers）。実データ（`~/.cache/mujou/mnist`）で測った。

time scale 1 では、ホストが各バッチを S × period = 32 ms（実時間）見せるので、学習の時間は 938 バッチ × 32 ms ≒ 30 s でほぼ決まる。計算が遅くなったことは、epoch の時間より先に、ノードの更新回数と dt の分布に出る。time scale 2 では最初の層（784 入力）が周期に追いつかなくなり始めるので、計算の悪化が epoch の時間と l1 の更新回数に出る。

| time scale | 学習の時間（PC-ALM） | 1 バッチ | prequential | test | l1 / l2 / out の更新回数 | l1 の dt（50/90/99%、周期） | BP の学習の時間 |
|---|---|---|---|---|---|---|---|
| 1 | 30.4 s | 32.42 ms | 92.32% | 96.50% | 35,316 / 35,317 / 35,449 | 1 / 1.25 / 1.25 | 0.8 s |
| 2 | 15.3 s | 16.32 ms | 92.34% | 96.49% | 30,567 / 35,353 / 35,634 | 1.25 / 1.25 / 2 | 0.8 s |
