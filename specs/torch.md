# PyTorch の利用

mujou は、ノードの内側の計算に PyTorch を全面的に採用する。この文書では、モジュールの構成と、PyTorch を使うノードの方針・ノードの基底クラス `mujou.Node` の仕様を定める。

> 状態: `mujou.Node` は実装済み（2026-10-16）。Port の読み書きの実装は [ネットワーク](network.md#port-の読み書き) を参照。

## モジュールの構成

| モジュール | torch への依存 | 中身 |
| --- | --- | --- |
| `mujou._core._native` | しない | Rust の拡張モジュール。コアの Python インターフェース。値のバッファ・スロット・コアのノード `Node`・スケジューラ・グローバルタイマー・DLPack での受け渡しなど |
| `mujou._core` のほか（`spec` / `port` / `network` / `node` / `session`） | する | `TensorSpec`・Port・Network・`mujou.Node` の実装と、Port での `torch.Tensor` の読み書き |
| `mujou` / `mujou.time` | する | 利用者に公開する名前（`mujou._core` から再公開する） |
| `mujou.pc`（予定） | する | PC-ALM のノード |

torch は mujou の必須の依存である。実装は private な `mujou._core` パッケージに集め、その中の拡張モジュール `mujou._core._native` だけは torch を import しない。コアを特定のテンソルライブラリに依存させないためである（[ネイティブコア](native-core.md#メッセージの値の型)）。

`mujou._core` は private なパッケージで、利用者は直接使わない。`TensorSpec` など利用者が使うものは、mujou のトップレベル（`mujou.*`）に公開する。利用者がやり取りする値は `torch.Tensor` だけで、コアの中の値の型は公開しない（[メッセージ](messages.md#値の型)）。

コアにも `Node` という名前のクラスがあるが、利用者が継承するのはトップレベルの `mujou.Node` である。`mujou.Node` はコアの `Node` を継承し、PyTorch を使う前提の設定を加えたものである。利用者が直接使うクラスなので、`Torch` のような接頭辞は付けない。

バックエンドを分けた `mujou.torch` や `mujou.jax` は、必要になったら mujou 1.0 などの正式版で検討する。それまでは torch 以外のバックエンドを想定しない。

## GPU の扱い

mujou のコアとメッセージは GPU をサポートしない。コアはスロットの値をホストのメモリにだけ置き（[メッセージ](messages.md#コアの中の値)）、デバイス上の値は持たない。`torch.Tensor` との受け渡しは CPU 上で DLPack を使い、必ずコピーする。

ノードの内側で GPU を使うかどうかは、ノードの自由である。GPU で計算するノードは、ノードの境界で device → host → device とコピーする。大きな行列の計算を CPU で行うと CPU を食い潰すので、それを GPU に逃がす手段は残しておく。

コアで GPU をサポートしない理由は次のとおり。

- スロットの値をデバイス上に置くと、スロットにバッファと CUDA event の組を持たせることになる。ストリームをまたぐ同期、バッファの再利用の安全性、タイムスタンプの意味（公開した時刻か、計算が完了した時刻か）を、すべてコアが背負うことになる
- ストリームから 1 サンプルずつ学ぶ非同期のノードでは、計算は小さな行列×ベクトル積の連続になり、もともと GPU の効率は出にくい

対象とするデバイスは CPU と CUDA である。Apple の MPS は対象にしない。

## ノード間の独立性

境界でホストへコピーするなら、GPU を使うノード同士は、正しさと実行順序の面で互いに影響しない。ただし、次の 3 つを守る必要がある。

1. ノードごとに自分の CUDA ストリームを持つ。既定のストリームを共有すると、ホストへ書き出す前の同期が、ほかのノードが積んだ仕事まで待つ
2. 同期は自分のストリームに対してだけ行う。デバイス全体を待つ `torch.cuda.synchronize()` は使わない
3. プロセス全体に効く設定や状態を、ノードの中で変えない（[プロセス全体に効くもの](#プロセス全体に効くもの)）

GPU の演算器・メモリ帯域・PCIe の帯域・GPU メモリは、全ノードで取り合う。これは CPU のコアの取り合いと同じで、各ノードの $\Delta t$ の伸びとして連続時間の定式化が吸収する（[実行モデル](execution-model.md)）。

各ステップの終わりに自分のストリームを同期するので、CPU が GPU を追い越してカーネルを積み続けることはない。グローバルタイマーで測る $\Delta t$ と、実際に計算した時間がずれない。

## mujou.Node

`mujou.Node` は、利用者が継承するノードの基底クラスである。コアの `mujou._core._native.Node` を継承する。上の 3 つの条件と、mujou で要らない機能を切る設定を、ノードの作者に代わって行う。PyTorch を使うノードは、専用スレッドで実行する（[ネイティブコア](native-core.md#mn-スケジューリング)）。

### 実行スレッドの設定

フレームワークは、ノードを実行するスレッドの上で、まず内部の hook `_on_thread_start()` を呼び、次に公開の `on_thread_start()`、`on_start()` の順に呼ぶ（[ノード](nodes.md#ライフサイクル-hook)）。`mujou.Node` は `_on_thread_start()` で次を設定する。公開の hook とは別にしたので、サブクラスが `on_thread_start` や `on_start` を override して `super()` を呼ばなくても、設定は漏れない。どれもスレッドごとの設定なので、ほかのノードには影響しない。

| 設定 | 内容 | 理由 |
| --- | --- | --- |
| 勾配の記録を止める | `torch.set_grad_enabled(False)` | mujou の更新手法は更新式を直接計算するので、autograd のグラフは要らない |
| デバイス | CUDA のときは `torch.cuda.set_device` でノードのデバイスをこのスレッドの現在のデバイスにする | `device="cuda"` と書いた確保や演算が、ノードのデバイスに載る |
| ストリーム | CUDA のときは自分の `torch.cuda.Stream` を作り、`torch.cuda.set_stream` でこのスレッドの現在のストリームにする | 以降の演算がすべて自分のストリームに積まれる |
| ステップの終わりの同期 | CUDA のときは、各 `on_update` の直後に呼ばれる `_after_update()` で自分のストリームを `synchronize` する | CPU が GPU を追い越さない |
| 乱数生成器 | ノードごとの `torch.Generator` を、渡された seed で作る | 既定の乱数生成器はプロセス全体で共有されるので、テストが決定的でなくなる |

デバイスと seed は、`mujou.Node` の構築時に `super().__init__(device=..., seed=...)` で渡す。デバイスは CPU か CUDA で、それ以外は `ValueError`。seed を省略すると、乱数生成器を決定的でない seed で作る。`super().__init__()` を呼ばないサブクラスでも動く。そのときデバイスは CPU になり、seed は省略したのと同じになる。

乱数生成器は `self.generator` で使う。ノードのスレッドの上で作るので、`on_start` より前（`__init__` の中など）に読むと `RuntimeError` になる。生成器は起動のたびに seed から作り直すので、復元しても生成器の状態は戻らない。再開後も同じ乱数列にしたいノードは、`state_dict()` に `self.generator.get_state()` を入れ、`load_state_dict()` で `set_state` する。

`_on_thread_start` はスレッドの ID（`threading.get_ident()`）を記録する。Port の `recv` / `send` は、この ID を使って、呼んだのが所有ノードのスレッドかを確かめる。あわせて、このスレッドを「hook の中」として印を付け、ネットワークのホスト用のメソッドを呼べないようにする。

`_on_thread_start`・`_after_update`・`_restore_state`・`_capture_state` は、コアの `Node` が持つフレームワーク用の内部の hook である（[ノード](nodes.md#ライフサイクル-hook)）。利用者の hook とは別なので、`on_thread_start`・`on_start`・`on_update`・`load_state_dict`・`state_dict` を override しても、インスタンス属性で置き換えても、設定と同期は漏れない。

`state_dict()` は、ノードのスレッドではなく制御スレッドで、ノードが止まっている間に呼ばれる。正常に終了した後は、`state_dict()` を呼んだホストのスレッドで呼ばれる。これらのスレッドでは勾配の記録の設定は効かない。ランタイムは `state_dict()` を直接は呼ばず、`_capture_state()` を呼ぶ。`mujou.Node` の `_capture_state()` は、CUDA のときは次の順で同期する。

1. `with torch.cuda.stream(自分のストリーム):` の下で、まず自分のストリームを同期する。`on_update` に限らず、`on_start`・`load_state_dict`・`on_pause` などのどの hook が積んだ仕事も、ここで終わる
2. `state_dict()` を呼ぶ。中で作るコピーは自分のストリームに積まれる
3. もう一度自分のストリームを同期してから返す

CUDA のときにどこで何を同期するかを次の表にまとめる。どの同期も、自分のストリームか、そのスレッドが自分で積んだ仕事だけを待つ。同期するのはネットワークのノードが使うデバイスだけで、使っていない GPU に CUDA のコンテキストを作らない。

| いつ | どのスレッドで | 何を同期するか | 同期しないと |
| --- | --- | --- | --- |
| 各 `on_update` の直後（`_after_update`） | ノードのスレッド | 自分のストリーム | CPU が GPU を追い越し、$\Delta t$ と実際に計算した時間がずれる |
| 状態の取得（`_capture_state`） | 制御スレッド（終了した後はホストのスレッド） | 自分のストリーム（上の 1〜3） | `state_dict()` が、ほかの hook の仕事が終わる前の値を返す |
| 状態の取得で、木をコピーした後、ノードを再開する前 | 制御スレッド（終了した後はホストのスレッド） | 制御スレッドの現在のストリーム | 再開したノードがその場で更新した重みが、木のコピーに混ざる |
| 復元で、`mujou.run(..., state=...)` が木をコピーした後 | `mujou.run` を呼んだホストのスレッド | そのスレッドの現在のストリーム | ノードが、コピーが終わる前の値を使う |
| 復元で、ノードの `load_state_dict` の後（`_restore_state`） | ノードのスレッド | 自分のストリーム | `mujou.run` が戻った後にホストが木を手放すと、ノードのストリームがまだ読んでいる記憶域を、キャッシュアロケータがほかの確保に回す |
| `mujou.run` がノードを起動する前 | `mujou.run` を呼んだホストのスレッド | そのスレッドの現在のストリーム | ノードが、`__init__` で確保した Tensor を確保が終わる前に使う |

`mujou.run` が同期するのは、`mujou.run` を呼んだスレッドのストリームだけである。ほかのホストのスレッドで確保した Tensor は、そのスレッドで同期してから `mujou.run` する。

PyTorch は `torch.cuda.Stream()` をデバイスごとのプール（32 本）から順に割り当てる。そのため、1 つのデバイスに 32 を超える CUDA のノードを置くと、複数のノードが 1 本のストリームを共有する。正しさは変わらないが、同期のときにほかのノードの仕事も待つ。

`device="cuda"` のように添字の無いデバイスを渡すと、構築したときのホストの現在のデバイスに決まる。CUDA が使えない環境で CUDA のデバイスを渡すと、構築時に `ValueError` になる。

> 状態: CUDA の経路（デバイスとストリームの設定、ステップの終わり・起動・取得・復元の同期）は、2026-10-16 に RTX 4090 と RTX 4060 の 2 枚で確かめた（torch 2.14.1+cu130、3.14t の GIL なし・あり）。テストは `tests/mujou/_core/test_node.py` と `test_network.py` の `TestCuda` で、CUDA の無い環境では skip になる。どの同期を 1 つ外しても、少なくとも 1 件のテストが落ちる。

### 境界の変換

Port の `recv()` と `send()` は `torch.Tensor` でやり取りし、コアとの変換は `mujou.Node` が受け持つ。利用者は変換を意識しない。

- 読むとき: コアのバッファの中身を、ノードのデバイスの新しい `torch.Tensor` へコピーする
- 書くとき: 値を `detach()` する（ノード内 BP の中で計算した値でも、勾配はノードをまたがない）。GPU 上の値は自分のストリームでホストへコピーし、自分のストリームだけを同期する。そのうえで、コアがプールのバッファへコピーする

転送に pinned memory を使うかどうかは、実装するときに測って決める。

### 状態

更新式を直接計算するノード（PC-ALM など）は、パラメータや活動を `requires_grad=False` のただのテンソルとして持つ。ノード内 BP を使うノードは、`nn.Module`（`nn.Parameter` を持つ）や `requires_grad=True` のテンソルを持ってよい。どれも属性に代入すれば、`mujou.Node` が状態として自動で集め、既定の `state_dict()` / `load_state_dict()` が保存・復元する（[状態の自動収集](nodes.md#状態の自動収集)）。

`requires_grad` と `.grad` は状態の木に入れない。木の Tensor は `detach()` したもので、復元は `torch.no_grad()` の下でその場の `copy_` なので、`requires_grad` の leaf は leaf のまま勾配を記録し続ける。`.backward()` で数歩分の勾配を溜めてから更新するノードは、復元すると溜めていた勾配を失い、止めずに続けた結果と一致しない。optimizer の状態（モーメントなど）も Tensor の属性ではないので自動では集まらない。どちらも、使うノードは `state_dict` を override して足す。

状態は `add_`・`sub_`・`addmm_` などでその場で更新し、ステップごとに新しいテンソルを確保しない。隣へ送る値（$W^\top\varepsilon$ など）は、重みを更新する前に計算する。大きな重みを毎ステップ確保し直すと、多数のスレッドで動かしたときにメモリの確保が律速になる（[性能の測定](#性能の測定)）。

### ノード内の BP

ノードの内側で BP を行う場合は、その部分だけを `with torch.enable_grad():` で囲み、`# mujou: local-autograd` を付ける（skill `locality-and-async`）。ノードをまたぐ `.backward()` は禁止のままである（[ノード](nodes.md#bp-の取り込み)）。

既定で `torch.inference_mode()` は使わない。その中で作ったテンソルは backward に使えないので、スロットから来た入力を使うノード内の BP がエラーになる。

## プロセス全体に効くもの

次の設定と状態はプロセス全体で共有されるので、ノードの中で変えない。必要ならホスト（またはテスト）が実行の前に 1 回だけ設定する。

- `torch.manual_seed` と既定の乱数生成器
- `torch.set_num_threads`、`torch.use_deterministic_algorithms`、`torch.backends.*` のフラグ
- `torch.cuda.synchronize()`、`torch.cuda.empty_cache()` などデバイス全体に効く操作

CPU で計算する torch の演算は、呼び出したスレッドごとに内部でスレッドを立てる。ノードの数と内部のスレッド数の積がコア数を大きく超えると、CPU を取り合って全体が遅くなる。内部のスレッド数は小さく設定しておく。

mujou は内部のスレッド数を設定しない。プロセス全体の設定なので、ホストが `mujou.run` の前に決める。目安は、CPU で計算するノードの数と `torch.set_num_threads(n)` の `n` の積が、物理コア数を超えないようにすることである。小さな行列を扱うノードが多いときは `n = 1` でよい。

## 性能の測定

2026-10-15 に、ノードの内側で使うライブラリを選ぶため、PC-ALM の隠れ層 1 つ分の `on_update` を多数のスレッドから同時に呼ぶ速さを測った。

- 1 ステップ: 隣の値 2 つをコピーして読む → 連続時間形を陽的 Euler で 1 回進める → 自分の値 2 つをコピーして書く。バッチ 1、f32、重みは n × n
- 各スレッドが自分専用のノードを 1 つ持つ。スロットのコストは含まない
- 環境: Python 3.14t（GIL 無効）、torch 2.14.1、jax 0.11.2。CPU は AMD Ryzen 9 7950X（16 コア 32 スレッド）、GPU は RTX 4090。各条件 3 回の中央値

全スレッドの合計で 1 秒あたりに進んだステップ数（torch は状態をその場で更新する版）:

| 条件 | torch | jax（`jit`） |
| --- | --- | --- |
| CPU、n=32、16 スレッド | 329k | 52k |
| CPU、n=256、16 スレッド | 322k | 47k |
| CPU、n=1024、1 スレッド | 5.6k | 3.0k |
| CPU、n=1024、16 スレッド | 36.9k | 1.8k |
| GPU、n=1024、8 スレッド（ノードごとのストリーム） | 44.1k | 8.4k |
| GPU、n=4096、1 スレッド | 6.1k | 1.4k |

わかったこと:

- JAX は、XLA の設定（非同期ディスパッチ・内部スレッド数）を変えても、合計が 4〜8 スレッドで頭打ちになった。スレッド数が論理コア数に達すると 1 ステップ 10ms まで落ちた。GPU でもストリームを分けられないので、スレッド数にかかわらず合計が一定だった。このため JAX は採らない
- torch は、状態をその場で更新するかどうかで大きく変わった。新しいテンソルを確保する書き方では、CPU、n=1024、16 スレッドの合計が 1.1k に落ちた（その場で更新すると 36.9k）
- GPU でノードごとにストリームを分けると、既定のストリームを共有するより約 2 倍速かった（n=1024、8 スレッド）
- torch でも、スレッド数を論理コア数（32）まで増やすと、16 スレッドのときより遅くなった。torch のノードを動かす専用スレッドの数は、物理コア数を超えないようにする
