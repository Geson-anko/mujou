# ネットワーク

ノードをどう組み合わせ、ノード間をどう双方向に接続するかを定める。メッセージの型とスロットは [メッセージ](messages.md) を参照。

## 構成要素

| 構成要素     | 役割                                                                                 |
| ------------ | ------------------------------------------------------------------------------------ |
| ノード     | 非同期処理の単位。ネットワークの末端の要素で、Port を宣言する                        |
| ネットワーク | ノードや別のネットワークを子として持ち、内側の Port を外向きに公開する             |
| Port         | ノードやネットワークの接続口。送るメッセージの型と受け取るメッセージの型の組を持つ |
| Channel      | 2 つの Port の間の接続 1 本。向きごとのスロット 2 本と、その両端からなる             |

ノードとネットワークは共通の基底を持つ（Composite）。どちらも Port を持ち、ネットワークは内側の Port を公開すれば、ノードと同じように Port 同士で接続できる。共通の基底が持つのは、属性に代入した Port（ネットワークでは子のノードとネットワークも）を登録する仕組みだけである（[属性の登録](#属性の登録)）。

ノードは実行時に存在する分散処理の最小単位で、ライフサイクル hook を持つ（[ノード](nodes.md#ライフサイクル-hook)）。ネットワークは構築時だけの構造で、hook を持たない。ネットワークに `on_update` を持たせると、ネットワークの単位で同期的に回すという意味が紛れ込むからである。

## define-and-run

ネットワークの構造は define-and-run で記述する。PyTorch の実行方式は define-by-run だが、mujou はこれと異なる。利用者は、PyTorch の `nn.Module` のように組み合わせて宣言的に書ける API でネットワークを記述し、最終的にスキーマオブジェクトを作る。各スロットのメッセージの型と shape は Port の spec で決まり、以後は変えない。初期値は送る側の Port の `initial`、ホストが書くスロットなら `mujou.run(inputs=)` の値で、どちらも無ければゼロである。スロットそのものは構築ではなく `mujou.run` の中で作る（[構築と実行](#構築と実行)）。

この API は `nn.Module` にたとえているだけで、`nn.Module` に相当する単位がノードになるわけではない。

`nn.Module` と同じく、ノードのインスタンスは定義と実行の両方を担う。`build()` は構造を検査して凍結し、構築した構造（`Graph`）を返す。`Graph` は宣言したネットワークとは別のオブジェクトである。`mujou.run` はノードとネットワークを受け取って構築し、その `Graph` を実行する（`Graph` を渡すと `TypeError`）。走らせると、各 Port はその実行のスロットに結び付けられ、同じノードのインスタンスが実行時に hook を呼ばれる。凍結したスキーマから、ノードを別に作り直すことはしない。

## Port

Port は向きを持たない。送るメッセージの型（send）と受け取るメッセージの型（recv）の組だけを持ち、2 つの Port は型が互いに逆向きのとき、つまり片方の send がもう片方の recv と一致するときだけ接続できる。一致を確かめる対象は、メッセージの型と各値の `TensorSpec`（shape と dtype）である。一致しなければ、`connect` を呼んだ時点でエラーになる。

Port は send と recv の一方だけを持ってもよい。send だけの Port と recv だけの Port は、メッセージの型と `TensorSpec` が一致すれば接続でき、その Channel のスロットは 1 本になる。入力を送るだけのノードや観測するだけのノードは、こうして使わない向きのスロットとメッセージを持たずに済む。

Port は未接続のまま残ってもよい。未接続の Port も、スキーマで宣言した型の値を持つスロットを持つ。ノードが未接続の Port から受け取ると、相手 1 つの Port は初期値を返し、複数の相手を取る Port は空の対応表を返す。

上流と下流、上と下の区別は、フレームワークでは決めない。PC-ALM の層の間の結合も、softmax のような層内の横方向の結合も、同じ仕組みで表す。こうして、PC-ALM 固有の上下という区別を基盤に持ち込まない。

Port は、つながる相手が 1 つか複数かを持つ。相手 1 つの Port に 2 本目の Channel を接続すると、`connect` を呼んだ時点でエラーになる。

Port は、送るメッセージと受け取るメッセージに、値とは別に付随データ（carry）を載せられる（[付随データ](#付随データ)）。

### PrevPort と NextPort

Port の宣言には 3 種類がある。

| 宣言       | 役割                                                         | 相手の数の既定 |
| ---------- | ------------------------------------------------------------ | -------------- |
| `PrevPort` | 前側の Port。慣習で `prev` と名付ける（`a.next.connect(b.prev)` の `b.prev`） | 1 つ           |
| `NextPort` | 次側の Port。慣習で `next` と名付ける（`a.next.connect(b.prev)` の `a.next`） | 複数           |
| `Port`     | 前側でも次側でもない Port                                    | 1 つ           |

分岐は次側で起きることが多いので、`NextPort` は既定で複数の相手を取る。どの宣言でも、相手の数は明示して上書きできる。たとえば合流を受けるノードは、`PrevPort` を複数と宣言する。

相手の数は宣言の時点で決まるので、受け取るときの戻り値の型（メッセージそのものか、相手ごとの対応表か）が静的に決まる。

`PrevPort` と `NextPort` は、相手の数の既定が違うだけの Port である。前側・次側という区別は、属性名 `prev` / `next` とともに読み手に向きを示す慣習で、フレームワークはそれを使って接続先を決めない。そのため、1 つのノードやネットワークがそれぞれをいくつ持ってもよい。前側や次側が無いノード（入力だけを流すノードなど）は、その宣言を持たない。

## 接続

接続は Port 同士だけで行い、`a.next.connect(b.prev)` のように書く。`connect` は Channel を 1 本作り、その両端を 2 つの Port に同時に登録する。そのため、B を A に接続した時点で、A にも B からの逆向きの経路が登録される。ネットワークは define-and-run なので、実行中に経路が増えたり減ったりすることはない。Port 自体は向きを持たないので、`a.next.connect(b.prev)` と `b.prev.connect(a.next)` は、Channel の `ends` の順が違うだけの同じ形の接続になる。

ノード同士やネットワーク同士をつなぐ書き方（`a.connect(b)` で a の `NextPort` と b の `PrevPort` をつなぐ）は、以前はあったが無くした（ユーザーの決定、2026-10-17）。ノードの入出力は複数ありうるので、コンポーネント同士をつなぐと、どの Port の経路かが曖昧になる。省略形のために「`PrevPort` と `NextPort` は直接の属性に 1 つずつまで」という制約も要っていた。Port 同士だけにすれば、どの経路かがいつも書いた行から読める。

```python
class Hidden(Node):
    def __init__(self, n_in: int, n_out: int) -> None:
        super().__init__()
        # 前へ W^T ε を送り、前から h を受け取る（相手 1 つ）
        self.prev = PrevPort(send=TensorSpec((B, n_in)), recv=TensorSpec((B, n_in)))
        # 次へ h を送り、次から W^T ε を受け取る（相手は複数）
        self.next = NextPort(send=TensorSpec((B, n_out)), recv=TensorSpec((B, n_out)))

l1, l2 = Hidden(784, 256), Hidden(256, 256)
ch = l1.next.connect(l2.prev)
```

Channel のスロット 2 本は、それぞれ書く側の端が所有する。各スロットの書き手は 1 つという原則は、分岐や合流があってもそのまま保たれる。

## 付随データ

> 状態: 実装済み（2026-10-20）。

付随データ（carry）は、値と同じメッセージに載せて経路に沿って運ぶデータである。サンプル ID・ターゲット・マスクのように、入力のサンプルに付いて先のノードまで届けたいデータに使う（PC のターゲット: [PC モジュール](pc-module.md#メッセージと-port)）。別の Port（別のスロット）で運ぶと、読み手は 2 つのスロットを別々の瞬間に読むので、値と付随データが別のサンプルの組になりうる。同じメッセージに入れておけば、読み手は常に同じサンプルの組を読む。

Port は向きごとに付随データの spec を持つ。

| 引数               | 意味                                                                                                                    |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------- |
| `recv_carry=spec`  | 受け取るメッセージに載る付随データ。相手 1 つの Port だけが持てる（相手が複数だと、どのメッセージの付随データか決まらない） |
| `send_carry=spec`  | 送るメッセージに載せる付随データ。`send` / `send_to` の `carry=` で値を渡し、値と同じくコピーする。付随データを作る側        |
| `send_carry=port`  | 同じノードの、`recv_carry` を持つ Port が最後に `recv` したメッセージの付随データを、コピーせずに載せる。中継する側          |

```python
class Relay(Node):
    def __init__(self) -> None:
        super().__init__()
        self.prev = PrevPort(recv=TensorSpec((B, 784)), recv_carry=CARRY)
        self.next = NextPort(send=TensorSpec((B, 256)), send_carry=self.prev)
```

- 「最後に `recv` したメッセージ」の付随データを中継するので、送る値の計算に使った入力と付随データが同じスナップショットになる
- `connect` は、値の spec と同じく付随データの spec も向きごとに照合する（`send_carry_spec` と相手の `recv_carry_spec`）。中継する Port の `send_carry_spec` は中継元の `recv_carry_spec` である
- 中継元は同じノードの Port に限る。ノードが読むのは自分の Port のスロットだけ、という局所性を保つためである。構築（`Network.build` と `mujou.run`）で検査し、違えば `ValueError`。Port は `__init__` の時点では所有ノードを知らないので、構築で検査する
- 中継はコアの中でバッファの参照を複製するだけで、torch もノードをまたぐ計算グラフも経由しない（[メッセージ](messages.md#付随データ)）。待ちもバリアも増えない
- `initial` は値だけを決め、付随データの初期値はゼロ（bool なら False）である。初期値を宣言する口（`initial_carry=`）は、要るまで足さない
- 最初の値が届く前の付随データ（ゼロ）は、実際に送られたゼロと区別できない。区別したいときは、付随データに有効かどうかのフィールドを入れる（PC の `mask` がこれに当たる）
- 付随データの意味（ターゲット・マスク・時刻など）はコアに持ち込まない。コアからはフィールドの列に見えるだけである

宣言の形を `carry=` 1 つ（spec なら受け取る向き、Port なら送る向き）にする案は採らなかった。付随データを作る側（送る向きの spec）も、両方の向きに付随データを持つ Port も書けないからである（2026-10-20）。

## 入れ子

ネットワークは、ノードや別のネットワークを子として持てる。ネットワークは内側の Port を自分の属性として持つことで外向きに公開し、外から見るとノードと同じように Port 同士で接続できる。慣習では、内側の前側・次側の Port を `prev`・`next` の名前で公開する（`self.prev = self.l1.prev`）。

```python
class Stack(Network):
    def __init__(self) -> None:
        super().__init__()
        self.l1 = Hidden(784, 256)
        self.l2 = Hidden(256, 256)
        self.l1.next.connect(self.l2.prev)
        self.prev = self.l1.prev         # 外向きに公開（前側）
        self.next = self.l2.next         # 外向きに公開（次側）

stack, head = Stack(), Head()
stack.next.connect(head.prev)            # stack.next は l2.next そのもの
run = mujou.run(stack, head)             # 2 つをまとめて構築して走らせる
```

入れ子は構築時の構造にとどまる。ネットワークの中のノードは、実行時もそれぞれ独立に非同期で動き、ネットワークの境界は非同期の境界を変えない。複数の層を 1 つの非同期処理の単位にしたいときは、スタックの大きさのノードとして書く（[ノード](nodes.md#ノードの大きさ)）。複数のノードを同じワーカーで決まった順に回すのは実行の配置の話で、ネットワークの構造とは別に扱う（[ノード](nodes.md#非同期の境界と実行の配置)）。

## 属性の登録

ノードとネットワークは、`nn.Module` が `_modules` と `_parameters` に登録するのと同じく、属性に代入された Port と子を代入の時点で登録する（ユーザーの決定、2026-10-17）。構築（`build`）は属性を探索せず、登録だけをたどる。

- 共通の基底 `Component` の `__init__` が、属性名から Port への対応（代入順）と、属性名から子のノード・ネットワークへの対応を用意する。`__setattr__` は、値が `Port` なら前者に、`Node` か `Network` なら後者に登録し、それ以外の値を同じ名前に代入するか `del` すると登録から外す。同じ名前に代入し直したときは、順番の位置を保つ
- `super().__init__()` の前に Port や子を代入すると `AttributeError`（`"cannot assign a port before Node.__init__() call; call super().__init__() first"`）。普通の値はその前に代入してよい
- ノードにノードやネットワークを代入すると、代入の時点で `ValueError`（`"the node Holder holds a Hidden at 'inner'; only networks hold nodes and networks"`）。以前は構築の時点で検査していた。代入の時点なら、どの行が原因かがトレースバックに出る
- 構築した木のノードとネットワークに Port や子を代入・削除する（普通の値で置き換えるのも含む）と `RuntimeError`。構築した `Graph` は登録をもとに作ったので、後から変えると両者が食い違うからである。普通の属性は構築後も自由に変えてよい。`mujou.run` が断られて構築を取り消した木は、また変えられる
- property の名前への代入は登録せず、setter が実際に代入した名前で登録する（状態の収集と同じ）
- リストや辞書に入れたノードや Port は登録されないので、ネットワークの一部にならない
- 登録の対応表は書き換えずに置き換える。`copy.copy` した浅いコピーと変更を共有しないためである（状態の収集と同じ）
- 同じ Port を 2 つの名前や 2 つのノードが持つこと、ネットワークが中に無い Port を公開すること、Port をクラス属性で宣言することは、従来どおり構築の時点で検査する。どれもノードのパスか木全体を見ないと判断できないので、構築の時点で検査する

`on_update` の中で `self.x = tensor` のように毎回代入する書き方があるので、`__setattr__` は普通の値の代入を速く保つ。普通の値では `isinstance` を 1 回（型のタプルに対して。`X | Y` の union は呼ぶたびに作られ、数倍遅い）と、登録の対応表の検索 2 回だけを行う。ノードの `__setattr__` はこれに加えて、状態の登録のために状態の名前の対応表を読み、`torch.Tensor` と `nn.Module` のタプルに対する `isinstance` を 1 回と、名前の検索を行う（[ノード](nodes.md#状態の自動収集)）。新しい名前に Tensor か Module を代入したときだけ、property かどうかの検査と登録が加わる。

## ネットワークの入力と出力

> 状態: 実装済み（2026-10-16）。名前と振る舞いは[実装](#実装)のとおりである。形は暫定で、使ってみて問題が見つかれば見直す。

ネットワークの入力と出力は、未接続の Port である。外からの入出力には 2 つの方法があり、両方を使える。どちらの方法でも、書く値と読む値は `torch.Tensor` である（[メッセージ](messages.md#値の型)）。

1. ホスト（ネットワークを動かす Python のコード）が、`mujou.run` の返す `Run` で Port を読み書きする
2. 入出力を普通のノードとして書き、ネットワークの中に置く。カメラやセンサのドライバのように、自分の周期で動いて外界と値をやり取りしたい入出力に向く。スケジューラの上で動くので、決定的なテストにも載せやすい

### 実行はバックグラウンドで行う

`mujou.run(component, *components)` はネットワークを構築してバックグラウンドで動かし始め、全ノードの起動（`on_start` と、復元するときの `load_state_dict`）が終わってその実行のタイマーが動き出したところで、実行のハンドル `Run` を返す。ノードの `on_update` は待たない。ホストのスレッドはノードの実行に使われず、以後ホストは `Run` のメソッドだけでネットワークとやり取りする。

起動が終わるまで待つのは、起動中にノードが投げた例外を `mujou.run` 自身が送出できるようにするためである。

ホストの操作は、宣言したネットワークではなく `Run` が持つ。`mujou.run` が実行するのは、宣言とは別のオブジェクトである構築した構造（`Graph`）だからである。初期値と復元する状態は、`mujou.run` の引数で渡す。ハンドルは起動が終わってから返るので、起動中のネットワークに書くことは無い。

| 操作                                  | 呼べるとき                 | 内容                                                                     |
| ------------------------------------- | -------------------------- | ------------------------------------------------------------------------ |
| `net.build()`                         | 何度でも                   | 構造と型を確定して `Graph` を返す。2 回目からは同じ `Graph` を返す       |
| `mujou.run(component, *components, timer=None, inputs=None, state=None)` | ネットワーク・ノードごとに 1 回 | 構築し、`state` を戻し、`inputs` を書き、バックグラウンドで実行を始め、全ノードの起動が終わったら `Run` を返す |
| `run.write(...)`                      | 正常な終了まで             | 未接続の Port に書き、書いた値に付いた時刻（`Timestamp`）を返す          |
| `run.read(port)`                      | いつでも                   | Port に送られた最新の値を返す                                            |
| `run.read_with_time(port)`            | いつでも                   | Port に送られた最新の値と時刻（`Timestamp`）の組を返す                   |
| `run.subscribe(port, timeout=math.inf)` | いつでも              | 呼んだ時点の最新の値と時刻を返し、以後は新しい値が書かれるたびに最新の値と時刻を返すイテレータ。`timeout` を過ぎると `TimeoutError` |
| `run.wait_for(port, condition, timeout=math.inf)` | いつでも | `condition` を満たす値が送られるまで待ち、その値と時刻の組を返す |
| `run.state_dict(timeout=30.0)`        | 実行中と、正常に終了した後 | 時刻のそろった状態の木のコピーを返す                                     |
| `run.timer`                           | いつでも                   | 実行のタイマー（渡した `timer`、無ければグローバルタイマー）を返す       |
| `run.shutdown(timeout)`               | いつでも                   | 終了を要求し、終了するまで待つ                                           |
| `run.join(timeout)`                   | いつでも                   | 終了するまで待つ                                                         |

`Run` は with 文で使え、抜けるときに `shutdown()` を呼ぶ。`Run` を作るのは `mujou.run` と `mujou.testing.run` だけで、直接呼ぶと `TypeError` になる。

```python
net = Classifier()                 # body.prev と head.teacher を未接続のまま公開
with mujou.run(net, inputs={net.prev: x0, net.teacher: y0}) as run:  # 初期値を渡して開始
    for x, y in dataset:
        run.write({net.prev: x, net.teacher: y})     # 複数の Port に同時に書く
        mujou.time.sleep(0.1)                        # 実行のタイマー（ここではグローバル）で提示時間だけ待つ
        pred, t = run.read_with_time(net.head.next)  # 最新値と時刻の組
        h1 = run.read(net.body.l1.next)              # 中間層を観測する

    for y, t in run.subscribe(net.head.next):        # 今の値の後、新しい値が来るたびに最新値を受け取る
        actuator.send(y)
state = run.state_dict()                             # 終了した時点の状態の木。保存はユーザーが決める
```

作る → 走らせる → 止める → 保存する、の順に使える。正常に終了した後の `state_dict()` は、終了した時点の状態を返す（[実行モデル](execution-model.md#状態の取得)）。例外で終了したときの状態は保存しない。

### 複数のネットワーク

複数のネットワークを 1 つの実行で走らせるときは、`Group(*components, **named)` で束ねる。`Group` も `Network` で、渡したネットワークを位置なら `"0"`, `"1"`, ...、キーワードならその名前の属性として持つ。そのためノードのパスは `"0.l1"` や `"enc.l1"` になる。`mujou.run(a, b)` は `mujou.run(Group(a, b))` と同じで、ネットワークが 1 つなら包まず、そのネットワークのパスのまま走らせる。束ねたネットワークは 1 つの実行で、1 本の時間軸を共有する。互いの停止で時間を止め合いたくないネットワークは、別のタイマーを渡して別々に走らせる（[実行モデル](execution-model.md#複数のネットワーク)）。

名前は `Group` とする（ユーザーの決定、2026-10-17。以前は `Compose`）。`Group` は渡したものを並べるだけで、互いにつながない。`Compose` は torchvision の `Compose` のように前の出力を次の入力へ渡す直列の合成に読めるので、改名した。振る舞いとパスの付け方は変えていない。

`Group` と `mujou.run` はノードもそのまま受け付け、ネットワークと混ぜてよい。ノードはネットワークの属性に置いたときと同じく、その位置か名前のパスに入る。ノード 1 つだけを試すときに、それを包むネットワークを書かずに済む。コンポーネントを 1 つだけ渡したときは、ネットワークでもノードでも包まずにそれを根にし、パスの先頭に位置を足さない（ユーザーの決定、2026-10-17。その方がシンプルだから）。`mujou.run(node)` のノードのパスは `""`、Port は `"prev"` / `"next"` などになる。根のパスが空なら、子のパスとの間に区切りの `.` を入れない。状態の木では、ノードの状態が `tree["nodes"][""]`、最後の更新の時刻が `tree["last_update_ns"][""]`、スロットが `"prev/in"`・`"next/out"` などのキーになり、pickle して復元すれば往復する。2 つ以上なら `Group(component, *components)` と同じで、位置が付く（`"0"`、`"1.l1"` など）。`Group` は 1 つでも位置を付ける（`Group(node)` のノードは `"0"`）。ホストは Port そのもので読み書きする（`run.write({node.prev: x})`）。エラーやログで根のノード（パス `""`）を指すときは、パスを出さずにクラス名で呼ぶ（`"Leaky has already run; ..."`、`"Leaky declares the port ..."`、ランタイムの `"node 'Leaky' raised in on_update"`）。

### 入力は実行の時間上の信号

スロットは最新値だけを持つので、ホストが書いた値は、次に書くまでそのまま保たれる。そのため入力は、値の列ではなく、その実行のタイマーの時間上で階段状に変わる信号 $x(t)$ として与えられる。

データセットを流すときは、1 つのサンプルをその実行の時間でどれだけ保つか（提示時間）を、ユーザーが決める。推論が平衡に近づくには、活動の時定数程度の時間がかかるからである。ホストはその実行のタイマーで待つ（グローバルタイマーなら `mujou.time.sleep`、自分のタイマーなら `Timer.sleep`。[実行モデル](execution-model.md#グローバルタイマー)）。実時間で待つと、時間のスケール・停止・テスト用の仮想時計と噛み合わない。速く回したいときは、そのタイマーを加速する。

### 書き込み

ホストが書けるのは、未接続で相手 1 つの、受ける型を持つ Port だけである。ネットワークの木の中の Port なら、ルートが属性として公開していなくても書ける。接続済みの Port には書けない。各スロットの書き手は 1 つという原則を保つためである。ホストは、外から書けるスロットの唯一の書き手になる。複数のホストのスレッドから `write` を呼んでもよく、その場合はホストの側で 1 回ずつ順に処理する。

`mujou.run(..., inputs=...)` で渡した値は、そのスロットの初期値になる。最初の入力を渡して走らせれば、ノードがゼロの入力で動き出すことはない。`mujou.run` は `state` を戻してから `inputs` を書く。書いた値の扱いと付く時刻は次のとおりである。

| 書き方                                 | 書いた値                       | 付く時刻                       |
| -------------------------------------- | ------------------------------ | ------------------------------ |
| `state` と一緒に渡した `inputs`        | 木の値を置き換え、初期値になる | 木の時刻 $T$                   |
| `state` なしで渡した `inputs`          | そのまま初期値になる           | 書いたときのその実行のタイマーの時刻 |
| 走り出した後の `run.write`             | そのまま入力になる             | 書いたときのその実行のタイマーの時刻 |

復元した系は時刻 $T$ から始まる。そのため、起動の前に書く値に起動の前のタイマーの時刻を付けると、スロットの時刻が復元した時間軸から外れる。

`run.write` は、書いた値に付いた時刻を返す。ノードが `recv_with_time` で見る時刻、状態の木の `/in` のスロットの時刻と同じ値である。`run.read_with_time` が返すのは送った時刻で、書いた時刻ではない。`inputs` に付く時刻は、`state` がなければ `mujou.run` が書いたときのタイマーの時刻で、走り出した後の `write` の時刻はそれ以上になる。`state` があれば $T$ で、タイマーも $T$ から進むので、その後の `write` の時刻も $T$ 以上になる。空の `write` は何も変えず、そのときの時刻を返す。

1 回の `write` で複数の Port に書いた値は、ある瞬間に読むどのノードから見ても一斉に切り替わる。1 つの Port に書くのは、要素が 1 つの場合として同じ仕組みで扱う。一斉の切り替えについて、保証すること・しないことは次のとおりである。

| 保証する                                                                                         | 保証しない                                                                                                                         |
| ------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------- |
| ある 1 つの瞬間に読むと、1 回の `write` の値は全部が新しいか全部が古い（新しい入力と古い教師信号が混ざらない） | ノードが 2 つの Port を順に読む間に、次の `write` が終わらないこと。`recv_with_time` の時刻が違えば、別の `write` の値である                                |
| 1 回の `write` で書いた値には、すべて同じ時刻が付く                                               | 別の実行に書いた値と同時に切り替わること。版番号は実行ごとに 1 つである                                            |

この切り替えでは、書き手も読み手も相手の更新の進み具合は待たない。待つのは、スロットごとの lock の下で値を読む・差し替える短い区間だけである。暫定的な方式として、外から書けるスロットとネットワークに次の仕組みを持たせる。

1. 実行は、外からの書き込みの版番号 $V$ を atomic な整数として 1 つ持つ
2. 外から書けるスロットは、現在の値と、版番号の付いた次の値の組を持つ
3. `write` は、書く各スロットに、版番号 $V+1$ を付けた次の値を置く（それまでの次の値は現在の値に繰り上げる）。全部置いてから $V$ を 1 つ進める
4. 読み手は、次の値の版番号が $V$ 以下なら次の値を、そうでなければ現在の値を読む

$V$ を進める 1 回の atomic な操作で、すべてのスロットが同時に切り替わる。接続済みの Port のスロットはノードが書くので、この仕組みを持たない。読み手のコストは、外から書けるスロットを読むときに atomic な読み出しが 1 回増えることだけである。

全ノードを止めてから書く方式も考えたが、書くたびに一番遅いノードの `on_update` が終わるのを待つことになり、サンプルごとに払うには重いので採らなかった。

### 読み出し

ホストはどの Port からでも、そのノードが送った値を時刻と組で読める。未接続の Port から読めばネットワークの出力になり、接続済みの Port から読めば中間層の観測になる。外からの読み出しは読み手が 1 つ増えるだけなので、ノードの動作には影響しない。

読み出しには 2 つの方法がある。

| 方法                       | 返すもの                                                                       | 向いている用途                                 |
| -------------------------- | ------------------------------------------------------------------------------ | ---------------------------------------------- |
| `read(port)` / `read_with_time(port)` | その時点の最新値（`read_with_time` は時刻との組）                     | 消費者が自分の周期で最新値を読む（制御ループなど） |
| `subscribe(port)`          | 最初に呼んだ時点の最新値と時刻を返し、以後は新しい値が書かれるたびに、その時点の最新値と時刻を返すイテレータ | 出力が更新されるたびに処理したい                 |

どちらも、外の消費者がどれだけ遅くてもノードを待たせない。`subscribe` で待つのは消費者だけで、書き手は通知するだけで消費者を待たない（待つのは、消費者が値を確かめる間にスロットの lock を持つ短い区間だけである）。消費者が遅いと途中の値は飛ばされ、最新値だけが返る。最初の値は待たずに返すので、出力がしばらく変わらなくても、消費者はすぐに今の値を受け取れる。ネットワークが正常に終了すると、`subscribe` のイテレータは終わる。

次の方法は持たない。

| 持たない方法                     | 理由                                                                                   |
| -------------------------------- | -------------------------------------------------------------------------------------- |
| 書き込みごとのコールバック       | ノードの hook を走らせるスレッドで利用者のコードが走り、消費者の遅さがそのまま書き手に伝わる         |
| すべての値の記録                 | ログには欲しいが、最初は要らない。future work とする（あふれたら古い値を捨て、書き手を待たせない形にする） |
| mujou の外のプロセスへの転送     | 複数マシンでの実行を想定していない。ROS や ZeroMQ などへの橋渡しは、ホストのスレッドか出力のノードでユーザーが書く |

### 入力と出力の対応

出力は、入力が変わってから平衡に近づくまでの時間だけ遅れて追従する。`write` の直後に `read` すると、前の入力に対する出力が返る。入力と出力を対応させたいときは、提示時間の終わりに読む。連続時間系なので、ある区間の終わりの出力を、その区間の入力に対する応答とみなす。

サンプルの ID をネットワークに流して対応させることはしない。ID を運ぶ仕組みを、すべてのノードに背負わせることになるからである。

## 分岐と合流

分岐と合流は、どちらも Port に Channel が複数つながった状態として表す。

```text
         ┌─ Channel ─ B.prev
A.next ──┼─ Channel ─ C.prev
         └─ Channel ─ D.prev
```

この形は `a.next.connect(b.prev)`、`a.next.connect(c.prev)`、`a.next.connect(d.prev)` と 3 回接続して作る。`A.next` は `NextPort` なので、既定で複数の相手を取れる。

### 送る側

複数の相手を持つ Port では、全員に同じメッセージを送る操作と、相手を指定して送る操作の両方を使える。全員に送ると、送った値はコアのバッファへ 1 回だけコピーされ、各 Channel のスロットにはそのバッファへの参照が書かれる。バッファは不変で参照カウントで管理するので、相手が何個でもそれ以上のコピーは起きない。

相手を指定して送る操作は、相手ごとに中身が違うメッセージのためにある。たとえば PC-ALM で B の前側に A1 と A2 が合流しているとき、B は相手ごとに異なる重みを使って、A1 には $W_1^\top \varepsilon$、A2 には $W_2^\top \varepsilon$ を送る。

### 受け取る側

相手 1 つの Port は、受け取ったメッセージをそのまま返す。複数の相手を持つ Port は、相手ごとのメッセージの対応表を返す。

対応表のキーは、接続のときに返る接続ごとのハンドル（Channel の端）である。同じノードと 2 本つないだ場合でも、ハンドルで区別できる。対応表の並びは接続した順に固定し、実行の再現性を保つ。

### 集約は更新手法の責任

複数の相手から受け取ったメッセージをどう束ねるかは、受け取るノードの更新手法が決める。たとえば PC-ALM なら $\sum_k W_k^\top \varepsilon_k$ のように足し合わせる。足し合わせなどの集約をフレームワークに組み込まないのは、更新手法を差し替えられるようにするためである（[更新手法](update-rules.md)）。

`mujou` のトップレベルには、利用者が使う名前として `Node`、`Network`、`Group`、`Graph`、`Run`、`Port`、`PrevPort`、`NextPort`、`Channel`、`TensorSpec`、`DictSpec`、`NetworkError`、`PauseTimeoutError`、`StateDict`、`run` がある。時間は `mujou.time` にある（`now` / `sleep` / `get_time_scale` / `set_time_scale` / `pause` / `resume` / `is_paused` / `Timer` / `ReadOnlyTimer` / `Timestamp`）。テスト用の口は `mujou.testing` にある（`run` / `ManualRun` / `VirtualTimer`、[実行モデル](execution-model.md#テスト)）。注釈に使う型は `mujou.typing` にある（`Single` / `Multi` / `MessageSpec`）。型は値を作る名前と分け、専用の名前空間に置く（ユーザーの決定、2026-10-17）。`mujou.time` と同じく `import mujou` で読み込み、標準の `typing` を隠さないよう `__all__` には入れない。

### 構築と実行

- `Network.build()` が構造を検査して凍結し、`Graph` を返す。何度呼んでも同じ `Graph` を返し、別々のスレッドから同時に呼んでも構築は 1 回だけ行う（構築は lock の下で 1 つずつ）。以後の `Port.connect` と、木の Port・ノード・ネットワークの代入と削除は `RuntimeError` になる（[属性の登録](#属性の登録)）。構築した木のノード・ネットワーク・Port には構築済みの印が付き、印の付いたものを含む木の `build` は `RuntimeError` になる（Port を持たないノードも、ほかの実行に入れられない）。`Graph` は `nodes`（パスとノードの組）と `port_path(port)` だけを公開し、直接は作れない（`TypeError`）
- `Port[S, R, M, CS, CR]` の型引数は、送る型・受ける型・相手の数（`Single` か `Multi`。既定は `Single` で、`NextPort` だけ `Multi`）・送る付随データの型・受け取る付随データの型である。付随データを持たない向きは `Never` で、どの Port でも受け取る注釈は `Port[Any, Any, Any, Any, Any]` になる。`send` と `recv` は位置でも渡せ、`multi=`・`initial=`・`send_carry=`・`recv_carry=` はキーワード専用である。`multi=True` の overload は `recv_carry` を受け取らない
- Port を作る時点の付随データの検査はすべて `TypeError` である: `send_carry` が spec・Port・`None` のどれでもない、`recv_carry` が spec でも `None` でもない、`send` が無いのに `send_carry`、`recv` が無いのに `recv_carry`、`multi=True` で `recv_carry`、`send_carry` に渡した Port が `recv_carry` を持たない
- `connect` は、spec（付随データの spec を含む）が互いに逆向きでないときと、両方の Port がどちらの向きの spec も持たない（何も流れない）ときに `TypeError` を投げる。付随データの不一致は `"A carries X with what it sends, but B expects Y"` の形で、値の不一致と並べて示す。自分自身との接続と、接続済みの相手 1 つの Port への 2 本目は `ValueError`、構築済みの木の Port は `RuntimeError` である
- `Channel` を作るのは `Port.connect` だけである。`Channel()` を直接呼ぶと `TypeError` になる。両端の Port に登録されない Channel は何も運ばないからである
- Port は、ノードの属性に初めて代入されたときに `<ノードのクラス名>.<属性名>`（例: `Shift.next`）という名前を持つ。`connect` のエラー、実行していないときの `recv` / `send` のエラー、`repr` はこの名前で Port を示す。名前は最初の代入で決まり、別名での代入やネットワークでの公開では変わらない。ノードに代入する前の Port は spec で示す。`initial` の検査は Port を作る時点で行うので、そのエラーには名前が無い（`"PrevPort initial"`）
- `mujou.run(component, *components, timer=None, inputs=None, state=None)` は、ネットワーク 1 つならそれを `build()` し、ノード 1 つならそれを根にした木を構築し、2 つ以上（ノードとネットワークを混ぜてよい）なら `Group(component, *components)` を `build()` して、その `Graph` を走らせて `Run` を返す。何も渡さないと `TypeError`（型検査でも引数が足りないと分かる）。`Node` でも `Network` でもない値があっても `TypeError`。1 つの `Graph` が走るのは 1 回で、2 回目は `RuntimeError`（同時に呼んでも走るのは 1 回）。ただし、何も起動せずに `ValueError` などで終わった `run` は数えないので、原因を取り除けば同じネットワークを同じ形で（単独なら単独で、まとめてなら同じ順にまとめて）走らせ直せる。複数のネットワークやノード 1 つを渡した `run` が断られたときは、`mujou.run` が自分で構築した木（`Group` かノードを根にした木）の構築を取り消すので、同じ形で走らせ直せる（ノードは、1 つで渡しても他と一緒に渡しても、断られた後どの形でも走らせ直せる）。ノードを 2 回走らせると、2 回目は構築がノードの構築済みの印に当たり、`RuntimeError` になる。走った（または走らせるために `mujou.run` が構築した）木の一部をもう一度構築したときの文言は、ネットワークでもノードでも `"<クラス名> has already run; create a new instance to run again"` にそろえる。利用者が `mujou.run` に渡したものは、`mujou.run` が作った `Group` のパス（`'0'` など）や根の空のパスを付けずにクラス名だけで呼ぶ。利用者が作った木の中にあるものは `"Leaky at 'node' has already run; ..."` のようにそのパスを付ける。走っていない構築済みの木（`build()` だけ呼んだネットワーク）の一部なら、従来どおり `"... belongs to a network that is already built"` である。付けるパスは `mujou.run` が作る木でのパスで、状態の木のキーと一致する（複数渡したときは `"Chain at '0.x' has already run; ..."` のように位置が付く）。並行に呼ばれた `run` のうち断られた側の文言は、`"... has already run; ..."` か `"... belongs to a network that is already built"` のどちらかになる（相手の起動が終わる前は、相手の木がまだ走ったと記録されていない）。どちらの場合も走るのは 1 回だけである。また並行の `run` では、相手が後で断られても、こちらが断られることがある。断られた `run` は走らせ直せる。単独の `build` は取り消さないので、単独で断られたネットワークは、ほかのネットワークとまとめては走らせられない。`KeyboardInterrupt` を受けた `run` は、どこで受けても走ったものとして数える。起動を待つ間ならバックグラウンドで起動が続き、インタプリタの終了時に止める。起動の前（状態の復元や入力の書き込みの途中）に受けた場合も、安全側に倒して数える。もう一度動かすには、ノードも含めて新しいインスタンスを作る（構築済みのネットワークのノードは、別のネットワークで `build` できない）
- スロットとランタイムは `build` ではなく `mujou.run` の時点で、その実行のタイマーで作る。`Session` が `Timer` を 1 つ持ち、`InputGroup`・`Outlet`・`Runtime` に同じものを渡す。正常な終了の時刻の記録もそのタイマーから読む。こうしてスロットの時刻と $\Delta t$ の時間軸が必ずそろう
- `mujou.run` の中の順序は、スロットを作り Port に結び付ける → 各ノードの周期を検査する（`period` を上書きしたサブクラスは `TypeError`）→ `state` を戻す（スロットはその場で、ノードの状態・最後の更新の時刻・タイマーは起動で）→ `inputs` を書く → 各ノードに `timer` を付ける → 起動、である
- `Group(*components, **named)` は位置のノードとネットワークを `"0"`, `"1"`, ... の属性に、キーワードのものをその名前の属性にする。`Node` でも `Network` でもない値は `TypeError`。空の名前、`.` を含む名前（パスが曖昧になる）、`_` で始まる名前、`Network` の属性名（`build` など）、位置と同じ名前は `ValueError`
- 送る spec を持つ Port は、外向きのスロット 1 本と、Channel ごとのスロットを持つ。未接続で相手 1 つの、受ける spec を持つ Port は、ホストが書くスロットを 1 本持つ。ホストが書くスロットは、実行に 1 つの版番号 $V$ を共有する
- スロットの名前は、所有ノードのパスと Port の属性名から作る。たとえば外向きは `"body.l1.next/out"`、Channel は `"body.l1.next/ch0"`（番号は書く側の Port で接続した順に 0 から）、ホストが書くスロットは `"body.l1.prev/in"`（公開した名前 `body.prev` ではなく、所有ノードのパスで付ける）である。この名前が状態の木の `"slots"` のキーになる
- スロットは書く側の Port が持ち、その Port の名前で付く。接続済みの Port が受ける値は、相手の Port の Channel のスロット（相手の名前の `/chK`）にある。たとえば `body.l1.next` に最初に接続した `body.l2.prev` が受ける値は、`"body.l1.next/ch0"` にある。`/in` を持つのは、ホストが書く未接続の Port だけである

### Port の読み書き

- `recv()` は相手 1 つなら値、複数なら `{Channel: 値}`（接続順）を返す。`recv_with_time()` は値と書かれた時刻（その実行のタイマーの `Timestamp`）の組を返す。`Timestamp` は pickle と deepcopy ができるので、ノードの状態に入れてよい（木の保存は pickle で行う。`torch.save` / `torch.load` を使うときは、`Timestamp` を含む木は `torch.load(..., weights_only=False)` で読む。`weights_only=True` では読めない）。どのタイマーの時刻かは持たないので、比べるのは同じタイマーの時刻とだけにする。どちらも毎回コアのバッファからノードのデバイスの新しい Tensor へコピーするので、受け取った Tensor をその場で書き換えても、スロットにもほかの読み手にも影響しない。`requires_grad` は False である
- 相手 1 つの Port は、相手（未接続ならホスト）がまだ書いていなければ初期値を返す。初期値は相手の Port の `initial`（無ければゼロ）、ホストが書く Port なら `inputs` の値（無ければゼロ）である（[メッセージ](messages.md#スキーマと初期値)）。相手を複数取る未接続の Port は `{}` を返す
- `has_received()` は、`recv()` が返す値が初期値ではなく書き手の書いた値かを返す。相手 1 つなら `bool`、複数なら `{Channel: bool}`（`recv` と同じキー。未接続なら `{}`）。書き手は相手のノード（`send` / `send_to`）か、ホスト（`inputs` と `run.write`）である。送った値が初期値と等しくても `True` になる。実装はコアの `Message` が持つ `sent` の印で、送った値（`Outlet.send` / `InputGroup.write`）は `True`、スロットを作ったときのゼロと `initial` は `False` である。状態の木はスロットごとに `(value, time_ns, sent)` を持ち、復元した実行は状態を取った時点の印を保つ。復元で書く `inputs` は `True` にする。時刻を番兵にする案は採らなかった。初期値の時刻（実行の開始の時刻）に送ることがあり（仮想時計で時刻を進める前に `on_start` で送るなど）、区別できないからである（2026-10-17）
- 付随データを作る Port（`send_carry=spec`）の `send(msg, carry=...)` / `send_to(channel, msg, carry=...)` は、`carry` を値と同じ検査とコピーで 1 つのメッセージに入れる。`carry` を渡さないと `TypeError`。中継する Port（`send_carry=port`）に `carry` を渡すと `TypeError` で、中継元の Port が最後に受け取ったメッセージの付随データ（`_native.Carry`）をそのまま載せる。付随データを持たない Port に `carry` を渡しても `TypeError`
- `recv_carry` を持つ Port の `Binding` は、最後に受け取ったメッセージの付随データ（`Carry`）を持つ。`recv` / `recv_with_time` のたびに、値を読んだのと同じメッセージの付随データに差し替える。`has_received` は差し替えない。最初の `recv` までは、実行を組んだ時点でその Port が読むスロットにあるメッセージの付随データ（ゼロ。復元したなら木の `"carries"` の値）である。ノードは `Message` ごと持たず `Carry` だけを持つので、値のバッファはプールへ戻る
- `carried()` は最後に受け取ったメッセージの付随データを、`carried(key)` は `DictSpec` のそのフィールドだけを、所有ノードのデバイスの新しい Tensor にコピーして返す。`recv_carry` を持たない Port と、`TensorSpec` の付随データに `key` を渡すと `TypeError`、無いキーは `KeyError`
- `send(msg)` はすべての相手に送り、外向きのスロットも更新する。`send_to(channel, msg)` はその Channel のスロットだけを更新し、外向きのスロットは変えない。そのため `send_to` だけを使う Port をホストが `read` すると、初期値（復元したなら木の値）が返る
- 送るときは値を `detach()` する。GPU の値は自分のストリームでホストへコピーし、その後コアがプールのバッファへコピーする。送った後に値を書き換えても、読み手には見えない
- `recv` / `recv_with_time` / `has_received` / `carried` / `send` / `send_to` を呼べるのは、Port を所有するノードの hook の中だけである。ほかのスレッド（ホストなど）や、ほかのノードの hook から呼ぶと `RuntimeError` になる。スロットの書き手を 1 つに保ち、ノードが読めるのを自分の Port のスロットに限るため（局所性）である。受け取った値を所有ノードのデバイスとストリームに載せるためでもある。判定はスレッド ID でなく、呼んだスレッドが今走らせているノードで行う（[切り替えごとの設定](torch.md#切り替えごとの設定)）。ワーカーはほかのノードも走らせるので、同じワーカーの上でもほかのノードの Port は呼べない。`state_dict()` も所有ノードの hook なので呼べるが、使わない（スロットは木に別に入り、送ると状態を取る最中の実行を変える）。提供するシナリオの外なので拒まない
- 新しい値が書かれるまで待つ機能は Port に持たせない。ノードが隣のノードを待つことになるからである。待つのはホストの `subscribe` だけである

### ホストの入出力

| メソッド                         | 振る舞い                                                                                                     |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `write({port: value, ...})`      | 書いた値に付いた時刻（その実行のタイマーの `Timestamp`）を返す。木の中の、未接続で相手 1 つの、受ける spec を持つ Port だけに書ける。ほかと、付随データを受け取る Port（`recv_carry`）は `ValueError`。shape の違いは `ValueError`、型と dtype の違いは `TypeError`。正常に終了した後は `RuntimeError`（ノードはもう読まない）。`mujou.run` の `inputs` も同じ検査をする |
| `read(port)` / `read_with_time(port)` | 送る spec を持つ Port の外向きのスロットの値を返す。付随データを送る Port（`send_carry`）は、付随データを捨てて値だけを返す（`subscribe` と `wait_for` も同じ）。`read_with_time` は時刻（`Timestamp`）との組を返す。Port の `recv` / `recv_with_time` と同じ分け方である（2026-10-17、ユーザーの決定。時刻を使わない読み出しが多く、`y, _ =` と書かずに済む）。値は CPU 上の新しい Tensor。最初に送られるまでは Port の `initial` かゼロ（復元したなら木の値） |
| `subscribe(port, timeout=math.inf)` | 最初に、呼んだ時点の最新値を待たずに返す（最初に送られるまでは Port の `initial` かゼロ、復元したなら木の値）。以後は新しく書かれた値を返す。待つ間に書かれた値は飛ばし、最新値だけを返す。ネットワークが正常に終了すると、イテレータも終わる（終了した後に呼ぶと、最後の値を 1 つ返して終わる）。`timeout` は反復全体にかける実時間の秒で、`subscribe` を呼んだときから数え、ループの本体にかかった時間も含む。2 つ目以降の値を返す前にこれを過ぎると、イテレータが `TimeoutError` を送出して終わり、実行は走り続ける。負か NaN なら呼んだ時点で `ValueError` |
| `wait_for(port, condition, timeout=math.inf)` | `subscribe` で最新値から順に確かめ、`condition` を満たした最初の値と時刻を返す。`timeout` を過ぎると `TimeoutError`（実行は走り続ける）、先に実行が正常に終了すると `RuntimeError`。期待した出力が届くまで待つホストの書き方を 1 行にするため（2026-10-17、例の読み直しループを置き換えた） |
| `state_dict(timeout=30.0)`       | 実行中と、正常に終了した後に呼べる。例外で終了した後は `NetworkError`。`timeout` は全ノードの停止を待つ実時間の秒で、有限の正の数（ほかは `ValueError`）。終了した後は待たず、検査だけする（[実行モデル](execution-model.md#実装-1)） |
| `timer`                          | 実行のタイマー。`mujou.run(..., timer=t)` の `t`、渡さなければグローバルタイマー（`mujou.time` が読むもの）。`ManualRun.timer` は渡したタイマーの型を保つ（2026-10-17、ユーザーの決定。自由実行でも、ホストがその実行のタイマーで待ち、時刻を比べられるように） |
| `shutdown(timeout=math.inf)` / `join(timeout=math.inf)` | 終了を要求して待つ／終了を要求せずに待つ。`shutdown` は終了の後は何もしない。`timeout` は実時間の秒で、負か NaN なら `ValueError` |
| `with mujou.run(...) as run:`    | 抜けるときに `shutdown()` を呼ぶ。本体が例外で抜けたときは本体の例外を優先し、`shutdown()` の `NetworkError` は捨てる（ノードの例外はログに出ている） |

- ホストは付随データを読み書きしない。付随データを送る Port を読むと、付随データを捨てて値だけを返す（2026-10-20、ユーザーの決定）。値の意味は付随データの有無で変わらず、捨てても読み違えない。断る案（`ValueError`）では PC の `Layer` の `next` を読めず、隠れ層の活動 `h` を見るのに状態の木を取るしかなかった。付随データを読む `Run.read_carried` は足さない。ホストに見せたい付随データは、PC の `Output` のように普通のメッセージで送る
- 付随データを受け取る Port（`recv_carry`）への書き込み（`write` と `inputs`）は `ValueError` のままにする。書き込みは値だけを渡すので、付随データを作る口が無いからである
- `mujou.run(..., state=tree)` で復元するネットワークは、木を取ったネットワークと同じノードのパスとスロット名を持たなければならない。違えば `mujou.run` は `ValueError` を送出し、何も起動しない。属性名や接続を変えると、パスとスロット名が変わる。同じタイマーでほかの実行が走っている間は、復元する `mujou.run` が `ValueError` になる。このとき何も起動しないので、ほかの実行を終了させるか別のタイマーを渡して走らせ直せる（[実行モデル](execution-model.md#復元)）
- `shutdown(timeout)` が時間内に終わらなければ `TimeoutError` を送出する。終了の要求は取り消さないので、ノードはもう更新せず、ネットワークはバックグラウンドで終了を続ける（`on_stop` がまだ走っているかもしれない）。終了を待つには `join()` を呼ぶ。`join(timeout)` が時間内に終わらなければ `TimeoutError` を送出し、ネットワークには何もしない。走っていれば走り続ける
- 例外で終了した後は、`write`・`read`・`read_with_time`・`subscribe`（とそのイテレータ）・`state_dict`・`shutdown`・`join` が `NetworkError` を送出する。`__cause__` は最初にノードが投げた例外である。例外で終了したときの状態の木は取得しない
- `mujou.run` と `Run` のメソッドはホストのためのもので、ノードの hook の中（ワーカーと専用スレッド、`state_dict()` を呼んでいる制御スレッド）から呼ぶと `RuntimeError` になる。ほかの実行のメソッドも同じである。ノードは自分の Port だけでやり取りする（局所性）。待つメソッドの場合は、待ち合いでデッドロックする代わりに `RuntimeError` になるという意味もある
- ネットワークの間の橋渡しは、ホストのスレッドで書くか、外界とやり取りする I/O のノードとして書く
- 走っている実行は、ホストが `Run` を手放しても止まらない。フレームワークは、ホストが終了を見るまで（`shutdown`・`join` など、またはほかの実行の `mujou.run`）参照を持ち、遅くともインタプリタの終了時に実行を終了させて `on_stop` を待つ。フレームワークは、non-daemon のスレッドを join するより前に実行の終了を始め、`atexit` の処理で終了が済むまで待つ。最初の `mujou.run` で daemon の監視スレッドを 1 本立て、`threading.main_thread().join()` で主スレッドの終わりを待つ。CPython はインタプリタの終了時に、主スレッドを終わった扱いにしてから non-daemon のスレッドを join するので、監視スレッドはその join より前に目を覚まし、走っている実行の終了を始める。終了は join と並行に進む。この順序は CPython の実装によるもので、文書で保証されてはいない（テストで確かめている）。そのため、`subscribe` を回すスレッドが残っていても、実行の終了とともにイテレータが終わり、プロセスは終われる。それでも、使い終わったら `shutdown()` を呼ぶ（with 文が呼ぶ）

## 未決定事項

API の形（クラス名・メソッド名）は実装したが、暫定である（[実装](#実装)）。shape の決め方も含めて、使ってみて見直す。
