# ネットワーク

ノードをどう組み合わせ、どう双方向に接続し、どう走らせるかを定める。メッセージの型とスロットは [メッセージ](messages.md)。

## 構成要素

| 構成要素 | 役割 |
| --- | --- |
| ノード（`Node`） | 非同期処理の単位。木の末端で、ポートを宣言する |
| ネットワーク（`Network`） | ノードや別のネットワークを属性に並べて繋ぐ、組み立て専用の入れ物 |
| `Group(**named)` | 名前を付けて並べるだけのネットワーク |
| `Port` / `MultiPort` | 接続点。送るメッセージの spec と受け取るメッセージの spec を持つ |
| `Channel` | 2 つのポートの間の接続 1 本。`connect` が作る |

ノードとネットワークは共通の基底 `Component` を持つ。基底が持つのは、クラスの定義の時点の検査（K1）だけで、レジストリは持たない。

ネットワークは組み立てだけの構造で、hook を持たない。ネットワークに `on_update` を持たせると、ネットワークの単位で同期的に回すという意味が紛れ込むからである。入れ子は組み立てだけにとどまり、ネットワークの中のノードは実行時もそれぞれ独立に非同期で動く。複数の層を 1 つの非同期処理の単位にしたいときは、スタックの大きさのノードとして書く（[ノード](nodes.md#ノードの大きさ)）。

利用者のオブジェクト（ノード、ポート、ネットワーク）は宣言だけを持つ。実行時の事実（スロット、Wire、走った印）は実行の側（`Run`、Driver）が持つので、走った後に凍結・解除・差し直しをする必要が無い。

## ポート

ポートは向きを持たない。送るメッセージの spec（`send`）と受け取るメッセージの spec（`recv`）の組だけを持ち、片方だけでもよい。2 つのポートは、片方の `send` がもう片方の `recv` と一致し、その逆も一致するときだけ繋げる（K10。両端の spec を示して断る）。上流と下流、上と下の区別はフレームワークでは決めない。PC-ALM の層の間の結合も、softmax のような層内の横方向の結合も、同じ仕組みで表す。

相手の数はクラスで表す。

| クラス | `recv()` | 相手の数 |
| --- | --- | --- |
| `Port` | 1 つの値 | 受け取る Port の相手は高々 1 つ。送るだけの Port は何本でも繋げ、`send` は全員に配る |
| `MultiPort` | `{Channel: 値}`（connect の順） | 同じ種類の相手をいくつでも束ねる。`send_to` で 1 本だけに送れる |

- 「受け取る Port の相手は 1 つ」は、`recv()` が 1 つの値を返すことから導かれる制約で、データの形の帰結である。受け取る Port に別の相手を繋ぐと、どちらの端から繋いでも `connect` で断る（K11。両端を見る）
- 役割の違う入力（予測と誤差など）は、`MultiPort` で束ねずに Port を分けて受ける
- 相手の数がクラスで決まるので、`recv()` の戻り値の型が静的に決まる（`tests/mujou/test_pyright.py`）
- `send` と `recv` の spec はキーワード専用。送りと受けの取り違えを、書いた行で見えるようにする
- `initial` は、そのポートが最初に `send` するまで、相手に見える値（とホストが読む値）。公開の読み取り専用 property で読める。送る側に置くのは、スロットの書き手が送る側だからである
- 属性名の `prev` / `next` は、向きを読み手に示す慣習として残す。フレームワークは使わない。上下の比喩（upper / lower）は使わない

ポートは実行時の状態を持たない。実行中の読み書きは `Wire`（label、outlet、読むスロット、device のただのデータと、recv / send の本体）が担い、ノードごとの Driver が `wires: dict[ポート, Wire]` を持つ。ポートのメソッドは、いま hook を走らせている Driver の `wires` から自分の Wire を引き、引けなければ K12。他のノードのポートを使う、ホストや `__init__` の中で使う、run の外で使う、`on_start` で作ったポートを使う、`state_dict` の中で使う、のどれもが同じ 1 つの失敗になる。

## 接続

接続はポート同士だけで、`a.next.connect(b.prev)` と書く。ノード同士をつなぐ書き方は持たない。ノードの入出力は複数ありうるので、どの経路かが曖昧になる。

各ポートは、接続を「相手 → Channel」の dict（挿入順）で持つ。`connect` は両端の dict に同じ Channel を入れる。

- 同じ相手にもう一度繋ぐと、同じ Channel を返す。「a と b は繋がっている」という集合の意味どおりで、2 本目の Channel も重複した channel の番号も表せない
- 自己接続も dict の 1 項目になるだけで、特別扱いしない
- 循環して繋いでよい
- 走り出した後の `connect` は、その実行に影響しない（宣言は次の run まで読まれず、同じインスタンスの次の run は K14 で断られる）

Channel のスロットは、それぞれ書く側の端が持つ。各スロットの書き手は 1 つという原則は、分岐や合流があっても保たれる。

## 入れ子

ネットワークは、ノードや別のネットワークを子として持てる。ネットワークに代入したポートはただの参照で、内側のポートを外向きに公開するのに使う（`self.prev = self.l1.prev`）。ホストはポートのオブジェクトそのもので読み書きするので、公開することに機能上の意味は無く、登録も所有者の検査もしない。木の外のポートを使ったときは、使ったその行で K17 / K18 が知らせる。

## 木の読み方

インスタンスの `__dict__` が、子とポートの唯一のレジストリである。run の段 1 で `tree.walk(root)` が `vars()` を代入の順に読む。

- ノードでは、`Port` / `MultiPort` の値がそのノードのポートになる
- ネットワークでは、`Node` / `Network` の値が子になり、ポートは読み飛ばす

代入のたびに登録する方式（`__setattr__`）は、属性の順序と所属を `__dict__` とレジストリの 2 か所で持ち、代入と `del` のたびに照らし合わせることになる。1 か所にすると、番兵、解除の処理、`copy.copy` 対策、property の除外、構築後の変更を拒む状態がすべて消え、`on_update` の中の `self.y = ...` も `__setattr__` を通らない。dataclass の Network もそのまま動く。失うのは、誤りを代入したその行で知らせられることだけで、代わりに段 1 で `パス.属性名` を名指しして知らせ、その run は同じインスタンスで直せる。

`walk` は何も変えない純関数で、次を検査する（[提供シナリオとガード](scenarios.md#ガード台帳)）。

- K2: `super().__init__()` を呼んでいないノード
- K3: ノードがノードかネットワークを持つ
- K6: ポート・ノード・ネットワークを list・tuple・dict に入れて代入した（1 段だけ見る）
- K13: 同じオブジェクトが木の 2 か所にある
- K15: 繋いだ相手のノードが木に無い
- K24: 2 つのノードが同じ状態を持つ

クラス属性に置いたポート・ノード・ネットワークと `__slots__` は `__dict__` に入らないので、クラスの定義の時点で断る（K1）。

## パスと label

- パスは、ルートから属性名をドットでつないだ文字列（`"body.l1"`）。ノード単体をルートにしたときのパスは `""`。状態の木のキーになる
- 表示用の呼び名は `tree.name(path)` の 1 関数が決める（`path` か、空ならルートのクラス名）
- ポートの label は `name(所有ノードのパス) + "." + 属性名`。ルートのノードのポートなら `"Leaky.prev"`、子なら `"body.l1.prev"`。エラー、スロットの名前、ログがこの 1 つの規則で名指しする
- パスをタプルにすると利用者が `tree["nodes"][("layers", "0")]` と書くことになり、負担が移るだけなので文字列にした

## ルートと Group

`mujou.run(root)` はルートを 1 つだけ受け取る。並べて走らせるときは `Group(**named)` に入れる。

- 位置引数で並べる形は持たない。持つと、同じノードのパスが組み方によって `""`、`"0"`、`"node"` と変わり、保存した木が合わなくなる
- `Network(**children)` で `Group` を兼ねる形は採らない。継承して組む使い方と、その場で並べる使い方を 1 つの基底のコンストラクタに混ぜることになる（`nn.Module` と `nn.Sequential` を分けているのと同じ理由）
- `Group` の名前には並べるだけで繋がないことを表す語を選んだ。`Compose` は直列の合成に読める
- 束ねたノードは 1 つの実行で、1 本の時間軸を共有する。止め合いたくないものは別のタイマーで別々に走らせる

## 起動の 3 段

`mujou.run` は 3 段で起動し、全ノードの `on_start`（と復元なら `load_state_dict`）が戻ってから `Run` を返す。起動中のノードの例外を `mujou.run` 自身が送出できるようにするためである。

1. **検査（何も変えない）**: `tree.walk(root)` で木を作って検査する。走った印（K14。走ったことのある最初のノードを名指しする）、`timer` と `state` の組（K23）、`workers`（K20）を見る
2. **配置（新しいオブジェクトだけを作り、書く）**: 実行のタイマーを決め（[実行モデル](execution-model.md#実行ごとのタイマー)）、`ReadOnlyTimer` を作る。`wiring.wire` が Outlet / Slot / InputGroup / Wire / Driver を作り、`initial` を書く。`state` があれば木の形を確かめて（K21）スロットに書き、inputs を書く（K17）。値の誤り（K9）は、ここでポートの label 付きで出る
3. **印と起動（取り消せない）**: 全ノードに走った印を付け（`run.py` の `WeakSet`）、`_native.start` を呼ぶ

段 2 は新しいオブジェクトだけを書くので、段 2 までに断られた run は利用者のオブジェクトを何も変えていない。同じインスタンスのまま、直してすぐに再実行できる。印を最後に付けるので巻き戻すものが無く、再実行を許すのは、そのためのコードを書いた結果ではなく順序の副産物である。段 3 で失敗するのは hook の例外と内部エラーだけで、そのときノードはもう走っているので、もう一度 run すると K14 で知らせる。

## ホストの入出力

ネットワークの入力と出力は、ホスト（ネットワークを動かす Python のコード）がポートで読み書きする。センサやアクチュエータのように自分の周期で外界とやり取りしたい入出力は、普通のノードとして書く。どちらも値は `torch.Tensor`（[メッセージ](messages.md#値の型)）。

実行はバックグラウンドで走り、ホストのスレッドはノードの実行に使われない。ホストは `Run` のメソッドだけで実行とやり取りする。メソッドの一覧と例外は `Run` の docstring にある。ホスト向けのメソッドを hook の中から呼ぶと、K16 が断る。断らなければ、ワーカーを占有してほかのノードの dt を伸ばすか、待つメソッドならデッドロックする。

### 書き込み

ホストが書けるのは、未接続で受け取る `Port` だけ（K17）。接続済みのポート、`MultiPort`、送るだけのポート、この実行の外のポートには書けない。各スロットの書き手は 1 つという原則を保つため。ホストは外から書けるスロットの唯一の書き手になる。

1 回の `write` で複数のポートに書いた値は、ある瞬間に読むどのノードから見ても一斉に切り替わり、同じ時刻が付く。`write` はその時刻を返す。新しい入力と古い教師信号が混ざらないようにするためである。

- 実装は版番号: 実行が外からの書き込みの版番号 $V$ を 1 つ持ち、外から書けるスロットは現在の値と版番号付きの次の値の組を持つ。`write` は書く各スロットに版 $V+1$ の次の値を置き、全部置いてから $V$ を進める。読み手は次の値の版が $V$ 以下なら次の値を読む。書き手も読み手も待たない
- ノードが 2 つのポートを順に読む間に次の `write` が終わらないことは保証しない（`recv_with_time` の時刻が違えば、別の `write` の値）
- 全ノードを止めてから書く方式は、書くたびに最も遅いノードの `on_update` を待つので採らない

初期値には 3 つの道がある。

| 道 | 誰が書くか | 時刻 |
| --- | --- | --- |
| 送るポートの `initial` | そのポート（最初の `send` まで） | `None`（まだ送っていない） |
| `mujou.run(..., inputs=)` | ホスト（段 2） | 起動の時刻（復元なら保存した時刻）の、その実行のタイマーの時刻 |
| `run.write` | ホスト（走り出した後） | 書いたときのタイマーの時刻 |

どれも無ければゼロ（`zeros()`）で、時刻は `None`。復元した実行は、タイマーが最初から保存した時刻にあるので、inputs の時刻も復元した時間軸に乗る。

### 読み出し

ホストは送るポートの outbox（最新の `send` の値）を読める。未接続のポートなら出力に、接続済みのポートなら中間層の観測になる。外からの読み出しは読み手が 1 つ増えるだけで、ノードの動作に影響しない。送らないポートやほかの実行のポートを読むと K18。

- `read` は値だけを返し、`read_with_time` は時刻（`Timestamp | None`）と組で返す。ノード側の `recv` / `recv_with_time` と対称にした
- `MultiPort.send_to` は outbox に書かない。`send_to` だけを使うポートを読むと、`initial` か zeros が返る
- `subscribe` は、呼んだ時点の最新値を待たずに返し、その後は新しい値が書かれるたびに最新値を返す。待つのは消費者だけで、書き手は通知するだけで待たない。消費者が遅いと途中の値は飛ばされる。実行が正常に終わるとイテレータも終わる
- `wait_for` は `subscribe` で値を順に確かめ、条件を満たした最初の値を返す。満たす前に実行が正常に終わると `RuntimeError`
- 書き込みごとのコールバック（消費者の遅さが書き手に伝わる）、すべての値の記録（future work）、mujou の外のプロセスへの転送は持たない

### 入力は実行の時間上の信号

スロットは最新値だけを持つので、ホストが書いた値は次に書くまで保たれる。入力は値の列ではなく、その実行のタイマーの時間上で階段状に変わる信号 $x(t)$ になる。データセットを流すときは、1 つのサンプルをどれだけ保つか（提示時間）をユーザーが決め、ホストはその実行のタイマーで待つ（`run.timer.sleep`）。実時間で待つと、時間のスケール・停止・仮想時計と噛み合わない。

出力は、入力が変わってから平衡に近づくまでの時間だけ遅れて追従する。入力と出力を対応させたいときは、提示時間の終わりに読む。サンプルの ID をネットワークに流して対応させることは、基盤ではしない。ID を運ぶ仕組みをすべてのノードに背負わせることになるからである（目標を入力と同じメッセージで運ぶのは、更新手法の選択。[mujou.pc](pc.md#メッセージ)）。

## 分岐と合流

分岐は送るだけの `Port` を何本も繋いで、合流は `MultiPort` で受けて表す。

```text
            ┌─ B.prev
A.next ─────┼─ C.prev        （A.next は送るだけの Port）
            └─ D.prev

A1.next ──┐
A2.next ──┴── B.prev         （B.prev は MultiPort）
```

全員に送ると、値はコアのバッファへ 1 回だけコピーされ、各 Channel のスロットにはそのバッファへの参照が書かれる。バッファは不変で参照カウントで管理するので、相手が何個でもそれ以上のコピーは起きない。相手を選んで送る `send_to` は、相手ごとに中身が違うメッセージのためにある（PC-ALM で合流した相手ごとに $W_k^\top \varepsilon$ を返すなど）。

複数の相手から受け取ったメッセージをどう束ねるかは、受け取るノードの更新手法が決める。足し合わせなどの集約をフレームワークに組み込まないのは、更新手法を差し替えられるようにするためである（[更新手法](update-rules.md)）。
