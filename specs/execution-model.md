# 実行モデル

ノード（[ノード](nodes.md)）を非同期に動かす方法を定める。

## 要点

1. ノード間の通信に queue・pipe を使わない。lock 付きの共有スロットへの値の読み書きだけで通信する
2. 各ノードは自分の周期で独自にループする
3. 1 つの実行を、その実行のタイマーの上の連続時間系として定義する。時間軸は実行ごとに 1 本で、1 つの実行の全ノード・全スロット・ホストの入力はその実行のタイマーを使う
4. 各ノードの更新則は微分方程式として扱い、その実行のタイマーで測った経過時間 $\Delta t$ で離散化する

## 共有スロット

ノード同士は、値を読み取ることと書き込むことだけでやり取りする。排他制御は lock だけで行い、メッセージングのためにノード同士が同期することはない。

共有する値を **スロット** と呼ぶ。各スロットに書き込むのは、そのスロットを持つ書き手 1 つだけ（送るポートか、ホスト）。書き込みは新しい値への参照の差し替えで行い、読み手が書きかけの値を見ないようにする。スロットは書き込みのたびに、その実行の時計の時刻を添える（[メッセージ](messages.md)）。

読み手は常に最新値だけを見る。書かれた値が一度も読まれずに上書きされることも、同じ値が何度も読まれることもある。複数のスロットを続けて読んでも、全体として一貫したスナップショットにはならない。各値が個別に一貫していればよい。これらはすべて正常な動作として扱う。

queue に値を溜めると、送り手と受け手の速度差でバックログが生じ、実質的にノード同士の歩調が結合する。最新値の読み書きだけにすれば、各ノードは互いを待たずに動ける。

## ノードのループ

各ノードは次の 1 ステップを自分の周期で繰り返し、その間にほかのノードを待たない。

1. 隣のスロットから、そのとき読める最新値を読む
2. 前回の更新からの経過時間 $\Delta t$ ぶん、自分の状態を更新する
3. 結果を自分のスロットに書く

この 1 ステップが `on_update(dt)` で、ループはフレームワークが持つ。周期は [ノード](nodes.md#実行の周期) にある。

## 連続時間の定式化

各ノードのステップの間隔はノードごとに異なり、しかも揺らぐ。そのため「1 ステップ分の更新」の意味がノードごとに変わる。ダイナミクスをステップ数ではなく、実行の全ノードに共通の時間 $t$ に対する微分方程式として定義すれば、周期が違っても同じダイナミクスを近似できる。

各ノードは、前回の更新からその実行のタイマーで測った $\Delta t$ で離散化する。陽的 Euler 法なら次のようになる。

$$x \leftarrow x + \Delta t \cdot f(x)$$

更新量はステップ数ではなく $\Delta t$ に比例させる。負荷が高いときは各ノードの $\Delta t$ が伸び、その影響は連続時間の定式化が吸収する。コアは $\Delta t$ の上限を持たない。打ち切るかはノードの選択（[ノード](nodes.md#実行の周期)）。

既定の更新手法 PC-ALM の連続時間形は [PC-ALM の連続時間系](pc-alm-continuous-time.md)。

## タイマー

タイマーは時間軸で、時刻を ns（u64）で持ち、秒（f64）はそこから計算する。`u64::MAX`（約 584 年）で飽和する。実装は Rust（`crates/mujou-core/src/time.rs`）で、ノードが GIL なしで参照できる。pamiq-core の `TimeController` を参考にした。

- `Timer(*, start, time_scale)` は、`start` から「実時間 × time scale」の速さで進む。時刻は「anchor の時刻 + anchor からの実経過 × スケール」で求め、スケールの変更・停止・再開では先に anchor を今の時刻へ張り替えるので、時刻は飛ばない
- `VirtualTimer(*, start)` は `advance(seconds)` でだけ進む `Timer` のサブクラス。テストとシミュレーションに使う。time scale は効かない。pause 中に `advance` すると `RuntimeError`（タイマーの契約）。`advance` という能力を型が持つので、仮想かどうかの分岐は要らない
- `global_timer` は、タイマーを渡さない実行が共有する普通の `Timer`（プロセスの最初の使用で 0）
- `ReadOnlyTimer(timer)` は読むだけの見方。誰でも作れるが、実行がノードに渡すもの（`Node.timer`）は実行の終わりで止まる（[RunClock](#runclock)）
- `Timestamp(*, ns)` はタイマー上の時刻。どのタイマーの時刻かは持たない。`a - b` は秒の float（ns の差を正確に取ってから f64 にする）。時刻差を秒で使う場面がほとんどなので、差は秒にした
- 停止には 2 種類ある。ランタイムが状態の取得と起動の間に取る **保持**（`PauseHold`。drop で解ける）と、ホストが使う **スイッチ**（`pause()` / `resume()`）。タイマーは保持の数を数え、保持が 1 つも無く、スイッチも切れているときだけ進む。1 つのタイマーで複数の実行が走りうるので、保持を数えないと、ある実行が取得を終えたときに別の実行の停止やホストの停止まで解いてしまう
- スイッチを公開するのは、ホストが時間を止めてその間に状態を取るためである。同じタイマーで走る複数の実行の状態を同じ時刻でそろえて取るのに要る（1 つずつ `state_dict` を呼ぶと、その間に時間が進む）
- `sleep(seconds)` はそのタイマーの時間で待ち、途中のスケールの変更に従い、停止中は再開まで戻らない。ホストが入力の提示時間を待つためのもので、状態の取得のための短い停止で提示が短くならない（pamiq-core は呼んだ時点のスケールで実時間を計算して眠り、停止中ならすぐ戻る）
- 状態の木に入れるのは時刻とスケールだけ。状態は必ず停止中に取るので、停止中かどうかは入れない。時計の種類はテストの設定なので入れない
- フレームワークがノードに渡す $\Delta t$ は ns の差から作る。秒の f64 同士の差を取ると絶対時刻に応じた丸めが入り、固定の $\Delta t$ で回すテストのオラクルが崩れる
- タイマーの制御（`sleep`、`pause`、`resume`、`set_time_scale`、`advance`）はホストだけが行う。hook の中から呼ぶと K16

時間の単位は 2 つある。timeout は実時間の秒、`sleep`・`advance`・`dt`・`period` はタイマーの秒。

## 実行ごとのタイマー

1 つの実行は 1 本のタイマーで走る。どれを使うかは起動の段 2 で決める。

| 起動 | タイマー |
| --- | --- |
| `mujou.run(root)` | `global_timer` |
| `mujou.run(root, timer=t)` | `t` |
| `mujou.run(root, state=tree)` | 保存した時刻と time scale から始まる新しい `Timer` |
| `mujou.testing.run(root)` | 新しい `VirtualTimer`（`state` を渡したなら保存した時刻から） |

`timer=` と `state=` を同時に渡すと段 1 で断る（K23）。

- 同じタイマーで動く実行は時間を共有する。1 つの実行の停止と起動は、同じタイマーで走るほかの実行の時間も止める。止め合いたくない実行は別のタイマーで動かす
- 復元した実行に専用のタイマーを与えるのは、共有のタイマーの時刻を巻き戻す場合をそもそも無くすためである。共有のタイマーへ時刻を読み込むと、ほかの実行の時刻が飛ぶ。それを拒むにはタイマーごとに走っている実行を数え、その数え上げと読み込みを 1 つの lock の下で行う必要があり、段 2 が既存のものを何も変えないという性質も崩れる。専用のタイマーなら、読み込みも数え上げも要らない。inputs も最初から正しい時刻の軸で刻まれる
- そのため、復元した実行は `global_timer.pause()` では止まらない。ホストは `run.timer.pause()` を使う

## RunClock

ランタイムの時刻は、すべて `RunClock`（Python の名前は `ReadOnlyTimer`）から取る。ノードの $\Delta t$、最後の更新の時刻、スロットのメッセージの時刻がこれに乗る。

- `RunClock.now = min(timer.now, end)`。end は、正常終了なら停止を求めた時刻、例外による終了なら失敗を検出した時刻（`on_exception` の前）。end を付けられるのはランタイムだけ
- 期限まで待つのは Timer の上で行い、end を付けたときに起こす
- Outlet、InputGroup、`start`、各ノードの Driver は、同じ 1 つの `RunClock` を持つ。違うタイマーで作ると、メッセージの時刻が $\Delta t$ を測る時間軸に乗らず、停止しても止まらない。Python の層は 1 つの実行のスロットを段 2 でその実行の時計から作るので、食い違うことはない
- 時刻源を 1 つにしたので、正常に終わった後の状態の木の時刻は、全スロットの時刻と全ノードの最後の更新以上になる。停止を求めた後に走った更新も、end より後の時刻を記録しない
- 終わった後の `on_exception` と `on_stop` では、`self.timer` は止まっている。減速のような処理は実時間で測る

## 停止と状態の取得・復元

停止の流れは pamiq-core の `ThreadController` を参考にした。

### 停止

1. 制御スレッドが停止要求のフラグを立て、続けてすぐにその実行のタイマーを時刻 $T$ で凍結する（保持を取る）
2. 各ノードは実行中の `on_update` を最後まで終え、次の区切りでフラグを見て止まり、`on_pause()` を呼ばれる。`on_update` の途中では止めない
3. 全ノードが区切りで止まったことを確かめる
4. 全ノードが止まっている間、制御スレッドは全ノードの状態とスロットを読める

pamiq-core は全スレッドが止まってからタイマーを止めるが、mujou では先に凍結する。待ってから凍結すると、早く止まったノードの最後の更新から凍結までの待ち時間が、再開後の最初の $\Delta t$ に混ざるからである。フラグを凍結より先に立て、更新を始めるかの判定を制御の lock の下で読むので、時刻 $T$ より後に始まる `on_update` は無い。凍結した後は、全ノードの最後の更新の時刻も、全スロットの時刻も $T$ 以下になり、停止中に読めば時刻 $T$ の状態として一貫する。

### 再開

制御スレッドがタイマーの保持を解き、続けてすぐに停止要求のフラグを下ろす。各ノードは `on_resume()` の後に次の `on_update` へ進む。タイマーを先に再開するので、再開後の最初の $\Delta t$ は 0 にならず、停止中の時間は混ざらない。混ざるのは 2 つの操作の間隔と、`on_resume` が終わり次の `on_update` に進むまでの時間だけで、通常のループの 1 周の手間と同じ性質のもの。

時間内に止まらないノードがあれば（`Run.state_dict(timeout=)`、実時間の秒）、取得を中止して止まらなかったノードを名指しし、`TimeoutError` を送出する。実行は続く。止まったノードには `on_resume()` を呼び、更新の途中だったノードはそのまま続ける。

### 状態の取得

1. [停止](#停止) する
2. 各ノードの Driver が、ノードの stream の上で `state_dict()` の戻り値を複製する（テンソルは detach してから）。ホストに返す前に stream を待つ
3. 制御スレッドが、スロットの値と各ノードの最後の更新の時刻を合わせて 1 つの木にまとめる
4. [再開](#再開) する
5. 再開した後に、ホストのスレッドで木のテンソルを CPU へ移して返す

停止中に CPU へコピーすると、停止の時間が延びる。そこで停止中は device の上で複製し、CPU へ移すのは再開の後にする。

ホストがスイッチでタイマーを止めている間も、流れは同じ。止まったままなのはタイマーだけで、ランタイムが保持を解いてもスイッチが残るので、時刻は $T$ のまま進まない。ノードを停止させたままにする API は無い。

正常に終わった後も状態を取れる（作る → 走らせる → 保存する）。このとき `Runtime.capture` が、呼び出し側のスレッドで lock を取って各ノードの Driver の `capture` を呼ぶ。2 つのホストのスレッドが同時に呼んでも hook は重ならない。木の時刻は end（停止を求めた時刻）で、終わった後に進んだ時間は系のダイナミクスの外なので入れない。そのため、正常に終わった後の `write` は断る（K17）。例外で終わった後は状態を取らず、`NetworkError` を出す。失敗したノードは更新の途中で止まっているからである。

フレームワークの役割は、時刻のそろった状態の木を返すところまで。保存はユーザーが行い、フレームワークもノードもファイルを扱わない。

### 状態の木の意味

木の形の正本は `Run.state_dict` の docstring で、`tests/mujou/test_state.py` が固定する。

木は素の dict で、テンソルはすべて CPU のコピーである。`torch.save(tree)` と `torch.load(..., weights_only=True)` がそのまま通るので、dict のサブクラスや safe globals の登録が要らない。中身は次の 4 つ。

| 対象 | 入れる理由 |
| --- | --- |
| その実行のタイマーの時刻とスケール | 復元した実行がその時刻から続く |
| 各ノードの `state_dict()` の戻り値 | ノードの内部状態 |
| 各ノードの最後の更新の時刻 | 次の $\Delta t$ の起点 |
| 各ポートのスロットの値と時刻（送るポートの outbox と相手ごとのスロット、ホストが書く入力） | 系の状態はノードの状態とスロットの中身を合わせたもの。スロットを初期値に戻して再開すると、隣のノードが再開直後に初期値を読み、平衡から外れる |

- ノードはルートからのパスで、ポートは属性名で、相手ごとのスロットは相手のポートのパスで引く。相手は「相手 → Channel」の dict で一意なので、接続の順序に依存しない。番号で引くと、相手の取り違えを復元の検査（K21）で見つけられない
- メッセージの項目は常に同じ形 `{"value", "time_ns"}` で、`time_ns` が `None` なら書き手がまだ書いていない
- バッファプールは入れない

### コピーする理由

`state_dict()` はテンソルのように、ノードが更新し続ける値への参照を返しうる。参照のまま返すと、再開した後のノードの更新でホストの手元の木が書き換わる。そこで停止している間に複製してから再開する。テンソルを detach してから複製するのは、状態はデータで、計算グラフを持ち越さないため。スロットの値は、torch に依存する層（`codec.py`）が新しい `torch.Tensor` にコピーして木に入れる。

### 復元

ホストは `mujou.run(..., state=tree)` で状態の木を渡す。

1. 段 2 で、木の時刻とスケールから実行のタイマーを作る（[実行ごとのタイマー](#実行ごとのタイマー)）
2. 木の形が木（ノードのパス、ポートの属性、スロットのキーの集合）と一致するかを確かめ、スロットに値と時刻を書く（K21）
3. inputs を書く（木の値を置き換える）
4. 段 3 で、各ノードの `on_start()` を呼び、続けて `load_state_dict()` で状態を戻す。最初の $\Delta t$ の起点は、保存した最後の更新の時刻

復元は新しいインスタンスで行う（K14 により、走ったインスタンスは再び走らない）。保存したときと同じ形にネットワークを作り直すことが前提で、手で書き換えた木はサポートしない。

## 終了と例外

### 終了

1. 制御スレッドが終了要求のフラグを立て、RunClock に end を付ける
2. 各ノードは実行中の hook を最後まで終え、次の区切りで止まる
3. 全ノードの `on_stop()` を呼ぶ。ある `on_stop()` が例外を投げても、ログに出して残りを呼び続ける
4. ワーカーと専用スレッドを join する

制御スレッドはホストの要求を 1 つずつ処理するので、状態の取得のための停止の途中に終了の要求が割り込むことはない。停止中に例外が起きた場合は、止まっているノードに `on_resume()` を呼ばず、`on_exception()` → `on_stop()` へ進む。

### 例外による終了

ノードのどの hook（`on_update` に限らず、`on_start`・`on_pause`・`state_dict` なども）が例外を投げても、システム全体を終了する。流れは pamiq-core を参考にした。

1. ノードを走らせているスレッドが例外を捕まえ、ノードの名前とトレースバックを `logging.getLogger("mujou")` に出し、例外を記録する。そのノードは、以後 `on_exception()` と `on_stop()` しか呼ばれない
2. 同じ場所で、ただちに RunClock に end を付け、終了要求のフラグを立てる。ループはフレームワークが持ち、各ノードは区切りごとにフラグを見るので、pamiq-core の制御スレッドのようにポーリングしなくてよい
3. 各ノードは区切りで止まった時点で、ほかのノードを待たずに自分の `on_exception()` を呼ぶ。安全停止をなるべく早く行うため。例外を投げたノード自身の `on_exception()` は、待っているほかのノードの分より先に呼ぶ。`on_exception()` の例外はログに出すだけで、終了の流れを続ける
4. 全ノードが `on_exception()` を終えるのを待つ
5. 全ノードの `on_stop()` を呼び、スレッドを join する（例外を投げたノードも、I/O などの資源を解放する）
6. ホストに最初に記録した例外を伝える。ほぼ同時に複数のノードが投げた場合、2 つ目以降はログに出すだけ

例外を投げたノードだけを止めて、ほかのノードを動かし続けることはしない。止まったノードのスロットには最後の値が残り、隣のノードがそれを読み続けて、気づかれないまま平衡から外れていくからである。ノードの再起動や、例外を投げた 1 ステップを飛ばして続けることもしない。

### ホストへの伝え方

`mujou.run` は全ノードの起動が終わってから戻り、その後の実行はバックグラウンドで続く。例外を返せる待ち中の呼び出しが無いので、例外で終わった後のホストの呼び出しで伝える。

- 起動中（`on_start`、`load_state_dict`）の例外は、終了の流れを済ませてから `mujou.run` が送出する
- 起動した後の例外は、その後のホストの呼び出し（`write`、`read`、`read_with_time`、`subscribe` とそのイテレータ、`wait_for`、`state_dict`、`shutdown`、`join`、`step`）が送出する
- どちらも `NetworkError` で、`__cause__` に最初の例外をつなぐ。`with` を別の例外で抜けるときは、そちらを優先する

### インタプリタの終了

ホストが `Run` を手放しても、実行は止まらない。`execution.py` は走っている実行を覚えておき、atexit で `shutdown` して `on_stop` を待つ（終了中のインタプリタにランタイムのスレッドが入らないようにするため）。CPython は non-daemon のスレッドを join してから atexit を呼ぶので、`with` も `shutdown` も使わずに `subscribe` を回すスレッドを残すと、終了がそのまま待つ。これはサポートしない（[提供シナリオとガード](scenarios.md#サポートしないもの)）。docs は `with` を前提に書く。

### グローバルなバリアとの関係

停止はシステム全体のバリアだが、不変の原則「グローバルなバリアを持ち込まない」の例外として認める。停止の間はその実行の時間が進まないので、系のダイナミクスから見れば停止は存在しないのと同じだからである。終了も、ダイナミクスをそこで打ち切るだけなので同じく例外とする。

停止を使ってよいのは、状態の取得・復元や観測などの制御のための操作だけ。全ノードを定期的に止めて重みを平均するなど、停止を学習アルゴリズムの一部に使ってはならない。

## ライフサイクルの遷移

ノードのライフサイクルの状態機械は `crates/mujou-core/src/runtime/lifecycle.rs` の 1 本だけで、専用スレッドのノードもプールのノードも同じ規則で動く。状態機械は hook を呼ばず、何も待たない。ノードを走らせるスレッドが「次に何をするか」を聞き、それを行って結果を記録する。

| 段階 | 次にすること |
| --- | --- |
| `Start` | `on_start`（復元するなら続けて `load_state_dict`）。戻ったら `WaitGo` |
| `WaitGo` | 全ノードの起動が終わるまで待つ。終わったら最初の目標を「最後の更新 + 周期」にして `Loop`。待つ間に停止なら `Finish` |
| `Loop` | 自由実行なら目標の時刻まで待って `on_update`。手動なら、ステップの許可が来て時刻が進んでいれば `on_update`（進んでいなければ何もせずにステップを終える）。停止の要求なら `on_pause` で `Paused`。終了の要求なら `Finish` |
| `Paused` | 同じ停止の間は待つ。停止が解けたら `on_resume` で `Loop`。停止の間に終了なら、`on_resume` を呼ばずに `Finish`（ただし停止が解けてから終了が来たなら、`on_resume` を呼んでから） |
| `Finish` | 例外による終了なら、まず `on_exception`。全ノードが `Finish` に入り（例外なら `on_exception` を終え）たら `on_stop` で `Done` |
| `Done` | 何もしない |

どの hook が失敗しても、そのノードは `Finish` に入る。このため、完了した取得の後には全ノードの `on_resume` が必ず続き、例外による終了では `on_exception` が必ず `on_stop` より先に呼ばれる。

## テスト

テストではタイマーを `VirtualTimer` にし、`mujou.testing.run` と `ManualRun.step(dt, *nodes)` で 1 ステップずつ回す。mujou 自身のテスト（既定のノードのテストを含む）と利用者のテストは、同じ口を使う。

- `step(dt, *nodes)` は、タイマーを `dt` だけ進めてから、`nodes` を渡した順に 1 回ずつ更新する。省くと全ノードを木の順に更新する（Gauss-Seidel。Jacobi の順が要るテストは出力側から逆順に渡す）
- 周期は無視する。同じ `step` に 2 回渡したノードは、2 回目は時刻が進んでいないので飛ばす
- `timer` を共有すると、`step` は共有しているほかの実行の時間も進める

全ノードを固定の $\Delta t$ で同期的に回すと、元の離散アルゴリズムに一致するはずである。これをテストのオラクルにする。手動モードは自由実行と同じ状態機械を使い、違いはステップの許可を待つことだけなので、テストで確かめた振る舞いは自由実行でも同じである。
