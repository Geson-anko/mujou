# 実行モデル

ノード（[ノード](nodes.md)）を非同期に動かす方法を定める。

## 要点

1. ノード間の通信に queue・pipe を使わない。lock 付きの共有スロットへの値の読み書きだけで通信する
2. 各ノードは、自分の周期で独自にループする
3. 1 つの実行を、その実行のタイマーの上の連続時間系として定義する。時間軸は実行ごとに 1 本で、1 つの実行の全ノード・全スロット・ホストの入力はその実行のタイマーを使う。既定はグローバルタイマー
4. 各ノードの更新則は微分方程式として扱い、その実行のタイマーで測った経過時間 $\Delta t$ で離散化する

## 共有スロット

### 方式

ノード同士は、値を読み取ることと書き込むことだけでやり取りする。排他制御は lock だけで行い、メッセージングのためにノード同士が同期することはない。

共有する値を **スロット** と呼ぶ。各スロットに書き込むのは、そのスロットを所有するノード 1 つだけである。書き込みは新しい値への参照の差し替え（またはコピー）で行い、読み手が書きかけの値を見ないようにする。

スロットは、書き込みのたびに、書いた時点のその実行のタイマーの時刻を自動で添える。時刻があれば、読み手は値がどれだけ古いかを判断できる。メッセージの型とスロットの詳細は [メッセージ](messages.md) にある。

### 読み手から見た性質

読み手は常に最新値だけを見る。そのため、書かれた値が一度も読まれずに上書きされることも、同じ値が何度も読まれることもある。複数の隣接スロットをまとめて読んでも、全体として一貫したスナップショットにはならない。各値が個別に一貫していればよい。これらはすべて正常な動作として扱う。

### queue を使わない理由

queue に値を溜めると、送り手と受け手の速度差でバックログが生じる。その結果、実質的にノード同士の歩調が結合してしまう。最新値の読み書きだけにすれば、各ノードは互いを待たずに動ける。

## ノードのループ

各ノードは次の 1 ステップを自分の周期で繰り返し、その間に他のノードを待つことはない。

1. 隣接ノードのスロットから、そのとき読める最新値を読む
2. 前回の更新からの経過時間 $\Delta t$ ぶん、自分の状態を更新する
3. 結果を自分のスロットに書き込む

この 1 ステップが、ノードの `on_update(dt)` である。ループ自体はフレームワークが持ち、ノードの作者は 1 ステップ分だけを書く（[ノード](nodes.md#ライフサイクル-hook)）。

周期はノードの `period`（その実行のタイマーの秒）で決まる。`None` ならできるかぎり速く回し、時刻が進まないとき（$\Delta t = 0$）だけ待つ。周期があれば、`period` ずつ離れた目標の時刻までタイマーの上で待ち、間に合っている間は平均で `period` に 1 回更新する。`period` 以上遅れたときは取り戻さず、その更新の時刻から数え直す。$\Delta t$ は実際の経過時間のままである（[実行の周期](nodes.md#実行の周期)）。

## 連続時間の定式化

### グローバルな時間で定義する理由

各ノードの計算は離散時間のステップで行う。しかしステップの間隔はノードごとに異なり、しかも揺らぐ。そのため「1 ステップ分の更新」の意味がノードごとに変わってしまう。ダイナミクスをステップ数ではなく、実行の全ノードに共通の時間 $t$ に対する微分方程式として定義すれば、周期が違っても同じダイナミクスを近似できる。

### 離散化

各ノードは、前回の更新からその実行のタイマーで測った経過時間 $\Delta t$ を使って微分方程式を離散化する。陽的 Euler 法なら次のようになる。

$$x \leftarrow x + \Delta t \cdot f(x)$$

更新量は、ステップ数ではなく経過時間 $\Delta t$ に比例させる。負荷が高いときは各ノードの $\Delta t$ が伸びるだけで、その影響は連続時間の定式化が吸収する。ただし $\Delta t$ が大きすぎると陽的 Euler 法は不安定になるので、ノードの内側で刻みを分割する。$\Delta t$ を打ち切ると経過時間が失われ、連続時間の定式化からずれるので、上限（`max_dt`）は今は持たない（[実行の周期](nodes.md#実行の周期)）。

既定の更新手法 PC-ALM の連続時間形は [PC-ALM の連続時間系](pc-alm-continuous-time.md) を参照。

## グローバルタイマー

既定では、プロセスのすべてのネットワークが 1 つのグローバルタイマーの上で動く。互いの停止で時間を止め合いたくないネットワークは、別のタイマーで動かせる（[複数のネットワーク](#複数のネットワーク)）。どのタイマーも時刻を秒（f64）とナノ秒（u64）の両方で持つ。

実装は pamiq-core の `TimeController`（<https://github.com/MLShukai/pamiq-core/blob/main/src/pamiq_core/time.py>）を参考にする。時間のスケール（加速・減速）、一時停止・再開、スレッドセーフ、状態の取得・復元の機能を持たせる。

タイマーはコア（Rust）側に置き、ノードが GIL なしで参照できるようにする（[ネイティブコア](native-core.md)）。

ホストが入力の提示時間などを待つために、タイマーの時間で待つ関数（グローバルタイマーなら `mujou.time.sleep(dt)`、名前は暫定）を用意する。時間のスケール・停止・仮想時計に従って待つ。実時間の `time.sleep` で待つと、これらと噛み合わない（[ネットワーク](network.md#入力は実行の時間上の信号)）。

### 実装

> 状態: 実装済み、公開する名前は暫定（2026-10-15）。タイマーを実行ごとに持てるようにした（2026-10-16）。

- Rust の `mujou_core::time::Timer` が本体で、`Arc<Timer>` で共有する。`Timer::new()` は時刻 0・実時計・スケール 1 の新しいタイマーを作る。`mujou_core::time::global()` は既定のグローバルタイマー（`&'static Arc<Timer>`）を返す。時刻の正は u64 のナノ秒で、秒の f64 はそこから作る。時刻はタイマーを作った時点を 0 とし、`u64::MAX`（約 584 年）で飽和する
- スロット（`Outlet` / `InputGroup`）とランタイム（`Runtime::start`）は、作るときに `Arc<Timer>` を受け取る。1 つの実行のスロットとホストの入力は、そのランタイムと同じタイマーで作る。違うと、メッセージの時刻が $\Delta t$ を測る時間軸に乗らず、停止しても止まらないので、停止中の時刻 ≤ $T$ の保証も崩れる。コアと bindings は一致を確かめないが、Python の層はスロットを `mujou.run` の時点でその実行のタイマーで作るので、利用者の操作で食い違うことはない（[ネットワークの実装](network.md#構築と実行)）。スロットはそのタイマーでメッセージに時刻を付け、ランタイムはそのタイマーで $\Delta t$ を測り、停止のときはそのタイマーだけを凍結する。復元の排他（同じタイマーで走っているランタイムがあれば時刻を戻さない）もタイマーごとに数える
- 時刻を表す値は `mujou_core::time::Timestamp`（u64 のナノ秒）。`Message::timestamp()` が返す
- 時刻は「anchor の時刻 + anchor からの実経過 × スケール」で求める。スケールの変更・停止・再開・時計の切り替えでは、先に anchor を今の時刻へ張り替えるので、時刻は飛ばない
- タイマーの時間で待つ処理は、条件変数で状態の変化を待つ。停止中は時刻が進まないので、停止中の `sleep` は再開まで戻らない
- 状態の木に入れるのは時刻（ns）とスケールだけである。状態は必ず停止中に取得するので、停止中かどうかは入れない。時計の種類はテストの設定なので入れない
- Python からは private な `mujou._core._native` で使う。`Timer()` が新しいタイマー、`mujou._core._native.timer`（`GlobalTimer` 型、`Timer` の派生）がグローバルタイマーで、どちらも全機能を持つ。`Outlet` / `InputGroup` / `Runtime` は `timer=` を必須の引数として受け取る（グローバルタイマーを使うときも `timer` を明示する）。`Timestamp` は `ts.float()`（と `float(ts)`）が秒、`int(ts)` が秒の整数部、`ts.ns` がナノ秒で、比較と hash ができる。`a - b` は `b` から `a` までの秒を符号付きの `float` で返す（`(a.ns - b.ns) / 1e9` と同じ丸め。ナノ秒の差を i128 で正確に取ってから f64 にする）。`Timestamp` を返すと、`b` の方が遅いときに例外か飽和のどちらかになり、テストやホストで経過秒を出すたびに `float(...)` で包む必要があった。時刻差を秒で使う場面がほとんどなので、差は秒にした。`Message.timestamp` が返す。`sleep` は GIL を外して待ち、50 ms ごとにシグナル（Ctrl-C）を確かめる
- 利用者に公開するのは、`mujou.time` の `now` / `sleep` / `get_time_scale` / `set_time_scale` / `pause` / `resume` / `is_paused`（グローバルタイマーを扱う）と、`mujou.time.Timer` / `mujou.time.ReadOnlyTimer` / `mujou.time.Timestamp`、テスト用の `mujou.testing.VirtualTimer` である。時刻を読む口は `now()`（`Timestamp`）の 1 つにした。秒は `now().float()`、ナノ秒は `now().ns` で取る。秒やナノ秒を直接返す `time()` / `time_ns()` を並べると、同じ時刻の読み方が 3 つになり、どれを使うか迷うからである（2026-10-17、ユーザーの決定）。native の `Timer.time()` / `time_ns()` はフレームワークとテストのために残す。`Timer` は native の `Timer` を包む Python のクラスで、`now()`（`Timestamp` を返す）・`sleep(seconds)`・`get_time_scale()`・`set_time_scale(scale)`・`pause()`・`resume()`・`is_paused()` だけを見せる。native の `load_state_dict`（走っているタイマーの時刻を飛ばせる）・`use_virtual_clock` はフレームワークとテストのためのものなので見せない。`Timestamp` は native の型をそのまま公開し、pickle と deepcopy ができる（`copyreg.__newobj_ex__` で `Timestamp(ns=...)` に戻す `__reduce__`）。`VirtualTimer` は `Timer` の派生で、時刻 0 の仮想時計から始まり、`advance(seconds)` を足す。`mujou.run(..., timer=...)` に渡すと、その実行のスロット・ホストの入力・ランタイムがすべてそのタイマーを使う。`timer=None` はグローバルタイマーである
- タイマーを動かすのはホストだけである。ノードは属性 `timer` で、タイマーの読み取り側（`ReadOnlyTimer`）を通して時刻を読む（[ノード](nodes.md#ライフサイクル-hook)）。`ReadOnlyTimer(timer)` は、native の `Timer.reader()` が返す `TimerReader`（`now()` と `time_scale()` だけを持ち、Python からは元のタイマーにたどれない）の束縛メソッドを `now` / `get_time_scale` として写し、タイマーのオブジェクトは属性に持たない。正常に終了した後の `state_dict` の中では、止まった時刻とスケールを繰り返し返すだけの関数（`itertools.repeat(...).__next__`）を写す。クラスの関数から module の globals（グローバルタイマーなど）にはたどれるが、これはどのクラスでも同じで、`import mujou.time` でも届く。実行に渡したタイマーそのものにはたどれない。`Timer.sleep` / `Timer.set_time_scale` / `Timer.pause` / `Timer.resume` / `VirtualTimer.advance` と `mujou.time.sleep` / `mujou.time.set_time_scale` / `mujou.time.pause` / `mujou.time.resume` は、ノードの hook の中から呼ぶと `RuntimeError` になる。ノードが時間を止めると、同じタイマーのほかのノードの更新まで止まり、Port を通らない通信路になる。ノードがスケールを変えると、同じ実行のほかのノードの $\Delta t$ が変わり、Port を通らない通信路になる（局所性）。ノードが仮想時計を進めると、手動ステップの $\Delta t$ がテストの進めた値からずれる。ノードがタイマーで待つと、停止はタイマーを先に凍結するので状態の取得が `PauseTimeoutError` になり、手動実行では誰も時計を進めないので `step` が戻らない
- 仮想時計（`use_virtual_clock(True)`）では、時刻は `advance(seconds)` で進めた分だけ進み、スケールは効かない。停止中は `advance` できない
- 停止には 2 種類ある。1 つは、ランタイムが状態の取得と起動の間に取る **保持** である。保持は Rust の `Timer::hold()` が返す `PauseHold` で、drop すると解ける。もう 1 つは、ホストやテストが使う **スイッチ**（`pause()` / `resume()`）である。タイマーは保持の数を数え、保持が 1 つも無く、スイッチも切れているときだけ時刻を進める。1 つのタイマーで複数のランタイムが走りうる（既定ではすべてグローバルタイマーで走る）。保持を数えないと、あるランタイムが状態の取得を終えたときに、別のランタイムの取得中の停止やホストの停止まで解いてしまう。`resume()` はスイッチを切るだけで、保持は解かない。`is_paused()` はどちらかで止まっていれば真になる
- スイッチは公開する（`mujou.time.Timer.pause` / `resume` / `is_paused` と `mujou.time.pause` / `resume` / `is_paused`。2026-10-17、ユーザーの決定）。用途は pamiq-core の `TimeController` の一時停止と同じで、ホストが時間を止め、その間に状態を取る・保存するなどをするためである。特に、同じタイマーで走る複数の実行の状態を同じ時刻 $T$ でそろえて取るのに要る。1 つずつ `Run.state_dict()` を呼ぶと、その間に時間が進み、実行ごとに木の時刻がずれる。スイッチが入っている間も `Run.state_dict()` は取れる（ランタイムは保持を重ねて取り、解いてもスイッチは残るので、時刻は $T$ のまま）。止めている間はノードの $\Delta t$ が進まず、ノードは時刻が進むまで待つ。再開後の最初の $\Delta t$ に止めていた時間は入らない。`sleep` は再開まで戻らず、`VirtualTimer.advance` は `RuntimeError` になる
- pamiq-core の `time.py` から、anchor の方式（スケールの変更・停止・再開で anchor を張り替える）を引き継いだ。次の点は意図して変えた
  - 時刻は 1 本だけで、0 から始まる。pamiq-core は `time` / `perf_counter` / `monotonic` を、それぞれ元の時計の値から始めて別々にスケールする
  - `sleep` はそのタイマーの時間で待つ。途中のスケールの変更に従い、停止中は再開まで戻らない。pamiq-core は呼んだ時点のスケールで実時間を計算して眠り、停止中ならすぐに戻る。mujou の `sleep` はホストが入力の提示時間を待つためのもので、状態の取得のための短い停止で提示が短くならないようにした。ノードのループの待ちを停止要求で起こす仕組みは、ランタイムの側に持たせた（$\Delta t = 0$ の待ちと周期の待ちは、目標の時刻か制御の要求で起きる。[実装](#実装-1)）
  - 状態の木にスケールも入れる。テスト用の仮想時計を足した
- フレームワークがノードに渡す $\Delta t$ は、ナノ秒の差から作る（`(now_ns - last_ns) / 1e9`）。秒の f64 同士の差を取ると、絶対時刻に応じた丸めが入り、固定の $\Delta t$ で回すテストのオラクルが崩れる

## 停止と状態の取得・復元

実行中のシステムを止めて、状態を取得・復元できるようにする。停止の流れは pamiq-core の `ThreadController`（<https://github.com/MLShukai/pamiq-core/blob/main/src/pamiq_core/thread/thread_control.py>）を参考にする。

### 停止

1. 制御側（ホスト）が停止要求のフラグを立て、続けてすぐにその実行のタイマーを時刻 $T$ で凍結する。ノードが止まるのを待ってから凍結するのではない
2. 各ノードは、実行中の `on_update` を最後まで終え、次のループの区切りでフラグを見て止まり、`on_pause()` を呼ばれる。`on_update` の途中では止めない
3. スケジューラが、全ノードが区切りで止まったことを確かめる。ワーカープールのノードは、ワーカーが実行を割り当てなくなった時点で止まる。専用スレッドのノードは、区切りでフラグを見て止まる
4. 全ノードが止まっている間、制御側は全ノードの状態とスロットを lock なしで読める

pamiq-core は全スレッドが止まってからタイマーを止めるが、mujou では先にタイマーを凍結する。全ノードが止まるのを待ってから凍結すると、早く止まったノードの最後の更新から凍結までの待ち時間が、再開後の最初の $\Delta t$ に混ざるからである。フラグを凍結より先に立てるので、時刻 $T$ より後に始まる `on_update` は無い。

凍結した後は、全ノードの最後の更新の時刻も、全スロットの値の時刻も $T$ 以下になる。凍結の前に読んだ時刻は $T$ より前で、凍結の後はタイマーが $T$ のまま進まないからである。スロットとホストの入力がランタイムと同じタイマーで時刻を付けることが前提になる（[実装](#実装)）。通常の実行中にスロットを読んでも一貫したスナップショットにはならないが、停止中に読めば、連続時間系の時刻 $T$ の状態として一貫する。

### 再開

制御側がその実行のタイマーを再開し、続けてすぐに停止要求のフラグを下ろす。各ノードは `on_resume()` を呼ばれてから、次の `on_update` に進む。タイマーを先に再開するので、再開後の最初の $\Delta t$ は 0 にならない。停止中の時間は $\Delta t$ に混ざらない。混ざるのは、制御側の 2 つの操作の間隔と、再開してから各ノードの `on_resume` が終わり次の `on_update` に進むまでの時間（スレッドが起きる遅れを含む）だけである。これは、通常のループの 1 周の手間が $\Delta t$ に入るのと同じ性質のものである。

### 複数のネットワーク

同じタイマーで動くネットワークは時間を共有するので、1 つのネットワークの停止（状態の取得）と起動は、同じタイマーで走っているほかのネットワークの時間も止める。既定ではすべてのネットワークがグローバルタイマーで動くので、プロセスのすべてのネットワークが止まる。別のタイマーで動くネットワークは止まらない。ほかのネットワークのノードは `on_pause` を呼ばれず、時刻が進まないので $\Delta t = 0$ のまま待つ。各ネットワークは自分の停止を別々に保持するので、1 つのネットワークが停止を解いても、ほかのネットワークの停止中に時刻は進まない（[グローバルタイマーの実装](#実装)）。グローバルタイマーで動くネットワークの停止なら、ホストの `mujou.time.sleep` も、止まっていた実時間だけ延びる。別のタイマーで動くネットワークが止まっても `mujou.time.sleep` は延びないので、ホストがそのネットワークへの提示時間を待つときは、そのタイマーの `sleep`（`mujou.time.Timer.sleep`）を使う。系のダイナミクスから見れば、どのネットワークにとっても停止は存在しないのと同じである。

### 状態の取得

ホストがビルドしたネットワークの状態を求めると、フレームワークは次の順に処理する。

1. [停止](#停止)する
2. 全ノードの `state_dict()` を呼び、スロットなどと合わせて 1 つの木にまとめ、そのコピーを作る
3. [再開](#再開)する
4. コピーした木をホストに返す

すでに停止しているときに求められた場合は、再開せずに停止したままにする。

正常に終了した後にも、状態の木を求められる。このときはノードのスレッドが無いので、フレームワークはホストのスレッドで各ノードの `state_dict()` を呼ぶ（CUDA のノードは、自分のストリームを同期してから呼ぶ）。正常な終了は、`shutdown` が最初に終了を要求した時刻 $T_\text{req}$ での停止とみなす。`shutdown` は要求の直前にタイマーの時刻とスケールを記録し、木のタイマーにはその時刻を入れる。ただし、要求の後にノードが更新したり `on_stop` が送ったりした時刻がそれより遅ければ、最も遅いものを入れる。こうすると停止と同じく、全ノードの最後の更新の時刻も全スロットの時刻も木のタイマー以下になる。最後の更新から $T_\text{req}$ までの時間は木に入り、止めずに続けた場合と同じく、復元した系の最初の $\Delta t$ に含まれる。終了した後もグローバルタイマーは進むが、その時間は系のダイナミクスの外にあるので木に入れない。そのため、正常に終了した後の `write` は `RuntimeError` にする（ノードはもう読まず、書いた時刻が終了後の時間になる）。例外で終了したときは、状態の木を取得しない。

`on_stop()` は `state_dict()` が返す状態を変えない約束である（[ノード](nodes.md#ライフサイクル-hook)）。正常に終了した後の木を、終了を要求した時点の状態に保つためである。

フレームワークの役割は、時刻のそろった状態の木を返すところまでである。木を pickle するか、どこにどう書き出すかは、ユーザーが決める。そのため、木の中身はすべて pickle できるようにしておく。`torch.save` で書いた木を `torch.load` で読むときは、ノードの状態に `Timestamp` などの Tensor 以外のオブジェクトがあれば `weights_only=False` を渡す。

```python
state = run.state_dict()         # 停止 → コピー → 再開 → 木を返す
with open("state.pkl", "wb") as f:
    pickle.dump(state, f)        # 保存の方法はユーザーが決める

run.shutdown()
state = run.state_dict()         # 正常に終了した後は、終了した時点の木を返す
```

### 状態の木の中身

| 対象                                                   | 持ち主         | 木への入れ方                     |
| ------------------------------------------------------ | -------------- | -------------------------------- |
| ノードの内部状態（重み、活動、双対変数など）         | ノード       | ノードの `state_dict()` が返す |
| 全スロットの最新値と書き込み時刻                       | フレームワーク | 自動                             |
| 各ノードの最後の更新の時刻（次の $\Delta t$ の起点） | スケジューラ   | 自動                             |
| その実行のタイマー（時刻、スケールなど）               | フレームワーク | 自動                             |

システムの状態は、ノードの状態とスロットの中身を合わせたものである。スロットを初期値に戻して再開すると、隣のノードが再開直後に初期値を読み、平衡から外れる。そのためスロットも木に入れる。ホストが外から書き込む入力のスロットも含む。バッファプールは含めない。

各ノードの状態は、ネットワークの木の中の属性のパス（`body.l1` など）で識別する。

### コピーを取る理由

ノードの `state_dict()` は、PyTorch のテンソルのように、ノードが更新し続ける値への参照を返すことがある。参照のままホストに返すと、再開した後のノードの更新で、ホストの手元の木が書き換わってしまう。そこでフレームワークは、停止している間に木のコピーを作ってから再開する。スロットの値は、`mujou._core._native` の外の torch に依存する層が `torch.Tensor` にコピーして木に入れる。

### 復元

ホストが `mujou.run(..., state=tree)` で状態の木を渡し、フレームワークがそこから状態を戻す。ネットワークを構築し、各ノードの `on_start()` を呼んだ後、最初の `on_update` の前に `load_state_dict()` で各ノードの状態を戻す。スロットの値、各ノードの最後の更新の時刻、その実行のタイマーも戻し、木を取得した時刻 $T$ から実行を始める。

その実行のタイマーは、停止したまま時刻を戻し、全ノードの準備ができてから再開する（停止 → タイマーの時刻を戻す → ノードの起動と状態の復元 → 再開）。走っているタイマーに時刻を戻すと、戻してから最初の `on_update` までの準備の時間が、最初の $\Delta t$ に混ざる。

同じタイマーでほかのネットワークが走っている間は、状態の木から復元して走らせられない。タイマーの時刻を戻すと、走っているネットワークの時刻が飛ぶからである。このときの `mujou.run` は何も起動せずに `ValueError` になり、ほかのネットワークを終了させるか別のタイマーを渡して走らせ直せる。別のタイマーで走っているネットワークは妨げにならない。

`state` と一緒に `inputs` で渡した入力には、木の時刻 $T$ を付ける（[書き込み](network.md#書き込み)）。

### 停止のタイムアウト

`on_update` の 1 回が長いノード（重い BP のスタックなど）があると、停止が遅れる。停止にはタイムアウトを設け、時間内に止まらなかったら状態の取得を中止し、止まらなかったノードの名前を例外のメッセージに入れる（[実装](#実装-1)）。

## 終了と例外

### 終了

1. 制御側が終了要求のフラグを立てる
2. 各ノードは、実行中の hook を最後まで終え、次のループの区切りで止まる
3. 全ノードの `on_stop()` を呼ぶ。ある `on_stop()` が例外を投げても、ログに出して残りのノードの `on_stop()` を呼び続ける
4. 専用スレッドを join し、ワーカープールを止める

停止中に終了を求められた場合も、同じ流れで終了する。

### 例外による終了

ノードのどの hook（`on_update` に限らず `on_start`・`on_pause`・`state_dict` なども）が例外を投げても、システム全体を終了する。流れは pamiq-core（スレッドが例外を投げると例外のフラグを立て、制御スレッドがそれを見つけて全体を終了する）を参考にする。

1. ノードを実行しているワーカーまたは専用スレッドが例外を捕まえ、ノードの属性のパスとトレースバックをログに出し、例外を記録する。そのノードの hook はそれ以後 `on_exception()` と `on_stop()` しか呼ばない
2. 同じ場所で、ただちに終了要求のフラグを立てる。ループはフレームワークが持っていて、各ノードはループの区切りごとにフラグを見るので、pamiq-core の制御スレッドのようにポーリングしなくてよい
3. 各ノードは、ループの区切りで止まった時点で、ほかのノードを待たずに自分の `on_exception()` を呼ぶ。例外を投げたノードも、捕まえた直後に呼ぶ。安全停止などをなるべく早く行うためである。すでに停止中のノードはその場で呼ぶ。`on_exception()` が例外を投げても、ログに出すだけで終了の流れを続ける
4. 全ノードがループの区切りで止まり、`on_exception()` を終えるのを待つ
5. 全ノードの `on_stop()` を呼び、専用スレッドを join し、ワーカープールを止める（[終了](#終了)と同じ）。例外を投げたノードの `on_stop()` も呼び、I/O などの資源を解放する
6. ホストに最初に記録した例外を伝える（[ホストへの伝え方](#ホストへの伝え方)）。ほぼ同時に複数のノードが例外を投げた場合、2 つ目以降はログに出すだけにする

Rust のネイティブなノードの panic も、例外と同じように扱う。

### ホストへの伝え方

> 状態: 実装済み（2026-10-16）。名前は[実装](#実装-1)のとおり。

`mujou.run` は全ノードの起動が終わると戻り、その後の実行はバックグラウンドで続くので（[ネットワーク](network.md#実行はバックグラウンドで行う)）、例外を返せる待ち中の呼び出しが無い。そこで、例外で終了した後のホストの操作で伝える。

- 起動中（`on_start` など）の例外は、`mujou.run` が終了処理を済ませてから送出する
- `write`・`read`・`state_dict` などの公開インターフェイスを呼ぶと、ネットワークが例外で終了したことを表す例外を送出する。最初に記録した例外を `__cause__` につなぐ
- `subscribe` のイテレータも同じ例外を送出する。ホストが購読のループで待っていても気づける
- `shutdown()` と `join()` も、例外で終了していれば同じ例外を送出する
- 例外で終了した後の `state_dict()` も同じ例外を送出する。例外で終了したときの状態は保存しない（2026-10-16、ユーザーの決定）。保存したい状態は、実行中か正常に終了した後に `state_dict()` で取る

例外を投げたノードだけを止めて、ほかのノードを動かし続けることはしない。止まったノードのスロットには最後に書いた値が残り、隣のノードはその古い値を読み続けて、気づかれないまま平衡から外れていくからである。ノードの再起動や、例外を投げた 1 ステップを飛ばして続けることもしない。

### グローバルなバリアとの関係

停止はシステム全体のバリアだが、不変の原則「グローバルなバリアを持ち込まない」の例外として認める。停止している間はその実行の時間が進まないので、系のダイナミクスから見れば停止は存在しないのと同じだからである。終了も、系のダイナミクスをそこで打ち切るだけなので、同じく例外として扱う。

ただし停止を使ってよいのは、状態の取得・復元や観測などの制御のための操作だけである。全ノードを定期的に止めて重みを平均するなど、停止を学習アルゴリズムの一部に使ってはならない。

## 実装

> 状態: 実装済み（2026-10-16）。

ノードの実行と制御はコア（Rust の `mujou_core::runtime`、Python からは private な `mujou._core._native.Runtime`）にあり、`mujou.run` と `mujou.Run` がそれを使う。`Run` のメソッドの一覧は [ネットワーク](network.md#実装) にある。

- ノードはそれぞれ専用のスレッドで動く。制御（起動・停止・状態の取得・終了・手動のステップ）は 1 本の制御スレッドが 1 つずつ処理する
- `mujou.run` は、その実行のタイマーを凍結 → タイマーと各ノードの最後の更新の時刻を戻す → 各ノードのスレッドで `_on_thread_start`（`mujou.Node` のスレッドの設定）→ `on_thread_start` → `on_start` →（復元なら）`load_state_dict` → タイマーを再開、まで済ませてから戻る
- `Run.state_dict()` が返す木は次の形で、pickle できる。ノードの状態は `copy.deepcopy`、スロットの値は新しい CPU の Tensor でコピーする

```python
{
    "nodes": {"body.l1": ..., ...},              # 各ノードの state_dict()
    "slots": {"body.l1.next/out": (value, time_ns), ...},  # value は Tensor か dict
    "last_update_ns": {"body.l1": int, ...},
    "timer": {"time_ns": int, "scale": float},
}
```

- 停止のタイムアウトの既定値は実時間 30 秒で、`mujou.run(..., pause_timeout=...)` で変える。`pause_timeout` は有限の正の秒数で、それ以外（0 以下・NaN・`math.inf`）は `ValueError` になる（メッセージに引数名 `pause_timeout` を入れる）。時間内に止まらなければ `PauseTimeoutError`（`TimeoutError` の派生）を送出し、止まらなかったノードの名前をメッセージに入れる。ネットワークは動き続ける
- 終了を待つ `shutdown(timeout)` と `join(timeout)` の既定は `math.inf`（いつまでも待つ）。時間内に終わらなければ `TimeoutError` を送出する（[ネットワーク](network.md#ホストの入出力)）。`shutdown` に有限の `timeout` を渡すと、コアに待たずに終了を要求し（`Runtime.request_stop`）、呼んだスレッドはコアの `join` で時間を区切って待つ。時間切れでも要求は残り、ネットワークは止まりに向かう
- 正常に終了した後の `state_dict()` は、ホストのスレッドで各ノードの `_capture_state()` を呼ぶ。CUDA のノードの同期は、制御スレッドで呼ぶときと同じである
- 例外は時間を止めない。ランタイムは例外で状態を取得しないので、例外の記録から終了処理の完了まで、タイマーは保持されずに進む。起動中や状態の取得中に例外が起きたときは、その保持を終了処理の最後に解く（[グローバルタイマーの実装](#実装)）。ホストがそのタイマーの時間で待つ処理（グローバルタイマーなら `mujou.time.sleep`）が戻らなくなるのを避けるためである
- ランタイムは各 `on_update` の直後に、同じスレッドでフレームワーク用の `_after_update()` を呼ぶ。状態の取得では `state_dict()` の代わりに `_capture_state()`（既定は `state_dict()` を返す）を呼ぶ。CUDA のノードは、`_after_update()` で自分のストリームを同期し、`_capture_state()` で `state_dict()` の前後に自分のストリームを同期する。どの hook が積んだ仕事も、これらの同期で終わる。フレームワークは、制御スレッドで木をコピーした後、ノードを再開する前に、制御スレッドの現在のストリームを同期する。復元では、ホストのスレッドでコピーした後に、そのスレッドの現在のストリームを同期する（[PyTorch の利用](torch.md#実行スレッドの設定)）
- 例外で終了したことは `NetworkError`（`RuntimeError` の派生）で伝える。メッセージにノードのパスと hook の名前を入れ、`__cause__` に最初の例外をつなぐ。hook の例外は `logging.getLogger("mujou")` にトレースバック付きで出す
- 手動モード（`mujou.testing.run` と `ManualRun.step(*nodes)`）は、自由実行と同じノードのループを使う。違いは、区切りでステップの許可を待つことだけである。その実行のタイマーの時刻が前回の更新から進んでいないノードは更新しない。周期は使わない
- 周期は、ホストがノードの `period` を秒のまま native の `Runtime.start(periods=...)` に渡し、bindings がコアの `seconds_to_ns` で ns に丸めて（0.5 は 0 から遠い側へ。1 ns 未満は 1 ns）コアの `RuntimeConfig::period_ns` に渡す。丸めはこの 1 か所だけで行う。ノードのループは目標の時刻を持ち、時刻がそこに達するまで `Timer::wait_until_ns_or` で待つ。最初の目標は最初の Δt の起点 + 周期（周期が無ければ + 1 ns）で、更新のたびに周期ずつ進める。更新の時刻が進めた目標に達していたら、目標をその時刻 + 周期にする。待ちは制御語（停止・一時停止・終了の要求）が変わると起きる

## テスト

テストでは、タイマーの時刻の源を、手動で進める仮想時計に切り替える。これで固定スケジュールのもと決定的に動かせる。

> 状態: 実装済み（2026-10-16）。

テスト用の口は `mujou.testing` に公開する。mujou 自身のテスト（既定のノードのテストを含む）と利用者のテストは、同じ口を使う。

- `VirtualTimer()`: 時刻 0 の仮想時計のタイマー。`advance(seconds)` で進めた分だけ進む
- `run(component, *components, timer=None, inputs=None, state=None, pause_timeout=30.0)`: 引数とその制約（`pause_timeout` は有限の正の秒数）は `mujou.run` と同じで、`ManualRun` を返す。ただし `timer` の既定は、実行ごとに新しく作る `VirtualTimer` である（2026-10-17。手動で回すテストの目的は $\Delta t$ を決めることなので、グローバルタイマーを既定にすると決定性を損なう）。仮想でない `Timer` を渡せば、仮想時計と手動のステップを独立に選べる
- `ManualRun.timer`: その実行のタイマー（作った `VirtualTimer` か、渡した `timer`）。型は渡したタイマーの型で、既定なら `VirtualTimer` なので `run.timer.advance(dt)` がそのまま型検査を通る
- `ManualRun.step(*nodes)`: 渡した順に各ノードを 1 回ずつ更新し、終わってから戻る。引数なしなら木の順に全ノード。時計は進めないので、`run.timer.advance(dt)` と組み合わせる。前回の更新から時刻が進んでいないノードは飛ばす（$\Delta t = 0$ になるため）

```python
with mujou.testing.run(net, inputs={net.prev: x}) as run:
    for _ in range(20):
        run.timer.advance(0.001)
        run.step(net.a, net.b)      # Gauss-Seidel: b は a のこのステップの値を読む
```

コアのテストは独立した native のタイマーを作って渡す。グローバルタイマーそのもの（`mujou.time` の関数）のテストだけは、公開の口では切り替えられないので、private な `use_virtual_clock` でグローバルタイマーを仮想時計にする。

全ノードを固定の $\Delta t$ で同期的に回すと、元の離散アルゴリズムに一致するはずである。これをテストのオラクルにする。
