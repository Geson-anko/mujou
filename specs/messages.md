# メッセージ

ノード間でやり取りするメッセージの型と、それを運ぶスロットの仕様を定める。実行モデル全体は [実行モデル](execution-model.md) を参照。

## 双方向通信の構成

ノード間の双方向通信は、向きごとに 1 本ずつ、計 2 本の片方向スロットで構成する。この 2 本の組を Channel と呼ぶ（[ネットワーク](network.md)）。各スロットの書き手は、そのスロットを所有するノード 1 つだけである。1 つのスロットを複数のノードが読んでもよい。

既定の PC-ALM では、層 $i$ のノードが上向きのスロットに $h_i$ を書き、層 $i+1$ のノードが下向きのスロットに $W_{i+1}^\top \varepsilon_{i+1}$ を書く。それぞれのスロットは、書く側のノードが所有する。

## 値の型

利用者がやり取りするメッセージの中の値は、すべて `torch.Tensor` である。ノードが Port で送受信する値も、ホストが外から読み書きする値も同じである（[ネットワーク](network.md#ネットワークの入力と出力)）。mujou は独自のテンソル型も dtype も公開しない。

サポートする dtype は次のとおり。

| 種類         | dtype                                                       |
| ------------ | ----------------------------------------------------------- |
| 浮動小数点   | `torch.float16`、`torch.bfloat16`、`torch.float32`、`torch.float64` |
| 符号付き整数 | `torch.int8`、`torch.int16`、`torch.int32`、`torch.int64`   |
| 符号なし整数 | `torch.uint8`                                               |
| 真偽値       | `torch.bool`                                                |

バッチを使う場合は、バッチ次元も shape の一部として扱う。フレームワークはバッチ次元を特別扱いしない。

### コアの中の値

コアは、スロットの値を不変なバッファとしてホストのメモリに持つ。連続した row-major の配置で、GPU などのデバイス上には置かない。このバッファは `mujou._core._native` の内部の型であり、利用者には見せない。不変なので、複数の読み手が同じバッファを同時に読んでも、書き手との間でデータ競合が起きない。

`torch.Tensor` とコアの間の受け渡しには DLPack を使う。DLPack は、データの場所・dtype・shape・strides を表す標準の形式で、torch は `__dlpack__` と `torch.from_dlpack` で対応している。コアは独自の dtype を持たず、DLPack の dtype の表現をそのまま使う。torch には `torch.dtype` を DLPack の dtype に直す公開 API がないので、torch に依存する側（`mujou._core._native` の外。`mujou._core.spec`）が、サポートする dtype の対応表を持つ。NumPy の配列を経由すると bf16 を受け渡せないので、DLPack を使う。

受け渡しは、読み書きのどちらでも必ずコピーする。ゼロコピーで共有すると、利用者が受け取った `torch.Tensor` をその場で書き換えたときに、ほかの読み手が見ているバッファまで変わってしまうからである。付随データの中継（[付随データ](#付随データ)）はコピーしないが、torch との境界を通らないコアの中の共有で、不変なバッファの参照を増やすだけなので、この理由に当たらない。

- 書くとき: 値を `detach()` し、GPU 上の値はホストへコピーしてから、中身をコアがプールから取り出したバッファへコピーする。勾配はノードをまたがない。ノードの `send()` でも、ホストの `write()` でも同じである。ノードの中では、ホストへのコピーに自分のストリームを使う（[PyTorch の利用](torch.md#境界の変換)）
- 読むとき: コアのバッファの中身を、新しい `torch.Tensor` へコピーする。デバイスが GPU のノードでは、ホストからデバイスへの転送がこのコピーを兼ねる。ホストの `read()` と `subscribe` が返す値は、CPU 上の `torch.Tensor` である

コアが受け取るのは、ホストから読めるメモリ上の値（DLPack のデバイス種別が `kDLCPU`、または pinned memory を表す `kDLCUDAHost`）だけである。

## TensorSpec

`TensorSpec` は、メッセージに入る `torch.Tensor` の shape と dtype の組を表す。torch に依存する Python 側のクラスで、コアには shape と DLPack の dtype に直して渡す。`TensorSpec(shape, dtype)` のように作り、dtype は [値の型](#値の型) の表から選ぶ。dtype を省略すると、`TensorSpec` を作った時点の `torch.get_default_dtype()` を読み取って確定する。あとで既定の dtype を変えても、すでに作った `TensorSpec` やスキーマは変わらない。shape の各次元は 1 以上の `int` で（`bool` は不可）、`()` はスカラーを表す。`int` でない次元とサポートしない dtype は `TypeError`、1 未満の次元は `ValueError` になる。

```python
spec = TensorSpec((B, 256))                  # dtype は作った時点の torch の既定（通常は float32）
spec = TensorSpec((B, 256), torch.bfloat16)
```

`TensorSpec` は、その形の `torch.Tensor` を作る生成関数を持つ。`TensorSpec.zeros()` はゼロで埋めた値を返し、どの dtype でも使える。`TensorSpec.rand()` は一様分布 $[0, 1)$ の乱数で埋めた値を返し、浮動小数点の dtype でだけ使える。`rand` には seed か `torch.Generator` を渡せ、渡せば結果が決定的になる。テストを決定的に保つためである。`TensorSpec.empty()` は値を設定しない領域を返す。どれも既定では CPU 上に作り、`device` 引数で置き場所を変えられる（`spec.zeros(device="cuda")`）。正規分布が必要になったら `randn` を別に足す。

ゼロと乱数のほかの値で始めたいときは、生成関数の結果をその場の操作で埋める（`spec.empty().fill_(0.5)`）。値ごとの生成関数は増やさない。

spec は device を持たない。spec の一致は shape と dtype だけで決まり、同じ spec のメッセージがノードごとに別のデバイスにあってよい。spec の一致には dtype も含むので、dtype が違う Port 同士は接続できない。書き込まれた `torch.Tensor` の shape か dtype が spec と違えばエラーになる。dtype の暗黙の変換はしない。

## メッセージの型

メッセージの型は次の 2 種類である。

| 型             | 意味                                           |
| -------------- | ---------------------------------------------- |
| `torch.Tensor` | 値 1 つ                                        |
| `TypedDict`    | キー名と値の型を明示した辞書。入れ子は許さない |

`TypedDict` を定義するときは、キー名と値の型を明示する。値の型は `torch.Tensor` である。

```python
class Feedback(TypedDict):
    error: torch.Tensor
    target: torch.Tensor
```

値が無いこと（`torch.Tensor | None` のような型）は、現時点では表さない。必要になったときに拡張する。

### 付随データ

> 状態: 実装済み（2026-10-20）。

メッセージは、値とは別に付随データ（carry）を持てる（[ネットワーク](network.md#付随データ)）。付随データの型も `torch.Tensor` か `TypedDict` で、spec は Port の `send_carry=` / `recv_carry=` で渡す。

- コアの `Message` は、値のフィールドのバッファと付随データのフィールドのバッファを 1 つの列に並べて持つ（値が先）。どちらのバッファも `Arc<Buffer>` で、付随データの中継は、受け取ったメッセージの付随データのバッファの `Arc` を新しいメッセージへ複製するだけである。中身はコピーしない
- 1 つのメッセージに値と付随データが入るので、読み手は 1 回の読み出しで同じサンプルの組を得る。読み手がスロットを 2 本読む方式だと、間に書き込みが入って組み違える
- Python からは、付随データは不透明な `_native.Carry`（`Message.carry`）に見える。ノードは付随データを `recv` で torch へ移さず、`Carry` のまま持ち、`carried()` で読むときだけコピーする

## スキーマと初期値

スロットのスキーマは、メッセージの型と各値の `TensorSpec`、付随データがあればその各フィールドの `TensorSpec` からなる（コアの `Schema(fields, carry)`。値のフィールドは 1 つ以上、付随データは 0 個以上で、名前の重複はそれぞれの中で検査する）。スキーマは Port を作るときに渡した spec で決まり、以後は変えない（[ネットワーク](network.md#define-and-run)）。書き込みはスキーマに照らして検証する。スロットそのものは `build` ではなく `mujou.run` の中で作る（[ネットワーク](network.md#構築と実行)）。shape が固定されているので、メッセージ用のバッファは同じ大きさのものを使い回せる（[メモリ管理](#メモリ管理-バッファプール)）。

Port には、メッセージの型に応じた spec を渡す。`torch.Tensor` のメッセージには `TensorSpec` を渡す。`TypedDict` のメッセージには、TypedDict と各キーの `TensorSpec` の対応表を `DictSpec` で渡す。

```python
Port(
    send=TensorSpec((B, 256)),
    recv=DictSpec(Feedback, error=TensorSpec((B, 256)), target=TensorSpec((B, 10))),
)
```

対応表は TypedDict と照合して検査する。TypedDict のキーはすべて必須で、値の注釈は `torch.Tensor` でなければならない。任意のキーや `torch.Tensor` 以外の注釈は `TypeError`、キーの無い TypedDict と対応表のキーの過不足は `ValueError` になる。2 つの `DictSpec` が一致するのは、TypedDict のクラスが同一で、各キーの `TensorSpec` が等しいときだけである。同じキーを持つ別の TypedDict とは一致しない。

スロットは常に、宣言どおりの型の値を持つ。そのため、スロットは初期値を持って始まる。既定の初期値はゼロ（`TensorSpec.zeros()`）である。送る側の Port は `initial=` で初期値を宣言できる（`NextPort(send=spec, initial=x0)`）。その Port が書くスロット（各 Channel と外向き）は、ゼロの代わりにその値で始まる。時刻はゼロのときと同じで、実行のスロットを作った時点のタイマーの時刻である。値は `send` と同じく spec と厳密に照合し、Port を作った時点でホストへコピーする。送る spec を持たない Port に `initial` を渡すと `TypeError` になる。状態を復元するときは木の値が上書きする。付随データの初期値はゼロで、`initial` は値だけを決める。ホストが書くスロットの初期値は `mujou.run(..., inputs=...)` で渡す（[ネットワーク](network.md#ホストの入出力)）。初期値を宣言する場所を送る側にしたのは、スロットの書き手が送る側の Port だからである。ノードの `on_start` で `send` しても最初の値にはなるが、復元のときに復元した値を上書きしてしまう（2026-10-17、ユーザーの決定で `initial=` を足した）。

## 実行のタイマーの時刻の付与

スロットは、書き込みのたびに、書いた時点のその実行のタイマーの時刻（既定はグローバルタイマー）を自動で添える。時刻はナノ秒（u64）で持ち、秒はそこから計算する。読み手はメッセージと時刻を組で受け取り、値がどれだけ古いかを判断できる。

## メモリ管理: バッファプール

実行中にメッセージ用のメモリをヒープへ毎回確保し、使い終わったら解放する処理は避けたい。そこで、スロットはバッファのプールを持ち、バッファを再利用する。

書き手は、プールから空いているバッファを取り出して新しいメッセージを書き、書き終えたらスロットの参照を差し替える。読み手が見ているバッファに書き手が書き込むことはないので、書き込み先が競合しない。

N 個の読み手は、最新のバッファを読み取り専用で共有する。そのため、読み手の数に比例したバッファは要らない。バッファは参照カウントで管理し、どの読み手からも参照されなくなるとプールへ戻って再利用される。Python の読み手（`mujou.Node` とホスト）は読むときに中身を `torch.Tensor` へコピーするので、バッファを参照するのはコピーしている間だけである。Rust のネイティブなノードは、`on_update` の間だけバッファを直接参照する。

プールに空きが無いときは、書き手はバッファを追加で確保し、読み手を待たない。各ノードは連続時間上で動くものの、周期は近いと見込まれる。そのため定常状態では、ヒープへの確保と解放を起こさずに再利用が回る。

付随データのバッファは、それを埋めた書き手（付随データを作った Port の `Outlet`）のプールのものである。中継したメッセージが持っていても、最後の参照が消えたときに元の書き手のプールへ戻る。そのため中継する `Outlet` は、付随データのバッファを最初のゼロの 1 つしか確保しない。ただし復元の後は例外で、`Slot.restore` は付随データも含む全フィールドを自分のプールから埋めるので、中継する `Outlet` のプールにも付随データのバッファが確保される。作る側のプールには、中継しているメッセージと、中継するノードが最後に受け取った付随データの分だけ、バッファが多めに要る。

ホストが外から書くスロットは、複数の Port への書き込みを一斉に切り替えるために、現在の値と版番号付きの次の値の組を持つ（[ネットワーク](network.md#書き込み)）。

メモリの使用量は増えるが、安全性と速度を優先し、これ以外の方式（seqlock で 1 つのバッファを上書きし、読み手がコピーする方式など）は持たない。プールは空で始め、空きが無いときだけバッファを確保する。使い終わったバッファは解放せずにプールへ戻すので、プールは縮小しない。
